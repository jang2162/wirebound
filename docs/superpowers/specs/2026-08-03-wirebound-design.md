# wirebound 설계 문서

이 문서는 살아 있는 정본이다 — 늘 지금 참인 설계만 적는다. 시점 기록(계획 · 이월 장부)은 `docs/superpowers/plans/`가 갖는다.

---

## 1. 개요

**wirebound**는 웹 화면 설계 도구다. 프로젝트의 메뉴 트리를 좌측에 두고, 중앙에서 페이지 목업을 확인하며, 우측에서 번호별 코멘트와 상호작용 설명을 읽는다. Storybook이 컴포넌트를 트리로 탐색하게 만든 것처럼, wirebound는 **화면 설계서**를 트리로 탐색하게 만든다.

관리자 화면이 첫 번째 대상이지만 거기에 한정하지 않는다. 마케팅 사이트, 포털, 커머스, 문서 사이트까지 같은 도구로 설계한다. 이 범용성은 테마 시스템이 담당한다(§6).

기존 도구와의 차이는 세 가지다.

1. **목업이 그림이 아니라 데이터다.** 페이지는 컴포넌트 트리 JSON이며, 좌표가 아니라 구조로 표현된다. 따라서 기계가 읽고 검증하고 수정할 수 있다.
2. **테마가 디자인 시스템이다.** 같은 페이지 스키마가 테마에 따라 관리자 테이블로도, 마케팅 랜딩 페이지로도 렌더된다. 테마 교체가 곧 사이트 리디자인이다.
3. **LLM 에이전트가 1급 사용자다.** MCP 서버와 CLI가 사람과 동일한 편집 경로를 쓴다. 개발 리포에 `.wirebound.json`을 두면 코딩 에이전트가 설계서를 읽고 구현하며, 어긋난 부분을 설계서에 코멘트로 되돌려준다.

패키지명은 `wirebound`, CLI 명령은 `wireb`다.

### 1.1 대상 사용자

- **기획자 / PM** — 화면을 설계하고 코멘트를 단다. 코드를 쓰지 않으며, 테마는 고르기만 한다.
- **디자이너** — 레이아웃을 잡고 테마를 만든다. 테마는 headless SDK 위의 코드 패키지로 짠다(§6).
- **개발자** — 설계서를 읽고 구현한다. CLI/MCP로 접근한다.
- **코딩 에이전트** — MCP를 통해 설계서를 읽고 구현하며 피드백을 남긴다.

### 1.2 성공 기준

- 기획자가 코드 없이 화면 설계서 한 벌을 완성할 수 있다.
- 같은 페이지 스키마에 다른 테마를 적용하면 다른 성격의 사이트로 보인다.
- 두 사람이 같은 페이지를 동시에 열고 편집해도 서로의 작업이 유실되지 않는다.
- 내보낸 HTML 번들이 웹 앱에서 보던 것과 구조적으로 동일하다.
- 코딩 에이전트가 사람의 설명 없이 설계서만 읽고 화면을 구현할 수 있다.

## 2. 확정된 설계 결정

| 축 | 결정 | 근거 |
|---|---|---|
| 실행 형태 | 서버형 SaaS (웹 앱) | 프로젝트 단위 권한 분리와 실시간 협업이 요구사항 |
| 저작 방식 | 선언적 스키마(JSON 트리) + GUI 트리/폼 에디터 | 좌표 기반은 LLM이 다루기 어렵고 재사용·내보내기가 불리 |
| 기술 스택 | TypeScript 모노레포 (React + Node + PostgreSQL) | 스키마·검증·렌더러를 웹/CLI/MCP/내보내기가 공유 |
| 스타일 | 쉘(Layout) / 테마(Theme) 분리 | 여러 레이아웃이 같은 디자인 언어를 공유해야 함 |
| 테마 범위 | 디자인 시스템 정의 — headless SDK 위의 코드 패키지(뷰 + 토큰 + 패턴) (§6) | 관리자 외 다양한 형태의 웹을 같은 도구로 설계해야 함 |
| 형태 | 테마의 뷰가 마크업을 정하고, 카탈로그(컴포넌트 종류 · props)는 닫혀 있다 | 형태를 바꾸는 자유를 주면서도 검증 · 내보내기 · LLM 조작이 기대는 닫힌 스키마를 지킨다 |
| 이력 | JSON Patch 커맨드 로그, 개인 undo 스택, 태그형 스냅샷 | 동시편집 환경에서 누가 무엇을 바꿨는지 추적 가능 |
| 동시편집 | WebSocket 실시간 반영 + 노드 단위 소프트 잠금 | CRDT 없이 설계서 작업에 충분한 협업 수준 |
| 상호작용 | 선언적 트리거→액션 규칙 (고정 액션 목록) | 스크립트 없이 검증 가능, 자동 문장화 가능 |
| 컴포넌트 | 내장 카탈로그 고정 (확장 없음) | 스키마를 닫아두면 검증·렌더링·내보내기가 단순 |
| 권한 | 프로젝트 단위 멤버 초대 (owner/editor/viewer) | 요구된 3종 권한과 1:1, 조직 계층 불필요 |
| LLM 연계 | 서버 API 직결 MCP·CLI, `.wirebound.json` 리포 바인딩 | 파일 동기화 없이 실시간 반영 |
| 내보내기 | HTML 정적 번들, PPTX는 렌더 이미지 방식 | 렌더러 재사용으로 비용이 거의 없음. 도형 변환은 포기 |
| MVP 범위 | 실시간 동시편집 + 스냅샷 + 상호작용 포함, MCP/CLI 제외 | 협업 도구로서의 핵심을 먼저 완성 |

**서버 구현 결정**

| 축 | 결정 | 근거 |
|---|---|---|
| DB 접근 | Kysely 쿼리 빌더 + 손으로 쓴 SQL 마이그레이션 | JSON 컬럼(`schema`·`tokens`·`ops`)이 많고 §7.1의 트랜잭션 경계를 직접 제어해야 한다. ORM 추상화가 얻는 것이 없다 |
| 인증 | HttpOnly 세션 쿠키 + DB 세션 (§10) | WebSocket 핸드셰이크가 같은 쿠키를 쓰고, 권한 회수가 즉시 반영된다 |
| 비밀번호 | `node:crypto`의 scrypt (파라미터를 해시 문자열에 동봉) | 네이티브 의존 없이 OWASP 권장 KDF를 쓴다. 파라미터 동봉으로 나중에 비용을 올려도 기존 해시가 유효하다 |
| 패키지 배포 | `schema`·`renderer`를 tsdown으로 빌드, `exports`는 `dist` | §3.3의 "Node와 브라우저 양쪽에서 동작"을 번들러 없이 만족시킨다. 개발·테스트는 `development` 조건으로 소스를 직접 본다 |
| 테스트 DB | Docker Compose Postgres + 테스트별 트랜잭션 롤백 | §14의 권한 매트릭스·통합 테스트가 실제 Postgres 동작(제약·jsonb)을 요구한다 |
| 배포 형태 | 단일 리눅스 서버 · docker compose — api 프로세스 하나 · Postgres · 앞단(Caddy). 이미지는 저장소의 `Dockerfile`, compose 는 `deploy/` | 팀이 자체 호스팅하는 도구이고 실시간 층이 프로세스 하나를 전제한다. 절차 · 잰 값은 최상위 README 「배포하려면」 |
| PPTX 화면 이미지의 자원 상한 | 동시에 뜨는 브라우저 수(env `EXPORT_RENDER_LIMIT`, 비우면 2 — 넘은 요청은 줄을 서서 기다린다) · 한 장의 넓이(뷰포트 폭 × 8192 CSS px — 넘은 장은 그리지 않고 크기와 상한을 말한다. 테마의 전이 · 애니메이션을 끄고 글꼴을 한 장의 한도 안에서 기다린 뒤 재고 잰 크기로 묶어 찍는다 — 찍는 사이에 커진 장 · 글꼴이 한도 안에 안 온 장도 안 그린다) · 장 수(200). **바이트 상한은 두지 않는다** | 브라우저 하나가 수백 MB, 긴 페이지 한 장이 수 GB 를 먹는다 — 서버 하나의 메모리를 이 셋이 묶고, 파일 크기도 셋의 곱으로 묶인다. 넘은 장을 자르지 않는 것은 잘린 목업이 멀쩡한 한 장으로 읽히기 때문이다 |

### 2.1 명시적으로 제외한 것 (YAGNI)

- **페이지의 반응형 편집** — 페이지 스키마에 브레이크포인트별 분기를 두지 않는다. 반응형은 **테마가 정의**하고(§6), 사용자는 뷰포트 프리셋을 바꿔 확인만 한다.
- **자유 좌표 배치** — 레이아웃 규칙 기반 배치만 지원한다.
- **CRDT 실시간 협업** — 소프트 잠금으로 충분하다.
- **컴포넌트 플러그인** — 카탈로그는 닫혀 있다(§5). 테마는 코드 패키지지만 뷰 · 토큰 · 패턴만 내고 컴포넌트 종류 · props 를 더하지 못한다 — 닫아 둬야 검증 · 내보내기 · LLM 편집 · lint · 테마 교체가 성립한다(§6).
- **테마 코드의 격리** — 테마 패키지는 인스턴스 관리자만 올리고, 올라온 코드는 브라우저에서 같은 origin 의 신뢰 코드로 돈다(샌드박스 없음). 서버(api 의 Node 프로세스)는 테마 코드를 실행하지 않는다.
- **사이트 안의 테마 작성** — 사이트에는 코드 에디터 · 서버 쪽 빌드가 없다. 테마는 저장소 밖에서 짜서 `.wbtheme` 로 빌드해 올린다(§6). CLI 로 올리는 길 · 한 프로젝트 안의 토큰 여러 벌도 두지 않는다 — 까닭은 `docs/superpowers/specs/2026-09-27-code-themes-design.md` 「목적과 범위」.
- **PPTX 무손실 도형 변환** — 렌더 이미지 삽입 방식으로 확정한다.
- **조직/워크스페이스 계층** — 프로젝트 단위 초대로 시작한다.
- **비로그인 공유 링크** — 후속 과제.
- **CLI 양방향 파일 동기화** — 로컬 파일을 편집해 서버로 밀어 올리는 `push` 흐름은 만들지 않는다. 수정은 항상 서버 API를 직접 호출한다. 읽기 전용 덤프(`wireb pull`)만 제공한다.

## 3. 아키텍처

### 3.1 패키지 구조

```
apps/
  web        React SPA — 3분할 설계서 에디터
  api        Node(Fastify) — REST + WebSocket, PostgreSQL

packages/
  schema     노드 타입 정의 + zod 검증 + JSON Patch 유틸 + lint 규칙
  renderer   schema → React 렌더링 (노드마다 테마 뷰를 그린다)
  theme-sdk  테마 뷰 SDK — 뷰 계약 · SDK 기본 뷰와 그 CSS · 공유 런타임(`./runtime`)
  themes     테마 manifest 규격 · 검증 · 토큰 CSS · `.wbtheme` 읽기 · 쓰기 · 패턴 규격 · 스냅샷 payload 규격 · 설계 lint 입구
  theme-gallery 카탈로그 × variant 표본 갤러리
  theme-kit  테마 작성 도구 — `wb-theme dev` · `build` · `check` · `shots` · 스타터 템플릿
  exporter   HTML 정적 번들 · PPTX 생성
  cli        wireb
  mcp        MCP 서버

system-themes/
  admin · commerce · docs · portal · saas-marketing
             시스템 테마 다섯(id 는 system-<이름>) — 저장소 빌드가 `.wbtheme` 로 내고 api 가 기동 때 넣는다(§6)
```

### 3.2 핵심 원칙

**`schema` 패키지가 유일한 진실이다.**
웹 에디터, 서버 검증, HTML 내보내기, MCP가 전부 같은 타입 정의와 같은 검증기를 쓴다. 스키마가 한 곳에만 있으므로 "웹에서는 통과했는데 CLI에서는 실패"하는 상황이 생기지 않는다.

**렌더러는 하나뿐이다.**
`renderer`가 웹 앱의 캔버스와 내보낸 HTML 양쪽을 그린다. 두 개의 렌더 구현이 존재하지 않으므로 결과가 어긋날 수 없다.

**렌더러는 스타일을 갖지 않고, 형태는 테마의 뷰가 정한다.**
`renderer`는 노드마다 테마의 뷰(없으면 SDK 기본 뷰)를 React 컴포넌트로 그리고 `data-wb-*` 속성을 싣는다(§6.1). 스타일은 테마의 CSS가 담당한다. 카탈로그가 닫혀 있으므로 테마 교체로 형태가 바뀌어도 문서의 계약(컴포넌트 종류 · props)은 그대로다.

**모든 편집은 같은 파이프라인을 통과한다.**
사람의 GUI 편집, MCP의 patch, CLI의 수정이 모두 `검증 → revision 기록 → 브로드캐스트`를 거친다. 우회 경로가 없으므로 이력이 항상 완전하다.

### 3.3 각 패키지의 책임과 의존

| 패키지 | 책임 | 의존 |
|---|---|---|
| `schema` | 노드 타입, props 정의, zod 검증, patch/inverse 생성, 마이그레이션, lint 규칙 | 없음 |
| `renderer` | 스키마 트리 → 노드마다 테마 뷰(없으면 SDK 기본 뷰), 상호작용 런타임 | `schema`, `theme-sdk` |
| `theme-sdk` | 뷰 계약(`view` · `Root` · `Focus`), manifest 타입(`defineManifest`), SDK 기본 뷰와 그 CSS, 공유 런타임(`installRuntime` — `theme.js` 가 `__wirebound_runtime__` 에 등록한다) | 없음(react 는 peer) |
| `themes` | 테마 manifest 규격 · 검증(`validateManifest`), 토큰 → CSS 변수(`tokensCss`), `.wbtheme` 읽기 · 쓰기(`readWbtheme` · `packWbtheme`), 패턴 규격 · 검증 · 전개, 스냅샷 payload 규격과 lint 입력 변환, 설계 lint 입구(`lintProject`) | `schema`, `theme-sdk`(타입만) |
| `theme-gallery` | 카탈로그 × variant 표본을 그리는 갤러리(`ThemeGallery`) · 포커스 · 마커 겹쳐 보기 | `schema`, `renderer`, `theme-sdk` |
| `theme-kit` | 작성자 도구 `wb-theme` — `dev`(갤러리 · 토큰 패널 · 뷰포트 프리셋 · HMR), `build`(`.wbtheme`), `check`(갤러리 칸 전부를 jsdom 에서 번들로 그려 오류 · 안 쓰는 토큰 · 패턴이 쓰는 선언 밖 variant 를 본다), `shots`(갤러리를 실 Chromium 으로 폭마다 찍고 콘솔 오류 · 폴백 · 가로 넘침을 적는다), `pack-template`(스타터 템플릿 zip). 비공개 패키지(`schema` · `themes` · `renderer` · `theme-gallery`)는 산출물 안에 묶는다 | `theme-sdk`(peer), vite |
| `exporter` | 정적 HTML 번들 · PPTX 생성 | `schema`, `renderer`, `theme-sdk`, `themes` |
| `cli` | 터미널 명령, API 클라이언트 | `schema`, `themes` |
| `mcp` | MCP 도구 정의 | `cli` |
| `system-themes/*` | 시스템 테마 다섯의 소스(SDK 뷰 · manifest · `theme.css`) | `theme-sdk`(빌드는 `theme-kit`) |
| `apps/api` | 인증, 권한, 영속성, revision, WebSocket, 시스템 테마 시딩 | `schema`, `theme-sdk`, `themes`, `exporter` |
| `apps/web` | 에디터 UI, 실시간 동기화, undo 스택, 프로젝트 설정 · 테마 관리 화면 | `schema`, `renderer`, `theme-sdk`, `themes`, `theme-gallery` |

`schema`가 의존을 갖지 않는다는 점이 중요하다. Node와 브라우저 양쪽에서 동작해야 한다.

## 4. 도메인 모델

### 4.1 엔티티 관계

```
User
Project ──┬── ProjectMember (user, role: owner|editor|viewer)
          ├── ApiToken     (name, hash, createdBy, scope=projectId)
          ├── Layout       (name, schema)
          ├── MenuNode     (parentId, order, title)   ← 트리
          │     └── Page   (title, order, layoutRef?, description, schema)
          │           ├── Comment  (marker, nodeId, body, author)
          │           └── Revision (seq, actor, ops[], inverse[], createdAt)
          ├── PagePreset   (name, schemaFragment)
          └── Snapshot     (tag, description, atSeq, payload, createdBy)
```

### 4.2 테이블 정의

```sql
users(id, email, name, password_hash, is_instance_admin, created_at)
  UNIQUE (email)
  is_instance_admin = 테마 패키지를 올리고 숨기는 사람(§10). 주는 길은 서버의 명령 · 시딩뿐이다

sessions(id, user_id, expires_at, created_at, last_seen_at)
  id = 쿠키에 실린 세션 토큰의 sha256 해시 (원문은 저장하지 않는다)

projects(id, name, slug, description, default_layout_id,
         theme_id, theme_version, theme_tokens json, theme_rev int, created_at, updated_at)
  FK (theme_id, theme_version) → theme_packages  RESTRICT
  theme_id · theme_version 은 함께 NULL 이거나 함께 값이다 — NULL 은 «아직 고정 안 됨»(기동 시딩이 채운다)
  theme_tokens = 기본값과 다른 토큰 값만 · theme_rev = 바인딩 저장 · 판 3 복원마다 1 오른다

theme_packages(theme_id, version, name, description, sdk_range, manifest json,
               files bytea, size, sha256, uploaded_by, uploaded_at, hidden_at)
  PK (theme_id, version)
  files = .wbtheme zip 원본 · uploaded_by NULL = 시스템 테마(또는 지워진 사용자)
  행은 hidden_at 말고 안 바뀐다 — 지우는 길이 없다

project_members(project_id, user_id, role, invited_at)
  PK (project_id, user_id)
  role ∈ ('owner','editor','viewer')

api_tokens(id, project_id, name, token_hash, user_id, last_used_at, created_at)

layouts(id, project_id, name, schema jsonb, updated_at)

menu_nodes(id, project_id, parent_id, title, sort_order, created_at)
  parent_id NULL = 루트

pages(id, project_id, menu_node_id, title, sort_order, layout_id,
      description text, schema jsonb, schema_version int,
      head_seq bigint, updated_at)

comments(id, page_id, node_id text, body text,
         author_id, created_at, updated_at)
  번호(marker)는 이 행이 아니라 페이지 문서의 노드가 든다 (§4.3)

revisions(id, page_id, seq bigint, actor_type, actor_id, actor_label,
          ops jsonb, inverse jsonb, created_at)
  UNIQUE (page_id, seq)
  actor_type ∈ ('user','mcp','cli')

snapshots(id, project_id, tag, description, payload jsonb,
          created_by, created_at)
```

`pages.schema`는 materialized 상태다. 읽기는 항상 이 컬럼 하나로 끝난다. `revisions`는 append-only 이력이며, replay는 감사와 스냅샷 검증 용도로만 쓴다.

`pages.head_seq`는 해당 페이지의 최신 revision seq다. 클라이언트가 patch를 보낼 때 `baseSeq`로 사용한다. **한 페이지 id 에서 `head_seq`는 다시 작아지지 않고, 번호가 같으면 문서도 같다** — 서버는 편집의 자리 경로를 `baseSeq` 판에 그대로 적용하므로(「정방향 흐름」) 번호가 곧 편집의 판본이다. 복원이 되살린 페이지는 그 id 가 쓴 마지막 번호 다음에서 선다(「스냅샷」) — 그 번호에는 revision 이 없다.

### 4.3 페이지 스키마 노드

```jsonc
{
  "id": "n_7f3a",          // 안정 ID — 코멘트·상호작용·잠금·patch 경로의 공통 앵커
  "type": "List",
  "alias": "회원 목록",       // 사람이 붙인 이름 (선택)
  "props": { "columns": ["No", "아이디", "이름"], "items": 10, "pagination": true },
  "variant": "featured",   // 테마가 정의한 variant 중 하나 (선택)
  "marker": 2,             // 우측 코멘트 번호 (없으면 코멘트 없음)
  "interactions": [
    { "on": "click", "actions": [ { "type": "setProp", "target": "n_9c1e", "prop": "loading", "value": true } ] }
  ],
  "children": []
}
```

`id`는 생성 시 부여되고 절대 바뀌지 않는다. 노드를 트리 안에서 옮겨도 유지되므로 코멘트와 상호작용 타겟이 따라간다. 가져오기·프리셋 적용·패턴 삽입 시에만 새 id를 발급하며, 그때 참조도 함께 리매핑한다.

**별칭(`alias`)** 은 같은 타입이 여럿일 때 사람이 가르려고 붙이는 이름이다. 앞뒤 공백이 없는 1 ~ 60자(코드 포인트로 센다)이고, 받지 않는 글자 — 줄을 바꾸거나 출력을 제어하는 글자(C0 · DEL · C1 · U+2028 · U+2029) · 방향 제어 글자(U+061C · U+200E · U+200F · U+202A ~ U+202E · U+2066 ~ U+2069) · 짝 없는 서로게이트 — 가 없고, 보이는 글자가 하나는 있다(공백과 폭 없는 글자 U+200B ~ U+200D · U+2060 · U+FEFF 만이면 빈 값이다). 비우면 필드째 지운다. 받지 않는 글자의 표는 한 벌이다(`packages/schema/src/alias.ts`) — 봉투는 거절하고 화면은 같은 표로 다듬는다. 모양은 노드 봉투(`WbNodeSchema`)가 보므로 저장 경계(문서 저장 · 편집 · 가져오기 · 클립보드 봉투 · 프리셋)가 같은 판정을 받는다 — 별칭이 없는 옛 문서는 그대로 읽힌다. 문서 안에서 유일할 필요는 없다. 복사 · 붙여넣기 · 복제 · 프리셋 · 가져오기에서 노드와 함께 간다. 노드를 사람이 부르는 이름은 하나(`packages/schema` 의 `nodeDisplayName` — 별칭이 있으면 별칭, 없으면 라벨성 prop + 카탈로그 한국어 이름)이고, 노드를 가리키는 자리(구조 트리 줄 · 속성 패널 제목 · 상호작용 문장과 대상 고르개 · 코멘트의 노드 표시 · 캔버스 손잡이 · 내보낸 설계서 · CLI `page get` · MCP `get_page`)가 모두 그 이름을 거친다.

**노드는 스타일을 갖지 않는다.** `variant`로 테마가 정의한 표현 중 하나를 고를 뿐이고, 실제 스타일 값은 전부 테마에 있다. 이 성질 덕분에 테마 교체만으로 전체 설계서의 외형이 바뀐다. 반대로 "이 버튼만 빨갛게" 같은 일회성 스타일은 지원하지 않는다 — 필요하면 테마에 variant를 추가하는 것이 올바른 경로다.

노드가 어떤 형태로 그려질지는 노드가 아니라 **테마의 뷰가 결정**한다(§6). 같은 `List` 노드가 한 테마에서는 테이블로, 다른 테마에서는 카드 그리드로 그려진다.

### 4.4 레이아웃

레이아웃은 별도 형식이 아니라 **`Slot` 노드를 하나 품은 같은 스키마 트리**다.

```jsonc
{
  "id": "n_root",
  "type": "Page",
  "children": [
    { "id": "n_hdr", "type": "Flex", "props": { "direction": "row" }, "children": [ ... ] },
    { "id": "n_body", "type": "Flex", "props": { "direction": "row" }, "children": [
        { "id": "n_lnb", "type": "Flex", "props": { "direction": "column", "width": 240 },
          "children": [ { "id": "n_nav", "type": "Tree", "props": { "items": [ ... ] } } ] },
        { "id": "n_slot", "type": "Slot" }
    ]}
  ]
}
```

렌더링 시 페이지 스키마가 `Slot` 위치에 주입된다. "헤더 있음/LNB 있음" 같은 속성은 별도 플래그가 아니라 트리에 해당 노드가 존재하느냐로 표현된다. 그 결과 레이아웃 편집기와 페이지 편집기가 같은 UI를 쓰고, 렌더러도 하나로 끝난다.

페이지는 프로젝트 기본 레이아웃을 상속하되 `layoutRef`로 개별 지정할 수 있다.

### 4.5 스냅샷

스냅샷은 **삭제 없는 태그**다.

- 생성: 현재 프로젝트 전체 상태(메뉴·페이지·레이아웃·코멘트와 테마 바인딩)를 `payload`에 압축 저장하고, 각 페이지의 `head_seq`를 함께 기록한다.
- 복원: 이력을 지우지 않는다. 현재 상태에서 스냅샷 상태로 가는 patch를 계산해 **새 revision들로 append**한다. 따라서 복원 자체가 이력에 남고, 복원을 다시 되돌릴 수도 있다.
- **메뉴 연쇄 삭제도 안전망 스냅샷을 찍는다** — 지우기 직전의 프로젝트를 같은 트랜잭션에서 스냅샷 하나로 남긴다(태그 `메뉴 "<제목>" 삭제 전 <시각>` · 설명에 지운 수). 연쇄 삭제는 페이지의 이력까지 지워 되돌리기가 없고, 그 스냅샷으로 복원(owner)하면 지운 메뉴 · 페이지가 같은 id 로 돌아온다. 잠금은 복원과 같다(프로젝트 → 메뉴 → 페이지 → 레이아웃 → 코멘트) — 캡처가 프로젝트 전체를 보므로 서브트리 밖의 열린 편집도 그 커밋을 기다려 싣는다.
- 복원이 지워진 페이지를 되살리면 **같은 id** 로 서고, `head_seq`는 **그 id 가 지워질 때까지 쓴 번호 다음**부터 센다(지워진 이력은 되살아나지 않는다). 0 부터 다시 세면 복원 방송을 못 받은 클라이언트(연결이 끊긴 탭 · MCP · CLI)의 번호와 남의 편집으로 오른 번호가 우연히 같아지고, 그 클라이언트의 편집이 되살린 문서의 다른 노드에 적용된다. 그래서 페이지를 지울 때 그 id 의 마지막 번호를 남긴다 — 수명은 프로젝트다(복원이 되살릴 수 있는 것의 바깥 경계). 남긴 번호가 없는 id(번호를 남기기 전에 지웠다)는 어디까지 셌는지 알 길이 없어(스냅샷의 번호는 하한이다) 2^32 에서 센다.

payload를 통째로 저장하는 이유는 복원 속도 때문이다. revision replay는 페이지 수가 늘면 선형으로 느려지고, 스냅샷은 자주 만들지 않으므로 저장 비용이 문제되지 않는다.

**테마는 참조로 얼린다**(payload 판 3) — 테마 내용이 아니라 프로젝트의 바인딩 `{ themeId, version, tokens }` 를 싣는다. 테마 패키지는 지우지 않으므로 참조로 충분하다. 판 3 복원은 바인딩도 되돌리고(숨긴 버전이어도 된다) 값이 같아도 `theme_rev` 를 올려 `theme-changed` 를 보낸다. 판 2 이하 스냅샷의 복원은 바인딩을 건드리지 않는다(payload 에 `theme` 가 있어도). 가리킨 패키지가 그 서버에 없으면 복원하지 않는다(409). 토큰은 그 판의 manifest 로 바인딩 저장과 같은 검사를 지나고, 걸린 키는 버려 기본값으로 선다 — 복원을 거절하지 않는다.

## 5. 컴포넌트 카탈로그

카탈로그는 고정이며 프로젝트별 확장이 없다.

| 그룹 | 컴포넌트 | 설명 |
|---|---|---|
| 구조 | `Page` | 루트 노드. 페이지당 하나 |
| | `Slot` | 레이아웃 전용. 페이지가 주입되는 자리 |
| | `Section` | 세로 밴드. 풀블리드 배경 + 내부 컨테이너 정렬 |
| | `Flex` | 가로/세로 배치 |
| | `Grid` | 격자 배치 (열 수, 간격) |
| | `Card` | 제목·본문 영역을 가진 카드 |
| | `Tabs` | 탭 목록과 패널 |
| 데이터 | `List` | 목록. 컬럼/아이템, 개수, 페이지네이션, 선택 |
| | `Tree` | 계층 목록 |
| | `KeyValue` | 키-값 뷰 (상세 화면용) |
| 입력 | `SearchForm` | 검색 조건 필드 묶음 + 조회/초기화 |
| | `EntryForm` | 등록/수정 폼. 라벨-필드 배치 규칙 |
| | `Field` | 단일 입력요소 (text/number/select/date/dateRange/checkbox/radio/textarea/file) |
| 액션 | `Button` | 버튼 |
| | `Link` | 링크. 페이지 이동 대상 지정 가능 |
| 문서 | `Text` | 텍스트. `role`로 타이포 스케일 선택 (display/h1~h6/body/caption) |
| | `Media` | 이미지·영상·일러스트·차트 영역 |
| | `Divider` | 구분선 |
| | `Placeholder` | 미정 영역 자리표시 |

`Text` · `Divider` · `Placeholder`는 설계서 작성에 필수적이라, `Section` · `Media`는 관리자 외 사이트 설계에 필수적이라 카탈로그에 든다. `Section`은 "화면 전체 폭 배경 + 가운데 정렬된 콘텐츠"라는 사이트 레이아웃의 기본 단위다.

### 5.1 컴포넌트 정의 구조

각 컴포넌트는 한 파일에서 다음을 함께 정의한다.

```ts
defineComponent({
  type: 'List',
  label: '목록',
  description: '여러 건을 표·카드·목록 모양으로 늘어놓는다.',
  group: 'data',
  props: z.object({ items: z.number(), columns: z.array(z.string()).optional(),
                    pagination: z.boolean(), selectable: z.boolean() }),
  editor: [                                    // 속성 패널 폼이 여기서 자동 생성됨
    { prop: 'items',      control: 'number',     label: '항목 수' },
    { prop: 'columns',    control: 'stringList', label: '컬럼' },
    { prop: 'pagination', control: 'switch',     label: '페이지네이션' },
  ],
  states:     ['selected', 'disabled', 'loading', 'empty'],
  children:   'none',                          // none | many
})
```

**정의(계약)와 그리기는 패키지가 다르다.** 위 선언은 `schema` 패키지에 있고 React에 의존하지 않는다. 화면은 테마의 뷰가 그린다(§6). `schema`가 의존을 갖지 않아야 한다는 §3.3의 원칙 때문이다.

**구조 · 조각 · 변형은 카탈로그에 없다 — 테마가 선언한다.** 컴포넌트가 어떤 마크업으로 그려질지는 테마의 뷰가, 고를 수 있는 변형(`variant`)과 변형마다 감출 속성은 테마 manifest 가 정한다(§6.0). 그래서 스키마는 노드의 `variant` 값을 판정하지 않는다 — 테마에 없는 값이면 렌더러가 그 테마의 기본 변형으로 그린다.

**변형을 prop 에서 파생하는 컴포넌트가 있다**(`variantFrom` — `Text`의 `role` · `Field`의 `control` · `Divider`의 `direction`). 그 enum prop 의 값이 `data-wb-variant`가 되고, 노드의 `variant`는 무시된다(검증이 `ignored-variant` 경고로 알린다).

상태는 props에서 파생된다. `states`에 선언된 이름과 같은 props가 `true`이면 그 상태가 활성화되고, 렌더러가 `data-wb-state`에 실어 보낸다. 상태는 설계서 표현에 필수다. "필수값 미입력 시 저장 버튼 비활성", "선택된 행 강조" 같은 서술을 목업에서 실제로 보여주려면 상태를 켤 수 있어야 한다. 상태 목록은 여기 고정 선언되어 있어 임의 상태를 만들 수 없다.

속성 패널이 정의에서 자동 생성되므로 컴포넌트를 늘려도 에디터 코드를 수정하지 않는다.

## 6. 테마 시스템

### 6.0 테마의 범위

wirebound는 관리자 화면에 한정되지 않는다. 마케팅 사이트, 포털, 커머스, 문서 사이트의 설계도 같은 도구로 해야 한다. 이 요구가 테마의 범위를 결정한다.

**테마는 색 팔레트가 아니라 디자인 시스템 정의다.** 같은 페이지 스키마가 테마에 따라 데이터 테이블로도, 카드 그리드로도, 히어로가 있는 랜딩 페이지로도 렌더된다.

**테마는 코드 패키지다.** headless SDK(`@wirebound/theme-sdk`) 위에 컴포넌트마다 React 뷰를 짜고, manifest(토큰 · 컴포넌트별 변형 · 패턴)를 선언한다. 뷰가 없는 컴포넌트는 SDK 기본 뷰로 그린다. 카탈로그는 닫혀 있다 — 테마는 컴포넌트 종류나 props 를 더하지 못하고 형태만 정한다. 이 선을 지켜야 스키마가 닫힌 채로 남고, 검증 · 내보내기 · LLM 조작이 성립한다. 목표 설계 전체(업로드 · 버전 · 프로젝트의 테마 선택 · 토큰 편집 · 스냅샷의 테마 · 내보내기의 테마)는 `docs/superpowers/specs/2026-09-27-code-themes-design.md`가 든다.

**지금 서 있는 것:**

- **캔버스는 same-origin iframe 안에서 프로젝트가 고정한 `id@버전` 의 번들과 토큰으로 그린다.** iframe 문서는 표준 모드(`<!doctype html>`)로 선다 — 내보낸 번들 · PPTX 화면과 같은 레이아웃 규칙이라 같은 폭에서 노드 · 번호 마커가 같은 자리에 선다(quirks 모드면 폼 뒤 여백 · 줄 높이 셈이 갈린다). 번들(`theme.js`)은 에디터가 세션마다 하나 두는 숨은 적재 iframe 에 `<script>` 로 싣고 판마다 한 번만 싣는다. 캔버스 머리의 시트는 SDK 기본 뷰 CSS → 그 판의 `theme.css`(`<link>`) → 토큰 CSS 변수 차례다. 다른 사람이 테마 · 토큰을 저장하면 열린 캔버스가 `theme-changed` 로 새로고침 없이 따라가고(토큰만이면 변수만, 판이 바뀌면 번들을 다시 싣는다), 끊긴 동안 놓친 저장은 셸이 프로젝트를 다시 읽을 때의 `themeRev` 로 따라잡는다. 번들을 못 받으면(오류 · 등록 없음 · 10 초) SDK 기본 뷰로 그리고 셸 머리에 한 줄로 알리며 «다시 불러오기» 를 둔다.
- **프로젝트 설정 페이지**(`/projects/:projectId/settings` — §9)가 테마를 고르고(확인 창에 토큰 이어짐 · 버려짐 · 기본값 수와 페이지별 없는 variant 수) 토큰을 고친다(manifest 선언에서 짓는 폼 + 갤러리 미리보기). 인스턴스 관리자는 **테마 관리** 화면(`/admin/themes`)에서 패키지를 올리고 판을 숨기고 스타터 템플릿을 받는다 — 프로젝트 목록 머리의 링크는 관리자에게만 있다.
- **서버는 테마 패키지를 받고 프로젝트가 그중 하나에 고정된다.** 인스턴스 관리자(§10)가 `.wbtheme` 를 올리고(`POST /api/admin/theme-packages` — 본문은 zip 바이트, 서버는 코드를 실행하지 않고 `readWbtheme` · manifest · SDK 범위 · `system-` 접두어 · 같은 `id@version` 을 본다) 버전을 숨기고 되살린다. 올린 패키지는 불변이고 지우는 길이 없다. 로그인한 사람은 목록 · manifest · 패키지 안의 파일을 읽는다(숨긴 버전은 목록에서 관리자에게만 보이고 파일은 누구에게나 나간다 — 고정한 프로젝트가 그려져야 한다). 한 테마의 «최신» 은 숨기지 않은 버전 가운데 semver 가 가장 큰 것이다.
- **시스템 테마는 다섯이다** — `system-admin`(관리자 — 새 프로젝트가 서는 테마) · `system-commerce`(커머스) · `system-docs`(문서) · `system-portal`(포털) · `system-saas-marketing`(마케팅). 작성자 테마와 같은 SDK 로 짠 저장소 안의 테마이고(`system-themes/<이름>/`), 형태가 다른 구조(카드 그리드 · 아코디언 트리 · 정의 목록 등)는 variant 와 뷰로, 토큰은 사람이 고칠 만한 것(색 · 서체 · 모양 · 밀도 · 폭)만 선언한다. 한 테마 안에서 variant 는 여럿이고 `defaultVariant` 가 그 테마의 대표 모양이다 — 한 문서에 두 모양을 함께 둘 수 있다.
- **시스템 테마는 api 가 기동할 때 넣는다** — 저장소 빌드가 낸 `system-themes/*/dist/*.wbtheme` 가운데 DB 에 없는 `id@version` 만. 같은 `id@version` 인데 내용(sha256)이 다르면 기동을 멈춘다(판을 올려야 한다). 판마다 산출물의 sha256 을 `system-themes/<이름>/checksums.json` 에 적는다 — 판을 안 올린 채 내용이 바뀌면 기동이 멈추기 전에 테스트가 잡는다. 배포한 판의 줄은 고치지 않는다(그 판이 시딩된 DB 가 있다). 테마가 비어 있는 프로젝트는 그 자리에서 `system-admin` 최신판으로 채워지고, 새 프로젝트도 그 판으로 선다.
- **프로젝트의 테마 바인딩은 owner 가 바꾼다**(`PUT /api/projects/:projectId/theme` — `theme_rev` 낙관적 동시성, 숨긴 버전은 지금 고정한 판의 토큰만 고칠 때만). 토큰은 대상 manifest 로 검증하고 기본값과 같은 값을 뺀 뒤 저장한다(값 200 글자 · 전체 16 KB 상한). 저장은 프로젝트 룸에 `theme-changed` 를 방송한다. 바꾸기 전의 영향(이어지는 · 버려지는 · 기본값으로 서는 토큰 수, 새 테마에 없는 variant 를 쓰는 노드 수)은 `GET …/theme/impact` 가 계산한다. lint 의 테마 규칙이 «현재 테마에 없는 variant» 를 본다(§12.4).
- **변형은 manifest 가 선언한다** — `components[type].variants` · `defaultVariant` · `hideProps`. 노드의 `variant`가 선언 밖이면 렌더러가 `defaultVariant`로 그린다(페이지 데이터는 바꾸지 않는다). 속성 패널의 변형 칸과 감출 속성도 이 선언을 읽는다.
- **내보내기(HTML 번들 · PPTX 화면)도 프로젝트가 고정한 `id@버전` 의 번들 · CSS · 토큰으로 그린다**(§11.3). 테마 코드는 브라우저(내보낸 페이지 · PPTX 의 Chromium)에서만 돈다 — api 의 Node 프로세스는 패키지 파일을 바이트로 번들에 싣기만 한다.
- **테마는 저장소 밖에서 짜서 `.wbtheme` 한 파일로 빌드한다.** 스타터 템플릿(`wb-theme pack-template` 이 짓는 zip — SDK · kit tarball 과 코딩 에이전트용 `SKILL.md` 동봉)을 풀고 `wb-theme dev` 로 갤러리를 보며 짜고, `wb-theme build` 가 manifest 를 검증해 `dist/<id>-<version>.wbtheme` 를 낸다. `wb-theme check` 는 갤러리 칸 전부를 빌드한 번들로 그려 오류를, `wb-theme shots` 는 실 Chromium 스크린숏으로 콘솔 오류 · 가로 넘침을 본다(§3.3). `.wbtheme` 는 zip 이고 `manifest.json` · `theme.js`(IIFE — `react` · `react/jsx-runtime` · `@wirebound/theme-sdk` 를 번들에 넣지 않고 호스트가 세운 `__wirebound_runtime__` 에서 읽는다) · `theme.css` · `assets/**` 만 든다. 읽기(`readWbtheme`)는 크기 · 항목 수 · 경로 · 허용 목록 · 링크를 풀기 전에 본다. 시스템 테마 다섯도 `pnpm build` 가 같은 길로 `.wbtheme` 를 낸다. 만든 `.wbtheme` 는 관리자가 올린다(위 «테마 관리»).

### 6.1 노드 속성

노드의 루트에는 `data-wb-*` 속성이 실리고, 테마의 CSS는 이것을 셀렉터로 쓴다.

| 속성 | 값 | 누가 싣나 |
|---|---|---|
| `data-wb-id` | 노드 id | 렌더러 — 에디터의 선택 · 잠금 · 코멘트 앵커 |
| `data-wb-component` | 컴포넌트 타입 | 렌더러 |
| `data-wb-variant` | 변형(`variantFrom`이면 그 prop 값) | 렌더러 |
| `data-wb-state` | 공백 구분 상태 목록 | 렌더러 |
| `data-wb-marker` · `data-wb-marker-offset` | 번호 마커의 자리(`top-start` 등)와 어긋남 `x,y` | SDK `Root` — 뷰가 `marker` 를 줄 때 |
| `data-wb-focus` | 선택 외곽선 · 마커의 기준 상자 | SDK `Focus` — 없으면 루트가 기준이다 |
| `data-wb-structure` | 기본 뷰의 형태 이름 | SDK 기본 뷰 |
| `data-wb-part` | 기본 뷰의 내부 조각 이름 | SDK 기본 뷰 |

앞의 넷은 렌더러가 짓고 뷰가 자기 루트(`Root`)에 편다 — 어느 테마의 뷰든 같다. 마커 · 초점 자리는 뷰가 DOM 을 바꿔도 번호 마커 · 외곽선이 제 자리에 서게 하는 훅이고, 좌표는 `renderer` 의 한 함수가 이 속성으로 계산한다(에디터 오버레이 · 내보낸 번들 · PPTX 가 같은 함수를 쓴다 — `docs/superpowers/specs/2026-09-27-code-themes-design.md` 「뷰 계약」). 뒤의 둘은 SDK 기본 뷰의 마크업 훅이라, 자기 뷰를 짠 테마는 자기 마크업을 쓴다(테마의 뷰가 기본 뷰를 불러 감싸면 그 훅이 그대로 선다).

### 6.2 patterns — 테마가 소유한 구성 레시피

패턴은 테마 manifest 의 `patterns`에 든 **파라미터화된 스키마 조각**이다. 레이아웃이 패턴을 조합해 셸을 만들고, 페이지도 패턴을 꽂아 콘텐츠를 채운다.

```jsonc
{
  "patterns": {
    "hero.split": {
      "name": "히어로 — 좌우 분할",
      "slots": { "title": "text", "body": "text", "cta": "action", "image": "media" },
      "schema": {
        "type": "Section", "variant": "hero",
        "children": [
          { "type": "Grid", "props": { "columns": 2 }, "children": [
            { "type": "Flex", "props": { "direction": "column" }, "children": [
              { "type": "Text", "slot": "title", "props": { "role": "display" } },
              { "type": "Text", "slot": "body",  "props": { "role": "body" } },
              { "type": "Button", "slot": "cta", "variant": "primary" }
            ]},
            { "type": "Media", "slot": "image" }
          ]}
        ]
      }
    }
  }
}
```

패턴을 페이지에 넣으면 `schema`가 전개되고 노드 `id`가 새로 발급된다. `slots`에 선언된 자리는 우측 속성 패널에서 채운다.

`slot` 필드는 **패턴 템플릿에만 존재**한다. 전개된 페이지 노드에는 남지 않으므로(§4.3의 노드 형태 그대로다), 패턴은 삽입 시점의 편의 장치이지 런타임 개념이 아니다. 삽입 후에는 일반 노드와 구분되지 않고 자유롭게 편집된다.

핵심 성질은 **테마를 바꾸면 같은 패턴 이름이 다른 모양으로 재현된다**는 것이다. 두 테마가 같은 이름(예: `hero.split`)을 선언하면 슬롯 계약은 같고 전개 결과(구조 · variant)는 테마마다 다르다. 테마 교체가 곧 사이트 리디자인이 된다. 패턴은 테마마다 선택이다 — 선언하지 않은 테마도 있다.

패턴 이름은 `<범주>.<변형>` 규칙을 따르고, 범주는 고정 목록이다: `header` · `nav` · `hero` · `features` · `content` · `cta` · `pricing` · `testimonial` · `footer` · `auth` · `empty` · `error`.

**패턴과 페이지 프리셋의 차이**

| | 패턴 (Pattern) | 페이지 프리셋 (PagePreset) |
|---|---|---|
| 소유 | 테마 | 프로젝트 |
| 범위 | 페이지 일부 (섹션 단위) | 페이지 통째 |
| 테마 교체 시 | 다른 모양으로 재현됨 | 그대로 유지 |
| 용도 | 디자인 언어의 구성 단위 | 반복 화면의 출발점 |

## 7. 편집 · 실시간 · 이력 파이프라인

### 7.1 정방향 흐름

```
[클라] 속성 변경
   → 로컬 낙관적 적용 (즉시 화면 반영)
   → WS 전송 { pageId, baseSeq, ops[], clientOpId }
        ↓
[서버] 권한 확인(editor+) → 잠금 확인 → 적용 후 zod 검증
   → seq 부여 → revision insert (ops + inverse)
   → pages.schema / head_seq 갱신 → 룸 broadcast
        ↓
[본인] ack(seq) 수신 → pending 큐에서 제거
[타인] ops 수신 → 자기 pending 위에 리베이스 적용
```

서버 쪽 입구는 둘이다 — WS `patch` 프레임과 REST(`PATCH .../ops`). 검증·기록·브로드캐스트는
두 입구가 같은 절차를 공유한다(REST 의 ack 는 HTTP 응답이다).

`inverse`는 서버가 적용 직전 상태를 보고 생성한다. 클라이언트가 계산해 보내지 않는다 — 클라이언트 상태가 낙관적으로 앞서 있을 수 있기 때문이다.

**리베이스는 경로를 노드 id 로 다시 짓는다.** ops 의 경로는 자리(index) 경로라, 내 편집이 서버에 닿기 전에 남이 같은 배열 앞자리에 넣거나 빼면 같은 경로가 **다른 노드**를 가리킨다 — 그대로 얹으면 던지지 않고 남의 노드를 고치거나 지우고, 409 뒤 다시 내는 편집이 그 경로를 서버에 보낸다. 그래서 클라이언트는 편집을 큐에 넣을 때 그 경로가 지나는 노드의 id 를 적어 두고(넣을 자리는 부모 · 앞 형제들 · 뒤 형제들 — 가까운 것부터, 양옆이 함께 사라져도 살아 있는 형제 곁에 선다), 남의 ops 를 받으면 새 문서에서 그 id 의 자리로 경로를 다시 지어 얹는다. 다시 지은 ops 가 그 편집이 서버로 나가는 ops 다.

- 경로의 노드가 사라졌으면(남이 지웠다) 그 편집은 얹히지 않는다 — 버리고 알린다.
- 경로가 맞아도 뜻이 바뀌는 op 도 얹지 않는다: 만들 때 없던 키를 만드는 `add`인데 그 사이 남이 그 키를 만들었거나, `children` 배열을 통째로 바꾸는데 그 사이 자식 줄이 바뀌었으면 남의 것을 덮는다.
- 같은 필드 값을 남이 고쳤으면 내 값이 얹힌다(서버가 받는 순서대로 뒤의 것이 이긴다).
- **페이지를 서버에서 읽는 동안 온 그 페이지의 revision(남의 ops · 내 ack · 번호 응답)은 적어 두었다가 읽은 판 뒤에 번호 차례로 얹는다** — 판을 싣는 입구 전부다: 페이지 열기(떠났다 돌아오는 길 포함) · 재연결 · 복원 뒤 다시 읽기 · 편집 실패 수습. 읽은 판이 그 커밋 앞일 수 있고, 그 revision 은 이 탭에 다시 오지 않는다. 번호가 이어지지 않으면 얹지 않고 낡았다고 말한다. 적어 둔 것은 복원이 알려지거나 다른 페이지를 실으면 버린다 — 복원이 알려지기 전에 적은 것은 복원 앞 판의 것일 수 있다. 복원이 알려지기 전에 시작한 읽기의 판은 복원 앞일 수 있으므로, 실어도 «복원됐다»는 낡음을 그대로 둔다. **«복원됐다»는 복원이 바꾸는 것(메뉴 · 페이지 · 코멘트 · 설명 · 테마 선택)을 전부 다시 읽은 판만 거둔다** — 페이지만 읽는 조회(재연결 · 다른 페이지 열기 · 편집 실패 수습)로는 안 거두고, 다시 읽기를 시작한 뒤 새 복원이 알려졌으면 그 다시 읽기로도 안 거둔다. 다시 읽기를 시작한 **뒤에** 시작한 페이지 조회(다시 읽는 사이 다른 페이지로 옮긴 판)는 거둔다 — 나머지는 그 다시 읽기가 이미 읽기 시작했다. 내가 한 복원의 알림(연결 id 없이 나가 내 소켓이 되받은 것)은 복원 응답의 안전망 스냅샷 id 로 알아보고 넘긴다. 내 복원의 답을 잃으면(커밋 전에 거절됐는지 모른다 — 연결 실패 · 봉투 없는 5xx) 서버는 복원했을 수 있는데 그 알림은 내 연결로 안 오므로, «복원됐는지 모른다»는 같은 낡음을 세우고 같은 단추로 다시 읽게 한다 — 스스로 다시 읽지 않는다(그 읽기가 실패하면 판을 비우는데, 복원이 안 닿았으면 멀쩡한 화면을 지운다).
- **페이지를 떠나며 버린 편집은 전부 말한다.** 앞 편집의 답을 기다리는 동안 쌓인 편집은 서버에 가지 않았다 — 떠나는 순간 그 수를 말하고, 답을 기다리던 편집이 거절되거나 답을 못 받으면 둘을 합쳐 말한다. 그 답을 기다리는 동안 또 떠나면 그 떠남에서 버린 것도 합치고, 버린 것이 여러 페이지에 있으면 페이지 수를 싣는다. 떠난 페이지에 편집을 이어 보내지는 않는다(그 편집은 앞 편집의 결과 위에 지어졌고, 떠난 페이지의 남의 ops 는 이 탭이 얹지 않는다).
- **편집을 잃었다고 말하는 통지는 서로 덮지 않고 잇는다** — 통지 자리는 하나이고 잃음은 제 때에 온다(리베이스 버림 · 편집 실패 수습 · 판을 다시 싣는 읽기 · 떠남의 거절). 같은 틀의 문장은 수를 더하고, 반영됐는지 모름 · 저장되지 않음 · 되돌리기 이력 초기화 순으로 선다. 새 편집 · 되돌리기 · 닫는 단추가 이은 통지를 통째로 치운다 — 남겨 두면 방금 낸 편집도 실패한 것으로 읽힌다. 누른 뒤 답을 기다렸다가 서는 것(되짚기 이력을 받은 되돌리기 · 페이지 목록을 읽은 붙이기)은 기다리는 사이 선 잃음을 치우지 않는다 — 누른 때의 통지가 아니라 그 뒤에 온 잃음이고, 제 말은 그 뒤에 잇는다. 세션이 끊긴 통지는 잃음이 덮지 않는다. «화면에 남아 있는 편집은 저장되지 않았다»(수습이 판을 못 읽음)는 판이 다시 실리면 거둔다.
- **떠남의 통지는 페이지를 옮겨도 남는다** — 옮긴 뒤의 화면에 서는 것이 요점이다(판을 옮기면 이은 통지 가운데 떠남의 것만 남는다). 새 편집이 덮고, 그 통지가 가리키는 페이지를 다 다시 열면 풀리며, 닫는 단추로 닫는다(편집을 못 내는 화면 — 뷰 모드 · viewer — 에서는 새 편집이 덮을 일이 없다). 가리키는 페이지를 다시 연 뒤 그 페이지에서 또 편집을 버리고 떠났으면 그 다시 열기는 확인이 아니다 — 통지는 그 페이지를 다시 가리킨다.
- **로그아웃은 보낸 편집의 답을 받은 뒤에 나간다.** 칸에 친 채 누르면 그 클릭이 낸 편집과 로그아웃이 겨루고, 로그아웃이 먼저 세션을 지우면 편집은 거절되는데 화면이 내려가 말할 자리가 없다. 답이 한도(3초) 안에 안 오면 기다리지 않고 나간다 — 로그아웃은 권한을 줄이는 쓰기라 막지 않는다. 그때 답을 못 받은 편집(«모름») · 거절된 편집 · 못 보낸 편집(«저장되지 않았다»)의 수는 로그인 화면이 한 줄로 말한다 — 기다리는 동안 수습 · 다시 읽기가 버린 편집도 센다(그 화면은 셸째 내려가 아무도 못 봤다). «거절»은 큐에서 빠진 편집에만 선다 — 보내기가 거절됐어도 큐에 남은 편집은 번호를 기다린 뒤 다시 나가 커밋될 수 있어 «모름»이다. 그 탭에서만, 그 로그아웃이 연 세션 동안만 선다 — 같은 탭의 다음 사람은 로그인 전에 보고, 다음 세션이 끝난 뒤의 로그인 화면에는 없다. 기다리는 동안 세션이 끝났으면(다른 탭의 로그아웃 · 다른 사람으로 들어옴) 로그아웃 요청을 내지 않는다 — 쿠키는 이제 다른 세션의 것이라 내면 그 사람의 세션을 끊는다. 그때 두고 간 편집의 한 줄도 없다(그 세션을 끝낸 것은 이 탭이 아니다).
- 서버는 경로를 다시 짓지 않는다 — 받은 경로를 `baseSeq` 판에 그대로 적용한다(「에러 처리」의 `baseSeq` 불일치). 그래서 **번호가 곧 판본이어야 한다** — 한 페이지 id 에서 번호가 같으면 서버 문서도 같다(「테이블 정의」의 `head_seq` · 「스냅샷」의 복원). 클라이언트의 바탕이 같은 번호의 서버 판과 다르면(클라이언트가 얹은 것이 서버와 갈렸다) 이 장치가 막지 못하므로, 다시 붙을 때는 번호와 함께 문서도 견준다.

### 7.2 소프트 잠금

- 노드를 선택하면 그 **서브트리**에 잠금을 건다 — 여럿을 고르면 고른 서브트리마다 하나다(§9 «선택 — 고르는 법»). 한 연결은 **한 페이지의 노드 집합**을 쥐고, `lock` 프레임 하나가 «이 연결의 잠금을 이 집합으로»를 나른다 — 프레임마다 집합의 노드 **전부**를 판정하고(이미 쥔 노드도 — 같은 집합을 다시 보내는 하트비트도), 빠지는 노드는 놓는다. 이미 쥔 노드를 다시 판정하는 것은 쥔 뒤에 문서가 바뀌기 때문이다 — 복원은 잠금을 안 보고 문서를 갈아 끼워 두 사람의 잠금을 조상/자손으로 만들 수 있고, 다시 판정하지 않으면 그 겹침이 둘 중 하나가 놓을 때까지 서로의 편집을 423 으로 막는다. 다시 판정하면 먼저 하트비트를 보낸 쪽이 겹친 노드를 거절받는다. 대가는 같은 페이지에 남의 잠금이 있는 동안 하트비트도 머리 문서를 읽는 것이다. **판정은 문서를 한 번 돈다** — 판정은 동기이고 페이지 행을 쥔 채라, 노드마다 남의 잠금마다 문서를 훑으면 하트비트 한 번이 «고른 수 × 남의 잠금 수»로 늘어 그동안 서버 전체와 그 페이지의 편집이 선다(다시 재는 법: `apps/api/test/ws-lock-cost.test.ts`). 빈 집합은 다 놓는 것이다. 집합은 200 개까지다 — 편집 하나의 연산 상한과 같은 수(고른 것을 한 번에 지우는 묶음이 노드마다 연산 하나다).
- **서버는 획득을 판정한다** — 집합의 노드의 서브트리가 다른 사용자가 쥔 서브트리와 겹치면(한쪽이 다른 쪽의 조상이거나 같으면) **그 노드만** 받지 않고 요청한 연결에 그 노드들을 거절(`lock-denied`)로 답한다 — 나머지는 쥔다. 판정은 1차 방어(선택 차단)와 **같은 함수**다. 같은 사용자의 다른 탭은 막지 않고, 자기 집합 안의 조상과 자손도 견주지 않는다(잠금 소유자는 사람이다). 거절이 집합의 일부면 화면은 그 노드를 선택에서 빼고 «○○님이 편집 중이라 고를 수 없습니다»를 하단 바에 세운다(누구인지는 잠금 목록에서 읽는다 — 아직 모르면 «다른 사람이»). 전부면 선택을 **잡지 않은 채** 남기고 편집 입구는 남의 잠금으로 막힌다 — 자격을 보는 사이 멤버십이 바뀌었거나 서버가 끝내지 못한 획득도 프레임의 노드 전부를 거절하고 그 연결이 쥔 것을 다 놓는다. 배지가 아직 닿지 않은 창의 경합 · 재연결의 재알림도 이 판정을 지나므로 **겹친 잠금은 서지 않는다**. **편집 커밋과 잠금 획득은 페이지 행 하나에 줄 선다** — 편집은 그 행을 쥔 채 2차 방어를 판정하고 커밋하며, 획득도 모두 그 행을 쥔 채 판정한다 — 같은 페이지에 남의 잠금이 있어 문서를 봐야 하면 커밋된 문서로(편집이 트리를 옮기거나 노드를 더하는 사이의 획득도 겹치지 않는다). 그래서 판정을 지난 편집이 방금 선 남의 잠금 아래로 커밋되지도 않는다. 거절은 그 `lock` 프레임과 짝지어지고(화면이 매긴 차례를 되돌려준다), 서버가 오류로 판정을 끝내지 못한 획득도 거절로 답한다(답이 없으면 화면은 쥔 줄 안다). TTL 로 걷힌 잠금은 그 방에 알린다. 획득을 거절하지 않고 겹친 잠금을 «서로 막는 보수적 결과»로 받아들이면, 재연결 · 승격 뒤 첫 편집 · 보통 경합에서 잠금이 실제로 겹쳐 두 사람이 서로를 막는다.
- TTL 30초(집합째), 편집 중 하트비트(같은 집합을 다시 보냄)로 갱신, WS 연결 종료 시 집합 전부를 즉시 해제.
- 잠긴 노드마다 다른 사용자 화면에 "○○ 편집 중" 배지가 뜨고 선택이 차단된다(1차 방어) — 여럿을 고르는 몸짓(Cmd · Shift 클릭 · Cmd+A · 사각형)도 그 노드를 건너뛴다.
- 서버는 patch 수신 시 잠금 소유자를 재확인한다(2차 방어). 불일치면 423 `locked`(누가 잡고 있는지를 싣는다). **편집이 건드리는 자리는 연산마다 그 연산이 선 문서의 좌표로 잰다** — JSON Patch 의 포인터는 앞 연산을 적용한 뒤 문서의 좌표이고 `move` 의 `path` 는 `from` 을 뺀 뒤 좌표라, 잠긴 노드의 자리를 연산마다 따라가며 견준다(배열 번호는 적용이 읽는 대로). 화면이 편집을 미리 묻는 자리(끌어 놓기 · 컴포넌트 목록의 «넣기» 단추 · 되돌리기 · 다시 실행 · 붙이기 · 복제 · 여럿을 고른 판의 지우기 · 잘라내기 · 일괄 속성 · 고른 것이 바뀌어 내려가는 칸의 초안)도 같은 함수를 부른다 — 하나 고른 판의 지우기 · 순서 · 계층 · 속성 칸은 이 함수가 아니라 고른 노드의 잠금(선택 판정)으로 막는다. 적용이 실패하는 연산부터는 재지 않는다 — 그 앞에서(또는 그 연산 자신이) 잠긴 자리에 닿지 않았으면 묶음째 `patch-failed` 로 거절된다. 이 판정을 거치는 입구는 편집 셋(REST `PATCH …/ops` — MCP 의 `patch_page` 포함 · WS `patch` · `PUT …/schema`)이고, **거치지 않는 입구는 코멘트 번호 · 복원 · 가져오기**다 — 코멘트는 아래 줄, 복원은 프로젝트 전체를 되돌리는 owner 조작이라 대응하는 서브트리가 없고, 가져오기는 새 페이지라 잠금이 설 수 없다.
- **코멘트는 잠금 대상이 아니다.** 잠긴 서브트리 안의 노드에도 코멘트를 달 수 있고 그 번호(`marker`)가 문서에 써진다. 잠금은 같은 것을 동시에 고치는 것을 막는 장치이고, 번호는 속성·구조 편집과 부딪히지 않는다(잠금 소유자의 탭은 방송으로 받는다). 막으면 노드를 선택만 해 둬도 그 아래에 의견을 못 달고, 잠금을 걸지 않는 에이전트가 어긋난 점을 코멘트로 되돌려주는 길(원칙 3 · §7.4)도 막힌다.
- MVP는 서버 인메모리 저장소를 쓰되 인터페이스를 분리해, 다중 인스턴스 확장 시 Redis 구현으로 교체한다.

### 7.3 개인 undo/redo

클라이언트가 **자기 revision id 스택**을 보유한다.

- **undo**: 스택 최상단 revision의 `inverse`를 현재 문서에 적용 가능한지 검사한다. 경로는 「정방향 흐름」의 리베이스와 같이 노드 id 로 다시 짓는다 — `inverse`는 그 revision 의 문서에서 지은 자리 경로라, 그 사이 남이 같은 배열 앞자리에 넣었으면 옛 경로가 남의 노드를 가리킨다. 가능하면 새 patch로 전송하고, revision id를 redo 스택으로 옮긴다. 새로고침으로 재구성한 항목도 붙잡는다 — 지금 판에서 그 revision 뒤의 `inverse`를 최신 것부터 거꾸로 얹어 그 revision 의 문서를 짓고 거기서 노드 id 를 적는다. 그 사이에 남의 revision(코멘트 번호 · 토큰으로 낸 내 것 포함)이 끼어 있으면 그 구간의 이력을 누가 냈든 받아 함께 되짚는다(`GET .../revisions?beforeSeq=`) — 빠진 구간은 그 아래가 모두 찬 데까지 한 조회로 받는다. 받기 · 짓기 · 붙잡기는 **처음 되돌릴 때** 한다 — 페이지를 열 때 하면 되돌리기를 안 눌러도 문서 통째 교체 revision(문서 두 벌)이 낀 페이지마다 수 MB ~ 수백 MB 를 받고, 50 항목을 다 지으면 문서 크기 × op 수만큼 화면이 멈춘다. 되짚는 판은 목록을 실은 판이라 그 뒤에 판이 올라도 받을 구간은 늘지 않는다. 맨 위 세션 항목을 «적용 불가»로 건너뛴 누름이 그 아래 새로고침 항목에 닿아도 붙잡기 전에 받는다 — 건너뛴 것은 그 세션 항목뿐이고 함께 알린다. 되돌리기의 두 조회(목록 · 되짚기)는 `inverse`만 받는다 — `ops`는 되돌리기에 안 쓰이고, 문서 통째 교체 revision 이면 응답의 반이다. 받는 동안 되돌리기 · 다시 실행은 꺼지고(다시 실행이 맨 위를 바꾸면 그 누름이 버려진다), 그 사이 이 탭의 편집이 스택 맨 위에 올랐으면 그 누름은 되돌리지 않는다. 조회가 실패하면(답이 없으면 읽기의 시간 한도에서) 되돌리지 않고 알린다 — 항목은 남아 다시 누르면 다시 받는다. **문서를 못 지은 항목(한 누름에 받는 구간의 한도 밖에 번호가 남았다)은 경로 그대로 보내지 않는다** — 남의 노드를 고친다. 누를 때 «적용 불가»와 같이 건너뛰고 그 수를 말한다.
- **적용 불가**: 그 사이 다른 사람이 대상 노드를 지운 경우다. 에러가 아니라 정상 흐름으로 처리한다 — 스택에서 제거하고 "이미 변경되어 되돌릴 수 없습니다"를 안내한 뒤 다음 항목으로 넘어간다.
- **redo**: undo가 만든 revision의 `inverse`를 같은 방식으로 적용한다.
- **새로고침**: 서버에서 내 actor의 최근 revision 50개를 받아 스택을 재구성한다. 페이지를 실은 번호까지의 것만 싣고, 그 뒤 이 탭이 이미 쌓은 항목 **아래에** 서버 번호 순으로 끼운다 — 목록이 오기 전에 이 탭에서 고친 편집을 덮지 않는다. 목록을 받는 동안 판을 다시 실었으면(재연결 · 복원 · 실패 수습) · 떠났으면 그 목록은 싣지 않는다 — 다시 싣는 길은 스택을 채우지 않는다. 같은 페이지를 다시 실어 실을 항목을 버렸으면 그렇다고 알린다(이미 다른 통지가 서 있으면 그것을 덮지 않는다). 바탕이 서버와 갈라진 판(받은 편집이 안 얹혔다)에서는 싣지 않는다 — 되짚기가 서버의 노드를 붙잡는다는 보증이 없다.

undo도 새 revision으로 append되므로 다른 사람 화면과 절대 어긋나지 않는다.

**편집 하나 = 되돌리기 하나.** 여럿을 고른 판의 삭제 · 복제 · 잘라내기 · 붙이기 · 일괄 속성은 연산 묶음 하나(revision 하나)라 되돌리기 한 번에 통째로 돌아오고 다시 실행도 통째다.

**문서 전체 교체(`PUT .../schema`)가 만든 revision도 같은 방식으로 되돌릴 수 있다** — 그 `inverse`는 `/root`뿐 아니라 `/version`도 담지만 편집 경로가 그것을 받아들인다. undo 스택에 되돌릴 수 없는 항목이 섞이지 않는다.

### 7.4 LLM 편집 경로

MCP의 `patch_page`는 WebSocket 대신 REST로 들어오지만, 그 뒤 파이프라인(검증 → revision → 브로드캐스트)은 완전히 같다. 에이전트가 고친 내용이 열려 있는 사람 화면에 즉시 나타나고, `actor_type='mcp'`, `actor_label='<토큰명>'`으로 구분 표시된다.

에이전트는 노드 잠금을 걸지 않는다. 대신 patch에 `baseSeq`를 반드시 포함하며, 불일치 시 409를 받고 재조회 후 재시도한다.

## 8. 상호작용

### 8.1 모델

```jsonc
{
  "on": "click",              // click | change | select | submit
  "actions": [
    { "type": "setProp",    "target": "n_9c1e", "prop": "loading", "value": true },
    { "type": "setVisible", "target": "n_4a2b", "value": false },
    { "type": "switchTab",  "target": "n_1f8c", "tab": 2 },
    { "type": "navigate",   "target": "page:관리자/회원/상세" },
    { "type": "openModal",  "target": "page:관리자/회원/등록" }
  ]
}
```

액션 타입은 위 5종으로 고정한다. 스크립트나 표현식은 허용하지 않는다. 그래서 규칙을 정적으로 검증할 수 있고(타겟 존재 여부, prop 유효성), 자동으로 문장화할 수 있다.

### 8.2 자동 문장화

```
"① 검색 버튼 클릭 시 ② 목록이 로딩 상태로 바뀝니다"
"③ 상세정보 탭 선택 시 ④ 기본정보 영역이 숨겨집니다"
```

우측 패널, HTML 번들, PPTX 모두 이 문장을 싣는다. 설계서 독자가 규칙 JSON을 볼 일이 없다. 노드에 별칭(§4.3)이 있으면 문장은 그 노드를 별칭으로 부른다(«① 머리 저장 클릭 시 ② 회원 목록이 숨겨집니다» — 번호는 그 앞에, 조사는 별칭의 끝 글자에 맞춘다).

### 8.3 실행

편집 모드에서는 상호작용이 동작하지 않는다(노드 선택이 우선). 뷰 모드 토글 시 `renderer`의 상호작용 런타임이 활성화되어 실제로 동작한다. 내보낸 HTML 번들은 항상 뷰 모드다.

```

그림의 기호는 아이콘 단추다(아래 «단추의 아이콘»). `↶` · `↷` 는 되돌리기 · 다시 실행, `⬚` 는 배치 선 토글(아래 «배치 선»), `┊` 는 머리의 구분선, `1280▾` 는 뷰포트 폭 고르개, `−100%+` 는 줌(축소 · 배율 · 확대), `⟷` 는 화면 맞춤, `+` · `…` 는 트리 줄의 행동(편집할 수 있는 판에서 줄에 마우스 · 포커스가 있거나 고른 줄일 때 선다) · 컴포넌트 목록 카드의 `+` 는 «넣기» 단추, `││` 는 폭을 바꾸는 손잡이, `⠿` 는 고른 노드를 옮기는 캔버스 손잡이(세로 점 두 줄의 쥐는 자리 아이콘), `══` 는 하단 컴포넌트 목록의 높이를 바꾸는 손잡이다. 머리는 창 전체 폭, 하단 바는 캔버스 칸 아래(두 사이드바 사이)이고, 컴포넌트 목록은 펼치면 캔버스와 하단 바 사이에 선다(하단 바의 «컴포넌트»로 열고 접는다).

**단추의 아이콘.** 셸의 단추와 행동 메뉴 항목은 아이콘(lucide)을 쓰고, **같은 동작은 어디서나 같은 아이콘이다** — 추가는 `+`, 더 보기는 `…`, 지우기는 휴지통, 닫기는 `×`, 위로 · 아래로는 화살표처럼. 한 아이콘을 두 동작이 나눠 쓰지 않는다. 꼴은 셋이다.

- **아이콘만** — 트리 줄 · 트리 제목 줄의 `+` · `…`, 트리 제목 줄의 «모두 접기» · «모두 펴기», 머리의 `…` · 되돌리기 · 다시 실행 · «배치 선» · 축소 · 확대 · 화면 맞춤, 통지 · 대화 상자의 닫기, 컴포넌트 카드의 «넣기», 캔버스 손잡이, 속성 목록 항목의 «N번째 지우기» · 상호작용의 규칙 · 액션 지우기 · 코멘트의 지우기. **이름은 아이콘이 아니라 글이 든다** — 접근 이름과 마우스를 올렸을 때의 툴팁이 그 자리의 글 그대로다(«되돌리기» · «회원관리 더 보기» · «1번째 지우기» · «통지 닫기»). 지우기의 휴지통은 누르기 전 — 마우스를 올리거나 키보드 포커스가 오면 — 붉어진다(꺼진 단추는 안 붉어진다).
- **아이콘 + 글** — 행동 메뉴(트리 줄 · 트리 제목 줄 · 머리 · 셸 밖 화면 머리의 `…`)의 모든 항목(«삭제»는 붉은 글), 속성 목록의 «항목 추가» · 상호작용의 «상호작용 추가» · «규칙 N에 액션 추가», 하단 바의 «컴포넌트», 코멘트의 «코멘트 달기» · «문서 순서대로 재번호» · «수정», 가져오기 상자의 «JSON 직접 붙여 넣기»(접힘 · 펼침 꺾쇠).
- **글만** — 되돌릴 수 없는 일을 확정하는 단추(삭제 확인 · 복원 확인 · 토큰 폐기 확인 …)는 글과 위험 색 그대로다. 모드 · 탭 · 폼의 단추도 글이다.

줌 묶음이 아이콘만인 것은 머리가 한 줄로 서는 폭을 지키려는 것이다 — 머리가 한 줄에 드는 창 폭이 좁은 창의 접힘 문턱을 정한다(아래 «머리»). 다시 재는 법: `apps/web/build-test/editor-head-tools.test.ts`(머리 한 줄에 드는 최소 창 폭) · `icon-buttons.test.ts`(좁은 칸 · 머리 한 줄 · 휴지통의 위험 색).

**에디터는 데스크톱 창을 전제하고 좁은 창(폭 640px 이하)은 지원하지 않는다** — 좌측(최소 200px) · 우측 패널(최소 300px) · 손잡이와 여백(16px)이 폭을 내주지 않아, 두 사이드바가 최소 폭인 동안 캔버스 칸은 창 폭에서 516px 을 뺀 만큼이고(문서가 쓰는 폭은 안쪽 여백 48px 을 더 뺀 만큼), 창 836px 아래에서는 캔버스 몫(320px)이 깨지고, 556px 아래에서는 캔버스 상자가 우측 패널과 겹치며, 516px 아래에서는 우측 패널이 창 밖으로 잘린다(문서에 가로 스크롤은 서지 않는다). 다시 재는 법: `apps/web/build-test`의 `editor-stack`으로 두 폭을 최소로 저장하고(`localStorage` 의 `wirebound.editor.sidebar` 에 `{"sideWidth":200,"panelWidth":300}`) 뷰포트 폭마다 `.wb-shell-canvas`의 폭 · 안쪽 여백과 `.wb-shell-panel`의 왼끝 · 오른끝을 본다.

**머리 — 어디에 있고 무엇을 하는가.** 한 줄이다. 왼쪽은 로고(아이콘 + «wirebound» — 프로젝트 목록으로 가는 링크, 접근 이름 «프로젝트 목록»)와 프로젝트 이름(`<h1>` — 제목은 «지금 여기»라 링크가 아니다), 가운데는 되돌리기 · 다시 실행(편집 모드이고 editor 이상일 때만) · «배치 선»(편집 모드) · 모드(편집 / 뷰), 구분선, 그 뒤가 캔버스를 다루는 도구 — 뷰포트 폭 고르개와 줌(축소 / 배율 / 확대 / 화면 맞춤 — 배율 말고는 아이콘만의 단추)이고, 오른쪽 끝은 `…`(«더 보기»)다. 캔버스 도구는 두 모드 모두에 선다 — 보는 폭과 배율은 모드가 아니라 사람의 화면에 대한 값이다. 통지는 머리에 없다 — 하단 바에 있다. **좁은 창에서는 접는다** — 창 930px 아래에서는 «뷰포트 폭» 글을 눈에서만 감추고(고르개의 이름은 그대로), 875px 아래에서는 줌 묶음(과 구분선)을 머리에서 빼 `…` 의 맨 앞 항목(축소 · 확대 · 화면 맞춤)으로 접는다. 문턱은 편집 모드 · 프로젝트 이름 «관리자 콘솔 설계서» 에서 단계마다 머리가 한 줄에 드는 최소 창 폭(글 있음 909 · 글 감춤 855 · 줌 접음 683 — Chrome)에 여유를 얹은 값이라 창 1440 · 900 · 700 에서 머리가 한 줄이다. 문턱은 창 폭이라 이름이 긴 프로젝트에서는 머리가 두 줄로 줄을 바꾼다(창 밖으로 넘치지는 않는다). 다시 재는 법: `apps/web/build-test/editor-head-tools.test.ts` · 문턱은 `apps/web/src/shell/head-fold.ts`.

**`…` 메뉴.** 모든 역할에게 같은 다섯이 선다 — **계정 설정 · 프로젝트 설정 · 스냅샷 · 프로젝트 내보내기 · 로그아웃.** 머리가 줌 묶음을 접은 좁은 창(위 «머리»)에서는 그 앞에 축소 · 확대 · 화면 맞춤이 선다. 메뉴 머리에 로그인한 사람의 이름을 보인다. 계정 설정 · 프로젝트 설정은 주소가 있는 링크(`/account` · `/projects/:id/settings`)이고, 스냅샷 · 프로젝트 내보내기는 에디터 위 대화 상자를 연다. 역할로 항목을 감추지 않는다 — 스냅샷 목록 · 내보내기 · 설정(읽기 전용 칸)은 viewer 도 보고, 막는 것은 그 안의 생성 · 복원이다(「권한 모델」). 로그아웃은 보낸 편집의 답을 한도까지 기다린 뒤 나간다(「정방향 흐름」). 단추로 열고(클릭 · Enter · Space · ↓), 화살표 · Home · End 로 옮기고(꺼진 항목에도 선다 — 포커스가 서야 그 이유가 읽힌다. 꺼진 항목의 Enter · 누름은 아무것도 안 한다), Enter 로 고르고, Escape · 바깥 누름으로 닫는다 — 닫히면 포커스가 `…` 로 돌아온다. 바깥 누름은 캔버스 iframe 안의 누름도 센다. 항목을 포인터로 고른 뒤 같은 자리에 곧바로 오는 둘째 누름(더블클릭 간격 · 몇 px 안)은 삼킨다 — 메뉴가 닫힌 자리 밑의 단추가 그 누름을 받지 않게. **펼친 목록은 화면 맨 위 겹에 선다** — 행동 메뉴(머리 · 트리 줄 · 트리 제목 줄 · 셸 밖 화면 머리의 `…` · `+`) 모두 같다. 단추 아래로 열고, 창 아래가 모자라면 위 · 아래 가운데 넓은 쪽으로 열고(트리 맨 아래 줄은 위로), 창 밖으로 나가면 창 안으로 당긴다 — 트리 칸이 목록을 자르거나 캔버스 · 패널이 덮지 않고, 열 때 트리 칸이 굴러가지 않는다. 열린 동안 칸을 굴리거나 창 크기가 바뀌면 목록이 단추를 따라가고, 단추가 칸의 보이는 자리 밖으로 굴러가면 닫힌다(칸은 굴린 자리 그대로다). 목록 안의 키는 지금처럼 그 메뉴를 품은 트리의 키 처리에 닿고(메뉴 트리 안의 메뉴에서는 에디터 단축키가 안 선다) — 메뉴가 쥔 키(화살표 · Home · End · Escape · Enter · Delete · Backspace — 아래 «단축키»)는 그 트리의 단축키(메뉴 트리의 삭제 확인 · Alt+화살표)도 안 받는다 — Tab 은 `…` · `+` 다음 자리로, Shift+Tab 은 그 단추로 간다.

**대화 상자 — 스냅샷 · 프로젝트 내보내기 · 페이지 가져오기 · 메뉴 삭제.** 앱의 모달(`<dialog>` 의 `showModal`)이다. 스냅샷 · 프로젝트 내보내기는 머리의 `…` 가, 페이지 가져오기는 메뉴 줄 `+` 의 «JSON 에서 가져오기…»가, 메뉴 삭제(하위가 있는 메뉴)는 메뉴 줄 `…` 의 «삭제» · Delete 가 연다. 한 번에 하나만 선다. 제목과 닫기 단추가 있고, 포커스를 안에 가두고, Escape · 닫기 단추로 닫으며(한글 조합 중의 Escape 는 닫지 않는다), 닫히면 연 자리(`…` · 줄 `+`)로 포커스를 돌려준다. **바깥(배경막) 누름으로는 닫지 않는다** — 스냅샷 폼에 친 글 · 고른 파일을 잃지 않게. 상자 안에서 친 키는 뒤 트리의 단축키(`Delete` 의 삭제 확인)에 닿지 않는다. 열린 동안 뒤 화면(트리 · 캔버스 · 하단 바)은 누름 · 키를 받지 않는다. 상자는 셸 안에서 그려져 셸이 내려가면 함께 내려가고, **복원을 보낸 뒤 상자를 닫아도 복원의 답은 셸이 받는다**(다시 읽기 · «복원됐다» 신호 가르기 — 「정방향 흐름」). 내려간 셸의 답은 버린다. 복원의 답을 잃었다는 문장은 상자를 닫고 하단 바의 «다시 불러오기»를 누르라고 말한다 — 상자가 열린 동안은 하단 바를 못 누른다.

**페이지 가져오기 상자.** 제목이 대상 메뉴를 말한다(«페이지 가져오기 — 회원관리 메뉴로»). 대상은 **연 순간의 메뉴**다 — 열린 동안 남이 그 메뉴를 지우면 서버의 거절이 말한다. 파일 칸(끌어 놓기 · 눌러 고르기 · 키보드로 닿음 — 파일을 끌고 들어오면 강조한다)과 «JSON 직접 붙여 넣기»(기본은 접힘)로 글자를 받고, 미리보기가 서버와 같은 게이트(봉투 · 문서 버전 · 카탈로그 — §11.2)로 읽은 것을 말한다 — 들어갈 페이지 제목 · 노드 수 · 코멘트 수, 막는 이유와 파일의 자리, 막지 않는 경고 수(펴면 자리), 사라진 노드가 될 코멘트 수, 쓰지 않는 `layoutRef`, 그리고 미리보기가 못 보는 것(대상 메뉴가 아직 있는지 · NUL · 본문 크기 · 권한). 제목 칸을 비우면 파일의 제목을 쓴다. 바닥은 [취소] [가져오기]다 — 보내는 동안 «가져오는 중…»으로 꺼지고 «취소»도 꺼진다(보낸 요청은 멈출 수 없다). 머리 «닫기» · Escape 는 보내는 동안에도 닫는다(답이 오래 걸려도 가두지 않는다). **서버가 거절하면 상자를 닫지 않고** 고른 파일 · 글자 · 제목을 둔 채 이유를 보인다(보낸 뒤 상자를 닫았으면 그 이유는 트리의 실패 줄에 선다). 성공하면 상자를 닫고 새 페이지로 옮기고, 가져온 결과(코멘트 수 · 사라진 노드가 된 수 · 쓰지 않은 레이아웃)를 하단 바에 남긴다 — 보낸 뒤 상자를 닫았으면 옮기지 않고 하단 바의 결과만 남긴다.

**좌측 상단 — 메뉴·페이지 트리.** 메뉴 폴더와 페이지를 한 트리에 표시한다. 한 메뉴 아래 여러 페이지를 둘 수 있어 "상황별 화면"이 자연스럽게 표현된다.

**좌측 하단 — 구조 트리.** 선택된 페이지의 컴포넌트 트리다. 노드 선택·추가·삭제·이동을 여기서 한다 — 새 노드는 하단 컴포넌트 목록에서도 넣고, 캔버스에서는 손잡이로 옮긴다. 편집 모드에서만 보이며, 뷰 모드에서는 접혀 메뉴 트리가 전체를 쓴다. 두 트리 사이의 손잡이가 세로 배분을 바꾼다.

**트리 줄 접기.** 메뉴 트리는 페이지나 하위 메뉴를 품은 메뉴마다, 구조 트리는 자식 줄이 있는 노드마다 줄 앞에 펼침 단추(▸ 접힘 · ▾ 펼침)가 서고, 두 트리의 제목 줄에 «모두 접기» · «모두 펴기»가 선다(구조 트리의 «모두 접기»는 뿌리를 편 채 둔다 — 맨 위 갈래가 보인다). 고르기와 같은 읽기라 뷰 모드 · viewer 에게도 선다.

- **접힘은 화면의 상태다** — 구조 트리는 페이지마다, 메뉴 트리는 프로젝트마다 세션 동안 기억하고(페이지를 옮겼다 돌아와도 · 뷰 모드에 다녀와도 그대로) 새로 고침 뒤에는 모두 편다. 서버 · 다른 기기에 안 간다.
- **접고 편 상태는 줄 단추의 `aria-expanded` 가 말한다** — 펼침 단추는 포인터 몫이라 접근성 트리에 안 서고 Tab 정지점도 아니다. 키보드는 ← → 다 — 구조 트리는 에디터 단축키(아래 표), 메뉴 트리는 메뉴 줄에 포커스를 두고 ← 접기 · → 펴기. 구조 트리 줄 아래의 별칭 입력 안의 ← → 는 캐럿을 옮길 뿐 줄을 접거나 고른 노드를 옮기지 않는다.
- **고른 것이 접힌 줄 안으로 들어가면 그 조상을 편다** — 캔버스에서 고름 · 붙여넣기 · 복제 · 화살표 · 사각형 · 되돌리기, 남의 편집이 고른 노드를 접힌 줄 안으로 옮긴 판까지(고른 노드의 조상 사슬이 바뀌면 편다). 메뉴 트리는 열린 페이지와 고른 줄을 그렇게 편다. 사람이 고른 노드의 조상을 직접 접은 판은 다시 펴지 않는다.
- **보이는 차례** — ↑ ↓ 와 Shift+클릭 범위는 접힌 줄 안을 건너뛴다. 고른 노드가 접힌 줄 안에 숨어 있으면 ↑ ↓ 는 그것을 가린 보이는 조상에서 움직이고, 숨은 기준 노드에서 시작하는 Shift 범위는 서지 않는다(누른 줄 하나를 고른다).

**구조 트리 줄 — `타입 (별칭) 요약`.** 줄은 타입 이름 + 별칭이 있으면 ` (별칭)` + 흐린 요약이다(«Flex (머리 줄) 가로» · «Button 저장» · «Section»). 한 줄이고 넘치면 끝에서 줄임표로 자른다. 별칭 · 요약은 사람 글이라 방향을 격리한다(괄호는 격리 밖) — RTL 별칭이나 라벨 · 제목에 든 방향 제어 글자가 줄의 다른 조각을 뒤집지 않는다. **줄 단추의 접근 이름도 같은 글이고**, 줄 행동 `+` · `…` 의 이름은 그 글 뒤에 «추가» · «더 보기»를 붙인다(라벨이 «추가»인 Button 줄과 그 줄의 `+` 가 같은 이름이 되지 않게). 요약은 같은 타입이 여럿일 때 어느 것인지 가르는 데까지만이고 규칙은 카탈로그 정의마다 하나다(`summary` — `packages/schema/src/component/catalog/*.ts`): Flex 가로 · 세로(줄바꿈이면 «· 줄바꿈») · Grid «N열» · Button · Link · Placeholder 라벨 · Field 라벨 · 컨트롤 종류 · Card · EntryForm 제목 · Text 내용 앞 20자 · Tabs 탭 이름 · List 컬럼 이름 앞 셋(« · »로 잇고 더 있으면 «…») · KeyValue «N쌍» · Media 종류 · 설명 · Divider 방향 · Tree «항목 N» · Page · Slot · Section · SearchForm 없음. MCP `get_page` 의 노드 `rowLabel` 이 같은 글이다.

**별칭 고치기.** 속성 패널 맨 위 «별칭» 칸(하나 고른 판 · 어느 컴포넌트에나 — 칸을 떠나거나 Enter 로 커밋) · 구조 트리 줄의 더블클릭 · F2(구조 트리 · 캔버스 어디서나 — 아래 «단축키») · 줄 `…` «별칭 바꾸기». 트리 쪽 셋은 그 줄 아래에 입력을 열고(메뉴 트리의 «이름 변경»과 같은 꼴 — Enter 만 확정 · Escape · 다른 곳 누름은 취소, Enter · Escape 뒤 포커스는 줄로 돌아온다), 지금 별칭이 든 채 선다. 고침은 편집 하나(`add` · `replace` · `remove` `/…/alias`)라 되돌리기 · 실시간 방송 · 잠금 판정을 편집 길 그대로 탄다 — 남이 잡은 노드 · 여럿을 고른 판에서는 입력이 안 열리고 «별칭 바꾸기»가 꺼진다. 친 글은 봉투의 모양으로 다듬어 보낸다(줄을 바꾸는 글자를 공백으로 · 방향 제어 글자와 짝 없는 서로게이트를 빼기 · 앞뒤 공백 걷기 · 60자에서 자름). 비우거나 보이는 글자가 없으면 지운다. 트리 입력을 연 노드가 문서에서 빠지면(같은 사람의 다른 탭 · 에이전트 · 복원) 입력을 닫고, 친 글이 있었으면 하단 바에 «바뀐 선택 때문에 친 값을 쓰지 않았습니다» 한 줄을 세운다 — 같은 id 가 되살아나도(되돌리기 · 다른 탭) 입력이 다시 서지 않는다. 그 노드가 다른 부모로 옮겨지면 입력은 새 자리에 친 글째 선다.

**트리의 줄 행동 — `+` · `…`.** 두 트리에는 툴바가 없다. 편집할 수 있는 판(편집 모드이고 editor 이상)에서 줄에 마우스를 올리거나 · 그 줄을 고르거나 · 줄 안에 포커스가 오면 줄 오른쪽 끝에 `+` · `…` 가 선다(포커스가 줄에 있으면 Tab 이 둘에 닿는다). 뷰 모드 · viewer 에게는 없다. 누르면 **먼저 그 줄을 고르고** 연다 — 명령은 고른 줄에 대해 돌고, 키보드 단축키도 같은 명령이다. 구조 트리에서 여럿을 고른 판은 기준 노드의 줄에서 열면 고른 것 그대로이고(«삭제»가 고른 것 전부를 지운다 · 위로 · 아래로 · 들여쓰기 · 내어쓰기는 «노드 하나를 골랐을 때만 됩니다»로 꺼진다), 다른 줄에서 열면 그 줄 하나로 고른다. 열린 채 그 줄이 고른 줄(구조 트리는 기준 노드)이 아니게 되거나 구조 트리의 고른 목록이 바뀌면(메뉴 안의 Cmd+V · Cmd+D 가 넣은 노드를 고름 · 캔버스의 ↓ · Cmd+A · 남의 편집 · 잠금 거절) 메뉴가 닫힌다 — 항목 · 켜고 끔 · 이유가 다 연 때의 선택의 것이라, 남기면 연 줄의 이름을 단 메뉴의 «삭제»가 다른 노드들을 지운다.

| 줄 | `+` | `…` |
|---|---|---|
| 메뉴 | 하위 메뉴 · 페이지 추가 · JSON 에서 가져오기… | 이름 변경 · 위로 · 아래로 · 들여쓰기 · 내어쓰기 · 삭제 |
| 페이지 | — | 이름 변경 · 옮기기(소속 메뉴 고르기) · 위로 · 아래로 · JSON 내보내기 · 삭제 |
| 구조 노드 | 안에 추가 · 아래 추가 · 패턴 넣기 | 별칭 바꾸기 · 위로 · 아래로 · 들여쓰기 · 내어쓰기 · 삭제 |

- 판정이 지금 막은 항목은 끈 채 이유를 단다(뿌리 노드의 «아래 추가» · 순서 · 계층 · 삭제는 «루트가 아닌 노드를 고르세요»). 그 줄의 **종류**가 결코 못 하는 항목은 뺀다 — 페이지의 들여쓰기 · 내어쓰기, 메뉴의 옮기기(메뉴의 부모는 끌어 놓기 · 들여쓰기 · 내어쓰기가 바꾼다). 꺼진 항목은 지금 막힌 까닭을 한 문장으로 `title` 과 `aria-description` 에 든다 — 마우스를 올리면 보인다. 그 까닭은 항목마다의 조건보다 먼저 서는 원인(남의 잠금 · 고른 것이 없음 · 고른 것이 문서 · 트리에 없음 · 여럿을 고름 · 메뉴 조작을 보내는 중)이 있으면 그것이다. 트리 아래에 늘 서는 이유 줄은 없다 — 키보드로는 꺼진 항목에 화살표로 서서 그 문장(설명)에 닿는다. 메뉴 밖에서 이유를 드는 꺼진 단추(빈 트리의 «최상위 메뉴» · 삭제 확인 · 제목 충돌의 덮기 · 버리기 · 연쇄 삭제의 «모두 삭제»)도 포커스는 받고 누름은 안 받는다.
- 트리 제목 줄에 뿌리 `+` 가 하나씩 있다 — 메뉴 트리 «최상위 메뉴 추가», 구조 트리 «페이지에 추가» · «패턴 넣기» · «프리셋».
- 타입 · 패턴 · 프리셋 고르개 · 이름 입력 · 옮기기 목록은 그 줄 곁에 선다. 고르개 안의 Escape 는 고르개를 닫는다(«취소»와 같다 — 선택은 그대로). 페이지와 하위가 없는 메뉴의 삭제는 두 번 누르기 확인이고(되돌리기가 없다), 확인은 «삭제» 항목이 있던 자리에 서지 않는다(줄 아래). **하위(메뉴 · 페이지)가 있는 메뉴의 삭제는 확인 상자다** — «"회원관리" 메뉴와 하위 메뉴 N개 · 페이지 M개가 함께 삭제됩니다», 페이지가 있으면 경고 아이콘 · 위험 색의 경고 상자에 «페이지 M개와 그 안의 설계가 모두 삭제됩니다»와 지워질 페이지 이름 앞 다섯 · «외 N개»(상자의 설명이 문장과 경고 상자를 함께 품는다), 지우기 직전 상태를 스냅샷으로 남긴다는 한 줄, 확정 단추 «모두 삭제»(글 + 위험 색). 상자가 보인 목록의 id(밑의 메뉴 · 페이지)를 서버에 싣는다 — 서버가 다시 읽은 id 집합이 다르면(그 사이 페이지 추가 · 메뉴 옮기기 — 수가 같아도) 아무것도 안 지우고 지금 목록을 돌려주고, 화면은 그 목록으로 상자를 다시 세우고 «목록이 바뀌었습니다 — 다시 확인하세요.» 한 줄을 띄운다(트리도 다시 받는다). 이름만 바뀐 판은 같은 행이라 지운다. 열린 페이지가 지운 서브트리 안이면 프로젝트 루트로 옮긴다. 연쇄 삭제는 방송하지 않는다 — 페이지 삭제와 같다(지운 페이지를 연 사람은 다음 편집에서 «대상을 찾을 수 없습니다»를 받는다). 구조 노드의 삭제(줄 `…` · 키보드)는 확인 없이 바로 지운다(되돌리기로 돌아온다).
- 구조 트리에서 남이 잡은 노드(「소프트 잠금」)는 고를 수 없으므로 그 줄에는 줄 행동도 끌기도 없다.

**끌어 놓기.** 줄을 끌어 다른 줄의 **위 · 아래(형제로)** 나 **위에 겹쳐(자식으로)** 놓는다. 자식을 받는 줄은 높이의 위 25% · 아래 25% 가 형제 자리이고 가운데가 안이며, 자식을 안 받는 줄은 반으로 갈라 앞 · 뒤만 있다. 놓을 자리는 가는 선(형제) · 줄 강조(자식)로 보인다. 구조 트리 줄에는 하단 컴포넌트 목록의 카드(새 노드)와 캔버스 손잡이(그 노드)도 놓는다 — 같은 띠 · 같은 판정이다. 트리 줄을 끌어 캔버스에 놓지는 않는다(캔버스에서 옮기는 길은 손잡이다). **끄는 포인터가 접힌 줄 위에 0.7s 머물면 그 줄을 편다**(줄 끌기 · 카드 · 손잡이 모두 — 포인터가 멈춰 있어도 편다 · 놓거나 취소하면 걷는다). 접힌 줄에 «안»으로 놓으면 그 안 끝이다.

- **놓을 수 있는지는 이동 판정과 같다** — 메뉴는 메뉴의 형제 · 안으로, 페이지는 메뉴 안으로(다른 메뉴로 옮기기 포함 — 메뉴 줄 위에 놓으면 띠와 무관하게 그 메뉴의 끝), 구조 노드는 카탈로그가 자식을 받는 컴포넌트 안 · 형제 자리로. 자기 · 자기 자손 안, 뿌리 노드의 앞뒤, 남이 잡은 노드 안, 부모가 자식을 안 받는 노드의 앞뒤(검증을 안 지나는 문서에서만 선다), 그리고 낼 편집이 남의 잠금과 부딪치는 자리는 안 된다(구조 트리는 편집 묶음을 «소프트 잠금»의 2차 방어와 같은 함수로 미리 묻는다). 제자리면 보낼 것이 없다. 못 놓는 자리에서는 표시를 안 세우고, 놓아도 아무 일도 없다.
- **놓으면 줄 행동이 보내는 것과 같은 편집을 보낸다** — 구조는 `move` 편집, 메뉴는 `PATCH {parentId, sortOrder}`, 페이지는 `PATCH {menuNodeId, sortOrder}`(부모가 같으면 `sortOrder` 만). `sortOrder` 는 **옮긴 뒤 그 부모 안 차례**다 — 서버는 부모가 바뀌면 새 형제 줄에 끼울 자리로, 같으면 결과 배열의 자리로 읽고 두 뜻이 같은 값이다. 되돌리기 · 실시간 방송 · 서버 거절 수습이 줄 행동과 같은 길을 탄다. 끌어 놓기만의 편집 종류는 없다.
- 끌기는 4px 넘게 움직인 뒤에 선다(그 아래는 클릭 — 고르기). 끈 뒤의 클릭 하나는 삼킨다(줄이 링크면 끌어 놓은 페이지가 열린다). Escape · `pointercancel` 은 취소다. 트리 끝 24px 안에 닿으면 저절로 스크롤한다 — 포인터가 트리 상자 안일 때만이다(상자 밖은 끝 너머가 아니다).
- **구조 트리는 보인 자리에만 놓는다** — 떼는 순간 뗀 좌표로 다시 물은 자리가 지금 보이는 자리와 같을 때만 놓는다(앞 · 뒤는 부모 · 차례 · 띠가, «안»은 부모 · 띠가 같아야 한다 — «안»은 «그 상자 안 끝»이라 남이 그 상자에 자식을 넣거나 빼도 같은 자리다). 끄는 사이 남이 보인 줄의 노드를 지우거나 앞에 줄을 넣어 줄이 밀리면 놓아도 아무 일도 없다 — 표시는 옛 줄 자리에 남는다. 메뉴 트리는 뗀 좌표로 다시 물은 자리에 놓는다.
- **포인터 이벤트로 짓는다(HTML5 DnD 가 아니다)** — 끌기가 서면 누른 요소가 포인터를 붙잡아(`setPointerCapture`) 캔버스 iframe 위를 지나도 끊기지 않는다. 끌기를 시작한 포인터의 이벤트만 듣는다(마우스로 끄는 중 다른 손가락의 뗌이 끌기를 놓지 않는다). 장치는 무엇을 끄는지 모르는 부품이다 — 놓을 자리 판정과 놓았을 때 할 일은 부르는 쪽이 준다.
- 터치 한 손가락으로는 끌기가 서지 않는다 — 브라우저가 그 움직임을 스크롤로 가져간다.

**중앙 — 캔버스.** 문서는 same-origin iframe 안에 그린다 — 테마의 CSS가 셸에 새지 않고, 뷰포트 폭이 iframe 의 폭이라 테마의 미디어 쿼리가 그 폭을 본다. iframe 문서는 표준 모드라 내보낸 번들과 레이아웃 규칙이 같다(§6). 편집 모드에서 선택 아웃라인(고른 노드마다 — 기준 노드는 진하게)과 번호 마커 오버레이가 보이고, 배치 선을 켜면 그것도 보인다(아래). 캔버스에서도 노드를 클릭해 선택할 수 있다(여럿 고르기는 아래 «선택»). **속성 변경은 속성 패널에서 한다.** 구조 변경은 구조 트리(줄 행동 · 끌어 놓기)가 갖고, 캔버스에서는 **끌어 놓는 것 둘**만 한다 — 고른 노드를 손잡이로 옮기기와 하단 컴포넌트 목록의 카드를 끌어 넣기. 캔버스의 노드를 아무 데서나 눌러 끌지는 않는다(캔버스의 누름은 고르기 · 누르고 끌면 사각형 고르기다). 여러 노드를 한꺼번에 끌기 · 복사해 놓기는 없다.

**배치 선.** 머리의 «배치 선»(아이콘 토글 · 누름 상태 `aria-pressed`)은 편집 모드에서만 서고, 켜면 캔버스의 Flex · Grid 노드마다 점선 테두리(Flex 주황 · Grid 보라)와 왼쪽 위 모서리 표시를 그린다 — Flex 는 늘어놓는 방향(→ · ↓ · ← · ↑), Grid 는 «N열». 방향과 열 수는 **그려진 배치로 읽는다**(놓을 자리의 축과 같은 함수 — 아래 «캔버스에 놓기» · Grid 는 그려진 칸 수). 테두리 안에는 같은 색의 옅은 점선으로 칸을 가른다 — Grid 는 열과 열 · 행과 행 사이, Flex 는 자식과 자식 사이(가로 배치는 세로선 · 세로 배치는 가로선)와 줄바꿈으로 선 줄과 줄 사이다. 이 선의 자리도 CSS 가 아니라 **그려진 자식 상자로 정한다** — 서로 겹치는 자식끼리 열 · 행 · 줄로 묶고(칸 안에서 가운데 정렬된 자식의 윗끝이 칸마다 달라도 한 행이다), 이웃 묶음 사이 간격의 가운데에 긋는다(간격이 없으면 경계). 선은 자식이 덮는 범위 안에만 긋고, 자식이 하나 · 없으면 안쪽 선이 없다. 미리보기 노드는 세지 않는다. 칸을 둘 이상 덮는 자식은 그 사이의 선을 지운다. 다시 재는 법 · 선이 이웃 자식 사이 가운데와 1px 안인지 · 자식 수에 비례하는 비용: `apps/web/build-test/layout-guides.test.ts`(`[안쪽 선]` · `[다시 잼]` 로그). 선은 선택 아웃라인 · 번호 마커와 같은 셸 겹 · 같은 측정이라 줌 · 칸 스크롤 · 뷰포트 폭 · 남의 편집 · 배치 미리보기를 따라가고, 캔버스 문서에는 아무것도 넣지 않는다(테마 CSS 와 안 섞인다). 배치 미리보기 노드에는 안 그린다. 켬 · 끔은 사람마다 그 브라우저에 기억하고(못 읽으면 끈 채 시작한다), 뷰 모드에서는 단추도 선도 없다.

**캔버스 손잡이 — 고른 노드 옮기기.** 편집 모드이고 editor 이상이며 노드 **하나**를 골랐고 그것이 뿌리가 아니고 남이 잡지 않았을 때 선택 외곽선의 왼쪽 위 바깥에 손잡이 `⠿`(접근 이름 «<타입 (별칭)> 옮기기» — 별칭이 없으면 «<타입> 옮기기»)가 선다. 셸 겹의 단추라 테마 CSS 가 덮지 못하고, 줌을 걷어 화면에서 늘 같은 크기다. 끌면 그 노드를 옮긴다 — 캔버스 위에도, 구조 트리 줄 위에도 놓을 수 있다. 누르기만 하면 아무 일도 없다(고른 노드 그대로). 남이 그 노드를 잡거나 · 뷰 모드로 바꾸거나 · viewer 로 내려가면 손잡이가 곧바로 걷히고 끌던 것은 놓아도 아무 일도 없다. 고른 노드의 왼쪽 위가 캔버스 칸 밖으로 밀리면 손잡이도 칸 밖이다. 키보드로 옮기는 길은 트리 줄 `…` 의 위로 · 아래로 · 들여쓰기 · 내어쓰기다.

**캔버스에 놓기 — 놓을 자리.** 끄는 포인터 밑 캔버스 문서에서 가장 가까운 노드의 **그려진 상자**를 띠로 나눈다 — 부모가 늘어놓는 축의 앞 25% 는 앞 형제, 뒤 25% 는 뒤 형제, 가운데는 안(자식을 받는 컴포넌트일 때만 — 아니면 앞 · 뒤 반씩). 자식이 없는 빈 컨테이너는 상자 전체가 «안»이다. 문서 안에서 노드가 없는 바탕과 뿌리 자신은 **페이지 끝**(뿌리의 마지막 자식)이다 — 문서 밖의 칸 바탕은 놓을 자리가 아니다. 캔버스 칸 밖으로 밀려난 문서 부분(칸 스크롤 · 줌으로 넘친 쪽)은 캔버스로 세지 않는다.

- **앞 · 뒤의 축은 부모가 지금 그린 배치로 읽는다** — 테마마다 뷰가 달라 카탈로그가 아니라 그려진 결과다. 부모가 `flex` 면 `flex-direction`(`row*` 가로 · `column*` 세로), `grid` 면 자식 둘이 같은 줄(세로로 겹침)에 서 있을 때 가로, 그 밖은 이 노드가 형제와 같은 줄에 서 있으면 가로, 아니면 세로다. `*-reverse` 는 보이는 앞 · 뒤를 문서 차례로 뒤집는다. CSS `order` · `direction: rtl` 로 바뀐 보이는 차례는 안 읽는다 — 보이는 왼쪽 · 위를 문서의 앞으로 센다.
- **놓을 수 있는지와 놓은 자리(부모 + 차례)는 구조 트리와 같은 판정이다** — 대상 노드 + 띠를 같은 함수가 부모 + 차례로 바꾸고, 못 놓는 자리(자기 · 자손 안 · 남이 잡은 노드 안 · 자식을 안 받는 컴포넌트 안 · 낼 편집이 남의 잠금과 부딪침)도 같다. 못 놓는 자리에서는 표시를 안 세우고, 놓아도 아무 일도 없다.
- **표시는 배치 미리보기다** — 놓을 자리가 서 있는 동안 캔버스 문서의 그 자리에 그 컴포넌트(옮기기면 그 노드 서브트리의 사본)를 테마로 그려 반투명으로 실제로 끼운다. 옆 노드가 밀리고, 옮기는 원본은 제자리에 흐리게 남는다. 스토어 · 서버 · 되돌리기 · 실시간 방송 · 구조 트리 · 속성 패널은 미리보기를 모른다 — 캔버스가 지금 문서에 미리보기를 끼운 사본을 그릴 뿐이라 남이 문서를 바꾸면 새 문서 위에 다시 선다. 미리보기 노드는 선택 외곽선 · 번호 마커 · 손잡이 · 판정에 노드로 잡히지 않고(문서 id 의 꼴 밖의 id 를 단다), 외곽선 · 마커는 밀린 자리를 따르다 놓거나 취소하면 제자리로 온다. 못 놓는 자리에서는 미리보기도 없다. 끌기가 트리 줄 위에 있으면 트리 줄에는 선 · 강조가, 캔버스에는 같은 자리의 미리보기가 선다.
- **판정(띠)은 미리보기를 뺀 배치로 잰다** — 미리보기가 밀어낸 배치로 다시 물으면 자리가 옮고 옮은 미리보기가 다시 배치를 바꾸는 떨림이 생긴다. 미리보기를 뺀 배치로 재면 미리보기가 판정을 되먹이지 않아, 포인터가 멈춰 있으면 미리보기가 움직이지 않는다. 미리보기는 늘 포인터 밑 노드 곁(그 안 끝 · 그 뒤 — 노드가 안 밀린다, 그 앞 — 미리보기가 그 노드의 자리에 선다)에 선다.
- 줌 · 칸 스크롤을 반영한다. 캔버스 칸의 위 · 아래 끝 24px 에 닿으면 칸이 저절로 스크롤한다(세로만 · 포인터가 칸 안일 때만 — 칸 아래의 하단 판 위에서 머뭇거려도 칸은 안 밀리고, 판에서 캔버스로 올라가는 길은 끝 띠를 지나는 동안만 민다).

**캔버스로 끄는 끌기는 보인 자리에만 놓는다**(손잡이 · 컴포넌트 목록 카드 — 트리 위에 놓을 때도). 끄는 사이 남의 편집 · 늦은 글꼴로 놓을 자리가 바뀔 수 있다. 아래의 «표시»는 캔버스의 배치 미리보기와 트리 줄의 선 · 강조다.

- 남이 보인 대상을 잡거나 지우거나, 보인 형제 자리의 차례가 밀리면 표시를 곧바로 걷는다 — 포인터가 멈춰 있어도. 걷힌 뒤 포인터가 그 자리에서 4px 밖으로 움직여야 새 자리가 선다.
- 캔버스가 선택 외곽선 · 마커를 다시 잴 때(문서가 바뀜 — 남이 위 노드의 글을 늘려 노드가 밀린 판 포함 · 줌 · 폭 · 캔버스 문서의 크기가 바뀜) 마지막 좌표로 다시 물어, 같은 자리면 새 상자로 다시 그리고 **다르면 표시를 걷는다** — 멈춘 포인터 밑에서 표시가 다른 자리로 뛰어 곧바로 뗀 판이 안 본 자리로 가지 않게.
- 떼는 순간 뗀 좌표로 다시 물은 자리가 보이던 자리와 같을 때만 놓는다(구조 트리와 같은 견줌 — «안»은 부모 · 띠만) · 놓기 직전 지금 문서로 그 자리를 한 번 더 판정해 안 서면 아무것도 안 한다. **문서가 바뀌었다는 것만으로는 버리지 않는다** — 남이 다른 데를 고치거나 내 앞 편집이 리베이스돼도 보인 자리가 그대로면 놓인다.
- 끄는 중 페이지가 바뀌거나 캔버스 iframe 이 새로 서면 그 끌기는 아무것도 안 놓는다.

놓으면 옮기기는 `move` 편집, 넣기는 `+` 의 «추가»와 같은 함수로 지은 새 노드(카탈로그 기본 props · 새 id)의 `add` 편집 하나를 보낸다 — 줄 행동과 같은 편집 전송 길(되돌리기 · 실시간 방송 · 409 리베이스 · 423 통지)이고 끌어 놓기만의 편집 종류는 없다. 넣은 새 노드는 고른 노드가 된다.

뷰포트 폭 프리셋(1920 / 1440 / 1280 / 1024 / 768 / 375)과 줌(25% ~ 200%, «화면 맞춤»)을 제공한다. 폭을 바꾸면 테마가 정의한 브레이크포인트 스타일이 적용된다. 페이지 스키마 자체에는 반응형 분기가 없으므로, 이는 **편집이 아니라 확인**이다. 줌으로 줄인 문서는 그 줄인 폭만큼만 캔버스 칸을 차지한다 — «화면 맞춤»은 프리셋 폭을 칸에 맞춘 줌이고 그 뒤 가로 스크롤이 없다. 다만 줌 하한(25%)에 막히면(칸이 좁고 프리셋이 넓을 때) 줄인 문서가 칸보다 넓어 그만큼 가로로 넘친다.

**하단 바 — 통지와 «컴포넌트».** 캔버스 칸 아래 한 줄이다(좌 · 우 사이드바 사이, 캔버스와 같은 폭). 왼쪽은 통지 — 편집 실패 · 경고 · 남의 변경(복원 포함) · 테마를 못 실음 · 권한이 바뀜 · 페이지 JSON 의 가져온 결과 · 내보내기 실패 · 세션 전환 · 로그아웃 실패 — 이고, 오른쪽은 «컴포넌트»(하단 컴포넌트 목록을 열고 접는 토글 — 편집 모드이고 editor 이상일 때만)다. 캔버스 도구(뷰포트 폭 · 줌)는 머리에 있다(위 «머리»). 높이는 40px 아래로 줄지 않는다 — «컴포넌트»가 없는 뷰 모드 · viewer 의 빈 바도 같은 높이라 모드를 바꿔도 캔버스 칸이 튀지 않는다. 통지가 여럿이면 바가 위로 자라고 캔버스가 그만큼 준다 — 잘라 숨기지 않는다. 통지 칸이 읽을 폭(320px)을 못 받으면 «컴포넌트»가 통지 아래 줄의 오른쪽 끝으로 내려간다 — 도구가 제 폭을 지키고 통지가 남은 폭만 받으면 통지 한 줄이 한두 낱말이 되어 바가 캔버스를 먹는다. 통지가 없으면 한 줄이다. 페이지 JSON 의 두 통지는 저절로 걷히지 않는다 — 고아가 된 코멘트는 되돌릴 수 없어 읽기 전에 사라지면 안 된다. 그 통지의 «닫기» · 다음 가져오기(내보내기)를 보낼 때 · 에디터를 떠날 때 걷힌다. 페이지를 옮기거나 모드를 바꿔도 남는다.

**하단 컴포넌트 목록 — 열고 접기 · 높이.** 하단 바의 «컴포넌트»(`aria-expanded`)를 누르면 캔버스와 하단 바 사이(셸 그리드의 한 줄)에 판(«컴포넌트 목록» 영역)이 서고, 다시 누르면 접힌다. 판을 열면 캔버스 칸이 판 높이만큼 준다. 판 위쪽 손잡이로 높이를 바꾼다 — 끌기(위로 끌면 커진다) · 화살표 · Home/End · 두 번 눌러 기본값. 높이는 기본 340px · 최소 220px 이고(기본은 카드 한 줄과 둘째 줄의 머리가, 최소는 카드 한 줄의 대부분이 보이는 높이), 최대는 캔버스와 판이 나눠 쓰는 세로(좌측 사이드바 높이에서 하단 바와 칸 사이 여백을 뺀 잰 값)에서 캔버스 몫(240px)을 뺀 만큼이다(최소보다 작아지지는 않는다). 통지로 하단 바가 자라거나 머리가 접히면 최대가 그만큼 줄어 판이 조여지고 캔버스 몫이 남는다 — 기억한 높이는 그대로라 통지가 걷히면 판이 돌아온다. 조여진 동안 손잡이를 만져도 키우는 쪽(위로 끌기 · ↑ · End)은 기억한 높이를 줄이지 않고, 줄이는 쪽(아래로 끌기 · ↓ · Home)은 그린 높이에서 움직여 그 높이를 기억한다. 하단 바가 창의 대부분을 먹어 최대가 최소로 주저앉는 판에서는 캔버스가 그 몫 아래로 주고, 그래도 모자라면(낮은 창에 통지가 여럿) 셸이 세로로 넘쳐 하단 바 아래가 창 밖으로 잘린다. 높이와 열림은 두 사이드바의 폭과 같은 자리에 사람마다 그 브라우저에 기억하고, 읽을 수 없는 값은 기본값으로 읽는다(`apps/web/src/shell/sidebar-layout.ts` 「하단 판의 높이」). **판과 토글은 편집 모드이고 editor 이상일 때만 선다** — 뷰 모드로 바꾸거나 viewer 로 내려가면 둘 다 사라지고, 기억한 열림은 그대로라 편집할 수 있는 판으로 돌아오면 다시 열린다. 판은 페이지를 옮겨도 그대로 있다.

**하단 컴포넌트 목록 — 카드.** 판의 위 줄은 갈래 탭(카탈로그의 갈래 — 구조 · 데이터 · 입력 · 액션 · 문서)과 이름 검색 칸이고, 아래는 고른 갈래의 카드다. **카드는 정해진 크기(264 × 200 — 축소판 창 264 × 176 + 이름 줄)이고 판 폭에 맞춰 여러 줄로 감싸이며, 넘치면 판이 세로로 스크롤한다** — 판을 키우면 카드가 커지지 않고 줄이 더 보인다(창 1440 × 900 의 최대 판에서 두 줄). 판이 카드보다 좁으면 카드 폭이 판에 맞게 준다. 카드는 `+` 의 타입 고르개와 같은 목록이다 — 페이지에 둘 수 있는 타입 · 갈래 안은 한국어 이름 차례. 검색어가 있으면 갈래를 가리지 않고 한국어 이름 · 영문 타입에 그 글이 든 카드만 선다(대소문자 무시 · 둘 다 NFC 로 맞춰 견준다). 맞는 것이 없으면 «맞는 컴포넌트가 없습니다». 카드는 축소판 · 한국어 이름 · 오른쪽 위의 «넣기» 단추(`+` 아이콘 — 접근 이름 · 툴팁 «<한국어 이름> 넣기»)다. 올리면 영문 타입과 설명이 툴팁으로 선다. 탭 줄과 카드 줄은 각각 Tab 정지점 하나이고(카드 줄의 정지점은 «넣기» 단추) 화살표 · Home/End 가 그 안을 옮긴다.

- **축소판** — 카드마다 그 컴포넌트의 갤러리 표본(없는 타입은 카탈로그 기본 props 로 지은 노드 하나)을 **프로젝트 테마**(캔버스와 같은 시트 차례 · 테마 정의 · 토큰)로 그려 줄여 보인다. **판 하나에 iframe 하나다** — 카드 판 뒤에 카드 판과 같은 크기로 깔아 함께 스크롤하고, 표본마다 그린 상자를 재서 카드 창에 맞춰 줄이고 상자 밖은 자른다. 남이 테마 · 토큰을 저장하면 따라가고, 테마 번들을 못 실으면 캔버스처럼 SDK 기본 뷰로 그린다. 축소판은 그림이다 — 안의 단추 · 입력은 누름 · 포커스를 받지 않고(`inert`) 누름은 위의 카드 몸통이 받는다.
- **카드 몸통은 끌기 전용이다** — 누르기만 하고 떼면(끌기 문턱 4px 안) 아무것도 안 한다(넣지도 고르지도 않는다).
- **«넣기» 단추 · Enter — «고른 노드 뒤에» 넣기.** 고른 것이 없거나 뿌리면 페이지 끝, 자식을 받는 컴포넌트면 그 안 끝, 잎이면 그 뒤(같은 부모)에 넣고 넣은 노드를 고른다. 누른 채의 키 반복은 넣지 않는다. 자리는 끌어 놓기와 같은 판정이고, 고른 잎을 남이 잡았으면 그 뒤에도 넣지 않는다(판정은 잠긴 노드 **뒤**에 넣는 편집을 막지 않지만 `+` 가 그 판에 항목을 다 끄는 것과 같이 간다). 안 끝에 넣는 판(뿌리 · 컨테이너)은 낼 편집의 판정에 맡긴다 — 페이지를 연 그대로(뿌리 선택) 남이 다른 노드를 고르고 있어도 페이지 끝에 넣는다. 못 넣으면 요청을 안 내고 판 머리에 이유 한 줄을 세운다 — 문장은 같은 판에서 화면이 이미 하는 말(구조 트리 꺼진 항목의 잠금 문장 · `+` «안에 추가»가 꺼진 까닭 · 속성 패널의 잠금 문장 · «고른 노드가 문서에 없습니다»)이다. 그 줄은 다음 누름이 걷고, 세운 판(페이지 · 고른 노드)이 바뀌어도 걷힌다(돌아와도 다시 서지 않는다).
- **끌기 — 넣을 자리에 놓기.** 카드를 끌어 구조 트리 줄이나 캔버스에 놓는다. 끄는 동안 포인터 곁에 카드 이름표가 따라온다. 놓을 자리 · 배치 미리보기 · 보인 자리에만 놓기는 캔버스 손잡이와 같다(위 «캔버스에 놓기 — 놓을 자리» · «캔버스로 끄는 끌기는 보인 자리에만 놓는다» · 트리 줄의 띠는 «끌어 놓기»). 끝 스크롤은 포인터가 마지막으로 지난 쪽(트리 · 캔버스 칸)이 한다. «넣기» 단추에서 시작한 끌기도 끌기다 — 끈 뒤의 클릭은 넣기로 새지 않는다.

**단축키.** 에디터 어디서나(구조 트리 · 캔버스 · 패널 바깥) 먹는다 — 호스트 문서와 캔버스 iframe 문서 둘 다에서 받는다. 표는 하나이고 `?` 가 그 표를 그대로 그리는 «단축키» 대화 상자를 연다. macOS 는 Cmd, 그 밖은 Ctrl 이다(엇갈린 쪽은 안 선다).

| 키 | 동작 |
|---|---|
| Cmd+Z | 되돌리기 — 머리 «되돌리기»와 같은 길(같은 판정 · 같은 편집) |
| Cmd+Shift+Z · Cmd+Y | 다시 실행 |
| Delete · Backspace | 고른 노드(들) 삭제 — 확인 없이 바로(되돌리기로 돌아온다). 여럿이면 묶음 하나다. 지운 뒤 선택이 빈다(줄 `…` «삭제»는 기준 노드의 부모를 고른다) — 이어 친 Delete 는 아무것도 안 지운다. 포커스가 열린 행동 메뉴(그 단추 포함) 안이면 메뉴가 받는다(아래 «키를 쓰는 위젯») |
| Cmd+C · Cmd+X · Cmd+V | 복사 · 잘라내기 · 붙여넣기(아래 «클립보드») |
| Cmd+D | 복제 — 고른 노드마다 제 바로 뒤에 사본(클립보드를 거치지 않는다 · 묶음 하나) · 사본 전부를 고른다 |
| Cmd+A | 형제 모두 고르기 — 기준 노드의 형제 모두(기준 노드가 루트거나 없으면 루트의 자식 모두 · 남이 잡은 것은 건너뛴다) · 브라우저의 «전부 고르기»는 막는다(입력 칸 안은 칸의 것) |
| Escape | 선택 해제(고른 것 전부) — 포커스가 열린 행동 메뉴(그 단추 포함) · 고르개 안이면 그것이 닫히고 선택은 그대로다. 끄는 중(트리 줄 · 손잡이 · 카드)이거나 사각형을 그리는 중이면 그것만 걷는다 |
| Alt+↑ / Alt+↓ | 위로 / 아래로 — 줄 행동과 같은 판정 · 같은 편집(하나 골랐을 때만) |
| Alt+Shift+← / Alt+Shift+→ | 내어쓰기 / 들여쓰기 — 같음 |
| ↑ / ↓ | 이전 / 다음 노드 — 구조 트리의 보이는 줄 차례(전위 · 접힌 줄 안은 건너뛴다), 남이 잡은 줄은 건너뛴다. 옮긴 노드를 구조 트리 · 캔버스에서 보이게 굴린다(하나 골랐을 때만) |
| ← / → | 자식 줄이 있는 펴진 줄의 ← 는 접기 · 접힌 줄의 → 는 펴기(고른 것은 그대로), 그 밖에는 부모 / 고를 수 있는 첫 자식(같이 굴린다 · 하나 골랐을 때만) |
| F2 | 별칭 바꾸기 — 고른 노드 줄 아래에 별칭 입력을 연다(하나 골랐고 남이 안 잡았을 때만 · 누른 채의 반복은 안 받는다). 고른 노드가 접힌 줄 안에 숨었으면 그 조상을 펴고 연다 — 고른 줄 자신의 접힘은 그대로 |
| ? | 단축키 목록 |

- 구조 트리 상자 안에서는 Alt+Shift+I(패턴 넣기) · Alt+Shift+P(프리셋)가 더 선다 — 그 트리의 고르개를 연다. 메뉴 트리 상자에 포커스가 있으면 그 상자의 단축키(메뉴 · 페이지)가 받고 이 표는 서지 않는다.
- **서지 않는 때** — 포커스가 글 입력 표면(입력 칸 · 글 상자 · 고르개 · `contenteditable` · 편집 역할 — 캔버스 문서 안의 것 포함)이다 · 한글 조합 중이다 · 모달이 열렸다 · 메뉴 트리 상자 안이다. 입력 칸의 Delete · Cmd+Z · Cmd+C 는 그 칸의 것이다. **캔버스 문서에서는** 포커스가 없거나(본문) 단추 · 링크일 때만 선다 — 그 밖의 포커스 받은 요소(테마가 그린 위젯 · 닫힌 shadow 안의 입력)는 입력 표면으로 본다. 클립보드도 같다.
- **키를 쓰는 위젯 안에서는 그 위젯이 쓰는 키만 이 표가 받지 않는다** — 메뉴 · 목록 · 고르기 무리(ARIA 역할)와 열린 행동 메뉴(그 단추 포함) · 구조 트리의 고르개(타입 · 패턴 · 프리셋)는 화살표 · Home · End · Escape · Enter, 탭은 탭 줄 축의 화살표(가로 줄이면 ← →) · Home · End, 손잡이 · 값 조절은 제 축의 화살표(세로줄 ← → · 가로줄 ↑ ↓) · Home · End(열린 줄 메뉴 안의 ← 가 선택을 옮기면 그 메뉴의 «삭제»가 옮겨 간 노드를 지운다). **행동 메뉴가 열려 있으면 Delete · Backspace 는 메뉴가 받는다** — 포커스가 그 메뉴(단추 포함) 안이면 노드를 지우지 않고(메뉴 트리 안의 메뉴에서는 삭제 확인도 안 선다) 메뉴는 열린 채다. 메뉴는 고른 노드에 대한 명령을 들고 열려 있어, 항목을 고르려다 친 Delete 가 노드를 지우고 메뉴째 닫으면 안 된다. 메뉴가 닫히면(Escape · 바깥 누름 · 항목 고르기) 다시 고른 노드를 지운다. 그 밖의 위젯 안에서 그 위젯이 안 쓰는 축의 화살표(탭의 ↑ ↓)와 Delete · Backspace, 어느 위젯 안에서든 Cmd 조합 · ? 는 입력 표면이 아니면 선다. 메뉴 · 고르개가 열려 있어도 포커스가 그 밖(캔버스 · 트리 줄 · 고르개를 연 `+` · 줌)이면 선다. 줄 · 캔버스에서 Escape · Delete 로 선택이 비면 «안에 추가» · «아래 추가» 고르개도 닫힌다(다음 선택 곁에 다시 서지 않는다).
- **누른 채의 키 반복** — Delete · Backspace · Cmd+D · Cmd+A 는 첫 누름 하나만 받는다(«넣기»와 같다 — 거른 반복도 브라우저 기본은 막는다). 되돌리기 · 다시 실행 · 붙여넣기 · 순서 · 계층 · 화살표 고르기 · Escape 는 반복을 받는다.
- **여럿을 고른 판에서 «하나 골랐을 때만»인 키**(순서 · 계층 · 화살표 고르기)는 아무것도 안 하고 하단 바에 그렇다고 말한다.
- 편집 단축키(되돌리기 · 다시 실행 · 삭제 · 복제 · 순서 · 계층 · 별칭 · 잘라내기 · 붙여넣기)는 편집 모드이고 editor 이상일 때만 선다. 삭제 · 잘라내기 · 복제 · 순서 · 계층 · 붙여넣기는 고른 노드(여럿이면 그 가운데 하나라도 — 붙여넣기는 기준 노드)를 남이 잡았으면 편집을 안 내고, 복제 · 잘라내기 · 붙여넣기는 하단 바가 이유를 말한다(삭제 · 순서 · 계층 키는 말없이 서지 않는다 — 그 이유는 고른 줄 `…` 의 꺼진 항목이 든다). 되돌리기 · 다시 실행은 선택이 아니라 낼 편집을 남의 잠금에 묻는다(머리 단추와 같다). 고르기 · 선택 이동 · Cmd+A · 도움말 · 복사는 뷰 모드 · viewer 도 선다.

**클립보드.** 키가 아니라 브라우저의 `copy` · `cut` · `paste` 이벤트로 받는다 — 그 이벤트 안의 `clipboardData` 는 권한 묻기 없이 읽고 쓴다(클립보드 권한을 안 준 Chrome 에서도 선다). 담는 것은 `text/plain` 봉투 하나다: `{ "wirebound": "nodes", "version": <문서 version>, "nodes": [ <서브트리> ] }`.

- **복사**는 고른 노드(들)의 서브트리를 문서 차례대로 담는다. 고른 것이 없거나 루트면 · 글자를 긁어 골랐으면 브라우저의 복사가 그대로다. **잘라내기**는 복사 + 삭제(삭제와 같은 판정 · 같은 편집 · 키보드 삭제처럼 선택이 빈다)이고, 지울 수 없으면 아무것도 담지 않는다.
- **붙이기** — 봉투가 아니거나 지금 문서에 실을 수 없는 노드(없는 타입 · 중복 id · 틀린 props)면 아무것도 안 하고 통지도 없다. 옛 `version` 은 문서 마이그레이션 체인으로 올린다. 노드 id 를 새로 짓고(붙이는 노드 안을 가리키던 상호작용 대상은 따라간다), 밖을 가리키던 동작은 붙이는 문서에 그 노드(페이지 대상이면 지금 프로젝트에 그 페이지)가 있으면 남기고 없으면 빼고 뺀 수를 하단 바에 말한다 — 동작이 다 빠진 상호작용은 상호작용째 뺀다. 번호 마커는 따라가지 않는다(코멘트가 따라가지 않는다).
- **자리** — 고른 노드 바로 뒤 형제로 봉투의 노드를 차례대로, 고른 것이 없거나 루트면 페이지 끝(여럿을 고른 판은 기준 노드 뒤). 넣은 노드 전부를 고른다 — 기준 노드는 마지막 것이라 이어 붙이면 그 뒤에 차례로 선다. 다른 프로젝트 · 다른 테마의 봉투도 그대로 붙는다. 페이지 대상이 든 봉투는 페이지 목록을 읽은 뒤 붙는다 — 자리는 누른 때 고른 노드다(읽는 사이 다른 노드를 골라도). 그 사이 페이지를 옮겼으면(돌아왔어도) 붙이지 않고 하단 바에 한 줄로 말한다. 같은 페이지를 다시 실은 것(재연결 · 복원 뒤 다시 불러오기 · 편집 실패 수습)은 옮긴 것이 아니라 붙는다 — 누른 때의 노드가 다시 실은 문서에 없으면 페이지 끝이다. 기다리는 사이 선 잃음 통지는 붙이기가 치우지도 덮지도 않는다(붙이지 못했다는 말도 그 뒤에 잇는다).
- 붙이기 · 복제 · 잘라내기는 **편집 하나**(되돌리기 하나)다. 묶음이 연산 200 개(편집 하나의 상한 — 넣기 · 지우기는 노드마다 연산 하나)를 넘거나 넣은 뒤 문서가 검증을 못 지나면 보내기 전에 막고 이유를 말한다.

**선택 — 고르는 법.** 고른 것은 **목록 + 기준 노드**다 — 기준 노드는 마지막으로 고른 것이고 Shift 범위 · 화살표 이동 · 붙일 자리 · 속성 패널 · 줄 행동의 기준이다. 하나 고른 판은 목록 길이 1 이다.

| 몸짓 | 동작 |
|---|---|
| 클릭(트리 · 캔버스) | 그것 하나 |
| Cmd+클릭(트리 · 캔버스) · Shift+클릭(캔버스) | 더하기 · 빼기 — 더한 것이 기준 노드 · 뺀 것이 기준 노드였으면 목록의 마지막이 기준 · 빈 곳의 수식 키 클릭은 고른 것을 지킨다 |
| Shift+클릭(트리) | 기준 노드부터 누른 줄까지 보이는 줄 차례로(접힌 줄 안은 안 든다) — 목록을 갈아 끼우고 누른 줄이 기준 노드 |
| Cmd+A | 기준 노드의 형제 모두(위 단축키 표) |
| 캔버스 사각형 | 캔버스 문서 · 캔버스 칸의 빈 여백에서 누르고 4px 넘게 움직이면 선다. 떼면 그려진 상자가 사각형 안에 **완전히** 든 노드 가운데 가장 바깥 것들(뿌리는 빼고)을 고른다 — Shift 를 누른 채 떼면 더한다. 4px 안에서 떼면 클릭이고, 아무것도 안 감싼 사각형(Shift 없이)도 누른 점에서 16px 안에서만 움직였으면 누른 자리의 클릭이다 — 노드 위에서 흔들린 손은 그 노드를 고르고 칸 여백의 빈 사각형은 선택을 안 바꾼다(빈 사각형으로 선택을 비우지 않는다). 그보다 멀리 끈 빈 사각형은 아무것도 안 한다 — 고르지도 비우지도 않는다. 칸 끝에 닿으면 끌어 놓기와 같은 끝 스크롤이고, 줌 · 칸 스크롤과 무관하게 문서 좌표로 판정한다. Escape 는 사각형만 걷는다. 무언가를 고른 사각형의 뗀 뒤 클릭은 선택을 안 바꾼다 |

- **목록이 지키는 것** — 문서에 있는 노드만(남의 편집 · 되돌리기가 지운 노드는 빠진다 — 기준 노드가 빠지면 목록의 마지막이 기준) · 조상과 자손이 함께 없다(새로 누른 것이 관련된 쪽을 대신하고, 범위 · 사각형 · 문서가 바뀐 뒤에는 가장 바깥 것이 남는다) · 루트는 혼자일 때만(루트를 Cmd+클릭하면 루트 하나) · 문서 차례 · 200 개까지(넘는 몸짓은 더 고르지 않고 하단 바에 «한 번에 고를 수 있는 노드는 200개까지입니다»). 남이 잡은 노드는 어느 몸짓으로도 안 든다.
- **보이는 것** — 캔버스는 고른 것마다 외곽선(기준 노드는 진한 선 · 나머지는 가는 끊은 선), 손잡이는 하나 골랐을 때만. 구조 트리는 고른 줄을 모두 강조한다(기준 노드는 채움 · 나머지는 테두리).
- **잠금** — 고른 서브트리마다 하나(§7.2). 남의 화면에는 고른 것마다 배지다.
- **여럿을 고른 판의 동작** — 삭제(Delete · 기준 노드 줄 `…` «삭제») · 복사 · 잘라내기 · 복제는 고른 것 전부(묶음 하나), 붙여넣기는 기준 노드 뒤, 위로 · 아래로 · 들여쓰기 · 내어쓰기 · 화살표 고르기는 하나 골랐을 때만이다. 고른 것 가운데 하나라도 남이 잡았으면 삭제가 꺼지고 그 항목이 «○○님이 편집 중인 노드가 있어 함께 지울 수 없습니다»를 이유로 든다.

**우측 — 탭 패널.** 모드에 따라 탭 구성이 바뀐다.

| 모드 | 탭 |
|---|---|
| 편집 모드 | **속성**(선택 노드) / 코멘트 / 상호작용 |
| 뷰 모드 | **페이지 설명** / 코멘트 / 상호작용 |

속성 탭은 컴포넌트 정의의 `editor` 명세에서 자동 생성된다(5.1 참조). 제목은 `타입 (별칭)`(별칭이 없으면 타입)이고, 그 아래 맨 위 칸은 어느 컴포넌트에나 서는 «별칭»이다(위 «별칭 고치기»). 제목 · 상호작용 탭의 노드 이름과 문장은 긴 한 낱말 별칭도 패널 안에서 접고, 대상 고르개는 패널 폭을 넘지 않는다. **여럿을 고른 판** — 같은 타입이면 기준 노드의 칸을 그리되 칸마다 모두 같은 값이면 그 값, 갈리면 «여러 값»(글 · 수는 빈 칸과 자리표 · 고르개는 «여러 값» 칸 · 켬/끔은 반쯤 켬 · 목록 칸은 고치지 않는다)이다. 바꾼 칸만 고른 것 전부에 묶음 하나로 쓰고 다른 칸은 노드마다 제 값 그대로다. 고른 것 가운데 하나라도 남이 잡았으면 칸이 다 꺼진다. **칸을 떠나지 않은 채 고른 것이 바뀌면**(일부 거절 · 같은 사람의 다른 탭이 고른 노드를 지우거나 옮김 · 타입을 바꿈 — 하나 고른 판도 같다) 친 글은 칸을 떠날 때의 커밋과 같은 길로 **앞 목록 가운데 아직 문서에 있고 그 타입 그대로이며 남이 안 쥔 노드**에 간다 — 새 목록에는 안 간다. 그런 노드가 없으면 버리고 하단 바에 «바뀐 선택 때문에 친 값을 쓰지 않았습니다» 한 줄. 칸에 친 채 브라우저의 뒤로 · 앞으로로 다른 페이지에 갔으면 어느 페이지에도 쓰지 않고 같은 한 줄이 다음 페이지 화면에 선다(친 페이지를 다시 열면 걷힌다). 세션이 끝나 화면이 내려가면 끝난 세션으로 아무것도 쓰지 않는다 — 내 로그아웃은 누름의 blur 가 그 전에 칸을 커밋해 로그아웃의 한 줄이 그 편집을 세고, 다른 탭의 로그아웃이면 이 탭은 버린 초안을 말하지 않는다(셸째 내려가 말할 자리가 없다). 칸에 친 채 에디터를 떠나 셸 밖 화면(프로젝트 목록)으로 가면 친 그 페이지에 쓴다. 타입이 섞였으면 «N개 고름» · «일괄 속성 편집은 같은 타입끼리만 됩니다» · «고른 노드 삭제» 단추다. 상호작용 탭의 규칙 편집과 코멘트 탭의 새 코멘트는 하나 골랐을 때만이다(페이지의 상호작용 · 코멘트 목록은 그대로). **페이지 설명은 뷰 모드의 «페이지 설명» 탭에서 읽고 고친다** — editor 이상에게는 편집기, viewer 에게는 읽기 전용이다. 편집 모드의 속성 탭에 두지 않는다: 설명은 페이지 메타라 에디터 스토어가 들지 않고(페이지 문서는 한 번만 읽는다), 그 탭이 따로 읽고 쓴다.

**두 사이드바의 폭.** 좌측(기본 264px · 최소 200px)과 우측 패널(기본 300px · 최소 300px)은 캔버스와의 사이에 있는 손잡이로 바꾼다 — 끌기 · 화살표 · Home/End · 두 번 눌러 기본값(우측 손잡이는 왼쪽으로 끌면 넓어진다). 폭은 사람마다 그 브라우저에 기억하고, 읽을 수 없는 값은 기본값으로 읽는다. **두 폭은 한 예산을 나눠 쓴다** — 어느 쪽의 최대 폭도 창 폭에서 상대 폭 · 손잡이와 여백(16px) · 캔버스 몫(320px)을 뺀 만큼이라, 어느 쪽을 넓혀도 캔버스 몫이 남는다. 창이 줄면 우측을 먼저 최소까지, 그다음 좌측을 조여 읽는다 — 기억한 값은 그대로 두고 창이 다시 넓어지면 돌아온다.

**셸 밖의 화면.** 로그인 · 프로젝트 목록 · 프로젝트 설정 · 계정 설정 · 테마 관리(인스턴스 관리자). 셸 밖 화면으로 가면 에디터 셸이 내려간다. 로그인 밖의 넷은 같은 머리를 쓴다 — 왼쪽은 로고(프로젝트 목록으로 — 목록 화면 자신에는 없다)와 화면 제목, 오른쪽 끝은 `…`(머리에 로그인한 사람의 이름, 항목 **계정 설정 · 테마 관리(인스턴스 관리자만) · 로그아웃**)다. 세션 전환 · 로그아웃 실패의 통지는 머리 아래에 선다.

- **프로젝트 목록** — 만들기와 줄마다 이름(에디터로) · 설명 · «설정»(모든 역할 — 프로젝트 설정으로). 이름 · 슬러그 · 설명은 목록에서 고치지 않고, **목록에서 지우지 않는다**(삭제는 프로젝트 설정의 위험 구역이다).
- **프로젝트 설정**(`/projects/:id/settings`) — 머리 아래 «에디터로 돌아가기». 절은 차례로 **일반**(이름 · 슬러그 · 설명) · **테마**(고르기 · 토큰 편집) · **멤버** · **위험 구역**이다. owner 가 아니면 일반 · 테마는 읽기로만 선다.
  - **멤버** — 모든 역할이 목록(이름 · 이메일 · 역할)을 본다. owner 에게만 초대(이메일 + 역할) · 역할 바꾸기 · 제외가 열린다. 서버의 거절(없는 계정 · 이미 멤버 · 마지막 owner 를 강등 · 제외)은 서버의 문장으로 그 자리에 말한다. 제외는 두 번 누르기 확인이다 — 묻던 단추는 그 자리에서 «취소»가 되고 확정은 줄 아래 한 줄에 선다(첫 누름 자리에 확정이 서지 않아, 따로 누른 두 번이 멤버를 빼지 않는다). 내가 나를 강등 · 제외하면 페이지가 프로젝트를 다시 읽는다. 남이 나를 바꾼 것은 다시 읽기 전까지 모르고 서버가 막는다 — 설정 페이지는 실시간 룸에 없다.
  - **위험 구역** — 맨 아래 · owner 에게만. **프로젝트 삭제**는 프로젝트 이름을 그대로 쳐야 확정이 열린다(두 쪽을 NFC 로 편 뒤 견준다 — 대소문자 · 공백은 그대로 가른다). 지우면 프로젝트 목록으로 간다.
- **계정 설정**(`/account`) — 절 셋: **내 정보**(이름 · 이메일 — 읽기만), **비밀번호 바꾸기**(지금 · 새 · 새 확인 — 새 둘이 다르면 요청을 안 낸다. 지금 비밀번호가 틀렸다는 답은 칸 곁의 문장이고 로그아웃이 아니다. 바꾸면 다른 기기의 로그인이 끊긴다고 말한다 — 「권한 모델」), **API 토큰**(내 토큰 전부 — 「권한 모델」). 옛 주소 `/tokens` 는 `/account` 로 넘긴다.
- **테마 관리**(`/admin/themes`) — 인스턴스 관리자의 화면(「권한 모델」).

**번호 마커** — 코멘트를 달면 다음 번호가 자동 부여된다. 수동 변경이 가능하고, "문서 순서대로 재번호" 버튼으로 일괄 정리한다. 번호는 노드 `id`에 묶여 있어 노드를 옮겨도 코멘트가 따라간다.

## 10. 권한 모델

| 역할 | 가능한 일 |
|---|---|
| **owner** | 전부 + 멤버 초대/역할 변경, 프로젝트 삭제, 레이아웃 편집, 스냅샷 복원, 프로젝트의 테마 바꾸기 · 토큰 고치기 |
| **editor** | 메뉴·페이지·컴포넌트·코멘트·상호작용 편집(하위째 지우는 메뉴 삭제 포함 — 안전망 스냅샷이 함께 남는다), 스냅샷 생성 (복원 불가) |
| **viewer** | 조회 전용 — 편집·코멘트 모두 불가. API 토큰 발급은 된다(토큰은 발급자의 권한을 넘지 않는다) |

- 사용자 인증은 **HttpOnly 세션 쿠키**다. 쿠키에는 랜덤 토큰이 실리고 서버는 그 sha256 해시만 `sessions`에 보관한다. WebSocket 핸드셰이크도 같은 쿠키를 쓰므로 REST와 WS의 인증 경로가 하나다. 세션 행을 지우면 열려 있는 WS 연결의 권한도 즉시 회수된다. 계정은 `migrate`가 환경변수로 만든다 — 가입 엔드포인트는 없다.
- 권한 체크는 REST와 WebSocket이 **동일한 가드 함수**를 쓴다.
- WS는 룸 참가 시 한 번, 각 patch 수신 시 한 번 확인한다(연결 도중 권한 회수 대응).
- 쓰기는 커밋 직전에 같은 트랜잭션 안에서 권한과 자격(세션·토큰)을 다시 본다. 잠금을 기다리는 동안 강등·제외되거나 로그아웃·토큰 폐기가 커밋되거나 세션의 수명이 다하면 그 쓰기는 가드와 같은 답(403·404·401)으로 되돌아간다. 예외는 자기 API 토큰의 폐기다 — 권한을 줄이는 쓰기라 되돌리지 않는다(되돌리면 멤버에서 빠진 뒤에도 남는 토큰이 다시 멤버가 될 때 되살아난다).
- 토큰 인증은 그 토큰의 마지막 사용 시각을 적는 갱신이 행을 찾아야 선다. 폐기와 겹친 요청은 그 갱신에서 폐기의 커밋을 기다렸다가, 토큰이 지워졌으면 401 로 끝난다 — 읽기에는 커밋 직전의 재확인이 없으므로 폐기된 토큰의 읽기를 막는 자리가 여기다.
- 세션 인증도 그 세션의 마지막 접속 시각을 적는 갱신이 행을 찾아야 선다. 로그아웃 · 세션 삭제가 요청이 세션을 읽은 뒤에 커밋되면 그 요청은 401 로 끝난다 — 지워진 세션으로 읽기가 답하지 않는다.
- 프로젝트 멤버가 아닌 사용자에게는 **404**를 준다(프로젝트 존재 자체를 숨긴다). 멤버지만 역할이 모자라면 **403**이다.
- **이메일 존재 여부는 로그인 경로에서만 감춘다.** 로그인 실패는 "없는 계정"과 "틀린 비밀번호"를 구분하지 않고 응답 시간도 맞춘다 — 미인증 상태에서 무제한 시도가 가능한 유일한 표면이기 때문이다. 반면 **멤버 초대의 404/409**는 이메일이 가입되어 있는지를 그대로 드러낸다. 이는 인지된 트레이드오프다: 초대는 계정이 있어야 도달할 수 있고, wirebound는 팀이 자체 호스팅하는 설계 도구이지 공개 가입 서비스가 아니다. "없는 계정/이미 멤버"라는 명확한 안내가 열거 방지보다 값지다. 인증된 사용자가 빈 프로젝트를 만들어 임의 이메일을 조회할 수 있다는 뜻이므로, 계정 발급이 통제되지 않는 배포에서는 이 결정을 재검토한다.
- **로그인은 시도 수를 제한한다**(비밀번호 바꾸기의 지금 비밀번호 시도도 같은 기록이다 — 아래). 키는 계정(정규화한 이메일)과 요청의 주소(IPv6 는 /64) 둘이고, 창(15분) 안에 계정 10 번 · 주소 30 번을 넘으면 비밀번호를 견주지 않고 429 + `Retry-After`로 답한다. 시도는 견주기 **전에** 세므로 동시에 몰린 요청도 한도 수만큼만 scrypt 를 돈다. 성공은 두 키에서 제 자리만 걷고 앞선 실패는 안 지운다 — 계정의 실패를 지우면 그 지움이 남의 다음 답에 보여 «그 사이 주인이 로그인했다 = 있는 계정»이 샌다. 막힌 동안은 옳은 비밀번호도 429 다 — 받아 주면 막힌 키에서 비밀번호를 맞혀 보는 창구가 남기 때문이고, 그 대가로 남이 틀린 비밀번호를 보내 내 새 로그인을 창 동안 막을 수 있다(이미 로그인한 세션 · 토큰은 그대로다). 막힌 키는 서버에 손이 닿는 사람이 명령으로 먼저 푼다 — 준 계정(또는 주소)의 기록만 걷는다. 명령은 api 가 연 유닉스 소켓(api 를 띄운 사용자만 들어가는 디렉터리)으로 보내고, api 의 TCP 포트에는 그 입구가 없다 — 인가가 파일 권한이다. 그래서 명령도 붙기 전에 api 와 같은 조건으로 그 자리(주인 · 권한 · 링크 아님)를 본다 — 공유 `/tmp` 에서는 남이 그 자리를 먼저 만들어 이메일을 받고 가짜 답을 낼 수 있다. 푼 것은 두드리는 쪽의 다음 답에 보인다(사람이 친 명령 한 번에 한 번 선다). 없는 계정도 같은 판정이다 — 키가 계정 행이 아니라 이메일 글자라 코드 · 문장 · 시간이 같다. 기록은 api 프로세스의 메모리에 있다(프로세스가 여럿이 되면 한도가 그 수만큼 곱해진다). 키 수에는 상한이 있고, 넘으면 창 안의 기록이 가장 적은 키부터 버린다 — 새 키로 표를 채워 막힌 계정의 기록을 씻지 못하게 하고, 주인의 성공이 버리는 차례를 바꾸지 않게 한다. 주소는 소켓 주소이고, 앞단 뒤에서는 그 앞단을 `TRUST_PROXY`로 믿게 해야 사람마다 갈린다.
- **비밀번호는 계정 설정에서 지금 비밀번호를 내고 바꾼다**(`POST /api/auth/password`). **세션으로만 부른다** — API 토큰으로 부르면 401 이다(프로젝트 밖 라우트라 토큰이 사람을 채우지 않는다 · 토큰은 프로젝트 범위이고 계정 자격을 바꾸지 않는다). 지금 비밀번호를 견주는 시도는 **로그인과 같은 한도 기록 · 같은 두 키**(그 사람의 이메일 · 요청 주소)에 센다 — 훔친 세션이 비밀번호를 맞혀 보는 창구가 되지 않게. 바꾸기의 실패는 로그인 한도에, 로그인의 실패는 바꾸기 한도에 함께 세이고, 막힌 동안은 옳은 지금 비밀번호도 429 다. 틀리면 로그인 실패와 같은 401 · 같은 문장에 이슈 `wrong-password` 를 싣고 세션은 그대로다(화면은 그 이슈로 «세션 끝»과 가른다). 새 비밀번호의 규칙 · 해시는 재설정 명령과 같다. **바꾸면 이 세션만 남기고 그 사람의 다른 세션을 모두 지운다** — 지운 세션의 WS 는 로그아웃과 같은 길로 곧바로 닫힌다. **API 토큰은 남는다** — 비밀번호와 따로 발급한 자격이고, 거두는 길은 계정 설정의 토큰 절이다. 쓰기는 커밋 직전에 세션을 다시 본다(위 쓰기 규칙 — 그 사이 로그아웃했으면 401 이고 아무것도 안 바뀐다).
- **로그인은 견준 해시가 아직 그 사람의 해시일 때만 세션을 낸다.** 로그인은 트랜잭션 밖에서 비밀번호를 견준 뒤 세션을 넣으므로, 그 사이 비밀번호 바꾸기 · 재설정이 커밋되면 옛 비밀번호로 낸 세션이 그 쓰기의 «다른 세션을 끝낸다» 뒤에 태어나 남는다. 그래서 세션 삽입이 사용자 행을 그 해시 조건으로 다시 읽고(그 행을 고치는 쓰기의 커밋을 기다리는 모드로 — 커밋 안 된 갱신을 지나 옛 값을 읽는 모드면 그 쓰기의 세션 삭제와 커밋 사이에 낀다), 0 행이면 틀린 비밀번호와 같은 401 이다. 한도에는 실패로 센다 — 낸 비밀번호가 세션을 낼 때 이미 그 사람의 것이 아니다.
- **노드 잠금은 역할 밖의 막음이다**(「소프트 잠금」). 남의 잠긴 서브트리를 건드리는 편집은 역할이 되어도 423 이다. 편집 묶음은 연산마다 잠긴 자리를 따라가며 견주고(앞 연산이 민 좌표 · `move` 의 뺀 뒤 좌표), 서버의 2차 방어와 화면이 편집을 미리 묻는 자리(끌어 놓기 · 컴포넌트 목록의 «넣기» 단추 · 되돌리기 · 다시 실행 · 붙이기 · 복제 · 여럿을 고른 판의 지우기 · 잘라내기 · 일괄 속성 · 고른 것이 바뀌어 내려가는 칸의 초안)가 같은 함수를 부른다. 그 판정을 거치지 않는 편집 입구는 코멘트 번호 · 복원 · 가져오기다.
- API 토큰은 **발급자의 권한을 상속**한다. editor가 만든 토큰으로는 스냅샷 복원이 안 된다. 토큰 스코프는 프로젝트 단위다.
- 토큰은 **세션으로만** 발급·조회·폐기한다(토큰으로 토큰을 다루지 않는다). 프로젝트 안에서는 자기가 만든 토큰만 보고 거두고, 계정 아래에서는 **자기 토큰 전부를 프로젝트를 가리지 않고** 보고 거둔다 — 멤버에서 빠진 프로젝트에 남은 토큰(다시 멤버가 되면 산다)까지다. 그 줄에는 프로젝트의 이름을 싣지 않는다(빠진 뒤의 이름을 숨긴다 — 비멤버에게 프로젝트를 숨기는 규칙과 같다). 계정 설정의 «API 토큰» 절이 그 길이다.

- **인스턴스 관리자**는 프로젝트 역할과 별개인 표시다(`users.is_instance_admin`). 하는 일은 테마 패키지 업로드 · 버전 숨김과 되살림 · 스타터 템플릿 내려받기이고 프로젝트 권한을 넓히지 않는다. **API 에는 관리자를 만들거나 바꾸는 라우트가 없다** — 주는 길은 서버의 명령(`admin grant|revoke`)과 시딩(`SEED_USER_ADMIN`)뿐이다. 올라온 테마 코드는 같은 origin 에서 신뢰 코드로 돌기 때문이다. 관리자 판정은 요청마다 DB 에서 읽고, 관리자 쓰기는 커밋 직전에 그 표시(사용자 행)와 자격(세션)을 **그 차례로** 다시 본다 — 비밀번호 바꾸기 · 재설정이 사용자 행 → 그 사람의 다른 세션 차례로 잡으므로, 반대 차례면 같은 사람의 다른 세션이 낸 관리자 쓰기와 서로를 기다리는 고리가 선다. 관리자 라우트 · 패키지 읽기 라우트는 `:projectId` 가 없어 세션으로만 부른다(토큰은 프로젝트 범위다).

레이아웃 편집을 owner로 제한한 이유는 레이아웃이 프로젝트 전체 페이지의 외형을 한 번에 바꾸는 전역 자원이기 때문이다. 테마 바꾸기를 owner 로 둔 것도 같은 까닭이다.

## 11. 프리셋 · 가져오기 / 내보내기

### 11.1 페이지 프리셋

내장 3종을 기본 제공한다.

- **검색 + 목록형** — `SearchForm` + `List` + 페이지네이션
- **상세 조회형** — `Card` + `KeyValue` + 액션 버튼 그룹
- **등록/수정 폼형** — `EntryForm` + 필드 묶음 + 저장/취소

"현재 페이지를 프리셋으로 저장"으로 프로젝트 프리셋을 추가할 수 있다. 프리셋 적용 시 노드 `id`를 새로 발급한다.

프리셋은 **테마 패턴(§6.2)과 다른 것**이다. 프리셋은 프로젝트가 소유한 페이지 통째 템플릿이고 테마를 바꿔도 그대로다. 패턴은 테마가 소유한 섹션 단위 레시피이고 테마를 바꾸면 다른 모양으로 재현된다. 페이지를 만들 때 프리셋으로 출발하고, 그 안에 패턴을 꽂아 채우는 것이 일반적인 흐름이다.

  "wireboundVersion": "1",
  "page": { "title": "회원 목록", "layoutRef": "admin-lnb", "description": "..." },
  "schema": { "version": 1, "root": { "id": "n_root", "type": "Page", "children": [ ... ] } },
  "comments": [ { "nodeId": "n_7f3a", "body": "검색 조건은 AND 결합" } ]
}
```

`schema`는 root 노드가 아니라 문서 봉투(`{ version, root }`)다 — 버전이 없으면 가져오기가 옛 버전 문서를 마이그레이션 없이 지금 버전으로 받는다(§13.1). 코멘트의 번호는 `schema` 안의 노드가 든다(§4.3) — `comments[].marker`는 받지 않고 400으로 거절한다. 두 자리에 적으면 둘이 어긋날 때 무엇을 믿을지 정할 규칙이 없다.

가져오기 시 노드 id를 재발급하되 코멘트의 `nodeId`와 상호작용의 `target`을 함께 리매핑한다. `wireboundVersion`은 스키마 마이그레이션 진입점이다.

에디터에서는 메뉴 트리의 줄 행동이 이 파일을 주고받는다(「설계서 화면 구조」) — 페이지 줄 `…` 의 «JSON 내보내기»는 **그 줄의** 페이지를(열린 페이지가 아니다) 서버에서 문서와 코멘트를 같은 순간에 읽어 파일로 받고, 메뉴 줄 `+` 의 «JSON 에서 가져오기…»는 그 메뉴 밑에 새 페이지를 만드는 대화 상자를 연다(덮지 않는다). 둘 다 편집 모드이고 editor 이상일 때만 있다 — 설계서를 읽는 사람의 내려받기는 «프로젝트 내보내기»(§11.3)다.

### 11.3 HTML 정적 번들

```
wirebound-export/
  index.html            첫 페이지의 사본
  pages/
    관리자-회원-목록.html
    관리자-회원-상세.html
  assets/
    shell.css           뷰어 셸의 CSS
    views.css           SDK 기본 뷰의 CSS
    runtime.js          내보내기 런타임 — react · 카탈로그 · renderer · theme-sdk 런타임
    theme/theme.js      프로젝트가 고정한 패키지의 파일 그대로 (theme.css · assets/** 도) — 테마가 있을 때
    tokens.css          프로젝트 토큰 값 → CSS 변수 — 테마가 있을 때
```

`exporter`는 셸(트리 네비게이션 · 설명 · 코멘트 · 상호작용 목록)만 서버에서 짓고, 목업은 페이지에 실린 문서 JSON 을 **내보내기 런타임이 브라우저에서** 그린다 — 캔버스와 같은 `renderer` · 같은 시트 차례(기본 뷰 → 테마 → 토큰) · 같은 상호작용 런타임 · 같은 마커 좌표 함수라 결과가 어긋날 수 없다. 모든 스크립트가 일반 스크립트라 `file://` 로 열어도 돈다. 테마 번들을 못 쓰면(등록 없음 · 다른 판 · 뷰가 던짐) 기본 뷰로 그리고 까닭을 상태 줄과 `<html data-wb-failed>` 에 적는다 — 등록을 못 쓴 판은 테마 시트도 걷는다(기본 뷰에 테마 CSS 가 얹힌 반쪽 화면을 내지 않는다). PPTX 의 화면은 Chromium 이 이 번들의 페이지를 셸 없이(`#wb-screen`) 열어 찍는다 — 설계는 `docs/superpowers/specs/2026-09-27-code-themes-design.md` 「내보내기와 PPTX」.

## 12. LLM 연계 (P9)

### 12.1 리포 바인딩

개발 리포 루트에 `.wirebound.json`을 둔다.

```jsonc
{
  "server": "https://wirebound.example.com",
  "projectId": "prj_a1b2"
}
```

이 파일은 "이 리포가 어느 설계 프로젝트에 대응하는가"만 선언한다. 리포에서 `wireb`나 MCP를 쓰면 프로젝트를 매번 지정할 필요가 없어진다.

설계서 페이지와 소스 파일을 잇는 매핑은 두지 않는다. 대상 프로젝트의 기술 스택과 디렉터리 구조가 제각각이라 wirebound가 규칙을 가정할 수 없기 때문이다. 에이전트는 페이지 경로(`관리자/회원/목록`)로 설계서를 조회하고, 그 리포에서 어느 파일이 대응하는지는 리포의 컨벤션에 따라 스스로 판단한다.

### 12.2 MCP 도구

| 도구 | 용도 |
|---|---|
| `list_pages` | 프로젝트 메뉴/페이지 트리 조회 |
| `get_page` | 페이지 스키마 + 코멘트 + 상호작용 문장 조회 |
| `patch_page` | 사람 편집과 동일 경로의 수정 (baseSeq 필수) |
| `add_comment` | 구현 중 발견한 이슈를 설계서에 기록 |
| `validate` | lint 규칙 실행 |

`get_page` 의 노드 개요(`nodes[]`)는 노드마다 이름(`name` — 문장이 부르는 이름이라 별칭이 있으면 별칭) · 별칭(`alias` — 있을 때만) · 구조 트리 줄과 같은 글(`rowLabel` — `타입 (별칭) 요약`)을 싣는다.

### 12.3 CLI

```
wireb login                        토큰 발급 및 저장
wireb init                         .wirebound.json 생성
wireb pull                         프로젝트 스냅샷을 로컬 JSON으로 (읽기 전용)
wireb page get <경로> [--json]     페이지 조회
wireb lint [경로]                  규칙 검증
wireb export --format html -o dir  정적 번들 생성
```

### 12.4 lint 규칙

"LLM을 통한 검증"의 실체다. 규칙은 `schema` 패키지에 두어 웹·CLI·MCP가 공유한다.

**설계서 규칙**
- 코멘트가 없는 주요 컴포넌트 (`List`, `EntryForm`, `SearchForm`)
- 어느 메뉴에도 연결되지 않은 페이지
- 대상 노드가 삭제된 상호작용 규칙
- `navigate`/`openModal` 대상 페이지가 존재하지 않음
- 중복된 코멘트 번호
- `EntryForm` 안에 `Field`가 하나도 없는 등 구조적 공백
- 프로젝트 명명 규칙 위반 (설정 가능)

**테마 규칙** — 테마 자체의 결함(manifest · 토큰 · 뷰)은 lint 가 아니라 테마 빌드와 업로드 검증이 막는다(`docs/superpowers/specs/2026-09-27-code-themes-design.md` 「업로드 검증」). lint 는 문서가 프로젝트가 고른 테마와 어긋나는 것을 본다 — `wireb lint` · MCP `validate` 가 `GET /api/projects/:projectId/theme` 으로 그 manifest 를 받고, 못 받으면 이 규칙은 돌지 않고 그렇다고 말한다(`theme-unavailable`).
- 현재 테마에 없는 `variant` — 프로젝트가 고른 테마의 `components` 가 선언한 컴포넌트에서만 본다

### 12.5 스킬

에이전트에게 다음 흐름을 가르친다.

1. 화면 구현 요청을 받으면 `list_pages`로 대상 페이지를 찾는다.
2. `get_page`로 스키마·코멘트·상호작용을 읽는다.
3. 구현한다.
4. 설계와 어긋나거나 결정이 필요한 부분을 `add_comment`로 회신한다.
5. `validate`로 설계서 자체의 결함을 보고한다.

## 13. 에러 처리

| 상황 | 응답 | 클라이언트 동작 |
|---|---|---|
| 스키마 검증 실패 | 422 | 낙관적 적용 롤백 후 서버 상태로 재동기화 |
| 잠금 충돌 | 423 `locked` + 점유자 정보 | UI 사전 차단이 1차 방어, 발생 시 안내 — 자동 재시도하지 않는다 |
| baseSeq 불일치 | 409 | 페이지 재조회 후 재시도 |
| 권한 없음 | 403 | WS는 룸에서 강제 퇴장, 읽기 전용 전환 |
| undo 대상 소실 | 클라 사전 검사에 걸리면 에러 아님, 서버까지 오면 409 | 스택에서 제거하고 안내 |
| WS 연결 끊김 | — | 지수 백오프 재연결, 다시 붙으면 연 페이지를 재조회한다 — `head_seq`와 문서가 **둘 다** 같을 때만 가진 판을 둔다(§4.5) |

`baseSeq` 불일치는 **서버가 리베이스하지 않고** 곧바로 409로 돌려준다 — 서버가
리베이스하려면 무엇을 리베이스할 수 있는지(겹치지 않는 경로인지, 같은 서브트리인지)가
먼저 정해져야 한다. 클라이언트 쪽 리베이스(§7.1의 "타인 ops 수신 → 자기 pending 위에
리베이스")는 그와 별개로 클라이언트가 한다.

`undo 대상 소실` 행이 두 갈래인 이유는 §7.3의 undo가 클라이언트 사전 검사(경로 존재
확인)를 전제하기 때문이다. 그 검사를 통과해 서버까지 도달한 요청은 파이프라인에서
`patch-failed`가 되어 409로 나간다(`편집을 적용할 수 없습니다: …`). 어느 쪽이든
클라이언트의 대응은 같다 — 그 항목만 스택에서 버리고 나머지는 그대로 쓴다.

### 13.1 스키마 마이그레이션

컴포넌트 props는 반드시 바뀐다. `schema` 패키지에 버전별 마이그레이션 함수 체인을 두고, 페이지를 읽을 때 최신 버전으로 올려 읽는다. 가져오기와 스냅샷 복원도 같은 경로를 탄다.

```ts
migrations = [
  { from: 1, to: 2, migrate: (doc) => { /* List.rows 기본값 도입 */ } },
]
```

`pages.schema_version`에 현재 버전을 기록하고, 마이그레이션이 실행되면 다음 저장 시 갱신한다.

**열린 항목 — 미지원 버전 문서의 복구 경로가 없다(결정 필요).**
저장된 문서의 `version`이 이 프로세스가 아는 `CURRENT_DOCUMENT_VERSION`보다 크면
`migrateDocument`가 던지고, 그러면 `GET .../pages/:pageId` · `PATCH .../ops` ·
`PUT .../schema` **세 경로가 전부 400**이 되어 그 페이지를 API로 되살릴 수 없다.
일어나는 경우는 배포 롤백이나 여러 버전이 같은 DB를 공유하는 롤링 배포다.

`PUT .../schema` 전체 교체는 탈출구가 아니다 — PUT도 편집 파이프라인을 타고, 그
파이프라인이 **저장된** 문서를 먼저 `migrateDocument`에 태우기 때문에 같은 이유로
막힌다. 이것은 모든 스키마 변경이 revision을 남긴다(§3.2 «모든 편집은 같은 파이프라인을
통과한다»)의 직접적인 대가이고, 파이프라인을 우회하는 두 번째 쓰기 경로를 두면 그 원칙이
다시 뚫리므로 두지 않는다.

스냅샷 복원도 탈출구가 아니다 — 복원도 같은 파이프라인을 타고 저장된 문서를 읽어야 하므로
미지원 버전 문서를 되살리지 못한다. 대신 복원은 쓰기 전에 400으로 끊으며 어느 페이지가
어떤 버전이라 막혔는지 말한다(`apps/api/README.md` 「미지원 버전 탈출구」 절).
되살릴지, 되살린다면 어떤 형태인지는 별도 결정이다. 그 전까지는 400 응답이 최소한 원인을
말해 주는 상태로 둔다.

## 14. 테스트 전략

| 대상 | 방식 |
|---|---|
| `schema` | **patch/inverse 왕복 속성 테스트** — 임의 편집 시퀀스를 적용한 뒤 역순으로 역적용하면 원본과 정확히 일치해야 한다. 이력 시스템 전체의 안전망 |
| `schema` | zod 검증 경계값, 마이그레이션 체인 |
| `renderer` | 뷰 경로(테마 뷰 · 기본 뷰 · 뷰 예외의 노드 단위 폴백), `data-wb-*` 속성 계약 검증 |
| `themes` | 패턴 규격 · 전개(슬롯 · id 재발급), 스냅샷 payload 규격 |
| `theme-sdk` | 기본 뷰가 카탈로그 전부를 덮는지, 뷰 계약(`Root` · `Focus`), 공유 런타임 등록 · 받기 |
| `themes` | manifest 거부 표(참조 · 순환 · 카탈로그 · variant · 패턴), `.wbtheme` 안전성(`..` · 절대 경로 · 링크 · 크기 · 항목 수 · 허용 목록) |
| `theme-kit` | 빌드한 `theme.js` 에 SDK · react 가 묶이지 않음, dev 갤러리의 실브라우저 판(`build-test`), 템플릿 zip 을 풀어 빌드 · 타입검사(저장소 밖 설치는 `WB_TEMPLATE_INSTALL=1`) |
| `api` | 동시편집 통합 테스트 — 두 클라이언트 동시 patch, 잠금 경합, 편집 중 권한 회수, WS 재연결 후 델타 복구 |
| `api` | 권한 매트릭스 (역할 × 엔드포인트) |
| `exporter` | 내보낸 HTML의 DOM과 웹 렌더 DOM의 동등성 검증 |
| e2e | 페이지 생성 → 편집 → 코멘트 → 스냅샷 → 복원 한 줄기 (Playwright) |

patch/inverse 왕복 테스트가 가장 중요하다. undo, 스냅샷 복원, MCP 편집이 전부 이 성질에 의존한다.

## 15. 로드맵

| 단계 | 내용 | 완료 시 가능한 것 |
|---|---|---|
| **P0** | 모노레포 + `schema`(노드 타입·zod·patch 유틸) + `renderer` 골격(구조 1종씩) | 스키마 JSON을 넣으면 화면이 그려진다 |
| **P1** | 인증, 프로젝트, 멤버/권한, 메뉴 트리, 페이지 CRUD | 프로젝트와 메뉴 구조를 만든다 |
| **P2a** | 편집 파이프라인 — revision 로그, JSON Patch 엔드포인트, 개인 undo/redo의 서버 쪽 | 편집 이력이 쌓이고 되돌릴 수 있다 |
| **P2b** | 에디터 3분할 셸 — 메뉴·구조 트리, 캔버스, 속성 패널, 낙관적 편집 | 혼자서 설계서를 작성할 수 있다 |
| **P3** | WebSocket 실시간 동기화 + 소프트 잠금 | 여럿이 동시에 작업한다 |
| **P4** | 테마 — 코드 테마 차수 A1 ~ A6(`docs/superpowers/specs/2026-09-27-code-themes-design.md` 「진행 단계」): 뷰 SDK · iframe 캔버스(A1), `.wbtheme` · 작성자 도구(A2), 업로드 · 버전 · 프로젝트 바인딩(A3), 테마 선택 · 토큰 편집 화면(A4), 내보내기(A5), 시스템 테마 5종(A6) | 관리자 외 사이트 형태를 테마로 그리고, 테마를 코드로 짜서 올린다 |
| **P5** | 코멘트/번호 마커 + 상호작용 규칙 + 뷰 모드 | 설계서로서 완성된다 |
| **P6** | 스냅샷 태그/복원 | 버전을 관리한다 |
| **P7** | 페이지 프리셋 + 테마 패턴 삽입 + JSON 가져오기/내보내기 | 반복 작업이 빨라진다 |
| **P8** | HTML 정적 번들 내보내기 | **MVP 릴리스** — 설계서를 배포한다 |
| **P9** | `wireb` CLI + MCP + 스킬 + `.wirebound.json` + lint | 에이전트가 설계서를 읽고 구현한다 |
| **P10** | PPTX 내보내기 (렌더 이미지 방식) | 보고용 산출물을 만든다 |

각 단계는 그 자체로 동작 가능한 상태를 만들고 끝낸다. P2b까지 가면 단독 사용이 가능하고, P8이 1차 릴리스다.

P2를 둘로 쪼갠 이유: P2a는 서버(편집 파이프라인과 이력)이고 P2b는
그 위에 얹히는 에디터 UI다. 테스트 방식이 서로 다르고(vitest + Postgres vs.
컴포넌트 테스트), P2a만으로도 REST로 편집·되돌리기가 동작하는 상태가 된다.

## 16. 열린 질문 (구현 중 결정)

- **패턴 슬롯 타입 체계** — `text` · `media` · `action` 정도로 시작하되, 실제 패턴을 만들며 필요한 타입을 확정한다.
- **스냅샷 보관 정책** — 개수 제한 또는 보관 기간. 실사용 데이터가 쌓인 뒤 결정한다.
- **revision 로그 압축** — 페이지당 revision이 수만 건이 되면 오래된 구간을 주기적으로 압축한다. 성능 문제가 실제로 관측되면 착수한다.
