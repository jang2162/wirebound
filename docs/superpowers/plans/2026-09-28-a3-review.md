## 3. 바인딩 저장 `PUT /api/projects/:projectId/theme`

### 3a. 두 owner 의 동시 저장 — 재현 안 됨

A 의 저장(rev 0 · `#aaaaaa`)을 `update "projects"` 앞에 붙잡고 B 의 저장(rev 0 · `#bbbbbb`)을 커밋시킨 뒤 놓았다: **B 200 · A 409**(`current.tokens`
`#bbbbbb`), 행 `#bbbbbb · rev 1`, `theme-changed` 프레임 1 개(`#bbbbbb`).

### 3b. 숨긴 판을 새로 고르는 경주 — 결함 · 낮음

- **입력**: 프로젝트를 `hidden-x@1.0.0` 에 고정(rev 1)한 뒤 그 판을 숨김. B 가 `hidden-x@1.0.0 · rev 2` 를 보내고 `update "projects"` 에 붙잡힘(바탕 =
  `hidden-x` · rev 1 을 이미 읽음 → «고정한 판» 으로 숨김 판정을 지남). 그 사이 A 가 `other-y@1.0.0 · rev 1` → 200 · rev 2. B 를 놓음.
- **답 · 결과**: **B 200**, 행 `hidden-x@1.0.0 · rev 3`. 대조 — 같은 두 저장을 차례로 보내면 B 는 422 `hidden-version`.
- **원인**: 숨김 판정의 바탕(`current`)은 트랜잭션 밖에서 읽고, 갱신은 요청이 실은 `rev` 로만 거른다 — 요청의 `rev` 가 읽은 바탕의 `rev` 와
  같다는 것을 아무도 안 본다. 보고서의 «그 사이의 저장은 갱신이 걸러 409» 는 요청이 바탕과 같은 `rev` 를 실을 때만 참이다.
- **닿는 사람**: 그 프로젝트의 owner 가 바탕보다 새 `rev` 를 실어야 한다 — 옮긴 저장의 답을 받기 전에 `rev + 1` 을 짐작하는 클라이언트(연달아 보내는
  저장 둘)나 손으로 만든 요청. 결과는 «한때 고정했던 숨긴 판» 으로 돌아가는 것뿐이다(복원도 숨긴 판을 되돌린다).
- **빨강**: `project-theme-review.test.ts` «바탕을 읽은 뒤 · 갱신 앞에서 남이 다른 판으로 옮기면 …» → `expected 200 not to be 200`.
  판 카나리아는 «B 가 붙잡혔거나 먼저 끝났다» 와 A 의 200. 고칠 방향 두 가지를 심어 둘 다 초록을 봤다(백업 · 바이트 비교 복원): 핸들러에서
  `current.rev !== body.rev` 면 409 · 트랜잭션 안에서 `FOR UPDATE` 로 다시 읽고 숨김을 판정. 첫 판의 케이스는 앞 고침에서 B 가 갱신 앞에서 끝나
  붙잡을 질의가 없어 **시간 초과로 죽었다**(구분력이 아니다) — «먼저 끝남» 도 판으로 받고, 안 쏜 붙잡기를 거두게 고쳤다.
- **고칠 방향**: 요청의 `rev` 가 읽은 바탕의 `rev` 와 다르면 409, 또는 숨김 판정을 갱신과 같은 트랜잭션의 잠근 읽기로 옮긴다.
- **한계**: 숨김(관리자)과 겹친 저장은 보고서 이월대로 잰 것이 아니다 — 이번 판은 «바인딩이 옮겨진» 겹침이다.

### 3c. 토큰 값이 스냅샷 · 복원을 막는다 — 결함 · 중간

- **입력**: `font.body`(font) 를 선언한 테마에 `"a\ud800b"`(짝 없는 상위 서로게이트) · `"a\udc00b"`(하위) · `"a\u0000b"`(NUL) 를 PUT.
- **답**: 셋 다 **200** — `FONT_LIST` 의 따옴표 문자열(`[^"\\\r\n<]`, `u` 플래그)이 짝 없는 서로게이트와 NUL 을 받는다. `projects.theme_tokens` 는
  `json` 이라 그대로 저장된다.
- **실제 결과**(그 뒤 같은 프로젝트에서):

  | 토큰 | `POST …/snapshots` | 앞서 찍은 스냅샷 복원 | `GET …/snapshot`(CLI) | `GET …/export?format=html` | `GET …/theme` |
  | --- | --- | --- | --- | --- | --- |
  | 짝 없는 서로게이트 | **500** `internal` | **500** | 200 | 200 | 200 |
  | NUL | **400** «스냅샷에 NUL 문자(U+0000)를 포함할 수 없습니다» | **500** | 200 | 200 | 200 |

  캡처가 바인딩을 `snapshots.payload`(`jsonb`)에 넣다 죽는다 — `jsonb` 는 둘 다 거절한다. 복원은 안전망 캡처를 먼저 하므로 **그 프로젝트는 어느
  스냅샷으로도 돌아갈 수 없고**, editor 가 찍는 스냅샷도 같은 캡처라 막힌다(owner 로만 쟀다). 빠져나오는 길은 owner 가 그 토큰을 다시 저장하는 것뿐이다(400 문장은 테마를 말하지 않는다).
- **빨강**: `project-theme-review.test.ts` «font 값에 짝 없는 서로게이트 …» → `'put 200 · snapshot 500 · restore 500'`, «… NUL …» →
  `'put 200 · snapshot 400 · restore 500'`. 단언은 «PUT 이 422 로 거절하거나, 받았으면 스냅샷 201 · 복원 200» — 고칠 자리를 고르지 않는다.
  PUT 에 `isWellFormed()` · NUL 거절을 심으면 둘 다 초록(복원함).
- **원인**: 토큰 값 문법(`packages/themes` 의 `FONT_FAMILY`)이 C0 제어 글자 · 짝 없는 서로게이트를 막지 않고, 저장 칸(`json`)과 스냅샷 칸(`jsonb`)의
  받는 글자가 다르다(0006 이 이미 적은 `json` · `jsonb` 의 NUL 차이).
- **고칠 방향**: `FONT_FAMILY` 의 따옴표 문자열에서 C0 · 짝 없는 서로게이트를 빼(manifest 기본값 · kit 까지 한 자리) PUT 이 422 를 낸다.
- **한계**: `font` 만 쟀다 — 다른 다섯 타입은 문법이 ASCII 꼴로 닫혀 있어(`LENGTH` · `HEX` · `COLOR_FN`) 재지 않았다. manifest 기본값에 같은 글자를 넣은
  업로드는 재지 않았다(기본값은 바인딩에 안 실리므로 캡처는 안 막힌다고 읽었다 — 값으로는 안 봤다).

### 3d. 한도 · «기본값과 같은 값은 뺀다» · 판 바꾸기 뒤 옛 키 — 재현 안 됨

| 입력 | 답 |
| --- | --- |
| `font` 에 이모지 99 개를 따옴표로(UTF-16 200) | 200 |
| 이모지 100 개(202) | 422 `token-too-long`(202) |
| `a` + 결합 문자 196 개(200 단위) | 200 — 한도는 UTF-16 단위라 결합 문자로 늘지 않는다 |
| `number` 에 `1e308` · `-0` | 200(`1e+308` · `0`) — 유한한 수 |
| `color` 에 수 5 · `number` 에 `"4"` | 422 |
| 기본값과 같은 `4` · `#e11d48` | 200 · 저장 `{}` |
| 대소문자만 다른 `#E11D48` | 200 · 저장 `{"color.accent":"#E11D48"}` — 글자 비교라 안 빠진다(설계대로) |
| 없는 키 5 만 개(요청 639 KB) | 422 · **응답 4,327,856 B** · 77ms — 이슈를 키마다 싣는다 |

키 수는 manifest 의 항목 수로 묶이고(없는 키는 `unknown-token`) 값 하나가 200 단위라, 16 KB 전체 한도를 넘는 저장이 받아지는 입력은 못 찾았다.
판 바꾸기 뒤 옛 키는 새 manifest 에 없으면 `unknown-token` 422 다. 5 만 키의 6.8 배 응답은 owner 전용 · 본문 1 MiB 상한이 묶어 **관찰**로만 적는다.

## 4. 스냅샷 판 3 복원

### 4a. `missing-theme` 409 — 재현 안 됨

`gone@1.0.0` 에 고정하고 메뉴 하나 · 스냅샷(판 3) → 메뉴 하나 더 · `system-admin` 으로 옮김 · `gone` 행을 DB 에서 지움(다른 인스턴스 · DB 복구의 모양) →
방에 WS 를 붙이고 복원.

- 답: **409** «스냅샷의 테마 패키지가 이 서버에 없습니다: gone@1.0.0 — 복원하지 않았습니다».
- 앞뒤 행: 메뉴 2 · 페이지 0 · 스냅샷 1(안전망 없음) · 리비전 0 · `system-admin@0.1.0 rev2` · `projects.updated_at` 같음 — 복원이 지웠을 메뉴 B 가 남았다.
- 프레임(500ms 기다림): `joined` · `presence` · `locks` — `restored` · `theme-changed` 없음.

판정은 코드상 첫 쓰기(안전망 `insertSnapshot`) 앞이고 값도 그렇다.

### 4b. 규격 밖 `theme` 를 복원이 쓴다 — 결함 · 낮음

payload 는 서버만 짓는다(스냅샷을 받는 라우트가 없다) — 그래서 판을 DB 의 payload 를 손으로 고쳐 세웠다. 복원은 payload 를 규격(`SnapshotPayloadSchema`)으로
다시 읽지 않는다(앞 차수부터의 길 — 페이지 문서만 편집 파이프라인이 본다).

| 손댄 payload | 복원 | 바인딩 | 그 바인딩을 GET 해 그대로 PUT |
| --- | --- | --- | --- |
| 판 2 + `theme`(`font.body: serif`) | 200 | `fx@1.0.0 · serif` — 판 2 인데 바인딩을 썼다 | 200 |
| 판 3 + 없는 키 `no.such` | 200 | `{"no.such":"x"}` | 422 `unknown-token` |
| 판 3 + 5000 글자 값 | 200 | 5000 글자 | 422 `token-too-long` |
| 판 3 + 문법 밖 `a;}body{display:none` | 200 | 그 값 | 422 `token-default-type` |
| 판 3 + `theme` 안에 선언 안 한 키 | 200 | `{}` | 200 |

- **빨강**: `project-theme-review.test.ts` «판 3 payload 의 theme.tokens 에 manifest 에 없는 키가 있으면 바인딩에 넣지 않는다» →
  `expected [ 'no.such' ] to not include 'no.such'`(대조: 같은 토큰의 PUT 은 422). 복원이 manifest 에 없는 키를 걸러 쓰게 심으면 초록.
- **원인**: `set-theme` 단계가 `step.theme.tokens` 를 manifest 로 안 보고 쓰고, 계획이 `payloadVersion` 을 안 보고 `theme` 가 있으면 단계를 넣는다.
- **고칠 방향**: 복원이 PUT 과 같은 토큰 정리(`cleanTokens`)를 첫 쓰기 앞에서 돌려 거절하거나 걸러 쓰고, `set-theme` 은 판 3 이상에서만 넣는다.
- **한계**: API 로 닿는 길은 없다 — 무게는 «다른 인스턴스 · 옛 판 · 손댄 DB» 에서 온 payload 를 믿는 폭이다. 문법 밖 값이 캔버스 CSS 에 실리는지는
  재지 않았다(렌더러가 `tokensCss` 이슈로 거르는지 안 봤다).

## 5. 기동 시딩(`buildApp`)

### 5a. 같은 DB 에 기동 둘 — 재현 안 됨

테스트 DB 의 패키지 행을 비우고, A 를 프록시 뒤 풀로 세워 채우기(`update "projects"`)에 붙잡았다 — A 는 `system-admin@0.1.0` 을 넣고 커밋 전이다. B 를
직접 풀로 세웠다: `pg_stat_activity` 에서 **B 의 `insert into "theme_packages"` 가 잠금 대기 1**. A 를 놓자 **둘 다 떴고** 행 1 개. B 는 중복 키 →
세이브포인트 되돌림 → 다시 찾아 sha256 견줌 → `kept` 로 넘어간다(`withTransaction` 이 트랜잭션 안에서 세이브포인트를 쓴다). **한계**: 두 프로세스가 아니라
한 프로세스의 풀 둘로 쟀다 — 겹침의 판은 DB 쪽이라 같다고 읽었다.

### 5b. 판을 안 올리고 바꾼 판 — 설계대로 · 그러나 빠져나오는 길이 빈 판 둘

같은 `system-admin@0.1.0` 인데 바이트가 다른 산출물(`theme.css` 끝에 주석) → «이미 올린 버전의 내용이 바뀌었습니다: system-admin@0.1.0 — 판을
올리십시오(<파일> 의 sha256 c801c666… · DB 5ff20aed…)». README 「시스템 테마 — 기동 때 넣는다」 의 표가 «그 테마의 `version` 을 올린다» 로 받는다 — **설계대로.**

**5b′ — 결함 · 낮음.** kit 의 `buildTheme` 은 `dist` 를 비우지 않는다(`mkdirSync` 뒤 `<id>-<version>.wbtheme` 하나만 쓴다 · `system-themes/admin` 의
`build` 는 `wb-theme build` 하나). 개발자가 소스를 고쳐 빌드하면 `system-admin-0.1.0.wbtheme` 가 **새 바이트로 덮이고**, 기동이 멈춰 판을 0.1.1 로
올려 다시 빌드해도 그 옛 이름 파일이 남는다. 그 `dist`(0.1.0 = 새 바이트 · 0.1.1)로 시딩 → **같은 «판을 올리십시오» 로 계속 멈춘다.** 옛 파일이 원래
바이트면(대조) `inserted 0.1.1 · kept 0.1.0` 으로 뜬다. 빠져나오는 길(그 옛 산출물을 지운다)이 문장 · README 어디에도 없다. 빨강은 세우지 않았다 —
고칠 자리가 «빌드가 옛 판 산출물을 치운다» 와 «문장이 지울 파일을 말한다» 로 갈리고, api 판에서 kit 이 남기는 `dist` 를 흉내 내면 kit 을 고친 뒤에도
빨강이 남는다. **고칠 방향**: 멈추는 문장에 «같은 id 의 더 높은 판 산출물이 있으면 이 파일은 옛 빌드가 덮은 것 — 지운다» 를 싣거나, kit 이 같은 id 의 옛
산출물을 치운다.

**5b″ — 결함(탐지 공백) · 중간.** system-admin 소스(`src/theme.css`)에 규칙 한 줄을 더하고(백업 · 바이트 비교 복원) `system-themes.test.ts` ·
`project-theme.test.ts` · `system-themes/admin/test` 를 돌렸다: **3 파일 43 통과** · 산출물 sha256 `5ff20aed…` → `ce4f516b…`. global-setup 이 테스트 DB 를
매번 새로 올리므로 «판을 안 올린 변경» 을 보는 케이스가 없다 — 그 빌드를 배포하면 이미 `5ff20aed…` 를 시딩한 DB(운영 · 개발)는 **기동이 멈춘다.**
소스를 안 고쳐도 번들러 등 빌드 의존이 바뀌어 출력이 달라지면 같다(재지 않았다 — 같은 입력이면 같은 바이트라는 보고서의 실측은 한 기계 · 한 lockfile 판이다).
복원 뒤 재빌드한 sha256 은 `5ff20aed…` 로 돌아왔다. 빨강은 세우지 않았다 — 견줄 «판마다 적어 둔 sha256» 이 저장소에 없고, 그것을 두는 것이 고침이다.
**고칠 방향**: 시스템 테마의 `id@version → sha256` 표를 저장소에 커밋하고 테스트가 산출물과 견준다(바뀌면 판을 올리거나 표를 고치라고 말한다).

### 5c. 섞인 산출물

| `SYSTEM_THEMES_DIR` 안 | 결과 |
| --- | --- |
| `admin/dist/foo-1.0.0.wbtheme`(id `foo`) | 멈춤 «시스템 테마의 id 는 `system-` 로 시작해야 합니다: foo@0.1.0(<경로>)» — 설계대로 |
| `admin/dist/notes.txt` | 무시 |
| 깨진 `.wbtheme` | 멈춤 «… 검증을 못 지났습니다(<경로>) — zip 파일이 아닙니다» — 설계대로 |
| `admin/dist/system-admin-9.9.9.wbtheme`(옛 실험 산출물) | **`inserted 9.9.9`, 그 뒤 새 프로젝트가 `system-admin@9.9.9` 에 고정** — 5c′ 결함 · 낮음(5b′ 과 같은 뿌리) |

5c′ 은 개발 기계에서만 선다(운영 이미지는 깨끗한 체크아웃을 빌드한다). 빨강은 5b′ 과 같은 까닭으로 세우지 않았다.

## 6. 마이그레이션 0019 `down`

일회용 DB `wb_a3_rv`(5443)를 올리고 앱으로 채웠다: 패키지 2(`system-admin` · 올린 `rvtheme`) · 관리자 1 · 바인딩 찬 프로젝트 1(토큰 있음) · 판 3 스냅샷 1.
그 뒤 실제 명령 `pnpm --filter @wirebound/api migrate:down`(그 DB 로 `DATABASE_URL`):

| 걸음 | 결과 |
| --- | --- |
| down(0019) | 종료 0 «Down 0019-theme-packages» — `projects.theme_*` 칸 · `theme_packages` 표가 사라짐 |
| 그때 스냅샷 | **`payloadVersion` 3 · `theme` 키 있음** |
| down(0018) | 종료 0 — 스냅샷 **여전히 판 3**(0018 `down` 은 판 2 만 판 1 로 고친다) · `themes` 키 없음 |
| up(latest) | 종료 0 — 판 3 그대로 · 바인딩 null(기동 채우기 전) |

- **판정**: `down` 은 돈다. 그러나 판 3 payload 를 판 2 로 되돌리지 않는다 — **결함 · 낮음.** 되돌린 배포(main)는 판 3 을 복원에서
  `payload-version` 400 «이 서버가 읽을 수 없는 스냅샷 형식입니다 (형식 3, 지원 2)» 로 거절하고(main 의 `services/restore.ts` · `routes/snapshots.ts`
  — 코드로 확인, main 을 띄워 재지는 않았다) CLI 의 엄격 파싱도 못 읽는다. A3 에서 찍은 스냅샷(복원이 남긴 안전망 포함)은 페이지 · 메뉴가 판 2 와 같은데도
  돌아갈 수 없다. 0018 의 `down` 은 같은 판을 판 1 로 되돌린다 — 선례와 어긋난다.
- **빨강**: `migration-0019-down-payload.test.ts` «0019 → 0018 — 판 3 payload 가 판 2 모양(theme 없음)으로 돌아온다» → `expected [ { version: 3, theme: true } ]
  to deeply equal [ { version: 2, theme: false } ]`. `down` 첫 줄에 `payload - 'theme' || {"payloadVersion":2}`(판 3 만)를 심으면 초록.
- **고칠 방향**: 0019 `down` 이 판 3 payload 에서 `theme` 를 빼고 판 2 로 적는다(0018 `down` 과 같은 꼴).
- 일회용 DB 는 지웠다(`wb_a3` · `wb_a3_test` 만 남음). 그 DB 에서 `migrate` 가 `.env` 의 `SEED_USER_*` 로 계정을 하나 만들었다(지운 DB 안).
