# P7-3 페이지 JSON 가져오기 · 내보내기 구현 계획

> **에이전트에게:** 태스크 단위로 실행한다. 각 태스크는 실패하는 케이스 → 최소 구현 →
> 통과 → 커밋의 순서를 지킨다.

**목표.** §11.2의 페이지 JSON을 세운다. 이 슬라이스가 끝나면 *"페이지를 파일로 내보내고,
그 파일로 페이지를 만들 수 있다"*가 참이 되고 **P7이 닫힌다.**

**§11.2 봉투:**

```jsonc
{
  "wireboundVersion": "1",
  "page": { "title": "회원 목록", "layoutRef": "admin-lnb", "description": "..." },
  "schema": { "id": "n_root", "type": "Page", "children": [ ... ] },
  "comments": [ { "marker": 1, "nodeId": "n_7f3a", "body": "검색 조건은 AND 결합" } ]
}
```

*"가져오기 시 노드 id를 재발급하되 **코멘트의 `nodeId`와 상호작용의 `target`을 함께
리매핑**한다. `wireboundVersion`은 스키마 마이그레이션 진입점이다."*

**스택.** `packages/schema`(봉투) · `apps/api`(가져오기 라우트) · `apps/web`(파일 I/O·화면) · vitest.

- **워크트리 안에서만 작업한다.**
- `pnpm test` · `pnpm typecheck` · `pnpm build`가 마지막에 전부 통과해야 한다.
  **종료 코드는 파이프 없이 따로 찍어라.**
- **api 테스트는 Postgres 하나(포트 5433)를 공유한다.** 컨테이너를 새로 띄우지 마라.
- **`git checkout --`을 쓰지 마라.** python 치환으로 심고 `finally`에서 원본 전문을 되쓴다.
  **`git diff`로 확인하지 마라** — 새 파일은 untracked라 늘 비어 있다.
- **0 사망이 나오면 그렇다고 보고해도 된다. 다만 원인을 단정하지 마라.** 못 죽였으면
  **겨냥을 바꿔 다시** 재라.
- **수를 산문에 적지 마라.** 세야 한다면 **케이스가 만들게 하라.** 못 하면 왜 못 하는지
  한 줄 적어라.
- **머리말은 본문보다 늦게 고쳐진다.** 계약을 바꿨으면 **같은 커밋에서** 고쳐라.
- **문장을 옮길 때는 그 문장이 가리키는 자리를 다시 열어 보라** — *"재지 않았다"*·
  *"도달하지 않는다"*처럼 **오늘의 상태를 말하는 것**은 옮기는 순간 이미 낡았을 수 있다.
  P7-2 이월 머리말이 그것을 이 저장소의 **세 번째** 사례로 적어 두었다.
- **설계 문서(`docs/superpowers/specs/*`)는 고치지 않는다.** 어긋나면 판정해 보고한다.
- **`apps/web`에 새 런타임 의존을 더하지 않는다.**
- **남이 잰 값은 귀속을 붙여 옮긴다.**

## 확정한 결정

### D1. **봉투 규격은 `packages/schema`가 소유한다**

봉투가 참조하는 것은 `PageDocument`와 코멘트뿐이고 **테마를 모른다.** 스냅샷 payload가
`apps/api`로 간 것은 `Theme`를 참조했기 때문이지(P6-1 D2) 서버 것이라서가 아니다 —
같은 규칙을 적용하면 이것은 `schema`다.

**그리고 P9의 `wireb pull`이 이 봉투를 쓴다**(§12). 소비자가 이미 둘 보인다.

### D2. **`wireboundVersion`은 세 번째 버전 축이다 — 섞지 마라**

| 축 | 어디 | 무엇 |
|---|---|---|
| `wireboundVersion` | 이 봉투 | **파일 형식** (§11.2 — 문자열 `"1"`) |
| `PageDocument.version` | 문서 | 컴포넌트 props 규격 (§13.1) |
| `payloadVersion` | 스냅샷 | 스냅샷 payload 형식 (P6-1 D3) |

- **모르는 `wireboundVersion`은 거부하고 그 값을 말한다.** P6-1 D3이 스냅샷에서 같은 선을
  그었다.
- **봉투 안의 문서는 `migrateDocument`를 지난다** — §13.1이 *"가져오기와 스냅샷 복원도 같은
  경로를 탄다"*고 적은 자리다.

### D3. **내보내기는 페이지 하나다**

§11.2의 제목이 *"페이지 JSON"*이고 봉투에 `page` 하나가 있다. 여러 페이지는 스냅샷(§4.5)과
HTML 번들(§11.3)의 일이다.

### D4. **가져오기는 새 페이지를 만든다 — 절대 덮지 않는다**

P6-2 이월 §1이 그은 선이다: *"`planRestore`는 payload 상태로 **수렴**시키고 가져오기는
**삽입**이다. 재사용하면 가져오기가 기존 페이지를 지운다."*

- 대상 **메뉴 노드**를 받는다(페이지는 메뉴에 매달린다).
- **`insertPage`를 쓴다** — id를 발급하고 맨 끝에 붙이고 형제를 재번호하는 쪽이다.
  **`insertPageWithId`·`writePagePlacement`를 쓰지 마라**(복원 전용).
- **`layoutRef`는 §11.2의 필드인데 오늘 레이아웃을 이름으로 고르는 경로가 없다.**
  어떻게 다룰지 **판정하고 근거를 적어라** — 무시하든, 맞는 것이 없으면 기본 레이아웃을
  쓰든, 거부하든. **조용히 버리지는 마라.**

### D5. **id는 재발급하고 참조 **셋**을 함께 옮긴다**

§11.2가 명시한 둘(`comments[].nodeId` · 상호작용 `target`)에 **문서 안의 marker**가 붙는다.

- `remapNodeIds(root)` → `{ root, mapping }`.
- **`mapping`을 코멘트의 `nodeId`에 적용한다** — P7-2 이월 §6이 *"P7-3이 그 맵을 처음 쓰는
  자리"*라고 지목했다.
- **트리 밖 참조(`page:...`)는 그대로 둔다.** 끊긴 것은 `validatePage`가 **warning**으로
  말하고, 화면이 그것을 막으면 서버보다 엄격해진다(P7-1 이월 §7).
- **매핑에 없는 `nodeId`를 가리키는 코멘트가 파일에 있을 수 있다.** 그것이 §11.2가 남의
  파일을 받는다는 뜻이다 — **무엇을 할지 판정하고 케이스로 고정하라.** 넣으면 고아
  코멘트를 **만들면서 들어가는 것**이고(P7-2 이월 §4의 셋째 경로), 버리면 사용자가 적은
  것이 사라진다. **조용히 둘 중 하나를 하지는 마라.**

### D6. **`marker`는 노드가 든다 — 봉투의 `comments[].marker`는 §11.2와 코드가 어긋나는 자리다**

§11.2의 예시는 `comments[]`에 `marker`를 싣는데, **P5-1 D1이 그것을 노드로 옮겼다**
(`repos/comments.ts` 머리말: *"번호(`marker`)는 여기 없다"*). 봉투에 다시 실으면 **같은 값의
출처가 둘**이 되고, 파일의 둘이 어긋날 때 무엇을 믿을지 정해야 한다.

**내 판정: 봉투의 `comments[]`는 `marker`를 싣지 않는다.** 번호는 `schema` 안의 노드에 이미
있고, 내보내기가 그것을 그대로 낸다.

**이것은 설계서와 어긋나는 판정이므로 워커가 다시 판정하고 보고하라.** 설계서를 고치지는
마라 — 어긋남을 보고서에 적는다. **내 판정에 동의하지 않으면 그렇게 말하고 근거를 적어라.**

### D7. **가져오기는 새 라우트 하나다 — 한 트랜잭션이어야 하기 때문이다**

P7-1 D4는 *"새 엔드포인트를 만들지 않는다"*였다. **그것은 문서 편집 하나였고 여기는 다르다** —
가져오기는 **페이지 생성 · 문서 쓰기 · 코멘트 넣기** 세 자원을 만진다.

두 요청으로 나누면 중간 실패에서 **빈 페이지가 남는다** — 이 저장소가 일곱 형태로 만난
*"실패했다고 말하는데 조작은 일어났다"*이다. P6-2 이월 §8이 정확히 이 슬라이스를 겨냥해
적혀 있다.

- **`POST /:projectId/pages/import`** 하나. `withTransaction` 안에서 전부 한다.
- **문서 쓰기는 `applyEdit`을 지난다**(D1 — 모든 스키마 변경이 revision을 남긴다).
- **`applyEdit`의 실패는 반드시 던진다.** 값으로 `return`하면 앞 단계 쓰기가 커밋된다.
- **실패 갈래마다 *"이 갈래는 무엇을 되돌리는가"*를 답하라.**

### D8. **판정은 결과 문서 전체이고, 실패 문장은 파일의 자리를 가리킨다**

P7-2 이월 §3: 가져오기는 root까지 바꾸므로 프리셋의 경계(root는 교체 대상이 아니다)가
사라진다. 대신 **실패 문장이 가리킬 것이 파일뿐**이다.

**`validatePage`의 이슈에는 `path`와 `nodeId`가 이미 있다.** 그것을 화면까지 나르면 사용자가
파일의 어디를 고칠지 안다. **나르는지 케이스로 고정하라.**

### D9. **권한 — 가져오기는 editor, 내보내기는 viewer**

§10: editor가 *"메뉴·페이지·컴포넌트·코멘트·상호작용 편집"*을 한다. 가져오기는 페이지를
만드는 것이므로 페이지 생성과 같은 등급이다. 내보내기는 읽기다.

**`permission-matrix.test.ts`가 새 라우트에서 먼저 죽는다**(P7-2 이월 §7). 그것이 신호다.

### D10. **파일 I/O는 이미 있는 것을 쓴다**

P4c-3이 테마 가져오기/내보내기를 만들며 `apps/web/src/theme/file-io.ts`를 세웠다.
**재사용할 수 있는지 먼저 재고**(재라 #2), 가능하면 공용 자리로 옮긴다. 두 벌을 만들지 마라.

**그리고 P4c-3이 닫은 사고를 되풀이하지 마라** — 파일 읽기가 실패했는데 앞서 읽은 텍스트가
남아 *"초안에 넣기"*가 이전 것을 넣었다.

### D11. **가져오기 UI는 `typing-surface.ts`를 쓴다**

P7-2 이월 §2. 파일 이름·페이지 제목 같은 입력 칸이 구조 트리와 같은 키보드 상자 안에 들어가면
**타이핑이 문서를 지운다.** 그 슬라이스가 순수 모듈로 갈라 놓았으니 그것을 쓴다.

**완전히 막지 못하는 표면 둘이 있다**(`mode:'closed'` shadow 호스트 · 편집 가능성도 역할도
선언 안 하는 위젯). 새로 만드는 입력이 그 둘이 아닌지 확인하라.

| 5 | **가져오기가 새 테이블을 필요로 하지 않는다**(가져오기 이력을 안 남긴다) | 판정이지 측정이 아니다. P7-2 이월 §7이 *"가져오기 이력은 어디에도 없다"*를 열어 뒀다 |
| 6 | **`validatePage`의 이슈가 `path`와 `nodeId`를 든다** | 코드를 읽었다. D8이 걸린다 |
| 7 | **코멘트 본문 1~2000자 상한이 가져오기에도 걸린다** | 추론이다. 남의 파일은 그 상한을 안 지킨다 |

- **여러 페이지를 한 번에** — D3. 스냅샷과 HTML 번들의 일이다.

  정한다)"*고 적었다. **재서 보고하고, 상한을 둘지는 판정하라.**
