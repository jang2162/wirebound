## 1. renderer 버블 겹침(`packages/renderer/src/render.tsx`) — 재현 안 됨

**세운 판(jsdom):** 겹layer를 상태에 **안 싣는** 호스트(캔버스의 `onEvent` 를 무시)로 안쪽 노드를 두 번 눌러, 앞 이벤트의 쓰기가
뒤 이벤트로 새는지 봤다. 고침은 `WeakMap<nativeEvent, overlay>` 로 같은 네이티브 이벤트 안의 핸들러끼리만 겹layer를 잇는다.

**값(jsdom):** 네 핸들러의 겹layer = `[{inner}, {inner,outer}, {inner}, {inner,outer}]`. 둘째 누름의 안쪽 핸들러(3번째)가
`{inner}` 만으로 **새로 출발했다** — 앞 이벤트의 `{inner,outer}` 를 보지 않았다. 네이티브 이벤트가 디스패치마다 유일한 객체라
`WeakMap` 키가 겹치지 않고, 이벤트가 버려지면 항목도 GC 된다.

**판정:** 재현 안 됨. 편집 모드는 `interaction === undefined` 라 `handlersFor` 를 안 달고 `fire` 를 안 부른다(영향 0). 버블을
막는 규칙(`stopPropagation`)은 renderer·뷰 어디에도 없다. 실브라우저 값은 안 쟀다 — jsdom 으로 누수 없음이 결정적이고, 좌표가
아니라 겹layer 객체의 동일성 문제라 브라우저가 새 값을 주지 않는다.

## 2. change 규칙의 뜻이 바뀐 것 — 결함 아님(옛·새 공통)

**센 것(정적):** shipped 뷰 전부(`packages/theme-sdk/src/default-views/**` · `system-themes/admin` · `packages/theme-kit/template` ·
kit 샘플 픽스처)에 네이티브 `<input>`·`<select>`·`<textarea>` 와 `onChange` 를 건 컨트롤이 **하나도 없다**(`git grep` 0건).
`SearchForm`·`EntryForm` 은 `<form>` 이지만 `Field` 는 `<div data-wb-part="control">` 다.

**판정:** 결함 아님. change 규칙은 새 런타임(React `onChange`)에서도 **영영 안 돈다** — 그런데 옛 번들(네이티브 `change` 위임)
에서도 change 를 내는 컨트롤이 없어 똑같이 안 돌았다. 즉 「onChange 를 안 걸어 규칙이 영영 안 도는 판」은 **카탈로그 × 규칙 표의
모든 칸**이지만, 그것은 **옛·새 공통의 성질**이고 renderer 스스로 적어 둔 계약이다(`render.tsx` 「change·submit 은 사용자
조작으로는 닿지 않는다」). 회귀가 아니다. 옛→새 차이(위임 대 React onChange)가 관찰되려면 테마가 네이티브 `<input>` 을 그려야
하는데, 그때는 새 쪽이 더 맞다(React 가 그 입력의 onChange 를 받는다). 유일하게 잃는 판은 «뷰가 노드 attrs 를 안 펼친 하위
입력의 네이티브 change 를 위임이 주웠던» 경우 — 커스텀 테마의 드문 판이라 무게 없음.

## 4a. PPTX 준비 뒤 `data-wb-failed` 읽기에 한도가 없다 — 결함(높음)

**세운 판(실브라우저):** 테마 코드가 `Element.prototype.getAttribute` 를 덮어 `'data-wb-failed'` 읽기를 **끝나지 않는 Promise**
로 만든다. 이 테마로 한 장(+멀쩡한 둘째 장)을 한 장 한도 2s 로 그렸다. 테마 코드는 이 브랜치가 브라우저에서 실행한다(spec 「내보내기와
PPTX」의 «테마 코드는 브라우저에서만 돈다»).

**값(실브라우저):** `renderOne` 이 **영영 안 끝났다** — 30s 가드에도 `{kind:"hung"}`. 멀쩡한 둘째 장은 다 그려졌지만
`renderAll` 의 `Promise.all` 이 덫 장을 기다려 **배치 전체가 멈췄다.** 대조로 세운 다른 «준비가 안 오는» 판은 전부 한도 안에
끝났다: theme.js 머리 `for(;;){}` · theme.css 응답 영영 붙잡음 · 글꼴 응답 영영 붙잡음 · 준비 직후 스핀 → 모두
`한 장의 한도 안에 준비되지 않았습니다 — 3000ms`(멀쩡한 장 ok). **오직 `data-wb-failed` 읽기 한 줄만 한도를 못 받는다.**

**빨강 케이스:** `apps/api/build-test/screen-sandbox-review.test.ts` 「준비 뒤 data-wb-failed 읽기가 멈추면 그 장만 실패하고
배치는 한도 안에 끝난다」. **실패 값:** `expected 'hung' to be 'returned'`(8s 가드 안에 render 가 안 돌아옴).

**원인:** `renderOne`(`apps/api/src/services/screen-render-chromium.ts:322`)의
`const failed = await page.evaluate("…getAttribute('data-wb-failed')")` 가 `left()`(남은 한도)를 안 쓴다. `page.evaluate` 는
컨텍스트 기본 한도(`setDefaultTimeout`)를 안 받는데(같은 파일 `measure` 머리말이 그 함정을 적고 `measure`·screenshot·waitReady 는
모두 `left()`·`Promise.race` 로 감쌌다) 이 한 줄만 빠졌다. CLAUDE.md 「도구의 기본 한도가 닿지 않는 호출에 기다림을 넣으면 그
단계만 한도 없이 남는다」의 그 함정이다.

**고칠 방향:** 그 evaluate 를 `measure` 처럼 `Promise.race([evaluate, 마감(left())])` 로 감싸고 마감이면 `notReady` 를 낸다.
**실증:** 그 한 줄을 감싸는 고침을 넣자 케이스가 2.1s 에 `notReady` 로 초록이 됐고(배치 복귀), 바이트 비교로 복원했다.

**영향·한계:** 하나의 적대적 테마에 고정된 프로젝트를 PPTX 로 내보내면 그 요청이 영영 안 끝나 **그리기 칸(`renderLimit` 기본 2)을
쥔 채**다 — 그런 요청 둘이면 서버의 모든 PPTX 내보내기가 줄 뒤에서 멈춘다(DoS). `ended`(끊김) 신호는 in-flight `render` 로
안 내려가 클라이언트가 끊어도 안 풀린다. **실현성:** 임의 테마 JS 가 필요하다(업로드 검증은 구조만 본다 · JS 동작은 안 본다) —
샌드박스가 겨누는 «작성자가 고른 코드»의 위협 모델 안이다. 평범한 무한 루프는 대개 `waitReady` 가 먼저 잡는다(준비 직후 스핀
판이 `notReady`) — 이 evaluate 를 확실히 멈추는 것은 getAttribute 를 thenable 로 만드는 의도적 수법이다. main 은 서버가 목업을
SSR 하고 브라우저에서 테마 JS 를 안 돌려 이 길 자체가 없었다 — **이 브랜치가 연 길.**

## 4b. 준비 뒤 크기를 바꾸는 테마 뷰 — 결함 아님

**세운 판(실브라우저):** 테마 `Page` 뷰가 `useEffect` 로 0·30·150·600·2500ms 뒤 2000px 를 더한다. 각 지연을 3회씩.

**값:** 0ms → `ok 1440x4304`(준비 전 자라 통째로 찍힘). 30ms → 3회 중 2회 `페이지가 그리는 동안 커져 화면을 그리지
않았습니다 — 720×573px 에서 720×2152px`, 1회 `ok 4304`. 150·600·2500ms → 전부 `ok 1440x1146`(찍은 뒤 자람 · 안 찍힘).
큰 이미지(3000px·246KB)를 크기 없이 실은 판도 6회 전부 `ok 2400x6304`(same-origin 이라 첫 프레임에 실려 측정됨).

**판정:** 결함 아님. **찍은 뒤 다시 재기(`grew` 검사)가 찍는 창 안의 자람을 잡아** 잘린 그림을 «정상»으로 내보내지 않는다.
찍기 뒤에 자란 것(150ms+)은 안 찍혔을 뿐 잘린 것이 아니다(그 순간의 완전한 한 장). 30ms 판이 3회 중 2회만 `grew` 로 죽는
흔들림은 있으나 **어느 판에서도 잘린 그림이 정상으로 나가지 않는다** — 무게 없음. jsdom 은 좌표를 안 재 이 판은 실브라우저 전용.

## 5. 가짜 origin 차단이 WebSocket · WebRTC 를 안 막는다 — 결함(높음)

**세운 판(실브라우저):** 테마 코드가 채널 열둘을 서로 다른 주소로 연다. 채널마다 다른 포트의 127.0.0.1 리스너(TCP·UDP)를
두고 **실제로 소켓이 열렸는지**(리스너가 받은 연결)와 **`Route.abort` 가 본 주소**를 함께 셌다.

**값(실브라우저):**
- **실제 egress(리스너가 받음):** `WebSocket`(wss) · WebRTC `turn`(TCP) · WebRTC `stun`(UDP 20B) — **세 채널이 소켓을 열었다.**
  `Route.abort` 는 이 셋을 **못 봤다**(차단 목록에 없음). 페이지는 `ok` 로 그려졌다(내보내기가 성공하며 조용히 나간다).
- **차단됨(`Route.abort` 가 봄 · 소켓 0):** `fetch` · `sendBeacon` · `@import` · `EventSource`(sse) · `Worker`(fetch) ·
  dynamic `import()` · `<img>` — 일곱 채널. `preconnect`·`dns-prefetch` 는 이 판에서 소켓을 안 열었다(헤드리스가 사변 연결을
  안 함) — 확정 egress 로 세지 않았다.
- 127.0.0.1 직접(host-resolver 없이)으로도 ws·turn·stun 이 똑같이 egress(tcp 2·udp 1) — 대상이 무엇이든 채널이 열린다.

**빨강 케이스:** `apps/api/build-test/screen-sandbox-review.test.ts` 「테마 코드의 WebSocket · WebRTC 는 바깥으로 소켓을 열지
못한다」. **실패 값:** `expected { tcp: 2, udp: 1 } to deeply equal { tcp: 0, udp: 0 }`.

**원인:** `newRenderContext`(`screen-render-chromium.ts`)의 `context.route('**/*', …abort)` 는 fetch·하위 자원만 가로챈다 —
playwright 의 `context.route` 는 **WebSocket 핸드셰이크와 WebRTC ICE(STUN·TURN)를 안 가로챈다.** 그 채널의 존재 이유(같은
파일 머리말 「바깥으로 나가는 요청을 막는다」 — «그 코드를 적은 쪽이 고른 주소로 서버가 요청을 보내는 자리»)를 정면으로 뚫는다.
운영에서는 `evil.example.com` 이 실제 DNS 로 풀려 서버의 Chromium 이 공인 주소로 나간다(WebSocket 은 양방향이라 렌더된 화면·
데이터 유출 채널이 된다).

**고칠 방향:** 첫 그림 전 초기화 스크립트(`FREEZE_MOTION_INIT` 옆)에서 `WebSocket`·`RTCPeerConnection`·`webkitRTCPeerConnection`·
`EventSource` 를 지운다(정적 목업 렌더러라 셋 다 필요 없다). **실증:** 그 초기화 스크립트를 넣자 egress 0 으로 초록이 됐고
(그 장은 여전히 `ok`), 바이트 비교로 복원했다. (WS 만 막으려면 `context.routeWebSocket` 도 있으나 WebRTC 는 route 로 못 막아
초기화 스크립트가 한 자리로 셋을 덮는다.)

**한계·실현성:** 임의 테마 JS 가 필요하다 — 4a 와 같은 위협 모델(작성자가 고른 코드)이고 샌드박스가 바로 그것을 겨눈다.
main 은 브라우저에서 테마 JS 를 안 돌려 이 채널이 **닿을 수 없었다** — `context.route` 의 ws/webrtc 빈틈은 main 에도 있었으나
(그때도 route.abort 가 있었다) 실행되는 untrusted JS 가 없어 죽은 길이었다. **이 브랜치가 «테마 JS 를 렌더 브라우저에서
실행»하며 그 빈틈을 살아 있는 유출 채널로 만들었다.** 리스너가 받은 «소켓이 열렸다» 까지만 값으로 봤다 — 공인 주소로의 실제
데이터 전송량까지는 안 쟀다.

## 6. worker thread 로 큰 테마 복제 — 재현 안 됨

**세운 판(api):** 1·5·9MB 바이너리 테마 자산이 든 프로젝트를 `ExportWorkerPool`(limit 1)로 HTML·PPTX 내보냈다.
`.wbtheme` 상한이 압축 10MB 라 9MB 가 상한 근처다. 힙 64MB 판도.

**값:** HTML 187·179·203ms(zip 나옴). 같은 스레드 vs 워커 zip **바이트 동일**(9MB, 171648B). 힙 64MB 아래에서 9MB PPTX
도 `ok`. **멈춤·OOM·워커 죽음 0.** 워커로 넘기는 `{ t:'rows', part:'theme' }` 메시지가 9MB `Uint8Array` 를 structuredClone
하지만 문턱(«내보내기 실패·서버 멈춤»)에 못 미친다. **판정: 재현 안 됨.**

## 지침 보고

`CLAUDE.md` 「검증」 계열에 넣을 만한 한 문장(있으면 좋음, 없어도 됨): **playwright 의 `context.route('**/*')` 는 fetch·하위
자원만 가로채고 WebSocket·WebRTC(STUN·TURN)는 그 아래로 빠진다 — 브라우저에서 untrusted 코드를 돌리며 바깥 요청을 막을 때는
route 만으로 못 막고, 초기화 스크립트로 그 API 를 지워야 한다(재는 법: 채널마다 다른 127.0.0.1 포트로 소켓이 열리는지).**
넣을 자리는 「목 · 계측은 불린 수를 값으로 확인하고…」 절 끝(구현자가 제안한 «가짜 origin(https)에서 …» 문장 바로 뒤) —
그 문장은 «서버 적중만 세지 마라» 이고, 이 문장은 «route 가 아예 안 보는 채널이 있다» 로 한 겹 더 나간다.
