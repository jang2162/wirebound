## 3. 실행 중 내려진 판정 (계획에 없는 것)

계획을 읽어도 알 수 없고, 다음 태스크에 영향을 주는 결정들이다.

### 3.1 표준 규칙 — 제약 위반은 `withTransaction`을 거친다

**가장 중요한 항목이다.** 테스트 하네스가 각 테스트를 하나의 Postgres 트랜잭션 안에서 돌리므로, 제약 위반이 나면 트랜잭션이 abort되고 **이후 모든 문장이 `25P02`**를 받는다.

- `withTransaction`의 중첩 분기는 SAVEPOINT를 쓴다 (`src/db/tx.ts`). 프로덕션의 요청당 트랜잭션 의미를 테스트 안에서 재현한다.
- **제약 위반을 낼 수 있는 라우트 경로는 반드시 `withTransaction`을 거친다.**
- **충돌 테스트는 409 뒤에 DB를 향해 뭔가 단언해야 한다.** 409에서 멈추면 동작하는 savepoint와 없는 savepoint를 구분할 수 없다 — 태스크 8에서 실제로 그 구멍이 났고 리뷰가 잡았다.

태스크 12(중복 없음), 13(FK RESTRICT 위반 가능)에 그대로 적용된다.

### 3.2 테스트 하네스는 `app.ready()`를 부르지 않는다

Fastify 5는 ready 이후 라우트 등록을 거부한다. 여러 테스트가 훅을 확인하려고 임시 라우트를 등록하므로 `withApi`가 ready를 부르면 안 된다. `inject()`가 첫 호출에서 알아서 태운다.

### 3.3 세션 정책

로그인은 기존 세션을 **건드리지 않는다**. 한 계정이 여러 기기에 로그인할 수 있다. `destroyUserSessions`는 export되어 있으나 로그인 경로에 연결되어 있지 않다(후속 "모든 기기에서 로그아웃"용).

### 3.4 이메일 검증은 ASCII 전용

`z.email()` 기본값을 쓴다. 계획의 한국어 로컬 파트 픽스처(`없는사람@`, `초대대상@`)는 장식이었고 전부 ASCII로 정정했다. **새 테스트에서 한국어 이메일을 쓰지 않는다.**

### 3.5 동시성 테스트를 만들지 않는다

`withApi`는 단일 커넥션의 한 트랜잭션이라 `Promise.all`로 요청을 겹쳐도 직렬화된다. 그런 테스트는 잠금이 있든 없든 통과한다 — **실패할 수 없는 테스트**다. 대신:

- 불변식은 **순차** 테스트로 고정한다.
- 잠금(`SELECT ... FOR UPDATE`)은 **리뷰어가 SQL에서 확인할 코드 요구사항**으로 둔다.

진짜 경합 테스트는 실제 커밋이 필요하므로 P3의 격리 전략(TRUNCATE)과 함께 온다.

### 3.6 `packages/schema/src`의 전역 제약

`src`는 `types: []` + `lib: ["ES2022"]`로 컴파일된다. Node 전역도 DOM도 없고, `structuredClone`과 `crypto.getRandomValues`만 `src/globals.d.ts`에 선언되어 있다. 설계 §3.3("브라우저와 Node 양쪽")을 컴파일러가 강제한다. `test`는 별도 프로젝트(`tsconfig.test.json`, `types: ["node"]`)다.

### 3.7 마이그레이션

정적 레지스트리(`src/db/migrations/index.ts`)를 쓴다. `FileMigrationProvider`의 동적 import는 실행기마다 동작이 달라 쓰지 않는다. `Kysely<unknown>`을 쓴다(`any` 아님). **모든 마이그레이션은 동작하는 `down`을 갖는다** — `global-setup`이 매 실행마다 latest → 전부 down → latest를 돌리므로 깨진 `down`은 즉시 전체 실행을 막는다.

### 3.8 계층

- `requireProjectRole`은 Fastify를 모른다. P3의 WebSocket이 그대로 재사용한다.
- `roleAtLeast`가 **코드베이스에서 두 역할을 비교하는 유일한 지점**이다.
- `repos/`는 SQL만, `routes/`는 HTTP만 안다. SQLSTATE 처리는 `repos/` 안에 갇힌다(코드뿐 아니라 **제약 이름**까지 확인한다 — `repos/users.ts`가 패턴).
- API 키는 camelCase, DB 컬럼은 snake_case. 변환은 `repos/`가 한다.

### 3.9 404 대 403

프로젝트 비멤버는 **404**(존재를 숨긴다), 멤버지만 역할 부족은 **403**. 앞의 둘(없는 프로젝트 / 비멤버)은 의도적으로 구분되지 않는다. 설계 §10에 기록되어 있다. **테스트가 "비멤버 404"와 "역할 부족 403"을 실제로 구분해야 한다** — owner와 외부인만 테스트하는 스위트는 이 규칙이 뒤집혀도 못 잡는다.

## 5. 이월 항목 (최종 브랜치 리뷰에 전달할 것)

수정 루프에 넣지 않고 미룬 Minor들이다. 최종 리뷰가 병합 전 처리 여부를 판단한다.

### 태스크 12가 받을 것 (Important)

- **PATCH/DELETE `/api/projects/:projectId/members/:userId`에 anonymous(401)·outsider(404) 커버리지가 없다.** 403만 있다. "대상이 멤버가 아니면 404"는 라우트의 `notFound`이지 `projectGuard`의 outsider 404가 아니다 — 다른 경로다. 태스크 12가 매트릭스에 `setup` 훅을 만드므로 거기서 두 라우트를 행으로 추가하는 것이 자연스럽다.

### 최종 리뷰용

- **`packages/schema`:** `assertValidLayout`에 테스트가 없다(`assertValidPage`에는 있다).
- **`dist-loadable.test.ts`**가 `beforeAll`에서 `pnpm`을 셸아웃해 두 패키지를 재빌드한다. `pnpm test`가 pnpm 존재와 빌드에 결합된다.
- **`password.ts`의 `p`가 무제한이다.** 메모리 상한 `128*N*r`에 `p`가 없어 메모리 관점은 맞지만 CPU 시간 레버가 남는다(실측 `p=2000` → 6.23ms). 수정 라운드 1의 `MAX_P=16` 대비 회귀.
- `hashPassword` 대칭 테스트의 `N=1000` 케이스는 Node가 어차피 거부하므로 비판별.
- **로그인 타이밍 방어**(없는 이메일에도 더미 해시 검증)가 코드 읽기로만 보장된다. 타이밍 단언은 flaky, 목은 저장소 방침 위반.
- 대소문자 무시 로그인 테스트가 상태 코드만 단언한다.
- `signup()` 픽스처 자체에 직접 테스트가 없다(여섯 태스크가 간접 사용).
- `password_hash` 누출 단언이 signup 응답에만 있고 login/me에는 없다.
- **`withTransaction`**: savepoint 롤백 자체가 던지면 원본 에러가 대체된다. `withApi`: `fn`과 `close`가 동시 실패하면 close 에러가 조용히 버려진다.
- `findMembership`이 `repos/` 대신 `auth/roles.ts`에서 raw SQL을 돈다(브리프대로). 나중에 `repos/projects.ts`가 같은 쿼리를 중복하지 않도록.
- 태스크 10 리포트의 미테스트 방어 분기 자진신고가 절반만 셌다(4개 중 2개).
- `invitedAt` 직렬화 형식이 미검증(키 존재만 확인).
- `permission-matrix.test.ts`가 `beforeEach`를 import만 하고 안 쓴다.

### 계획 문서 자체의 정정 필요

- 계획과 P0 이월 문서가 `renderComposed(page, layout)`이라고 적었으나 **실제 시그니처는 `renderComposed(layout, page)`**다. 태스크 3 구현자가 지적했다.

### P0 이월 중 P1이 처리하지 않은 것

`2026-08-03-p0-carryforward.md`의 6~10번(P2·P4a·P4b용)과 "사소한 것들" 대부분은 그대로 남아 있다. 태스크 1~3이 처리한 것은 1·2·3·4·5번과 사소 항목 넷이다.

## 6. 완료 판정 (계획 §완료 판정 재확인)

P1이 끝났다는 것은 다음이 전부 참이라는 뜻이다.

1. `docker compose down -v && docker compose up -d` 직후 `pnpm build && pnpm --filter @wirebound/api migrate && pnpm test`가 통과한다.
2. `pnpm typecheck`가 exit 0이다.
3. 권한 매트릭스가 **모든 엔드포인트 × 5종 액터**를 덮는다.
4. `PUT .../schema`가 봉투 위반에 400을, 카탈로그 위반에 422를 내고, 실패 시 기존 스키마가 보존된다.
5. 순수 Node가 `@wirebound/schema`를 로드한다.
6. `apps/api/README.md`의 엔드포인트 표가 실제 라우트와 일치한다.

`-v`는 로컬 개발 DB 볼륨을 지운다. 이 컨테이너는 P1 개발용이라 잃을 데이터가 없다.

1. `.superpowers/sdd/2026-08-03-p1-api/` 삭제 **전에** 이월 사항을 `docs/superpowers/plans/2026-08-04-p1-carryforward.md`로 옮긴다(P0 때 그렇게 했다).
2. `superpowers:finishing-a-development-branch`를 쓴다. 사용자에게 3지선다(로컬 병합 / PR / 유지)를 제시하고 **기다린다** — 통합 결정은 사용자 몫이다.
3. 저장소에 동작하는 remote가 없다(`origin/main` upstream이 사라진 상태). P0 때 `git pull`을 건너뛰었다.
