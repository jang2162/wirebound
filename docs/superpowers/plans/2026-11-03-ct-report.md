## 결정과 이유

1. **코멘트 묶음은 노드를 고른 동안만 세운다**(`selectedNodeId !== null`). 고른 것이 없을 때 세우면 쓸모없는 조회가 나간다. 그런데 **페이지를 열면 스토어가
   루트를 고른다** — 그래서 편집 모드에서 페이지를 열 때마다 «컴포넌트» 탭의 코멘트 묶음이 목록을 **한 번** 읽는다. 그 묶음은 화면에 보이는 자리라(루트의
   코멘트) «보지도 않는 목록을 위한 요청» 이 아니라고 판단했다. jsdom 케이스 «탭을 열기 전에는 조회하지 않는다» 를 «코멘트를 안 그리는 탭에서는 조회하지 않는다 —
   «컴포넌트» 탭은 고른 노드의 묶음을 그려 읽는다»(열 때 1 · 옆 탭으로 옮기고 고름을 풀어도 1)로 바꿨다. 다른 쪽(루트는 묶음을 안 세움)은 루트에 단 코멘트가
   «컴포넌트» 탭에서 안 보이는 대가라 고르지 않았다.
2. **가짜 api 의 `listComments` 기본값을 빈 목록으로**(`apps/web/test/helpers.tsx` — `readTree` 와 같은 꼴). 위 1 때문에 노드를 고르는 jsdom 케이스마다 목록을
   읽어, `notStubbed` 면 «코멘트를 불러오지 못했습니다» alert 이 하나 더 서서 88 건이 죽었다(alert 수 · 통지 목록을 세는 케이스). 부른 수 · 답을 재는 케이스는 그대로 덮어쓴다.
3. **재번호는 «코멘트» 탭에만** — 페이지 전체의 일이라 «고른 노드의 묶음» 에 두면 그 묶음 밖을 바꾼다.
4. **Cmd/Shift 클릭도 탭을 옮긴다** — «캔버스에서 노드를 누르면(고르면)» 의 누름이다. 뺀 클릭(목록에서 빠짐) · 남이 잡아 안 골라진 클릭은 안 옮긴다.
5. 묶음 이름은 `<h2>`(노드 제목 `.wb-shell-panel-title` 도 `<h2>`) — 패널의 heading 목록이 «속성 · 타입 · 코멘트» 가 된다(`property-panel.test.tsx` 두 줄을 그 목록으로).
6. **«코멘트» 탭에서 캔버스로 고르면 이제 탭이 «컴포넌트» 로 간다** — 결정 기록대로다. «코멘트» 탭에 머문 채 노드를 바꾸는 길은 구조 트리 줄이다. jsdom 케이스 중 «코멘트 탭을
   연 채 캔버스에서 고르는» 꼴(`comment-panel.test.tsx` 열한 곳 · `alias-naming.test.tsx` 둘)은 «고른 뒤 «코멘트» 탭으로 돌아온다»(`pickInCommentTab`)로, 옆 탭 왕복
   (`toPropsTab`)은 «상호작용» 탭으로(«컴포넌트» 탭에도 코멘트 상자가 있어 언마운트를 못 잰다) 바꿨다. `props-lock.test.tsx` 의 위젯 · 안내 셈은 «속성» 묶음으로 좁혔다
   (남이 잡은 노드에도 코멘트는 단다 — «코멘트» 탭과 같다).

## 남은 것

- **코멘트 목록의 실시간 갱신**(q-ct Q1 · 코디네이터 답 «기본값대로 · 이월»). 남이 단 코멘트는 두 자리 다 목록을 다시 읽을 때(탭을 다시 열거나 · 노드를 처음 고름 ·
  내 쓰기 뒤) 선다. WS 로 오는 것은 번호 patch 뿐이다. «컴포넌트» 탭은 노드를 자주 바꾸는 자리라 «코멘트» 탭보다 낡은 목록이 더 자주 보일 수 있다 — 노드를 바꿔 골라도
  목록은 다시 안 읽는다(같은 마운트).
- **편집 모드에서 페이지를 열면 코멘트 목록 조회가 하나 는다**(결정 1). 페이지 문서 조회는 그대로 한 번이다.
- Cmd/Shift 클릭이 탭을 옮기는 것은 실브라우저 케이스가 없다(하나 고르는 클릭만 잰다 — 결정 4).
- 병합 충돌 자리: `apps/web/src/panels/property-panel.tsx`(머리말 한 줄만 — gr 도 이 파일을 고친다) · `apps/web/src/panels/page-info.tsx`(머리말 한 줄 — ub 의 페이지 정보 스타일) ·
  `apps/web/src/shell.css`(«탭 몸통» 규칙 바로 뒤에 두 규칙을 더했다).
