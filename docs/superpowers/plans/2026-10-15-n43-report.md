# N43 보고 — 가드 뒤 실패 응답의 남은 낮음 둘: L-322(404 · 400 줄) · L-323(얇은 409 창)

## 결과 한 줄

**L-322 는 갈래 열아홉 곳(브리프 줄에서 푼 열일곱 + 목록 밖 둘)이 전부 재현됐고 전부 고쳤다** — 가드를 지난 뒤 잠금을 기다리는 사이 빠지거나 내려간 사람이 «페이지 · 메뉴 · 프리셋이 지워졌다 · 그 모양이다» 문장을 받던 것이, 이제 처음부터 그 자리였던 사람의 가드 응답(404 · 403)과 상태 · 본문 · 헤더가 같다. **L-323 은 둘로 갈렸다** — `PUT …/theme` 의 앞선 409 는 «설계(조치 없음)», `POST …/snapshots` 의 지문 불일치 409 는 캡처가 길어질 수 있는 창이라 재현했고 고쳤다.

## 1. L-322 — 줄을 다시 센 표

센 방법: 브리프의 라우트 다섯 파일(`comments` · `pages`(가져오기 포함) · `menu` · `presets` · `projects`)의 핸들러를 읽고, `git grep -cE 'throw notFound\('` 로 파일마다 다시 셌다(`comments` 7 · `pages` 6 · `menu` 5 · `presets` 1 · `projects` 3 — 그 가운데 **가드 뒤 잠금 대기를 지난 트랜잭션 안의 «대상이 없다»** 만 아래 표에 든다; 나머지는 트랜잭션 앞의 읽기 한 번(코멘트 PATCH · DELETE · 재번호의 `loadDocument` · `findCommentById` 등) 이거나 GET 이다). 브리프의 줄(13)이 아래 표의 갈래 17 로 풀렸고(코멘트 4 · 페이지 5 · 가져오기 1 · 메뉴 5 · 프리셋 1 · 프로젝트 1 — 페이지 · 메뉴 PATCH 가 갈래별로 갈렸다), **목록 밖 둘**(메뉴 DELETE 404 · 연쇄 DELETE 404)을 더했다.

## 2. L-323 — 얇은 409 창

**잰 방법**: `pg.Client.prototype.query` 를 감싸 질의 글자와 시각을 적었다(스크래치 탐침 — 커밋 안 함). 가드의 멤버 조회(`select "role" from "project_members" …`)부터 판정까지의 질의 목록 · 시간.

| 요청 | 가드 → 판정 사이 | 값 |
|---|---|---|
| `GET …/theme`(기준 — 읽기 라우트) | 질의 4 | **1.6 ms** |
| `PUT …/theme` 앞선 409(`rev` 불일치) | 질의 5 — `findThemePackage` · `findProjectTheme` · 뷰를 짓는 읽기 둘 | **2.7 ms** |
| `GET …/snapshot`(덤프 — 기준) | 질의 8(캡처 전부) | 3페이지 프로젝트 **4.2 ms** · 150페이지(스키마 0.6 MB 압축) **51–61 ms** |
| `POST …/snapshots` 캡처 → 지문 불일치 409 | 질의 8(같은 `captureSnapshot`) | 3페이지 **4.5 ms** · 150페이지 **54–58 ms** |

**`PUT …/theme` 앞선 409 — 설계(조치 없음) 제안.** 가드와 판정 사이에 **기다림이 없다**(잠금 · I/O · 렌더 없음 — 읽기 질의 다섯이 전부다). 간격은 기준(`GET …/theme`)과 같은 폭이다(질의 5 대 4 · 2.7 ms 대 1.6 ms — 질의 하나 차이). 그 409 가 싣는 것(`current` — 지금 테마 · 판 · 토큰 · rev)은 `GET …/theme` 가 viewer 에게 내주는 값과 같은 칸이다. 재현은 안 했다(잴 창이 없다).

**`POST …/snapshots` 지문 불일치 409 — 재현했고 고쳤다.** 이 창은 «기다림이 있다»: 캡처가 프로젝트의 페이지 · 코멘트를 전부 읽으므로 길이가 크기에 비례한다(3페이지 4.5 ms → 150페이지 54–58 ms, 약 12배). 판: 캡처의 코멘트 읽기 질의(`from "comments"`)에서 붙잡고, 그 사이 앨리스가 페이지를 편집(지문이 바뀐다)하고 밥을 빼거나 내린 뒤 놓는다. (나) 고치기 전 = 409 `conflict` «스냅샷을 뜨는 동안 프로젝트가 바뀌었습니다. 다시 시도해 주세요» · (가) = 404 / 403 — **재현**(remove · demote 둘 다 빨강).

- **고침**: 지문 불일치를 낼 때 **쓰지 않는 트랜잭션 하나**(재확인의 행 잠금만 쥔다)로 `recheckProjectRole` 을 지난 뒤 던진다(`routes/snapshots.ts`). 캡처를 트랜잭션 안으로 옮기는 길은 고르지 않았다 — 그 머리말의 «캡처와 삽입을 한 트랜잭션으로 묶지 않는다» 근거가 그대로 서 있다(큰 payload 를 든 트랜잭션이 삽입까지 열려 있게 된다).
- **어느 쪽이 좁은가**: 재확인을 409 앞에 두면 가드 → 응답 사이에서 빠진 사람이 받는 것은 «가드 응답»뿐이다(재확인의 멤버 조회 → 던지기는 잠금 대기 없이 끝난다). 판정을 트랜잭션 안으로 옮기는 길은 같은 효과에 잠금 점유 시간을 늘린다.
- **잠금 순서 값**(아래 §3 의 `POST …/snapshots · 409`): 실패 갈래가 재확인 자리에서 쥔 것 = 프로젝트 행 자유 · 페이지 행 자유(성공 갈래는 프로젝트 행 `KEY SHARE`). 새 차례가 없다 — 트랜잭션 하나뿐이라 앞에 쥔 것이 없다.
- **같은 창의 기준선**: 덤프 라우트 `GET …/snapshot` 은 **같은 캡처 구간**을 가드 뒤에 돌고 payload 전부를 돌려준다 — 재확인 없다. 이번 고침은 그 읽기 라우트의 창을 닫지 않는다(§새 이월 첫째).

## 3. 잠금 순서 — 실패 갈래가 재확인 자리에서 쥔 행이 성공 갈래의 부분집합인가

재확인의 멤버 행 질의(`"user_id" = $2 for share`)에서 붙잡고 다른 연결로 `FOR UPDATE NOWAIT`(쥔 것이 있으면 못 잡는다). 대상이 지워진 판이라 **두 단계**로 붙잡았다 — 그 쓰기의 첫 잠금 질의에서 붙잡고 앨리스가 지운 뒤, 재확인 질의를 붙잡아 놓고 처음 것을 푼다(`holdQuery` 의 칸은 붙잡힌 질의가 나가면 비므로 둘째를 걸 수 있다). 짝(대조)은 같은 쓰기가 지우지 않은 대상에 닿아 성공하는 판이다. 값은 «프로젝트 행 자유 · 페이지 행 자유»(`true` = 쥐지 않음).

| 갈래 | 실패 — 프로젝트 · 페이지 | 성공(짝) — 프로젝트 · 페이지 | 부분집합 |
|---|---|---|---|
| 코멘트 POST 404 · 재번호 404 | 자유 · 자유 | 자유 · **쥠** | 예 |
| 코멘트 PATCH 404 · DELETE 404 | **쥠**(`KEY SHARE`) · 자유 | **쥠** · **쥠** | 예 |
| 페이지 POST 404 · 가져오기 404 | 자유 · 자유 | **쥠** · 자유 | 예(세이브포인트가 되돌려 놓았다) |
| 페이지 PATCH 404 — 바탕 | 자유 · 자유 | 자유 · **쥠** | 예 |
| 페이지 PATCH 404 — 자리 옮김 · 페이지 DELETE 404 | **쥠** · 자유 | **쥠** · **쥠** | 예 |
| 페이지 PATCH 404 — 옮길 메뉴 | 자유 · 자유 | **쥠** · **쥠** | 예 |
| 메뉴 POST 404 · PATCH 404 — 새 부모 | 자유 · 자유 | **쥠** · 자유 | 예 |
| 메뉴 PATCH 404 — 바탕 | 자유 · 자유 | 자유 · 자유(제목 행만) | 예 |
| 메뉴 PATCH 404 — 자리 · 메뉴 DELETE 404 | **쥠** · 자유 | **쥠** · 자유 | 예(같다) |
| 연쇄 DELETE 404 | **쥠** · **쥠**(`lockProjectForRestore`) | **쥠** · **쥠** | 예(같다) |
| 프리셋 DELETE 404 | 자유 · 자유 | 자유 · 자유 | 예 |
| 스냅샷 409(지문) | 자유 · 자유 | **쥠** · 자유 | 예 |

18 갈래 모두 «실패가 쥔 것 ⊆ 성공이 쥔 것». **새 차례가 없다** — 실패 갈래가 새로 잡는 것은 «(그 쓰기가 이미 쥔 행) → 자격 행 → 멤버 행» 뿐이고 그 앞부분은 성공 갈래가 같은 차례로 이미 쥔다. 던지는 갈래(`ParentNotFoundError` 등)는 세이브포인트가 되돌려 쥔 것을 놓은 뒤 재확인한다(N41 의 메뉴 DELETE 와 같다). **«안 기다린다»고 적은 자리 셈**: 이번 고침이 실패 갈래에 재확인을 더한 자리는 «멤버 행 `FOR SHARE`»를 더 서게 한다 — 그 목록의 케이스(`restore-lock-census` · `guard-in-lock` · `lock-census` · `late-commit-stale` · `member-owner-recheck` · `pre-guard-hook-census`)가 포함된 전량 api 게이트(499 파일)가 통과했다. **기존 케이스가 바뀌지 않았다**(N41 의 `guard-in-lock` 다시 넣기 케이스 같은 «곧바로 끝난다» 단언이 이번 갈래에는 없었다 — `q-n43.md` 에 물음을 안 냈다).

케이스 잠금: `n41-failure-recheck.test.ts` 의 새 describe «실패 갈래의 재확인 자리 — 대상이 사라진 판의 잠금 차례 (N43)» 18 케이스(실패 값 · 성공 값 · 부분집합 단언).

## 4. 503 · 늦은 커밋

재확인이 던지면 본문이 끝나지 않아 `runConfirmedTransaction`(트리 쓰기) · `runRevisionTransaction`(코멘트 쓰기)이 롤백하고 그 `ApiError`(404 · 403 · 401)가 그대로 나간다 — 503 «모름» · 늦은 `onCommit` 이 나갈 길이 없다(N41 과 같다). 재확인 앞에서 쓴 것이 없다 — 던지는 갈래는 세이브포인트가 되돌렸고 값으로 돌려주는 갈래(`deleted === 'not-found'` 등)는 쓴 것이 없다. `POST …/snapshots` 의 새 재확인은 **캡처 뒤 · 삽입 트랜잭션 밖의 트랜잭션 하나**라 확인 콜백 · 늦은 커밋 지켜보기가 닿지 않는다(쓴 것이 없으니 «모름»이 뜻이 없다). 확인한 증거: 전량 게이트의 `late-commit-stale` · `menu-changed` 가 통과했다.

## 5. 변조 표 — 자리마다 실패 갈래의 재확인을 뗌

## 못 잰 것

- 잠금 순서의 «재확인을 잠금 앞으로 옮기는» 변조는 안 돌렸다(N41 의 못 잰 것과 같다 — 잠금 순서 케이스는 재확인을 떼면 시간 초과로만 죽는다).
- **트랜잭션 앞의 읽기 한 번 사이**: 코멘트 PATCH 의 `findPageById` · `findCommentById` 404, 코멘트 DELETE · 재번호의 `loadDocument` 404, 페이지 PATCH(제목 · 설명만)의 첫 읽기 `null`, 메뉴 PATCH(제목만)의 첫 읽기 `null`. 기다림이 없어 가드 뒤 곧바로 읽는 라우트와 같은 폭이다 — 재현하지 않았다(L-323 꼴). 페이지 · 메뉴 PATCH 의 비바탕 갈래는 재확인을 무조건으로 만들어 이 창도 덮인다(케이스는 자리를 옮기는 판만).
- `SelfParentError`(400)는 본문에서 오는 값이라 케이스를 안 세웠다 — catch 에는 들어 있다.
- 프로젝트 PATCH 의 `DuplicateSlugError` 409(다른 프로젝트가 그 slug 를 쓴다)는 트랜잭션 안에서 재확인 앞에 나간다 — **프로젝트 안의 사실이 아니라 인스턴스 전체 사실**(프로젝트 생성이 같은 충돌을 모든 로그인 사용자에게 말한다)이라 이번 범위에서 뺐다.
- 코멘트 재번호의 `!edited.ok` 실패(`applyEdit` 가 재확인 앞)는 문서에서 오는 값(잠근 문서의 번호 연산 적용 실패)이라 안 셌다.

## 지침 보고

1. **무엇이 비어 있나** — 변조 보고의 «실행 수»를 `-t` 로 좁혀 돌릴 때 vitest json 의 `numTotalTests` 는 필터가 건너뛴 케이스까지 센다(이번 실행에서 모든 변조가 120 을 냈고 실제 실행은 3~7). 지침의 «「통과」를 보기 전에 몇 개가 실행됐는지 확인한다»는 «건너뛴 수도 적는다»만 말하고 이 필터 판은 안 짚는다.
   **어느 문서 · 어느 절**: `AGENTS.md` 「검증 — wirebound」 의 «「통과」를 보기 전에 몇 개가 실행됐는지 확인한다 — 덧붙임» 끝(소스는 `.ruler/` 아래 wirebound 소유 파일).
   **넣을 문장**: «**`-t` 로 좁힌 변조 실행의 실행 수는 `통과 + 실패`로 적는다** — vitest json 의 `numTotalTests` 는 필터가 건너뛴 케이스까지 센다(120 케이스 파일에서 4 케이스를 돌려도 120). 실행 수 0 의 판정도 `통과 + 실패` 가 0 인지로 한다.»
2. **무엇이 비어 있나** — 대상이 지워진 판에서 «그 쓰기의 첫 잠금에서 붙잡고 → 대상을 지우고 → 재확인 질의에서 다시 붙잡는» 두 단계 붙잡기는 `holdQuery` 의 칸이 붙잡힌 질의가 나가면 비는 성질에 기댄다 — `pg-fault-proxy.ts` 머리말(`holdQuery`)에는 «푼 칸도 다음 같은 글자 질의 하나에 쏴지고 사라진다»만 있고 «첫 붙잡기가 걸린 뒤에는 둘째를 걸 수 있다»가 없다.
   **어느 문서 · 어느 절**: `apps/api/test/pg-fault-proxy.ts` 의 `holdQuery` 설명(테스트 지원 파일의 주석 — 지침 문서가 아니다).
