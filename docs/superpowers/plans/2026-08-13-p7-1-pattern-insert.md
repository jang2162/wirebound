# P7-1 패턴 전개 · 삽입 구현 계획

> **에이전트에게:** 태스크 단위로 실행한다. 각 태스크는 실패하는 케이스 → 최소 구현 →
> 통과 → 커밋의 순서를 지킨다.

**목표.** §6.6의 테마 패턴을 **페이지에 꽂을 수 있게** 한다. 이 슬라이스가 끝나면
*"패턴을 골라 페이지에 넣으면 테마가 정한 모양으로 전개된다"*가 참이 된다.

**§6.6:** *"패턴을 페이지에 넣으면 `schema`가 전개되고 노드 `id`가 새로 발급된다."*
`slot` 필드는 패턴 템플릿에만 존재하고, 슬롯은 *"우측 속성 패널에서 채운다."*

**§11.1:** *"패턴은 테마가 소유한 섹션 단위 레시피이고 테마를 바꾸면 다른 모양으로
재현된다. 페이지를 만들 때 프리셋으로 출발하고, 그 안에 패턴을 꽂아 채우는 것이 일반적인
흐름이다."*

**P7을 셋으로 나눈다.** ① 패턴 전개·삽입(이 슬라이스) → ② 페이지 프리셋 → ③ 페이지 JSON
가져오기/내보내기. **①이 *"노드 트리를 페이지에 꽂는다"*는 경로를 세우고 ②가 그것을
재사용한다.** ③은 파일 경계·봉투 버전·코멘트 동반이 붙어 성격이 다르다.

**스택.** `packages/themes`(전개) · `apps/web`(고르개·삽입) · vitest.

---

## 전역 제약

- **워크트리 안에서만 작업한다.**
- `pnpm test` · `pnpm typecheck` · `pnpm build`가 마지막에 전부 통과해야 한다.
  **종료 코드는 파이프 없이 따로 찍어라** — `| tail`을 붙이면 `$?`가 tail의 것이 된다.
- **api 테스트는 Postgres 하나(포트 5433)를 공유한다.** 컨테이너를 새로 띄우지 마라.
- **`git checkout --`을 쓰지 마라.** python 치환으로 심고 `finally`에서 원본 전문을 되쓴다.
  **`git diff`로 확인하지 마라** — 새 파일은 untracked라 늘 비어 있다. **파일 내용으로** 본다.
- **0 사망이 나오면 그렇다고 보고해도 된다. 다만 원인을 단정하지 마라** — P6-1에서
  *"구조적으로 구분할 수 없다"*가 거짓이었고 리뷰어가 둘 다 죽였다. **불변량을 재는 케이스는
  그 불변량이 고정하지 않는 축을 잴 수 없다.** 못 죽였으면 **겨냥을 바꿔 다시** 재라.
- **세는 단위를 문장으로 못박아라.** P6-2에서 이 실수가 **세 번** 났다 — 라우트 "아홉"이
  실제 열넷, 표 "24줄"이 실제 25줄, 그리고 계수 스크립트가 대괄호를 먼저 세어 0을 냈다.
  **숫자를 산문에 적는 순간 그 수만 검사 바깥에 남는다**(P6-2가 그렇게 적어 뒀다).
  가능하면 숫자를 **실행되는 케이스**가 만들게 하라.
- **측정이 예상과 다르면 대상이 아니라 측정 장치를 먼저 의심하라.** 의심했으면 같은 장치를
  다시 돌리지 말고 **다른 장치로** 재라. **한 번 관측한 것이 flake일 수 있다.**
- **비율을 적을 때는 파라미터를 함께 적어라** — P6-2에서 같은 레이스가 2/12와 12/12로 갈렸고
  둘 다 참이었다(속도의 성질이었다).
- **설계 문서(`docs/superpowers/specs/*`)는 고치지 않는다.** 어긋나면 판정해 보고한다.
- **`apps/web`에 새 런타임 의존을 더하지 않는다.**
- **남이 잰 값은 귀속을 붙여 옮긴다.**

## 이 계획이 딛고 선 사실

| # | 사실 | 누가 쟀나 |
|---|---|---|
| 1 | **`remapNodeIds`가 이미 `schema`에 있다** — 트리 전체에 새 id를 발급하고 **트리 안을 가리키던 상호작용 `target`도 함께 바꾼다.** 주석이 *"가져오기·프리셋 적용·패턴 삽입에서 쓴다"*고 자기 소비자를 적어 뒀다 | 내가 `tree.ts:50`을 읽었다 |
| 2 | **전개는 아직 0건이다.** `spec/patterns.ts`가 *"전개는 만들지 않는다(D7) — 이름·슬롯 계약·`schema` 조각의 정합성까지다"*라고 적어 두었다 | 같은 파일 |
| 3 | **`ResolvedTheme.patterns`가 `ReadonlyMap<string, ThemePattern>`으로 이미 실린다** | `resolved.ts:52` · `resolve/index.ts:97` |
| 4 | **시스템 테마 다섯 중 패턴을 가진 것은 둘이다** — `portal`의 `content.noticeBoard`(슬롯 `title`·`keyword`), `commerce`의 `content.product`(슬롯 `image`·`title`·`price`·`cart`). **나머지 셋은 0개다** | 내가 셌다. **워커가 다시 세라 — 세는 단위는 `patterns` 키 하나다** |
| 5 | **`PatternNode`에는 `id`가 없고 `marker`·`interactions`도 받지 않는다** — 규격이 그렇게 정했다(§6.6) | `spec/patterns.ts:60` |
| 6 | **슬롯 타입은 노드 타입과 대조하지 않는다.** §16이 그 체계를 열어 뒀고, 지금 대응표를 지어 넣으면 이 단계가 그것을 닫는다 | `spec/patterns.ts:35` |

## 확정한 결정

### D1. **전개는 `themes`가 소유한다**

`spec/patterns.ts`가 *"전개는 만들지 않는다"*고 미뤄 둔 자리가 여기다.

| 후보 | 왜 아닌가 |
|---|---|
| `packages/schema` | `ThemePattern`을 모른다. 알게 하면 `schema → themes` 역방향 의존이다 |
| `apps/web` | **P8(exporter)·P9(MCP)가 못 쓴다.** 패턴 삽입은 에이전트가 할 일이기도 하다(§12) |
| **`packages/themes`** ✅ | `schema`에 의존하므로 `WbNode`를 만들 수 있고, 방향이 맞다 |

### D2. **전개는 `slot`을 결과에 남기지 않는다**

`WbNodeSchema`는 strictObject다 — 선언 안 된 키가 있으면 파싱이 죽는다(**내가 안 읽고
가정했다. 재라 #1**). `slot`은 템플릿에만 있는 필드이므로(사실 5) 전개 결과에서 **사라져야
한다.**

### D3. **슬롯은 채우지 않는다 — 어느 노드가 그 슬롯인지만 돌려준다**

§6.6은 슬롯을 *"우측 속성 패널에서 채운다"*고 했다. 그런데 **슬롯 값이 노드의 어느 `prop`에
들어가는지는 규격에 없다.**

**여기서 대응표를 지어 넣지 않는다.** 넣으면 §16이 열어 둔 *"패턴 슬롯 타입 체계 — 실제
패턴을 만들며 필요한 타입을 확정한다"*를 이 단계가 닫는 것이고, `spec/patterns.ts`가 같은
이유로 대조를 거부한 것과 정면으로 어긋난다(사실 6).

**그래서 전개의 결과는 둘이다:**

```
{ nodes: WbNode[], slots: Map<슬롯이름, 새 노드 id> }
```

저작 UI는 *"이 슬롯이 이 노드다"*를 알고 **이미 있는 속성 패널로** 채운다. 새 규격을 만들지
않고 §16도 열어 둔 채로 둔다.

**슬롯 이름이 `slots` 선언에 없는 노드에 붙어 있으면 그것은 오류다** — 패턴 저작의 실수이고
`checkPatterns`가 이미 볼 수도 있다(**재라 #3**). 전개가 조용히 무시하지 않게 하라.

### D4. **삽입은 기존 편집 경로를 탄다 — 새 엔드포인트를 만들지 않는다**

패턴 삽입은 결국 `add` op 몇 개다. 웹의 기존 커밋 경로(`use-edit-commit`)를 그대로 쓰면
**undo·낙관적 편집·경고 표시가 전부 공짜**로 따라온다. 서버는 `applyEdit` 하나로 끝나고
`revisions`에도 평범한 편집으로 남는다.

**새 API를 만들면** 그 경로가 `applyEdit`을 다시 부르는 두 번째 쓰기 자리가 되고, P2a가 D1을
위해 없앤 것을 되살리는 방향이다.

### D5. **꽂는 자리 — 선택 노드의 자식 끝, 자식을 못 받으면 형제 뒤**

- 선택이 없으면 root의 자식 끝.
- 선택된 노드가 자식을 받을 수 없으면 **그 노드 바로 뒤 형제로** 꽂는다. 거부하지 않는다 —
  사용자가 *"여기쯤"*을 가리킨 것이고, 거부는 어디를 눌러야 할지 알려 주지 않는다.
- **카탈로그가 자식 허용 여부를 안다고 가정하지 마라(재라 #6).** 어떻게 아는지 먼저 재고,
  알 수 없으면 그 사실을 보고하고 규칙을 다시 정하라.
- **패턴의 노드가 여럿이면 전부 같은 자리에 순서대로 꽂는다.**

### D6. **`marker`는 따라오지 않는다 — 구조가 보장하지만 케이스로 고정하라**

`PatternNode`가 `marker`를 안 받으므로(사실 5) 전개 결과에 marker가 있을 수 없다.
**그래도 케이스로 고정한다.** 이 저장소는 *"문서에 marker가 있는데 코멘트 행이 없다"*를
이미 만났다(P5-1의 고아 marker). 규격이 지켜 주는 성질도 **누가 지키는지 적혀 있지 않으면
다음 사람이 깬다.**

### D7. **패턴이 0개인 테마가 정상이다 — 화면이 그렇게 말한다**

시스템 테마 다섯 중 셋이 패턴을 갖지 않는다(사실 4). **버튼을 회색으로 만들어 두지 말고,
*"이 테마에는 패턴이 없습니다"*를 보여라** — 없다는 것과 고장난 것을 사용자가 갈라야 한다.

**패턴을 새로 만들어 넣지 마라.** 그것은 테마 저작(§6.10·P4c)의 일이고, `portal`·`commerce`
둘로 이 슬라이스를 실증할 수 있다.

### D8. **고르개는 구조 툴바에 붙는다**

컴포넌트 고르개(`panels/type-picker.tsx`)와 나란한 성격이다 — *"무엇을 넣을까"*를 고르는
자리다. 새 패널을 만들지 말고 그 옆에 둔다.

목록이 보여야 하는 것: 패턴 이름(`name`) · 범주(키의 앞부분) · 슬롯 이름들.

### D9. **전개가 만든 문서가 유효해야 한다 — 그러나 이 슬라이스가 그것을 보증하지 않는다**

꽂은 뒤 `validatePage`가 보고(파이프라인 6단계), `error`가 있으면 편집이 422로 거부된다.
**패턴 자체가 카탈로그에 없는 타입을 담고 있으면 그 순간 사용자는 아무것도 못 꽂는다.**

그것은 **테마 저작의 문제**이고 `checkThemePatterns`가 저장 경로에서 이미 볼 수 있다
(**재라 #3**). 이 슬라이스는 **그 상태가 어떻게 나타나는지를 재서 보고**하고, 화면이
*"패턴이 잘못됐다"*와 *"내가 잘못 눌렀다"*를 가르게 한다.

## 태스크

### T1. 전개 — `themes`

**파일:** `packages/themes/src/pattern/expand.ts`(신규) · `packages/themes/src/index.ts`(수출)

- `ThemePattern` → `{ nodes, slots }`. D2·D3.
- **실패하는 케이스 먼저.** 최소한 이 넷을 각각 케이스로 잡아라:
  `slot`이 결과에 없다 · 새 id가 매번 다르다 · `slots` 매핑이 실제 노드를 가리킨다 ·
  선언 안 된 슬롯 이름은 오류다.
- id 발급은 **주입 가능**해야 한다(`schema`의 `remapNodeIds`가 `generate`를 받는 것과 같다).
  안 그러면 케이스가 결과를 고정할 수 없다.

### T2. 전개 결과가 문서에 들어갈 수 있는가

**파일:** `packages/themes/test/pattern-expand.test.ts`

- `portal`·`commerce`의 실제 패턴 둘을 전개해 **`validatePage`가 통과하는 문서**가 되는지
  재라. 안 되면 **원인을 판정해서 보고하라** — 고치는 자리가 이 슬라이스 안일 수도, 테마
  쪽일 수도 있다.
- D6(marker 없음)을 여기서 고정한다.

### T3. 고르개

**파일:** `apps/web/src/panels/pattern-picker.tsx`(신규) · `structure-toolbar.tsx`(수정)

- D7·D8. 패턴 0개 상태를 케이스로 고정하라.

### T4. 삽입

**파일:** `apps/web/src/edit/`(삽입 ops) · 기존 커밋 경로 재사용

- D4·D5. **꽂은 뒤 선택이 어디로 가는지 정하고 케이스로 고정하라** — 슬롯을 채우려면
  사용자가 그 노드를 골라야 한다(D3). 아무 데도 안 가면 D3의 흐름이 끊긴다.
- **실패 갈래마다 *"이 갈래는 무엇을 되돌리는가"*를 답하라**(P6-1 이월 §6의 규칙).
  낙관적 편집이 실패하면 화면의 문서가 되돌아가는지, 알림이 남는지.

### T5. 구분력 실증 · 회귀 · 보고

- 변이를 심어 각 케이스가 **실제로** 죽는지 확인하고 복구한다. `git status`로 확인한다.
- 재라 표 일곱을 각각 재서 판정한다.
- `pnpm test` · `pnpm typecheck` · `pnpm build` — **종료 코드를 파이프 없이 따로.**
- 보고서 `docs/superpowers/plans/2026-08-13-p7-1-report.md`.

## 계획이 재지 않은 것

- **페이지 프리셋** — P7-2. 이 슬라이스가 세운 삽입 경로를 재사용한다.
- **페이지 JSON 가져오기/내보내기** — P7-3. **P6-2 이월 §1·§2·§8이 전부 그것을 겨냥한다**
  (복원 전용 repo 함수 여섯을 쓰면 안 된다 · `sort_order` 전제 · 파이프라인 실패는 던진다).
- **슬롯 값이 어느 `prop`에 들어가는가** — §16이 열어 둔 자리다(D3).
- **새 패턴 저작** — 테마 저작(§6.10)의 일이다(D7).
- **WebSocket 알림** — P3이 0건이다.
