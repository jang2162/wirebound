## 쓰기 × 잡는 행 · 모드 · 차례

«재확인» 은 `recheckInstanceAdmin` — 요청자 사용자 행 `FOR SHARE` → 자격 행(세션 · 토큰) `KEY SHARE`. 잠금 함수가 이미 요청자 행을 쥐었으면 같은 행을 다시 잡는다.

| 쓰기 | 차례 |
|---|---|
| 비활성화 | 대상 `FOR NO KEY UPDATE` · 요청자 `FOR SHARE`(id 순) → 재확인 → `users` 고침 → 그 사람이 만든 초대 · 재설정 링크 거둠(`UPDATE`) → 그 사람에게 만든 재설정 링크 막음 → 세션 `DELETE` → 토큰 `DELETE`(id 순) → 기록 |
| 다시 활성화 · 관리자 지정 | 대상 · 요청자(id 순, 위와 같은 모드) → 재확인 → `users` 고침 → 기록 |
| 관리자 해제(API · 명령) | 대상 · 요청자(id 순) → 재확인 → `users` 고침 → 그 사람이 만든 링크 거둠 → 기록. 명령은 요청자 · 재확인 없이 대상 행부터 |
| 재설정 링크 만들기 | 대상 · 요청자(id 순) → 재확인 → 그 사람의 앞 링크 막음(`UPDATE`) → 삽입 → 기록 |
| 초대 만들기 | 재확인 → 삽입 → 기록 |
| 초대 거두기 | 재확인 → 링크 행 `FOR UPDATE` → 고침 → 기록 |
| 가입 | 링크 행 `FOR UPDATE` → 상태 · 만든 사람(잠그지 않고 읽음) → 사용자 삽입(`invite_id` FK `KEY SHARE`) → 기록 → 세션 삽입 |
| 재설정 링크 쓰기 | 링크를 잠그지 않고 읽어 대상을 앎 → 대상 행 `FOR NO KEY UPDATE` → 링크 행 `FOR UPDATE` → 다시 봄 → 비밀번호 고침 · 세션 `DELETE`(`replacePassword`) → 씀 표시 → 기록 |
| owner 넘기기 | 요청자 · 대상 `FOR SHARE`(id 순) → 재확인 → 프로젝트 행 `KEY SHARE` → 대상의 그 프로젝트 토큰(id 순) → owner 행 → 삽입 · 고침 → 기록 |
| 테마 올리기 · 숨기기 · 되살리기 | 바뀌지 않았다(쓰기 → 재확인) — 기록 삽입만 더했다 |
| 로그인 | 사용자 행 `FOR SHARE`(해시 · 비활성 표시를 한 문장에서) → 세션 삽입 |
| 세션 조회(«마지막 접속») | 1 분에 한 번 사용자 행 `FOR NO KEY UPDATE SKIP LOCKED` — 쥔 쓰기가 있으면 건너뛴다(기다리지 않는다) |

## 결정과 이유

1. **관리자 쓰기의 잠금 차례 — 사용자 행(id 순) → 재확인 → 링크 · 세션 · 토큰 · 프로젝트 행.** 대상 행은 `FOR NO KEY UPDATE`, 요청자 행은
   `FOR SHARE` 이고 한 함수(`repos/users.ts` 의 `lockUserRows`)가 id 순으로 잡는다. `FOR UPDATE` 가 아닌 까닭: 그 사람의 진행 중인 편집 · 코멘트의
   FK 검사(`KEY SHARE`)와 안 부딪혀야 비활성화가 그 쓰기를 사용자 행에서 안 기다린다(세션 `DELETE` 에서 기다린다 — 고리 없음).
2. **재확인(`recheckInstanceAdmin`)을 쓰기 앞에 둔다 — 계획 «공통 제약» 의 «쓰는 문장 뒤» 와 다르다.** 테마 라우트는 잡는 행이
   `theme_packages` 하나라 뒤여도 되지만, 링크 · 사용자 행을 고치는 쓰기에서 뒤에 두면 «링크 행 → 사용자 행» 이 되어 비활성화(«사용자 행 →
   링크 행»)와 고리가 선다 — M-A4j 가 교착 +1 로 잰다. 재확인이 잡은 잠금(요청자 행 `FOR SHARE` · 자격 `KEY SHARE`)은 커밋까지 쥐므로 판정은
   여전히 커밋 순간의 것이다. 테마 라우트는 그대로 두었다(기록만 더했다).
3. **«마지막 관리자» 는 «활성 관리자 행 전부를 id 순 `FOR UPDATE`» 로 잡지 않았다(계획 A5 와 다르다).** 해제 · 비활성화는 요청자가 관리자이고
   대상과 다를 때만 서고, 요청자 행을 `FOR SHARE` 로 쥔 채 재확인이 «관리자» 를 보고 커밋하므로 커밋 순간에도 요청자는 관리자다 — 관리자가
   0 이 되는 판이 없다. 서로를 동시에 해제하는 둘은 두 행을 id 순으로 잡아 줄을 서고 뒤 요청은 재확인에서 403 이다(A5 케이스). 모든 관리자
   행을 잡으면 관리자 쓰기 전부가 서로를 세운다. 활성 관리자 수 검사(`LAST_ADMIN`)는 겹으로 남겼다 — 혼자인 관리자의 자기 해제 · 비활성화를
   자기 자신 검사보다 뒤에서 받는다(M-A4i).
4. **링크를 쓰는 쓰기(가입 · 재설정 쓰기 · 거두기)는 만든 사람의 행을 잠그지 않고 읽는다.** 비활성화 · 해제가 «사용자 행 → 링크 행» 으로
   거두므로 링크 행이 차례를 세운다(`repos/invites.ts` · `repos/password-resets.ts` 머리말 «잠금»).
5. **재설정 링크 쓰기는 «대상의 사용자 행 → 링크 행»** — 링크를 잠그지 않고 읽어 대상을 알아낸 뒤 그 행부터 잡는다. 링크 행을 먼저 잡으면
   대상의 비활성화(«사용자 행 → 링크 행»)와 고리다. 새 링크 만들기도 대상 행을 `FOR NO KEY UPDATE` 로 잡아, 같은 사람에게 동시에 만든 둘 가운데
   하나만 산다.
6. **«마지막 접속»(`users.last_seen_at`)은 세션 조회가 1 분에 한 번, `SKIP LOCKED` 로 고친다.** 요청마다 사용자 행을 기다리며 고치면 그 행을
   쥔 쓰기(관리자 재확인 · 로그인 `FOR SHARE` · 비밀번호 바꾸기 · 비활성화)가 도는 동안 같은 사람의 모든 요청이 인증에서 선다 — 지금 케이스
   (`auth-password-review.test.ts` 의 «로그아웃 × …» 는 «안 기다린다» 를 든다)가 그 판이다. `GET /users` 의 `lastSeenAt` 은 사용자 행과 살아 있는
   세션 중 늦은 것이다.
7. **링크가 쓸 수 있는가에 «만든 사람이 지금 활성 관리자» 를 넣었다**(계획 A3 그대로). 비활성화 · 해제가 링크를 거두므로 겹이다 — 서버
   명령의 해제도 같은 함수(`applyInstanceAdmin`)라 링크를 거둔다. 서버 명령의 지정은 비활성 계정을 거절한다(`'inactive'` — 종료 1).
8. **재설정 쓰기의 한도 계정 키** — 쓸 수 있는 링크면 대상 이메일(계획), 못 쓰는 링크면 원문 해시(`reset:<hash>`). 대상이 없는 판에 이메일 키를
   지을 수 없어서다.
9. **기록의 `next` 는 마이크로초까지 적은 ISO 다** — `at` 이 `clock_timestamp()` 라 밀리초로 자르면 같은 밀리초의 앞선 줄이 다음 쪽에서 빠진다.
10. **owner 넘기기의 차례** — 사용자 행(요청자 · 대상 `FOR SHARE`, id 순) → 재확인 → 프로젝트 행 `KEY SHARE` → 대상의 그 프로젝트 토큰(id 순) →
    owner 행. 토큰이 owner 행보다 먼저인 것은 멤버 제거 · 프로젝트 삭제와 같은 차례다. 프로젝트 행은 `KEY SHARE` 라 삭제(`FOR UPDATE`)와 줄을 선다.
11. **owner 넘기기의 파라미터 이름은 `:id` 다**(계약 표는 `:projectId` 로 적었다 — HTTP 경로는 같다). 인증 훅(`auth/plugin.ts`)은 `:projectId` 라는
    **이름**을 가진 라우트에서 API 토큰을 받는다. 그 이름이면 관리자의 그 프로젝트 토큰으로 넘기기가 섰다(아래 «잰 값»). 핸들러에서 토큰을 거절하는
    겹(`requireSessionUser`)을 더하는 길도 있었지만, 다른 관리자 라우트와 같은 기전(토큰이 사람을 안 채움)으로 맞추는 쪽이 한 벌이다.

## 잰 값

- **토큰 결함(전량 api 판이 찾음)** — owner 넘기기가 `/projects/:projectId/owner` 였을 때 관리자의 API 토큰(그 프로젝트 viewer)으로 `POST` 가 **200**
  이었다(재현 케이스 «owner 넘기기는 세션 전용이다» — 고치기 전 `+ 200` / 기대 401). 이름을 `:id` 로 바꾼 뒤 401 · 역할 그대로(`viewer`), 파일 10/10.
- **동시 가입(한 번짜리 링크, 둘이 링크 행에 줄 선 판)** — `[201, 404]` · 사용자 1. 줄 선 것은 `pg_blocking_pids` 사슬로 확인했다.
- **서로를 동시에 해제하는 두 관리자** — `[200, 403]` · 남은 관리자 1. 두 겹(재확인 · 활성 관리자 수)은 각각 혼자 막는다(M-A5a · b 각 5/5 안 죽음),
  둘 다 떼면 관리자 0(M-A5c).
- **링크 거두기의 재확인 자리** — 쓰기 뒤에 두면 비활성화와 교착 1(M-A4j), 앞에 두면 0.

   `nohup nice caffeinate -i <스크립트> & disown` 으로 띄우면 그룹은 띄운 셸이 만든 것이라(이 판: pid 72811 · 그룹 72714) `kill -- -72811` 은 아무것도 안 내리고
   전량 테스트가 계속 돌았다. 어디: `.ruler/30-delegation.md` 「변이마다 전량을 돌리게 하지 않는다 …」 문단의 «멈출 때는 스크립트가 아니라 그 프로세스 그룹을
   내린다» 문장. 넣을 문장(괄호를 바꾼다): «(띄울 때 `echo "$(ps -o pgid= -p $$ | tr -d ' ')" > <상태>` 로 **그룹 id** 를 적고 `kill -- -<pgid>` — `$$` 는
   스크립트 셸의 pid 라 그룹 id 와 다르다. 내린 뒤 `ps -eo pid,pgid,command | awk '$2==<pgid>'` 가 비었는지 본다)».
3. **새 테스트 도우미의 타입** — 무엇이 빠졌나: 트랙이 세운 공용 도우미가 `inject` 의 `payload` 를 `unknown` 으로 받아 typecheck 130 오류가 났는데 케이스는
   전부 초록이었다(vitest 는 타입을 안 본다). 함정은 `apps/api/test/snapshots.test.ts` 머리말에만 있다. 어디: `.ruler/20-verification.md` 「`apps/*` · … 에
   `tsconfig*.json` 을 새로 두지 않는다」 앞에 새 절, 또는 「통과를 보기 전에 …」 덧붙임. 넣을 문장: «**api 케이스의 `inject` 를 감싸는 도우미는 `payload` 를
   `unknown` 으로 받지 않는다** — `inject` 오버로드 셋의 교집합으로 떨어져 호출부의 `.statusCode` · `.json()` 이 전부 타입 오류인데 vitest 는 초록이다
   (`apps/api/test/snapshots.test.ts` 머리말). `Record<string, unknown>` 으로 받고, 도우미를 세운 커밋에서 `pnpm typecheck` 를 한 번 돈다.»
