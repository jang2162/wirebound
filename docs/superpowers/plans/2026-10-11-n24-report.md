# N24 보고 — 늦게 커밋된 편집 · 게시의 `page-stale` 프레임(서버 + 웹 원자적 · L-106 · L-278 · L-114)

브랜치 `feat/n24-stale`(main `3f254528` 위) · 범위 `apps/api` · `apps/web` · 정본 문서(`apps/api/README.md` · 설계서). 서버와 웹을 한 브랜치로 넣었다 — 한쪽만 병합되면 효과가 없다(웹 파서는 모르는 프레임을 `null` 로 버리고 서버만 있으면 보낼 곳이 없다). 두 앱에 걸쳐 README 「트랙 게이트」 표의 «else full» 이다.

**값의 출처 표기.** «실서버» 는 `withProxiedRealApi`(api + Postgres + TCP 프록시) 의 값이다. «jsdom» 은 `apps/web/test` 값이고 실브라우저 값이 아니다. «Chrome» 은 `apps/web/build-test`(헤드리스 Chrome + 일회용 DB · api · vite) 값이다. 이 기계에서 도는 다른 일은 없었다.

**한 줄 요약.** 답을 잃은 편집 · 게시의 COMMIT 이 확인 한도(1s)를 넘겨 **늦게** 커밋되면 서버가 번호 없는 `page-stale { projectId, pageId }` 를 룸 전체에(낸 연결도) 보낸다. 웹은 열린(또는 여는 중인) 페이지의 신호면 «이 페이지에 늦게 반영된 변경이 있어 화면이 최신이 아닙니다» 경보를 세우고 «다시 불러오기» 가 **그 페이지만** 다시 읽는다. 그 revision 의 `page-changed` 는 늦게 내지 않는다.

## 1. 재현 — 입구마다(고치기 전 값)

장치: COMMIT 을 3s 늦춤(`revisions` 에 걸린 `DEFERRABLE INITIALLY DEFERRED` 제약 트리거의 `pg_sleep`) + api 쪽 연결만 끊음(`halfCutOnQuery('commit')`). 구경꾼 = 같은 프로젝트의 다른 멤버의 WS 연결. 고치기 전 소스(HEAD `3f254528`)에서 스크래치 케이스로 쟀다(코드에 안 남김).

| 입구 | 응답 | 3s 뒤 `head_seq` | 구경꾼이 받은 프레임(응답 뒤 4.5s) |
|---|---|---|---|
| **편집** `PATCH …/ops` | **503** | 1 → **2**(커밋됨) | `locks` — **`page-changed` 0** |
| **게시** `POST …/comments` | **503** | 1 → **2**(커밋됨) | `presence` · `locks` — **`page-changed` 0** |
| **복원** `POST …/snapshots/:id/restore` | **503** | (안전망 스냅샷 행이 생김 — 스냅샷 1 → **2**, 커밋됨) | **없음 — `restored` 0** |

나머지 입구(WS `patch` · `PUT …/schema` · 코멘트 삭제 · 재번호)는 고치기 전 값을 따로 안 쟀다 — 같은 `runEditTransaction` / `runRevisionTransaction` 을 지나고 그 둘이 늦은 커밋 갈래에서 아무것도 안 부르는 것이 원인이다(`services/lost-commit.ts` 의 `late` 가 없었다). 대신 **고침을 변조로 되돌린 판의 값**이 그 «고치기 전»이다(아래 S1a · S1b · S2 — 열 입구 모두 «커밋은 됐고(머리 +1) `page-stale` 목록은 `[]`»).

## 2. 고침

### 서버

- `ws/protocol.ts` — `ServerFrame` 에 `{ type: 'page-stale'; projectId; pageId }`. **번호 · `actor` 를 안 싣는다.**
- `ws/notify.ts` — `notifyPageStale`(룸 전체 · **낸 연결을 빼지 않는다** — 빼면 답을 잃은 탭이 제 다시 읽기보다 늦게 커밋된 편집을 모른 채 낡는다 · CLAUDE.md 「답을 잃은 쓰기에 세운 경보」) · `pageStaleOnLateCommit(app, projectId, pageId)` — 늦은 커밋 지켜보기(`app.lateCommits`)에 넘기는 `{ watch, onCommit }`. **서버가 지은 값(프로젝트 · 페이지 id)만 싣는다** — 요청이 실은 클라이언트 id 를 판정에 안 쓴다.
- `services/lost-commit.ts` — `runRevisionTransaction` · `runEditTransaction` 이 `late: LateCommitSignal | null` 을 **필수 인자**로 받는다(컴파일이 새 호출자의 빠뜨림을 막는다 — 호출자 전수 세기를 타입이 한다). 늦은 커밋 갈래(`settled === null`)가 `late.watch.add` 로 지켜보다 커밋되면 `late.onCommit`.
- 호출 자리 4 — `routes/pages.ts` 2(`PUT …/schema` · `PATCH …/ops`) · `ws/patch.ts` 1 · `routes/comments.ts` `runWrite` 1(게시 · 삭제 · 재번호가 공유). `git grep -nP 'runEditTransaction\(|runRevisionTransaction\(' -- apps/api/src` 로 센 호출자 4(정의 제외) — 전부 `late` 를 넘긴다(`null` 0).

### 웹

- `realtime/protocol.ts` — `page-stale` 파서. `projectId` · `pageId` 가 글자가 아니면 `null`, 모르는 필드(`seq` · `actor` …)는 안 옮긴다.
- `store/editor-store.ts` — `RemoteStale.reason` 에 `'late'`. 세기 `gap 1 < diverged 2 < late 3 < restored 4`(**원인이 증상을 덮는다** — 뒤따르는 갭 · 갈라짐은 늦은 변경의 결과일 수 있다). `markPageStale(pageId)` · `confirmPageFresh(pageId, ticket)` · `#lateKept` · `#lateAt`(페이지 → «신호 때까지 시작한 조회 수»).
- `shell/remote-alert.tsx` — 문장 «이 페이지에 늦게 반영된 변경이 있어 화면이 최신이 아닙니다.» + «다시 불러오기». **누가 썼는지 말하지 않는다**(신호가 모른다 — CLAUDE.md 「경보 문장이 누가 했는지를 말하면 그것도 같은 잣대다」).
- `routes/editor.tsx` — 셸의 `lateToken` + `CanvasFrame` 의 늦은 변경 이펙트: **그 페이지만** 다시 읽는다(트리 · 코멘트 · 테마는 안 읽는다). 복원 신호(`restoredToken`) · 재연결 신호(`resyncToken`)를 재사용하지 않는다 — 앞의 것은 프로젝트 전체를 다시 읽고 뒤의 것은 실패를 조용히 두고 앞머리가 «연결이 다시 붙어»다.
- 정본 — `apps/api/README.md` 프레임 표 · 「COMMIT 답을 잃은 편집」 절 · 설계서 실시간 절(`page-stale` 한 항목). 지금 참인 것만 적었다.

## 4. 변조 표(구분력)

모든 변조는 `백업(경로 전체 이름) → 한 곳 치환(맞은 수 1 — 아니면 건너뜀) → 해당 파일만 돌림 → 바이트 복원(복원 뒤 `bytes ==` 참)`(스크래치 스크립트, `git checkout` 안 씀). 34 건 + 재실행 9. **죽은 케이스는 실패 값으로 적었다**(아래 «시간 초과» 표시만 시간으로 죽은 것). 서버 변조는 `late-commit-stale.test.ts`(14) 만, 웹 변조는 `store/page-stale` · `shell/page-stale-alert` · `realtime/protocol`(75) 만, Chrome 은 `editor-late-commit`(1) 만 돌렸다 — 변조마다 전량은 안 돌렸다.

**처음 돌린 서버 «신호가 안 온다» 변조(S1a · S1b · S2 · S3 ~ S7)는 모두 시간 초과(`waitForCount` 의 9.5s «page-stale 프레임이 1개까지 차지 않았습니다»)로 죽었다 — 단언 값이 아니다.** 그래서 케이스를 고쳤다: 커밋은 DB 의 `head_seq` 값으로 기다리고(`committed`) 프레임은 던지지 않는 짧은 기다림 뒤 `toEqual` 로 견준다(`expectStale`) — 안 오면 `expected [] to deeply equal [{ type: 'page-stale', … }]` 로 죽는다. 아래 표는 고친 케이스로 **다시 돌린** 값이다(처음 돌린 값은 따로 안 적는다).

## 6. 복원 — 재현은 했고 코드는 안 바꿨다(Q1 에 답 없음)

고치기 전 값은 위 표대로 «503 · 커밋됨 · `restored` 0». **`page-stale { pageId }` 를 복원에 쓰면 거짓 경보가 선다** — 복원은 메뉴 · 페이지 여럿 · 코멘트 · 설명 · 테마를 한꺼번에 바꾸는데 그 신호의 단추는 페이지 하나만 다시 읽는다(CLAUDE.md 「경보의 단추가 다시 읽는 것 전부가 거두는 조건 안에 들어야 한다」의 거울 — 낡은 트리 · 코멘트가 조용히 남는다).

**권고 (가):** 늦은 커밋이 확인된 복원은 제때 커밋과 같은 꼬리(`restored` + `menu-changed` + 지운 페이지 잠금 놓기 + 테마)를 낸다. `restored` 프레임은 `seq` 를 안 실어(번호 이음이 없어) 늦게 내도 순서가 안 틀어진다 — 장부의 «복원의 방송은 번호 프레임이라 늦게 못 낸다» 는 편집 · 게시에만 맞고 복원에는 안 맞다. 웹은 «답을 잃은 내 복원의 늦은 신호» 를 이미 알아본다(`EditorStore.markRestored` · `#lostRestores`). 구현 자리: `routes/snapshots.ts` 의 복원 라우트가 `runConfirmedTransaction` 에 `late` 를 넘기고 꼬리를 함수로 뺀다(`menuRev` 는 트랜잭션 안에서 이미 지은 값 — `menu-changed` 는 멱등이라 늦게 옛 번호를 내도 받는 쪽이 넘긴다). 질문 파일 `q-n24.md` Q1 에 (가) · (나) · (다)를 적었고 답이 없어 «(다) 이번 차수에서 안 한다» 로 갔다.

## 7. L-114 — `actor` 읽는 자 세기와 권고

`page-stale` 에는 `actor` 를 안 실었다(읽는 자가 0 이므로). 기존 프레임의 `actor` 는 이번 차수에서 안 뺐다.

- **N24-2 게시: 한도 안에 커밋이 확인됐는데(503 «모름») 아무 신호도 안 나간다**(낮음 — 웹은 같은 키 재전송의 재생이 번호 프레임을 낸다) — 실서버 값: `dropCommitReplyAfter('insert into "revisions"')` 로 게시 → **503 · `head_seq` +1(커밋됨) · 구경꾼 프레임 `presence` · `locks` 뿐**(`page-changed` · `page-stale` 0). 같은 키로 다시 보내지 않는 클라이언트(MCP · CLI)는 남의 화면이 다음 변경의 `seq` 건너뜀까지 낡는다. 방향: `runConfirmedTransaction` 이 `settled === 'committed'` 인데 `confirm` 이 `null` 이면(게시는 `revisionOf` 가 없다) `late.onCommit` 을 그 자리에서 부른다 — 번호 없는 신호라 순서 걱정이 없다. 웹의 같은 키 재전송 재생과 겹치면 경보가 남는다(필요 없는 경보 · 위 표).

## 11. 이 판이 안 잰 것

- **복원의 늦은 커밋 신호** — 위 「복원」.
- **Chrome 으로 떠났다 돌아온 페이지 · 게시 재생과의 겹침 · 경보가 선 채 친 편집의 409 수습** — 스토어 · 코드 읽기 값만 있다.
- **WS 로 끊긴 구경꾼이 늦은 커밋 전에 다시 붙는 판** — 재연결 재조회가 읽는다고 코드로만 안다(이 변경 밖).
- **`page-stale` 이 폭주하는 판**(늦은 커밋이 수백 개) — 서버는 늦은 커밋마다 한 프레임이라 지켜보기 마감(30s) 안에서 일 수 있는 만큼이고, 웹은 멱등이다. 부하는 안 쟀다.
- **경보 문장 접근성**(`role="status"`) — `RemoteAlert` 의 기존 규칙을 따랐고 따로 안 쟀다.
