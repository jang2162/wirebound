# P1 서버 API 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 로그인해서 프로젝트를 만들고, 멤버를 초대하고, 메뉴 트리를 짜고, 페이지를 만들어 스키마를 저장할 수 있는 REST API를 완성한다.

**Architecture:** `apps/api`는 Fastify 5 위에 얇게 올라간다. 라우트는 요청을 파싱하고 권한 가드를 통과시킨 뒤 리포지터리 함수를 호출하는 것 이상을 하지 않는다. 문서 검증은 전부 `@wirebound/schema`가 소유하며 API는 그 결과를 HTTP 상태로 번역할 뿐이다. 그 전제가 성립하려면 스키마 패키지가 (a) 순수 Node에서 로드되고 (b) 노드·문서 봉투를 런타임에 실제로 검사해야 하므로, 태스크 1~3이 그 둘을 먼저 닫는다.

**Tech Stack:** TypeScript · Fastify 5 · Kysely + node-postgres · PostgreSQL 16 · zod 4 · vitest · tsdown

## Global Constraints

이 절은 모든 태스크의 요구사항에 암묵적으로 포함된다.

- **Node ≥ 22, ESM 전용.** `require`를 쓰지 않는다. 모든 패키지 `"type": "module"`.
- **TypeScript strict + `noUncheckedIndexedAccess`.** `any`를 새로 도입하지 않는다. 불가피하면 리뷰에서 근거를 밝힌다.
- **의존 방향은 한 방향이다** (설계 §3.3): `schema` ← `renderer` ← 나머지. `apps/api`는 `@wirebound/schema`에만 의존하고 `@wirebound/renderer`를 import 하지 않는다. `packages/schema`는 zod 외의 런타임 의존을 갖지 않는다.
- **사용자 대면 문자열은 전부 한국어다.** 에러 메시지, 검증 메시지 포함. zod 메시지는 `getKoreanErrorMap()`을 통과시킨다.
- **HTTP 에러 코드는 고정이다** (설계 §13, §10):

  | 상황 | 상태 | `error.code` |
  |---|---|---|
  | 요청 본문·경로 형식 오류 | 400 | `bad-request` |
  | 미인증 | 401 | `unauthenticated` |
  | 멤버지만 역할 부족 | 403 | `forbidden` |
  | 리소스 없음 **또는 프로젝트 비멤버** | 404 | `not-found` |
  | 상태 충돌 (중복 slug, 마지막 owner 강등, 자식 있는 메뉴 삭제) | 409 | `conflict` |
  | 페이지 스키마 검증 실패 | 422 | `validation-failed` |
  | 그 외 | 500 | `internal` |

- **에러 응답 본문은 항상 이 형태다:**

  ```jsonc
  { "error": { "code": "not-found", "message": "프로젝트를 찾을 수 없습니다", "issues": [] } }
  ```

  `issues`는 없으면 생략한다. 성공 응답은 봉투 없이 리소스를 그대로 낸다.

- **권한 체크는 단일 가드 함수를 지난다** (설계 §10). REST가 쓰는 그 함수를 P3의 WebSocket이 그대로 쓴다. 라우트 핸들러 안에서 역할을 직접 비교하지 않는다.
- **`pages.schema`는 materialized 상태다** (설계 §4.2). 읽기는 이 컬럼 하나로 끝난다.
- **API 응답의 JSON 키는 camelCase, DB 컬럼은 snake_case다.** 변환은 리포지터리 계층이 담당하고 라우트는 이미 camelCase인 객체를 받는다.
- **비밀은 로그에 남기지 않는다.** 비밀번호, 세션 토큰 원문, 쿠키 헤더는 로거에서 마스킹한다.

## 이번 단계에서 다루지 않는 것

계획을 읽는 사람이 "빠졌다"고 판단하지 않도록 명시한다.

- **revision 로그·개인 undo** (P2) — `pages`에 `head_seq` 컬럼을 만들지 않는다. P1의 스키마 저장은 전체 문서 PUT 하나뿐이다.
- **레이아웃·테마** (P4a) — `layouts`/`themes` 테이블과 `pages.layout_id`는 만들지 않는다.
- **코멘트·상호작용 저장** (P5), **스냅샷** (P6), **API 토큰 발급** (P9) — 테이블을 만들지 않는다. `sessions` 외의 인증 경로는 없다.
- **WebSocket** (P3) — 인증과 권한 가드는 WS가 재사용할 수 있는 모양으로 만들되, WS 자체는 붙이지 않는다.
- **프로덕션 패키징** — `apps/api`는 `tsx`로 실행한다. 배포 산출물 빌드는 P8 이후 릴리스 작업이다.
- **P0 이월 문서의 "사소한 것들"** 중 태스크 1~3이 명시적으로 집는 항목 외에는 손대지 않는다.

### 각 파일의 책임

- `app.ts`는 **listen 하지 않는다.** `buildApp({ db, config })`가 `FastifyInstance`를 돌려주고, `main.ts`만 `listen`을 부른다. 테스트는 `app.inject()`를 쓴다.

- `routes/*`는 HTTP만 안다. SQL을 쓰지 않는다.
- `auth/roles.ts`가 유일한 역할 비교 지점이다.

## Task 1: 패키지 빌드 파이프라인

이월 1번을 닫는다. `packages/schema`와 `packages/renderer`가 번들러 없이 순수 Node에서 로드되게 만든다. 개발·테스트는 계속 소스를 직접 본다.

**Files:**
- Create: `packages/schema/tsdown.config.ts`, `packages/renderer/tsdown.config.ts`
- Create: `packages/schema/test/dist-loadable.test.ts`
- Modify: `packages/schema/package.json`, `packages/renderer/package.json`, `package.json`
- Modify: `packages/schema/tsconfig.json`, `packages/renderer/tsconfig.json`, `apps/playground/tsconfig.json`, `tsconfig.base.json`
- Modify: `vitest.config.ts`, `.gitignore`

**Interfaces:**
- Produces: `pnpm build`가 저장소 루트에서 `packages/*`를 위상 순서로 빌드한다. 이후 모든 태스크가 이 스크립트를 전제한다.
- Produces: `@wirebound/schema`·`@wirebound/renderer`의 `exports`가 `development` 조건에서 소스를, 그 외에서 `dist`를 가리킨다.

**해결하는 문제**

지금 세 곳이 전부 소스 TypeScript를 가리킨다.

```jsonc
"main": "./src/index.ts", "types": "./src/index.ts", "exports": { ".": "./src/index.ts" }
```

그리고 소스의 상대 import에 확장자가 없다(`export { createNodeId } from './node'`). Node 22가 타입은 벗겨내지만 확장자 없는 상대 경로는 해석하지 못해 `ERR_MODULE_NOT_FOUND`가 난다. 번들러가 소비자일 때만 무해했고, `apps/api`는 번들러가 아니다.

**방식:** 소스는 그대로 두고 tsdown이 확장자를 붙여 `dist`로 낸다. `exports`에 `development` 조건을 앞세워 vitest와 `tsc`가 계속 소스를 보게 한다.

- 소스 관례를 바꾸지 않으므로 기존 파일 전체를 손댈 필요가 없다.
- `tsc --build`는 `customConditions: ["development"]`로 소스를 보므로 project references가 지금처럼 동작하고, typecheck에 빌드가 선행될 필요가 없다.
- vitest는 조건 해석에 기대지 않고 명시적 alias로 소스를 본다. 결정적이다.

- [ ] **Step 1: 의존과 무시 목록 추가**

`packages/schema/package.json`과 `packages/renderer/package.json`의 `devDependencies`에 `"tsdown": "^0.15.0"`을 추가한다.

`.gitignore`에 한 줄 추가한다 (`dist/`는 이미 있다):

```
.tsbuild/
```

- [ ] **Step 2: tsdown 설정 두 개를 만든다**

`packages/schema/tsdown.config.ts`:

```ts
import { defineConfig } from 'tsdown'

export default defineConfig({
  entry: ['src/index.ts'],
  format: ['esm'],
  dts: true,
  outDir: 'dist',
  target: 'node22',
  clean: true,
})
```

`packages/renderer/tsdown.config.ts`: 위와 동일하되 `entry`는 `['src/index.ts']` 그대로 두고 파일만 다른 패키지에 놓는다. tsdown은 `package.json`의 `dependencies`를 자동으로 external 처리하므로 `zod`·`react`·`@wirebound/schema`를 명시할 필요가 없다.

- [ ] **Step 3: package.json의 진입점을 바꾼다**

`packages/schema/package.json`에서 `main`/`types`/`exports`를 교체하고 `scripts`를 추가한다. **조건 순서가 의미를 갖는다** — `development`가 가장 앞이어야 한다.

```jsonc
{
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "development": "./src/index.ts",
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "default": "./dist/index.js"
    }
  },
  "files": ["dist"],
  "scripts": {
    "build": "tsdown",
    "build:watch": "tsdown --watch"
  }
}
```

`packages/renderer/package.json`도 같은 모양으로 바꾼다.

루트 `package.json`의 `scripts`에 추가한다:

```jsonc
"build": "pnpm --filter './packages/*' -r build"
```

`pnpm -r`은 워크스페이스 의존 그래프의 위상 순서로 실행하므로 `schema`가 `renderer`보다 먼저 빌드된다.

- [ ] **Step 4: tsconfig를 정리한다**

`tsconfig.base.json`의 `compilerOptions`에서 `lib`을 `["ES2022"]`로 좁히고 `customConditions`를 추가한다.

```jsonc
{
  "compilerOptions": {
    "lib": ["ES2022"],
    "customConditions": ["development"],
    // ...나머지는 그대로
  }
}
```

DOM이 필요한 프로젝트가 각자 되찾는다. `packages/renderer/tsconfig.json`과 `apps/playground/tsconfig.json`의 `compilerOptions`에 `"lib": ["ES2022", "DOM"]`을 추가한다. `packages/schema`는 추가하지 않는다 — 이것이 이월 문서의 "스키마가 `document`를 참조해도 typecheck를 통과한다"를 컴파일러 강제로 바꾼다.

세 패키지(`schema`, `renderer`, `playground`) tsconfig의 `outDir`을 `"dist"`에서 `".tsbuild"`로 바꾼다. tsdown이 `dist`를 소유하고, `tsc --build`의 선언·증분 산출물은 `.tsbuild`로 간다. 이월 문서의 "`dist/test/*.d.ts` 방출" 항목이 이걸로 닫힌다.

- [ ] **Step 5: vitest가 소스를 보도록 alias를 건다**

`vitest.config.ts`를 통째로 교체한다. 프로젝트를 둘로 나누는 이유는 태스크 5에서 `apps/api`만 DB `globalSetup`이 필요해지기 때문이다. 지금 나눠 두면 그때 한 줄만 추가하면 된다.

```ts
import { fileURLToPath } from 'node:url'
import { defineConfig } from 'vitest/config'

const src = (p: string) => fileURLToPath(new URL(p, import.meta.url))

// 프로젝트마다 별도 Vite 설정이므로 상속되지 않는다. 명시적으로 펼친다.
const shared = {
  // .ts 파일에서도 자동 JSX 런타임을 쓴다. renderer 테스트가 .tsx다.
  esbuild: { jsx: 'automatic' as const },
  // package.json exports가 dist를 가리키므로, 테스트는 alias로 소스를 직접 본다.
  // 조건 해석에 기대지 않아 결정적이다.
  resolve: {
    alias: {
      '@wirebound/schema': src('./packages/schema/src/index.ts'),
      '@wirebound/renderer': src('./packages/renderer/src/index.ts'),
    },
  },
}

export default defineConfig({
  ...shared,
  test: {
    projects: [
      {
        ...shared,
        test: {
          name: 'unit',
          include: ['packages/*/test/**/*.test.{ts,tsx}', 'apps/playground/test/**/*.test.{ts,tsx}'],
        },
      },
    ],
  },
})
```

- [ ] **Step 6: 빌드 산출물이 순수 Node에서 로드되는지 검증하는 테스트를 쓴다**

`packages/schema/test/dist-loadable.test.ts`. 이 테스트가 이월 1번의 회귀 방지선이다. **alias를 우회해야** 의미가 있으므로, vitest 프로세스 안에서 import 하지 않고 별도 `node` 프로세스를 띄운다. `cwd`를 `apps/playground`로 두는 이유는 그 패키지가 `@wirebound/schema`와 `@wirebound/renderer`를 workspace 의존으로 갖고 있어 `exports` 해석까지 함께 검증되기 때문이다.

```ts
import { execFileSync } from 'node:child_process'
import { fileURLToPath } from 'node:url'
import { beforeAll, describe, expect, it } from 'vitest'

const repoRoot = fileURLToPath(new URL('../../..', import.meta.url))
const playground = fileURLToPath(new URL('../../../apps/playground', import.meta.url))

function runInNode(script: string): string {
  return execFileSync(process.execPath, ['--input-type=module', '-e', script], {
    cwd: playground,
    encoding: 'utf8',
    stdio: ['ignore', 'pipe', 'pipe'],
  })
}

describe('빌드 산출물', () => {
  beforeAll(() => {
    execFileSync('pnpm', ['--filter', './packages/*', '-r', 'build'], {
      cwd: repoRoot,
      stdio: 'pipe',
    })
  }, 300_000)

  it('순수 Node가 @wirebound/schema를 로드하고 검증까지 돌린다', () => {
    const out = runInNode(`
      const m = await import('@wirebound/schema')
      if (typeof m.createNodeId !== 'function') throw new Error('createNodeId 없음')
      if (!/^n_[0-9a-f]{12}$/.test(m.createNodeId())) throw new Error('createNodeId 형식 오류')
      m.installCatalog()
      const doc = { version: 1, root: { id: m.createNodeId(), type: 'Page', children: [] } }
      const issues = m.validatePage(doc)
      if (issues.length !== 0) throw new Error('검증 실패: ' + JSON.stringify(issues))
      console.log('OK')
    `)
```

**설계 결정 — id 형식**

`createNodeId()`는 `n_` + hex 12자를 만들지만, 봉투 검증은 **그 형식을 강제하지 않는다.** 설계 §4.4의 레이아웃 예시가 `n_root`·`n_hdr`를 쓰고, §11.2의 JSON 가져오기가 외부에서 만든 id를 실어 온다. 대신 id가 안전하게 쓰일 수 있는 문자만 허용한다.

```
/^[A-Za-z0-9_-]{1,64}$/
```

이 집합은 JSON Pointer 이스케이프 문자(`/`, `~`)와 DOM 속성값에서 문제가 되는 문자(공백, 따옴표, `<`)를 전부 배제한다. 위 표의 `'hello world'`는 공백 때문에 거부된다.

**설계 결정 — strictObject**

노드에 선언되지 않은 키가 있으면 거부한다. 설계 §4.3의 "노드는 스타일을 갖지 않는다"를 런타임에서 강제하는 지점이다. 마이그레이션(§13.1)은 검증보다 먼저 돌므로 구버전 필드가 여기 도달하지 않는다.

`ValidationCode` 유니온에 `'bad-node'`와 `'bad-document'`를 추가한다.

`validatePage`와 `validateLayout`은 **가장 먼저** 봉투를 검사하고, 실패하면 그 이슈만 담아 **즉시 반환한다.** 트리 순회를 시도하지 않는다 — `root`가 `null`이면 `walkNodes`가 터진다.

zod 이슈 하나를 `ValidationIssue` 하나로 옮기는 규칙:

| `code` | `'bad-document'` |
| `nodeId` | 이슈 경로에서 노드 id를 알 수 있으면 그 값, 아니면 `null` |
| `path` | `'/' + zodIssue.path.join('/')` — 위 테스트가 `/root/id`를 기대한다 |
| `message` | zod의 한국어 메시지 |

**설계 결정 — 실제 필드가 아니라 팬텀 브랜드**

`kind: 'page' | 'layout'` 필드를 실제로 넣으면 저장 JSON 형식이 바뀌고 기존 픽스처·DB 컬럼이 전부 따라 움직인다. 그런데 위 세 결함은 **전부 컴파일 타임 결함**이고, 런타임에 종류를 알아야 하는 지점은 없다 — 페이지는 `pages` 테이블에, 레이아웃은 `layouts` 테이블에 산다. 팬텀 브랜드가 저장 형식을 건드리지 않고 셋을 다 잡는다.

`unique symbol` 키의 **선택적** 프로퍼티로 만드는 것이 핵심이다. 그래야 객체 리터럴로는 양쪽 다 만들 수 있고, 이미 타입이 붙은 값끼리는 대입이 막힌다. 이 동작은 `tsc --strict`로 실증했다.

```ts
import { describe, expect, it } from 'vitest'
import type { PageDocument, WbNode } from '../src/node'
import { invertOps } from '../src/patch/inverse'
import type { PatchOp } from '../src/patch/types'

function buildDoc(nodeCount: number): PageDocument {
  const children: WbNode[] = []
  for (let i = 0; i < nodeCount; i += 1) {
    children.push({
      id: `n_${String(i).padStart(12, '0')}`,
      type: 'Text',
      props: { content: `노드 ${i}`, role: 'body' },
    })
  }
  return { version: 1, root: { id: 'n_root00000000', type: 'Page', children } }
}

function timeMs(fn: () => void): number {
  const start = performance.now()
  fn()
  return performance.now() - start
}

describe('invertOps 성능', () => {
  const doc = buildDoc(400)

  it('move 50건이 200ms 안에 역전된다', () => {
    const ops: PatchOp[] = []
    for (let i = 0; i < 50; i += 1) {
      ops.push({ op: 'move', from: `/root/children/${i}`, path: `/root/children/${i + 1}` })
    }
    const elapsed = timeMs(() => invertOps(doc, ops))
    // 회귀 감지용 상한이다. 관측값은 30ms 언저리이고 CI 변동을 감안해 넉넉히 잡았다.
    expect(elapsed).toBeLessThan(200)
  })

  it('replace 50건이 200ms 안에 역전된다', () => {
    const ops: PatchOp[] = []
    for (let i = 0; i < 50; i += 1) {
      ops.push({ op: 'replace', path: `/root/children/${i}/props/content`, value: `바뀜 ${i}` })
    }
    const elapsed = timeMs(() => invertOps(doc, ops))
    expect(elapsed).toBeLessThan(200)
  })
})
```

이 테스트는 **절대 시간을 단언하지 않는다.** 상한이 관측값의 6배라 정상 변동에는 반응하지 않고, 문서 클론이 연산마다 중첩되는 종류의 회귀에만 걸린다. 실행 결과의 실제 수치를 리포트에 적는다 — P2가 그 숫자를 기준선으로 쓴다.

**설계 결정 — 정적 마이그레이션 레지스트리**

Kysely의 `FileMigrationProvider`는 마이그레이션 파일을 동적 `import()` 한다. `.ts` 파일을 동적 import 하는 동작은 실행기(tsx / vitest / 순수 node)마다 다르고, 그 차이가 바로 이 단계가 태스크 1에서 닫은 부류의 문제다. 대신 `migrations/index.ts`가 각 마이그레이션을 **정적으로 import 해 객체에 담는다.** 동적 해석이 사라지고, 마이그레이션 누락이 컴파일 오류가 되며, 순서가 파일에 명시된다.

**설계 결정 — `withTransaction`의 중첩 처리**

테스트 하네스는 트랜잭션 안에서 앱을 돌린다. 앱 코드가 그 안에서 `db.transaction()`을 또 부르면 Postgres에 두 번째 `BEGIN`이 나가 안쪽 커밋이 바깥 트랜잭션을 커밋해 버린다. `withTransaction`이 `db.isTransaction`을 보고 이미 트랜잭션 안이면 그대로 실행한다.

```ts
export async function withTransaction<T>(db: DbHandle, fn: (trx: DbHandle) => Promise<T>): Promise<T> {
  if (db.isTransaction) return fn(db)
  return db.transaction().execute(fn)
}
```

**대가:** 테스트에서는 안쪽 "트랜잭션"이 독립적으로 롤백되지 않는다. P1에는 요청 중간 부분 롤백에 의존하는 코드가 없으므로 문제가 없다. 이 한계를 `tx.ts`의 JSDoc에 적는다. P3의 동시편집 테스트는 실제 커밋이 필요하므로 그때 다른 격리 전략(테이블 TRUNCATE)이 필요해진다 — 그것도 JSDoc에 남긴다.

```ts
export function testConfig(): ApiConfig    // NODE_ENV=test, PASSWORD_SCRYPT_N=1024

/**
 * 테스트 하나를 트랜잭션으로 감싸고 끝나면 롤백한다.
 * 앱은 그 트랜잭션 핸들을 db로 받으므로 커밋되는 것이 없다.
```

`withApi` 구현의 핵심은 롤백을 **예외로 신호하고 바깥에서 삼키는 것**이다. Kysely의 `transaction().execute()`는 콜백이 정상 반환하면 커밋하므로, 롤백하려면 던지는 수밖에 없다.

```ts
class Rollback extends Error {}

export async function withApi(fn: (ctx: TestContext) => Promise<void>): Promise<void> {
  const db = getTestDb()
  try {
    await db.transaction().execute(async (trx) => {
      const app = await buildApp({ db: trx, config: testConfig() })
      await app.ready()
      try {
        await fn({ app, db: trx })
      } finally {
        await app.close()
      }
      throw new Rollback()
    })
  } catch (error) {
    if (!(error instanceof Rollback)) throw error
  }
}
```

`testConfig()`가 `PASSWORD_SCRYPT_N`을 1024로 낮추는 이유는 태스크 6의 기본 파라미터(32768)가 해시 한 번에 50ms 이상 쓰기 때문이다. 로그인이 등장하는 테스트마다 그 비용을 내면 스위트가 느려진다.

## Task 6: 비밀번호 해싱

`node:crypto`의 scrypt로 순수 함수 두 개를 만든다. DB도 HTTP도 모른다.

**Files:**
- Create: `apps/api/src/auth/password.ts`, `apps/api/test/password.test.ts`

**Interfaces:**
- Produces:

  ```ts
  export interface ScryptParams { N: number; r: number; p: number }
  export const DEFAULT_SCRYPT_PARAMS: ScryptParams   // { N: 32768, r: 8, p: 1 }
  export async function hashPassword(password: string, params?: ScryptParams): Promise<string>
  export async function verifyPassword(password: string, encoded: string): Promise<boolean>
  ```

**저장 형식 — 파라미터를 해시에 동봉한다**

```
scrypt$<N>$<r>$<p>$<salt base64url>$<hash base64url>
```

파라미터를 함께 저장하므로 나중에 비용을 올려도 기존 해시가 그대로 검증된다. 검증은 **저장된 파라미터**로 계산하고, 현재 기본값으로 계산하지 않는다.

**주의 — maxmem**

scrypt는 대략 `128 × N × r` 바이트를 쓴다. `N=32768, r=8`이면 32MiB이고 Node의 기본 `maxmem`이 정확히 32MiB라 경계에서 `ERR_CRYPTO_INVALID_SCRYPT_PARAMS`가 난다. `maxmem`을 `256 * N * r`(약 2배)로 명시한다.

**계층 — WS가 재사용할 지점은 `requireProjectRole`이다**

`requireProjectRole`은 Fastify를 모른다. `db`·`projectId`·`userId`·최소 역할만 받고 `ApiError`를 던진다. `projectGuard`는 그것을 Fastify preHandler로 감싸는 얇은 껍데기이며, P3의 WebSocket은 껍데기를 새로 만들되 안쪽 함수를 그대로 쓴다. **역할을 비교하는 코드는 `roleAtLeast` 하나뿐이다.**

**404 대 403**

| 상황 | 응답 |
|---|---|
| 프로젝트가 없다 | 404 |
| 프로젝트는 있지만 멤버가 아니다 | 404 — 프로젝트 존재를 숨긴다 |
| 멤버지만 역할이 모자라다 | 403 |

앞 둘이 같은 응답이므로 조회 한 번으로 끝난다. 설계 §10에 이 규칙을 명시해 두었다.

```ts
import { beforeEach, describe, expect, it } from 'vitest'
import type { ProjectRole } from '../src/db/types'
import { addMember, createProject, signup, withApi, type TestContext } from './helpers'

type Actor = ProjectRole | 'outsider' | 'anonymous'

interface Case {
  label: string
  method: 'GET' | 'POST' | 'PATCH' | 'DELETE' | 'PUT'
  /** :projectId 는 실제 id로 치환된다. */
  url: string
  payload?: unknown
  /** 이 역할 이상이면 통과한다. */
  allowed: Actor[]
}

// 태스크 12·13이 여기에 행을 추가한다.
const CASES: Case[] = [
  { label: '프로젝트 조회', method: 'GET', url: '/api/projects/:projectId', allowed: ['owner', 'editor', 'viewer'] },
  { label: '프로젝트 수정', method: 'PATCH', url: '/api/projects/:projectId', payload: { name: '바뀐 이름' }, allowed: ['owner'] },
  { label: '프로젝트 삭제', method: 'DELETE', url: '/api/projects/:projectId', allowed: ['owner'] },
  { label: '멤버 목록', method: 'GET', url: '/api/projects/:projectId/members', allowed: ['owner', 'editor', 'viewer'] },
  { label: '멤버 초대', method: 'POST', url: '/api/projects/:projectId/members', payload: { email: '초대대상@example.com', role: 'viewer' }, allowed: ['owner'] },
]

const ACTORS: Actor[] = ['owner', 'editor', 'viewer', 'outsider', 'anonymous']

/** 거부는 상태로 판별한다. 허용된 경우의 성공 상태는 케이스마다 다르므로 4xx가 아님만 본다. */
function expectedRejection(actor: Actor): number {
  if (actor === 'anonymous') return 401
  if (actor === 'outsider') return 404   // 프로젝트 존재를 숨긴다 (설계 §10)
  return 403
}

describe('권한 매트릭스 (역할 × 엔드포인트)', () => {
  for (const testCase of CASES) {
    for (const actor of ACTORS) {
      const allowed = testCase.allowed.includes(actor)
      it(`${testCase.label} — ${actor} → ${allowed ? '허용' : expectedRejection(actor)}`, async () => {
        await withApi(async (ctx) => {
          const owner = await signup(ctx)
          const project = await createProject(ctx, owner.cookie)
          // 초대 케이스가 쓸 대상 사용자를 미리 만들어 둔다.
          await signup(ctx, { email: '초대대상@example.com' })

          let cookie: { wb_session: string } | undefined
          if (actor === 'owner') {
            cookie = owner.cookie
          } else if (actor === 'editor' || actor === 'viewer') {
            const member = await signup(ctx)
            await addMember(ctx, project.id, member.user.id, actor)
            cookie = member.cookie
          } else if (actor === 'outsider') {
            cookie = (await signup(ctx)).cookie
          }

          const res = await ctx.app.inject({
            method: testCase.method,
            url: testCase.url.replace(':projectId', project.id),
            payload: testCase.payload as never,
            cookies: cookie,
          })

          if (allowed) {
            expect(res.statusCode, `${testCase.label}/${actor}: ${res.body}`).toBeLessThan(400)
          } else {
            expect(res.statusCode, `${testCase.label}/${actor}: ${res.body}`).toBe(expectedRejection(actor))
          }
        })
      })
    }
  }
})
```

이 파일 하나가 이후 모든 라우트의 권한 회귀를 잡는다. **새 엔드포인트를 추가하는 태스크는 `CASES`에 행을 추가해야 한다.**

**테이블**

`menu_nodes`: `id uuid PK`, `project_id uuid NOT NULL REFERENCES projects(id) ON DELETE CASCADE`, `parent_id uuid NULL REFERENCES menu_nodes(id) ON DELETE RESTRICT`, `title text NOT NULL`, `sort_order int NOT NULL`, `created_at timestamptz NOT NULL default now()`. 인덱스: `(project_id, parent_id, sort_order)`.

`parent_id`를 `RESTRICT`로 둔 이유는 자식이 있는 노드의 삭제를 API가 409로 막기 때문이다. DB가 두 번째 방어선이 된다.

**API 계약**

| 메서드·경로 | 최소 역할 | 본문 | 성공 |
|---|---|---|---|
| `GET /api/projects/:projectId/menu` | viewer | — | 200 트리 |
| `POST /api/projects/:projectId/menu` | editor | `{ parentId?: string \| null, title }` | 201 노드 |
| `PATCH /api/projects/:projectId/menu/:nodeId` | editor | `{ title?, parentId?, sortOrder? }` | 200 노드 |
| `DELETE /api/projects/:projectId/menu/:nodeId` | editor | — | 204 |

트리 응답 형태:

```jsonc
[
  { "id": "…", "title": "회원관리", "sortOrder": 0,
    "children": [ { "id": "…", "title": "권한", "sortOrder": 0, "children": [] } ] }
]
```

**정렬 규칙**

`sort_order`는 **형제 안에서 0부터 시작하는 연속 정수**다. 생성은 끝에 붙는다. `sortOrder`를 지정한 `PATCH`는 그 위치에 끼우고 형제를 재번호한다. 삭제 후에도 재번호한다. 재번호는 전부 한 트랜잭션 안에서 한다.

요청의 `sortOrder`는 `z.int().min(0)`이다. 음수는 zod가 걸러 **400**이고, 형제 수보다 큰 값은 오류가 아니라 **맨 끝으로 클램프**한다. 둘을 다르게 다루는 이유는 음수가 호출자의 계산 오류인 반면, 큰 값은 "맨 뒤로 보내라"는 흔하고 무해한 의도이기 때문이다.

이 규칙을 고른 이유는 응답 순서가 결정적이고 테스트가 정확한 배열을 단언할 수 있기 때문이다. 성긴 정수(10, 20, 30)나 fractional index는 이동이 싸지만 P1의 트리 크기에서는 이득이 없고 검증이 어렵다.

**금지 규칙**

| 상황 | 응답 |
|---|---|
| `parentId`가 자기 자신 | 400 `'메뉴를 자기 자신의 하위로 옮길 수 없습니다'` |
| `parentId`가 자기 자손 | 400 `'메뉴를 자기 하위 메뉴로 옮길 수 없습니다'` |
| `parentId`가 다른 프로젝트의 노드 | 404 |
| `parentId`가 없는 노드 | 404 |
| 자식 메뉴가 있는 노드 삭제 | 409 `'하위 메뉴가 있어 삭제할 수 없습니다'` |

자손 여부는 재귀 CTE(`WITH RECURSIVE`) 한 번으로 확인한다. 애플리케이션에서 트리를 올려 받아 순회하면 왕복이 늘고 경합에 열린다.

## Task 13: 페이지 CRUD와 스키마 검증 게이트

설계 §7.1이 말하는 서버 게이트를 세운다. **이 태스크가 태스크 2의 봉투 검증을 실제로 쓰는 곳이다.**

**Files:**
- Create: `apps/api/src/db/migrations/0004-pages.ts`, `apps/api/src/schema-setup.ts`, `apps/api/src/repos/pages.ts`, `apps/api/src/routes/pages.ts`, `apps/api/test/pages.test.ts`
- Modify: `apps/api/src/db/types.ts`, `apps/api/src/db/migrations/index.ts`, `apps/api/src/app.ts`, `apps/api/test/permission-matrix.test.ts`, `apps/api/test/helpers.ts`

**Interfaces:**
- Consumes: `@wirebound/schema`의 `installCatalog`, `listComponents`, `validatePage`, `migrateDocument`, `createNodeId`, `CURRENT_DOCUMENT_VERSION`, `DocumentEnvelopeSchema`
- Produces: `ensureCatalog()` — 멱등하게 카탈로그를 설치한다

**테이블**

`pages`: `id uuid PK`, `project_id uuid NOT NULL REFERENCES projects(id) ON DELETE CASCADE`, `menu_node_id uuid NOT NULL REFERENCES menu_nodes(id) ON DELETE RESTRICT`, `title text NOT NULL`, `sort_order int NOT NULL`, `description text NULL`, `schema jsonb NOT NULL`, `schema_version int NOT NULL`, `created_at`/`updated_at timestamptz NOT NULL default now()`. 인덱스: `(project_id, menu_node_id, sort_order)`.

`db/types.ts`의 컬럼 타입은 `schema: JSONColumnType<PageDocument>`다. `JSONColumnType<T>`는 `ColumnType<T, string, string>`이므로 **삽입·갱신 시 `JSON.stringify`가 필요하고 조회 시에는 파싱된 객체가 온다.** 명시적이라 좋다.

`menu_node_id`가 `RESTRICT`인 이유는 태스크 12가 자식 있는 메뉴 삭제를 막기 때문이다. 그 규칙에 "페이지를 가진 메뉴"도 포함되도록 태스크 12의 삭제 검사를 **이 태스크에서 확장한다** — 메뉴 삭제 시 자식 메뉴뿐 아니라 페이지도 센다.

**API 계약**

| 메서드·경로 | 최소 역할 | 본문 | 성공 |
|---|---|---|---|
| `GET /api/projects/:projectId/pages/:pageId` | viewer | — | 200 `{ id, menuNodeId, title, description, sortOrder, schemaVersion, schema }` |
| `POST /api/projects/:projectId/pages` | editor | `{ menuNodeId, title, description? }` | 201 페이지 (빈 스키마 포함) |
| `PATCH /api/projects/:projectId/pages/:pageId` | editor | `{ title?, description?, menuNodeId?, sortOrder? }` | 200 페이지 |
| `PUT /api/projects/:projectId/pages/:pageId/schema` | editor | `{ schema: { version, root } }` | 200 페이지 |
| `DELETE /api/projects/:projectId/pages/:pageId` | editor | — | 204 |

**생성 시 기본 스키마**

```ts
{ version: CURRENT_DOCUMENT_VERSION, root: { id: createNodeId(), type: 'Page', children: [] } }
```

**`PUT .../schema`의 게이트 순서** — 순서가 규격이다.

1. 본문을 `z.strictObject({ schema: DocumentEnvelopeSchema })`로 파싱한다. 실패 → **400** `bad-request`.
2. `migrateDocument`로 최신 버전으로 올린다. 던지면(지원하지 않는 버전) → **400**.
3. `validatePage`를 부른다. 이슈가 있으면 → **422** `validation-failed`, `issues`에 `ValidationIssue[]`를 그대로 싣는다.
4. `schema`와 `schema_version`, `updated_at`을 갱신한다.

1단계와 3단계가 나뉘는 이유는 응답 상태가 다르기 때문이다. 봉투가 깨진 것은 **요청이 잘못된 것**(400)이고, 봉투는 멀쩡한데 카탈로그 규칙을 어긴 것은 **내용이 처리 불가한 것**(422)이다. 설계 §13의 "스키마 검증 실패 → 422"는 후자를 가리킨다.

**읽기 경로의 마이그레이션** — `GET`은 저장된 문서에 `migrateDocument`를 적용해 내보낸다. 설계 §13.1의 "페이지를 읽을 때 최신 버전으로 올려 읽는다"이다. **읽기가 다시 저장하지는 않는다** — 같은 문서의 "다음 저장 시 갱신"된다.

**카탈로그 설치** — `validatePage`는 컴포넌트 레지스트리가 채워져 있어야 동작한다. `schema-setup.ts`의 `ensureCatalog()`가 `listComponents().length === 0`일 때만 `installCatalog()`를 부르고, `buildApp`이 이를 호출한다. 테스트는 한 프로세스에서 `buildApp`을 수백 번 부르므로 멱등성이 필수다.

- [ ] **Step 1: 테스트를 쓴다**

`apps/api/test/pages.test.ts`가 덮을 것:

## 계획 작성자의 주의 — P0에서 배운 것

P0 최종 리뷰가 짚은 것: **Important findings의 절반이 계획이 리터럴 구현 코드를 지정한 데서 왔다.** 태스크별 리뷰는 "코드가 계획과 일치하는가"를 검사하므로 그런 결함을 구조적으로 잡을 수 없다 — 코드가 계획과 정확히 일치하기 때문이다.

그래서 이 계획은 의도적으로 다르게 썼다. 세 층으로 나뉜다.

- **리터럴 코드 — 설정 파일, SQL 스키마, 타입·인터페이스 정의, 그리고 성질이 미묘한 테스트.** 이것들은 그 자체가 계약이라 구현자가 다시 쓰면 계약이 흔들린다. 태스크 1~9의 테스트가 여기 속한다(봉투 검증의 경계, 브랜드 타입, 세션 저장, 해시 형식, 역할 판정).
- **케이스 표 — 태스크 10~14의 테스트.** 형태가 반복적이라 리터럴로 적으면 분량만 늘고 계약이 묻힌다. 대신 **표의 각 항목이 `it` 하나에 대응한다**고 규정한다. 리뷰어는 표의 행 수와 테스트 수를 대조해 누락을 판정할 수 있고, 구현자는 단언 방식을 선택할 여지를 갖는다.
- **산문 — 라우트 핸들러와 리포지터리 본문.** 구현자가 코드를 쓴다. 스펙 준수 리뷰가 밀어붙일 대상이 생긴다.

리뷰어에게: 이 계획이 지시하는 것 중 리뷰 루브릭이 결함으로 볼 만한 것을 발견하면 plan-mandated로 보고한다. 계획이 스스로를 채점하지 않는다.
