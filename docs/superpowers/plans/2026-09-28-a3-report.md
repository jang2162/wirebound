### Task 6 — 프로젝트 바인딩 · impact · `theme-changed`

- 실행: 실패 먼저 23 실패 · 1 통과. 구현 뒤 24 통과(세 번 연속). 인구조사: `permission-matrix` 211(CASES 셋 × 역할 다섯) · `restore-lock-census` 33 · `guard-in-lock` 136(+4) · `actor-census` 28 · web `protocol` 44 · `protocol-parity` 5 · `use-realtime` 16.
- 변조:
  - `updateProjectTheme` 의 `WHERE theme_rev = expectedRev` 를 뗌 → «옛 rev 는 409» · «거절된 저장(409)은 방송하지 않는다» 둘이 `200 ≠ 409`.
  - `PUT` 의 `recheckProjectRole` 을 뗌 → guard-in-lock «복원 잠금에 쥐인 채 강등되면 403» · «트리 잠금 …» 둘이 `200 ≠ 403`(대조 둘은 통과).
- 계획과 달라진 것:
  - **먼저 읽고 견주는 rev 검사를 두지 않는다** — 조건은 갱신 문장에만 있다. 앞에서 견주면 `WHERE` 를 떼는 변조가 순차 케이스에서 안 죽는다(앞 검사가 막는다). 숨긴 판 판정의 바탕(지금 바인딩)은 트랜잭션 밖에서 읽는다 — 바인딩이 바뀌면 `rev` 도 바뀌므로 그 사이의 저장은 갱신이 걸러 409 가 된다.
  - 409 본문은 `{ error: { code, message }, current }`(오류 봉투를 지키고 `current` 를 곁에 싣는다).
  - impact 의 `variants` 는 트리 차례(메뉴 깊이 우선 · 형제 `sort_order`). 처음 판은 `created_at` 순이었는데 한 트랜잭션에서 만든 페이지들은 시각이 같아 id 로 갈려 첫 실행에서 흔들렸다.
  - 토큰 이슈의 경로는 `tokens.<키>`, 코드는 `tokensCss` 의 것(`token-default-type` · `token-select-default` · `unknown-token`)과 `token-too-long` · `token-too-large`. 값 한도는 UTF-16 글자, 전체 한도는 기본값을 뺀 JSON 의 UTF-8 바이트.
  - `GET /api/projects/:projectId` 의 `themeRev` 는 바인딩 조회를 하나 더 해 싣는다(`ProjectRecord` 를 넓히지 않았다 — 다른 네 응답의 키 집합이 그대로다).
  - `permission-matrix` 의 `Case` 에 선택 칸 `query` 를 더했다. `restore-lock-census` 의 PUT 줄은 Task 6 에서 `restoreWrites: false`, Task 7 에서 `true`.
  - 웹은 `theme-changed` 를 해석만 한다(`use-realtime.ts` 의 `default`).
  - 방송이 **없음**을 재는 케이스는 `WsProbe.quiet()` 의 반환이 아니라 `received` 전부를 본다 — `quiet()` 은 창 안의 것만 돌려줘 답보다 먼저 닿은 프레임을 못 본다.
