## 1. 흔들리는 테스트 — **이 브랜치 탓이 아니다**

구현자가 `apps/api/test/comments-concurrency.test.ts`의 B5 케이스가 `pnpm test` 전체에서
5번 중 1번 빨갰다고 보고했다(보고서 §10). **브랜치 탓인지부터 가렸다.**

### 1.1 잰 값

| 무엇 | 값 |
|---|---|
| 브랜치 `pnpm test` 전체 | **3회 · 전부 초록** (4785건) |
| **`main`(3b58936)** `pnpm test` 전체 | **5회 · 전부 초록** (4693건) |
| `main`에서 **그 파일만** + CPU 부하 14개를 건 상태 | **10회 · 전부 초록** |
| 브랜치가 `apps/` 아래를 건드린 파일 | **0개** (`git diff --name-only main...HEAD -- apps/`) |
| `apps/`가 `@wirebound/cli`를 쓰나 | **안 쓴다** — 소스에 참조 0건, `apps/api/package.json`의 의존 목록에도 없다 |

기준선은 별도 워크트리(`.worktrees/review-p9-4-main`)를 만들어 쟀다 — **이 워크트리의 브랜치를
갈아타지 않았고** 최상위 체크아웃에서도 아무것도 안 돌렸다.

### 1.2 판정과 근거

**브랜치가 그 케이스에 닿는 경로가 없다.**

- `apps/` 아래를 한 파일도 안 건드렸다.
- 공유 설정 중 바뀐 것은 `vitest.config.ts`의 `resolve.alias` **셋뿐**이고 전부
  `@wirebound/cli*`다. **`apps/`가 그 패키지를 안 쓰므로** 그 alias가 `apps/api`의 모듈
  해석을 바꿀 수 없다.
- 케이스 자체가 `[200, 409]`를 단언하는데 **두 요청이 실제로 겹쳤는지를 강제하지 않는다** —
  `Promise.all`로 던질 뿐이다. 앞 요청이 커밋을 마친 뒤에 뒤엣것이 `head_seq`를 읽으면
  **둘 다 200이고 그것이 옳은 동작이다.** 구현자의 진단을 코드에서 확인했다.

**그러므로 병합 불가 사유가 아니다.** 이 저장소가 P3-2에서 겪은 *"main이 빨간데 브랜치 탓이
아니었다"*와 같은 부류다.

**단정하지 않는 것 하나.** 나는 빨강을 **한 번도 재현하지 못했다**(내 실행 18회 전부 초록).
그러므로 *"브랜치가 흔들림 확률을 안 올린다"*를 실측으로 보인 것은 아니다 — 브랜치는 unit
파일 8개·케이스 92개를 더해 부하를 3%쯤 올린다(248→256 파일, 4693→4785건). 구현자의 진단이
*"부하 아래 직렬화"*이므로 **부하가 늘면 확률도 는다**는 방향은 있을 수 있다. 그러나 그것은
**이 브랜치의 결함이 아니라 그 케이스의 결함**이고, 고치는 자리는 `apps/api`다
(이월 §3에 이미 그렇게 적혀 있다).

## 3. 지적 — **자와 문서가 값보다 세게 적혀 있다**

넷 다 *"오늘 도는 코드가 틀렸다"*가 아니라 *"지키는 자가 없거나, 문서가 자보다 세게
적혀 있다"*이다. 그래서 병합 불가로 세지 않았다. **다만 R2는 이월 문서의 문장이 지금
틀렸으므로 고쳐야 한다.**

### R2. **표준출력 리다이렉트는 쓰는 자가 생겨도 하중을 안 받는다** (가장 무겁다)

계획서가 *"여기가 이 슬라이스에서 조용히 깨질 수 있는 가장 큰 자리"*라고 짚은 곳이다.

**구현자의 M17은 맞다** — `bin.ts`의 `out: base.err` 한 줄을 지워도 0 사망이고, 원인은
*"오늘 도구가 지나는 경로에 `io.out`을 부르는 자리가 하나도 없다"*이다. 나도 확인했다
(`packages/cli/src`에서 `io.out`을 부르는 자리는 `run`·`init`·`lint`·`export`·`pull`·
`page-get`·`login` **명령 파일들뿐**이고 그중 어느 것도 `embed`로 안 나간다).

**그런데 이월 §3이 이렇게 적었다:** *"쓰기 도구가 무엇이든 `out`으로 찍는 순간 그 줄이
하중을 받는다 — 그때 케이스를 세워라."* **그 문장이 틀렸다.**

**잰 방법.** `bin.ts`에서 리다이렉트를 지우고 **동시에** 진짜로 한 줄을 찍게 했다.

```
- const io = { ...base, out: base.err }
+ const io = base
+ io.out("wirebound mcp ready")
```

| 게이트 | 사망 |
|---|---|
| `pnpm test:build` (스모크 11건) | **0건 — 11/11 초록** |

**즉 표준출력이 실제로 오염된 상태에서 스모크가 통째로 통과한다.**

**그리고 스모크의 그 케이스가 이름이 말하는 것을 안 잰다.**
`서버가 표준출력을 더럽히지 않는다 — payload 경고가 프레임을 안 깬다`가 실제로 재는 것은
*"`payloadVersion: 99`일 때도 응답이 온다"*뿐이고, **그 경고는 이미 `io.err`로 간다.**
리다이렉트가 있든 없든, 표준출력이 깨끗하든 오염됐든 이 케이스는 통과한다.

**부수 관측 — 오늘 위험은 문서가 적은 것보다 낮다.** SDK 1.30.0의 `StdioClientTransport`는
**개행으로 끝나는 이물 한 줄을 만나도 연결을 안 끊는다**(위 실측이 그것이다). 문서가 적은
*"호스트가 프레임을 못 읽고 연결이 끊긴다"*는 이 클라이언트에서는 안 일어났다. 다만
**개행 없는 조각**이 섞이면 다음 프레임 앞에 붙어 그 프레임이 깨지고, 호스트마다 다르다 —
그래서 **줄을 지우자는 것이 아니다.**

**고칠 자리(둘 중 하나).**

1. **자를 세운다.** 스모크가 자식 프로세스의 **날 표준출력을 직접 읽어** 모든 줄이
   JSON-RPC 프레임인지 재는 케이스를 하나 둔다. `StdioClientTransport`가 그 스트림을
   독점하므로 별도 케이스에서 `spawn`으로 띄워 `initialize` 하나를 손으로 써 넣고 stdout
   전문을 읽는 모양이 된다. **그 자가 서면 M17이 처음으로 하중을 받는다.**
2. **문장을 값에 맞춘다.** 이월 §3의 그 줄을 *"쓰는 자가 생겨도 죽는 자가 없다 — 실측"*으로
   고치고, 스모크 케이스의 이름에서 *"표준출력을 더럽히지 않는다"*를 뺀다.

**둘 중 하나는 해야 한다.** 지금 상태로 두면 P9-5가 `add_comment`에서 `io.out`을 한 번
쓰고 **초록을 보고 지나간다.**

### R3. `packages/mcp`의 `assembly-census`가 **머리말이 적은 층 둘을 안 잰다**

그 파일의 머리말이 이렇게 적었다.

> 의존이 없어도 `@wirebound/cli/embed`가 타입을 재수출하므로 값을 넘겨받아 **여기서 다시
> 엮는** 길은 남는다. 그래서 소스도 훑는다.

**잰 방법.** `handlers.ts`에서 읽기 층의 export 하나로 목록을 다시 엮었다.

```
+ import { … orderedPages … } from '@wirebound/cli/embed'
+ const 다시엮음 = orderedPages(open.payload).map((page) => page.title)
```

| 게이트 | 사망 |
|---|---|
| `pnpm test` (`packages/mcp`) | **0건 — 84/84 초록** |

**원인.** 술어의 분모(`ASSEMBLY`)가 **손으로 적은 원시 열 개**이고 전부
`@wirebound/schema`·`@wirebound/themes`의 이름이다. `embed`가 **값으로** 내주는 읽기 층의
이름들(`orderedPages` · `projectPaths` · `countErrors` · `prepareCatalog` · `listProject` ·
`lookupPage` · `lintReport`)은 그 목록에 **하나도 없다.**

**구조 층(의존이 둘뿐이다)은 여전히 최악을 막는다** — `@wirebound/schema`를 직접 import하는
길은 실제로 막혀 있다(실측: `pageTargetPath`를 심으면 census가 죽는다). **그러므로
지적은 "자가 없다"가 아니라 "머리말이 자보다 세다"이다.**

**고칠 자리:** `ASSEMBLY`에 읽기 층의 이름을 더하거나(단, `listProject`·`lookupPage`·
`lintReport`는 **불러야 하는 것**이므로 허용 목록이 필요하다), 머리말에서 층 둘의 주장을
값에 맞춰 낮춘다.

### R4. D5의 자가 **새 도구에 대해서는 이름 블랙리스트뿐**이다

**잰 방법.** `validate`에 `namingRule`이라는 문자열 인자를 더했다.

| 게이트 | 사망 |
|---|---|
| `pnpm test` (`packages/mcp`) | **1건** — `받는 인자는 경로 하나뿐이다` |

**즉 오늘 셋은 화이트리스트가 지킨다.** 그러나 그 화이트리스트는 도구 **이름을 손으로 적어**
셋을 박아 뒀다.

```ts
expect(Object.keys(findTool('list_pages')!.inputSchema.properties)).toEqual([])
expect(Object.keys(findTool('get_page')!.inputSchema.properties)).toEqual(['path'])
expect(Object.keys(findTool('validate')!.inputSchema.properties)).toEqual(['path'])
```

**그리고 블랙리스트는 `namingRule`을 못 잡았다** — `['config','lint','naming','pattern','regex','rules']`가
이름을 정확히 맞추는 목록이기 때문이다.

**그러므로 P9-5가 `patch_page`를 더하면 그 도구의 인자는 어느 화이트리스트에도 안 걸린다.**
`TOOLS`를 분모로 도는 블랙리스트만 남고, 그것을 비껴가는 이름은 많다.

**이월 §2.1이 P9-5에게 걸릴 자리 여섯을 적었는데 이 자리가 그 표에 없다.** 더해야 한다 —
*"새 도구의 인자 화이트리스트를 그 케이스에 적어라"*.

## 10.1 흔들림 — **가설을 정면으로 쟀다**

코디네이터가 지목한 가설: *"부하가 원인이면 이 브랜치가 부하를 늘렸다. vitest의 projects가
동시에 돌면 unit 쪽 부하가 api의 시간 민감 케이스에 닿는다."*

### ⓐ **projects는 동시에 안 돈다** — 전제가 거짓이다

`--reporter=json`으로 **파일마다 시작·끝 시각**을 받아 두 번의 전체 실행에서 쟀다.

| 실행 | web + unit | api | api 창과 겹치는 비-api 파일 |
|---|---|---|---|
| ① | +0.0s ~ **+12.1s** | **+12.4s** ~ +102.7s | **0 / 197** |
| ② | +0.0s ~ **+13.0s** | **+13.2s** ~ +104.5s | **0 / 197** |

**술어를 보정했다.** 같은 검출기로 비-api 파일끼리를 재면 **한 파일과 최대 43개**가 동시에
돈다 — 겹침을 못 보는 검출기가 아니다.

**구조적 이유가 있다.** `api` 프로젝트만 `pool: 'forks'`(+`singleFork`)이고 unit·web은
기본 풀이라, vitest가 **풀 단위로 묶어 차례로** 돈다. 우연한 순서가 아니다.

> **그러므로 `unit`에 파일·케이스를 더해도 `api` 창에 동시 부하가 안 닿는다.**
> `singleFork`가 *"그 프로젝트 안의 격리"*라는 코디네이터의 지적은 맞지만, **애초에 다른
> 프로젝트가 그 시간에 안 돈다.**

### ⓑ **잔여 압력도 없다** — 부하를 맞춰 비교한 결과

*"앞선 197 파일이 남긴 메모리·워커가 api 창을 느리게 만드는가"*를 소요 시간으로 쟀다.

| 무엇 | 값 |
|---|---|
| `api` 프로젝트 **단독** 실행 6회 | 91.0 · 91.7 · 91.0 · 91.6 · 92.0 · **92.1s** |
| **전체 실행 안**의 api 창 | **90.3s** · **91.3s** |

**전체 실행 안에서 api가 더 느리지 않다** — 오히려 근소하게 빠르다. 잔여 압력이 관측되지
않는다. 즉 *"부하를 맞춰서 비교하라"*는 요구에 대한 답은 **맞출 부하가 없다**이다.

### ⓒ 재현 시도 — 이번에도 못 했다

| 무엇 | 값 |
|---|---|
| `api` 프로젝트 단독 (전체 실행과 api에 대해 **같은 조건**이다 — ⓐ) | **6회 전부 초록** |
| `pnpm test` 전체 | **2회 전부 초록** (4803/4803) |
| 앞 디스패치의 실행 | 18회 전부 초록 |
| **누적** | **26회 무재현** |

### ⓓ **두 케이스는 같은 부류가 아니다 — 그리고 동률 가설은 반증됐다**

구현자가 ⓑ에 대해 *"동률과 시계 역행 둘 다와 어울린다 — 둘을 가르지 못했다"*고 적었다.
**갈랐다.**

**잰 방법.** `clock_timestamp()`가 실제로 얼마나 떨어지는지를 두 조건에서 쟀다.

| 조건 | 표본 쌍 | 간격 min | p50 | **동률** | 역행 |
|---|---|---|---|---|---|
| PL/pgSQL 루프 안(왕복 없음) — **술어 보정** | 8,999 | 0 | **1µs** | **1,455 (16%)** | 0 |
| psql 세션에서 **네트워크 왕복을 지나는** INSERT | 899 | **30µs** | **51µs** | **0** | 0 |

**보정이 요점이다.** 동률은 **잴 수 있는 현상**이고(루프 안에서 16%), **왕복이 끼는 순간
사라진다.** 그리고 케이스가 지나는 경로(fastify `inject` → kysely → INSERT)는 **날 psql
INSERT 왕복보다 느리다.** 그러므로 세 코멘트의 `created_at`이 같은 마이크로초에 떨어질 수
없다.

**정렬이 `(created_at asc, id asc)`이므로**(`repos/comments.ts` — 라우트는 다시 정렬하지
않는다, 읽었다) `셋째`가 맨 앞이려면 **`셋째.created_at < 첫째.created_at`**이어야 한다.
동률이 배제되면 남는 것은 **시계가 뒤로 간 것** 하나다.

**시계 역행도 따로 쟀다 — 관측은 못 했다.**

| 무엇 | 값 |
|---|---|
| Postgres 안에서 `clock_timestamp()` 연속 표본 | **3,000,000개 · 역행 0** |
| 컨테이너 시계를 2초마다(9.5분) | **284 표본 · 역행 0** |

**판정.** 남은 기전은 **시스템 시계의 뒤로 뛰기** 하나이고, **`packages/` 아래의 어떤 코드도
시스템 시계를 뒤로 돌릴 수 없다.** 브랜치가 만든 결함이 아니다.

**ⓐ(B5)와 ⓑ는 부류가 다르다.** ⓐ는 *"두 요청이 실제로 겹쳤는가"*(경합이 안 일어나면
둘 다 200이고 그것이 옳다)이고, ⓑ는 *"연속한 삽입의 벽시계가 단조 증가하는가"*다.
공통점은 **둘 다 `apps/api` 안에서 시간에 매여 서 있다**는 것뿐이다.

### ⓔ *"전체 실행에서만 빨갛다"*의 올바른 읽기

ⓐ가 그 문장의 뜻을 바꾼다. **전체 실행과 `--project api` 단독은 api에 대해 같은 조건이다.**
갈리는 것은 *"그 파일만 돌리는가"* 하나이고, 그 차이는 **같은 포크에서 앞선 api 파일 60개가
남긴 상태**(커넥션 풀·힙·Postgres 캐시)다 — **전부 `apps/api` 안이다.**

**이월 §3.1의 표현을 고치는 것이 좋다:** *"`pnpm test` 전체 대 파일 하나"*가 아니라
**"`api` 프로젝트 전체 대 파일 하나"**다. 앞의 표현은 *"다른 프로젝트의 부하가 원인"*으로
읽히는데 ⓐ가 그것을 반증했다.

### ⓕ 흔들림 판정

**브랜치가 만든 결함이 아니다 — 병합을 막지 않는다.** 그리고 *"브랜치가 부하를 늘려 원래
약했던 케이스가 드러났다"***도 아니다**: 브랜치가 늘린 부하는 api 창에 **닿지 않는다**(ⓐ·ⓑ).

**약한 케이스를 고치는 것은 `apps/api`의 일이다.** 근거: 두 케이스 모두 그 패키지의 소스와
그 패키지의 테스트만으로 완결되고, 고치는 데 필요한 것(ⓐ는 *"겹쳤다"*를 강제하는 이음매,
ⓑ는 `created_at` 값을 함께 단언하는 것)이 전부 `apps/api` 안이다. **P9-4가 그것을 지고 가면
읽기 도구 슬라이스에 `apps/api` 변경이 섞인다** — 계획서 전역 제약이 *"`apps/api`를 고칠 일이
생기면 그것이 신호다"*라고 적은 자리다.

## 10.2 0 사망 변이 다섯 — **내 손으로 다시 심었다**

전부 python 치환 + `finally`에서 원본 전문 되쓰기. 매번 뒤에 작업 트리가 깨끗했다.

## 10.3 R2의 새 자를 **여러 모양으로 밀었다**

| 심은 모양 | `pnpm test` | `test:build` | 읽기 |

## 10.4 R4의 분모가 **정말 `TOOLS`인지**

**잰 방법.** 도구를 하나 더해 정규식을 받게 했다 — `patch_page`에 `namingPattern`.

| 게이트 | 사망 |
|---|---|
| `pnpm test` (`packages/mcp`) | **12건**, 그중 **`어느 도구도 허용 목록 밖의 인자를 안 받는다 (D4·D5)`** |

**닫혔다.** 리뷰 때 지적한 것(*"새 도구의 인자는 어느 화이트리스트에도 안 걸린다"*)이 이제

구현 유무)는 **P9-5가 도구를 더할 때 밟을 자리들**이고 이월 §2.1이 그것을 이미 든다.

## 10.5 델타에서 새로 찾은 것 둘 — **지적이 아니라 자의 경계다**

### D-1. 새 stdout 자는 **응답 뒤의 오염**을 못 본다

**잰 방법.** 리다이렉트를 지우고 `setTimeout(() => io.out("late log line"), 1500)`을 심었다.

| 게이트 | 사망 |
|---|---|
| `pnpm test:build` | **0건 — 14/14 초록** |

**원인(소스에서 읽었다).** `rawStdout`이 *"`id`를 든 요청 수만큼 프레임이 오면"* 곧바로
resolve한다. 그 뒤에 찍히는 것은 아무도 안 읽는다.

**왜 값이 있나.** 진짜 호스트의 세션은 **오래 살고 도구 호출이 계속 이어진다.** 응답 뒤에
찍는 로그는 *다음* 프레임의 앞에 붙으므로 실서버에서는 오히려 이쪽이 더 흔하다.
**고치는 것은 작다** — 프레임을 다 받은 뒤 한 박자(수백 ms) 더 읽거나, stdin을 닫고 EOF까지
읽은 뒤에 단언한다.

### D-2. `io-boundary`의 술어에 **`console.`이 없다**

§10.3의 첫 줄이 그 값이다: `console.log`를 `packages/mcp/src`에 심어도 `pnpm test`는
**0 사망**이다. `EFFECTFUL`이 보는 것은 `node:*` 지정자 · `process.` · 전역 `fetch(`뿐이다.

**구멍은 아니다** — `test:build`가 2건으로 잡는다. 다만 **stdout을 더럽히는 가장 흔한 한 줄이
`pnpm test`에서는 안 보인다.** `EFFECTFUL`에 `console.`을 더하면 그 자리가 `pnpm test`로
당겨진다(그리고 `packages/cli` 쪽 같은 자에도 같은 물음이 선다).

## 10.7 이 델타가 안 잰 것

- **흔들리는 빨강 자체** — 누적 26회에서 한 번도 재현 못 했다. ⓓ의 판정(*"남는 기전은 시계
  역행"*)은 **소거로 얻은 것**이고 역행을 직접 관측한 값이 아니다.
- **다른 호스트** — SDK 1.30.0의 관대함까지만 쟀다(리뷰 §R2 그대로).
- **`main`에서의 델타 재측정** — `apps/`가 0개 변경이고 projects가 안 겹치므로 `api` 프로젝트
  단독 실행이 곧 `main`의 그것이다. 별도 워크트리를 다시 만들지 않았다.
