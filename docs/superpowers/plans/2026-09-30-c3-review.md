## 1. 잠금 순서의 고리

### 센 것

- **사용자 행의 모드.** 비밀번호 바꾸기는 `UPDATE users SET password_hash`(`repos/users.ts` 의 `setPasswordHash`) 한 문장 — 키 열(유일 색인)을 안 고치므로 `FOR NO KEY UPDATE` 다. FK 검사의 `KEY SHARE` 와 안 부딪힌다. 값: 바꾸기가 사용자 행을 쥔 동안(자기 세션 재확인 질의에 붙잡음) 같은 사람의 다른 세션이 프로젝트를 만듦(`project_members.user_id` FK) → **13 · 16 · 17 · 20 · 54 ms, 201** · 바꾸기 204.
- **`users` 를 FK 로 가리키는 표**(`git grep -n "references('users" apps/api/src/db/migrations`): 8 — `sessions` · `project_members` · `comments.author_id` · `snapshots.created_by` · `presets.created_by` · `api_tokens` · `comment_tombstones.author_id` · `theme_packages.uploaded_by`. 전부 `KEY SHARE` 라 위 값과 같은 판이다(하나만 쟀다).
- **사용자 행을 `FOR NO KEY UPDATE` 와 부딪히는 모드로 잡는 자리**(`git grep` — `forShare` · `forUpdate` · `updateTable('users')`): `auth/admin.ts` 의 `recheckInstanceAdmin`(`isInstanceAdmin(…, 'share')` = `FOR SHARE`) · `repos/users.ts` 의 `setInstanceAdmin`(명령 · 한 문장) · `db/reset-password.ts`(명령) · 비밀번호 바꾸기 자신. **세션으로 들어오는 쓰기는 관리자 쓰기 둘(업로드 · 숨김 — `routes/admin-themes.ts`)뿐이다.**
- **차례.** `recheckInstanceAdmin` 은 **자격(세션 `KEY SHARE`) → 사용자 행 `FOR SHARE`** 다. 프로젝트 쓰기의 `recheckAtCommit` 은 자격 → **멤버 행** `FOR SHARE` 라 사용자 행에 안 닿는다(고리 없음 — 아래 3 의 판이 그 차례를 잰다).

### R1 — 관리자 쓰기와의 고리(빨강)

판(`apps/api/test/auth-password-review.test.ts` «같은 관리자의 다른 세션이 업로드 재확인에 선 동안 …» · «… 숨김 재확인 …»): alice(관리자)의 둘째 세션 B 로 업로드(또는 숨김)를 보내 `users … for share` 질의 앞에 붙잡는다(B 는 제 세션 행 `KEY SHARE` 를 쥠) → 첫 세션 A 로 비밀번호 바꾸기 → A 의 `delete from "sessions"` 가 B 백엔드 뒤에 줄 선 것을 `pg_blocking_pids` 사슬로 본 뒤 놓는다.

| 판 | 바꾸기 | 관리자 쓰기 | 걸린 시간 | 끝 상태 |
|---|---|---|---|---|
| 업로드 | **500** `internal` | 201 | 1016 · 1018 · 1020 · 1031 ms | 비밀번호 그대로 · 세션 2 |
| 숨김 | **500** | 200 | ~1060 ms | 비밀번호 그대로 · 세션 2 |
| 대조 — 다른 관리자(bob)의 업로드가 같은 자리에 섬 | 204(안 기다림 · 줄 0) | 201 | — | — |

PG 로그: `ERROR: deadlock detected — Process A waits for ShareLock on transaction …; blocked by B. B waits … blocked by A. A: delete from "sessions" where "user_id" = $1 and "id" <> $2 · B: select "is_instance_admin" from "users" where "id" = $1 for share`. 희생자는 먼저 기다린 바꾸기다(`deadlock_timeout` 1s).

- **원인:** 바꾸기는 사용자 행 → B 세션, 관리자 재확인은 B 세션 → 사용자 행. 서로 반대 차례.
- **원래 있던 길인가:** 재설정 명령 `resetPassword`(`db/reset-password.ts` — main 과 같은 소스)도 «사용자 행 `UPDATE` → 세션 전부 `DELETE`» 라 같은 판에 섰다 — 업로드 판 명령이 `deadlock detected` 로 던짐(1028 ms) · 업로드 201, 숨김 판 명령 실패 · 숨김 200. **고리는 main 에 있었고(명령 · 드묾), 이 트랙이 사람이 누르는 웹 입구를 더했다.**
- **고칠 방향(값으로 견줌 · 고치지 않음):**

| 방향 | 잰 값 |
|---|---|
| **F1 `recheckInstanceAdmin` 에서 사용자 행 `FOR SHARE` 를 자격 재확인 앞으로**(`isInstanceAdmin(…, 'share')` → `recheckCredential` → 판정) | 고친 차례에 맞춘 판(B 를 둘째 재확인 = 세션 `… for key share` 에 붙잡고 바꾸기가 `update "users"` 에서 B 뒤에 줄 선 것을 봄): 바꾸기 **204** · 업로드 **201** · 35 ms · 세션 1(B 가 먼저 커밋 → 바꾸기가 B 세션을 지움). 숨김 204 · 200. 같은 변조에서 `admin-themes.test.ts` · `guard-in-lock.test.ts` 161 초록. 재설정 명령의 고리도 같은 뿌리라 함께 닫힌다(추론 — 명령 판은 F1 으로 안 쟀다) |
| 바꾸기에서 다른 세션 `DELETE` 를 사용자 행 `UPDATE` 앞으로 | 안 쟀다 — «재확인 → 삭제» 가 사용자 행보다 앞이면 같은 사람의 두 바꾸기가 서로의 세션을 기다리는 고리다(구현 보고의 M6 이 같은 꼴을 잼: `expected 503 to be 401`) |
| 관리자 재확인을 `FOR KEY SHARE` 로 | 안 쟀다 — `setInstanceAdmin` 의 `UPDATE`(비키 열)와 안 부딪혀 «강등이 커밋을 기다린다»가 사라진다(잠금 호환표로 추론) |

- **F1 이 연 길을 세는 자리**(`CLAUDE.md` «재확인이 잡는 자격 행의 순서를 바꾸는 고침은 …»): 관리자 재확인을 부르는 쓰기는 업로드 · 숨김 둘. 세션 행을 잡는 다른 자리는 로그아웃 `DELETE` · `resolveSession` 의 `last_seen_at` 갱신(둘 다 한 문장) · 비밀번호 바꾸기 `DELETE`(사용자 행을 먼저 쥐어 F1 의 B 와 사용자 행에서 줄 선다 — 위 값). 사용자 행을 잡는 다른 자리는 `setInstanceAdmin`(한 문장).
- **판 카나리아:** F1 에서 R1 케이스는 붙잡는 자리의 B 가 세션 행을 아직 안 쥐어 «줄 서지 않았다»로 던진다(구분력으로 안 셈) — 케이스 머리말에 고친 뒤 바꿀 두 글자를 적었다.

### R2 — 옛 비밀번호 로그인이 바꾸기 뒤에 산다(빨강)

판(«옛 비밀번호로 견준 로그인이 세션 삽입 앞에 선 사이 …»): alice 의 옛 비밀번호 로그인을 `insert into "sessions"` 앞에 붙잡음(비밀번호는 이미 견줌) → 바꾸기 204 → 놓음 → 로그인 **200** · 그 쿠키 `/me` **200** · 세션 2.

- **원인:** 로그인은 트랜잭션 밖에서 해시를 읽고 견준 뒤 세션을 넣는다. 바꾸기의 `DELETE` 는 커밋 순간 있는 행만 지운다.
- **왜 높음인가(추론 — 되풀이 판은 안 쟀다):** 옛 비밀번호를 아는 쪽이 로그인을 되풀이하면 창(해시 읽기 → scrypt(운영 N=32768) → `isInstanceAdmin` → 삽입)이 바꾸기의 커밋을 걸칠 확률이 높다. 성공한 로그인은 제 한도 자리를 걷으므로(`admission.succeeded`) 되풀이가 한도에 안 막힌다. «다른 기기의 로그인은 끊겼습니다»(화면 문장)가 그 판에서 거짓이다.
- **원래 있던 길:** 재설정 명령도 같은 판에서 로그인 200 · `/me` 200 · 세션 1(명령은 전부 지움 — 늦은 로그인 하나가 남음).
- **고칠 방향(안 쟀다):** 세션 삽입을 «견준 해시가 아직 그 해시일 때만» 으로 — 예: `insert into sessions … select … from users where id = $1 and password_hash = $견준해시`(0 행이면 401), 또는 로그인이 삽입 트랜잭션에서 사용자 행을 `KEY SHARE` 로 다시 읽어 견준 해시와 같은지 본다(바꾸기의 `NO KEY UPDATE` 와는 안 부딪히므로 해시 비교가 판정이다).

## 4. 웹의 `wrong-password`

- 가르는 자리: `account/password-section.tsx` 의 `isWrongPassword`(코드 `unauthenticated` + 이슈 코드 `wrong-password`)가 `toFailure` **앞**이다. 이슈 없는 401 은 `toFailure` → `signed-out` → `<SignedOut />`(구현 W4 · 케이스 «대조 — 이슈 없는 401 …» 이 `/login` 을 잰다). 429 · 400 은 서버 문장(구현 케이스 둘).
- 흉내: 서버에서 `wrong-password` 를 싣는 자리는 `routes/auth.ts` 의 `/password` 핸들러(지금 비밀번호가 틀린 갈래) 하나(`git grep -n "WRONG_PASSWORD\|wrong-password" -- apps packages`). `unauthenticated(…, issues)` 를 이슈와 함께 부르는 자리도 그 하나이고 이슈는 상수다 — 요청이 이슈를 싣게 할 입력이 없다. 웹 http 클라이언트에는 401 을 스스로 다루는 자리가 없다.
- 판정: 초록. 새 케이스 없음.

- **원인:** 줄은 `.wb-shell-project-item`(flex · wrap)이고 이메일 칸이 `flex: 1 1 auto` 라 끝 단추가 줄 오른끝에 붙는다. 누르면 «제외» 자리에 «취소» · «… 제외 확정» 둘이 서고, 오른끝에 붙는 것은 확정이다. `detail > 1` 겹(jsdom 이 잼)은 연타만 막는다 — 따로 누른 두 번은 이 배치 하나가 가른다.
- **무게:** 제외는 다시 초대로 되돌리지만 **그 사람의 그 프로젝트 토큰은 서버가 함께 지운다**(되돌릴 수 없음).
- **고칠 방향(안 쟀다):** 토큰 절의 둘째 겹과 같은 꼴 — 확정이 묻던 자리에서 단추 한 높이 이상 떨어져 서게(`shell.css` «내 API 토큰» 블록 · `build-test/tokens-confirm.test.ts` «거리» 판). 이 파일의 «자리» 판은 그 거리를 안 잰다 — 고칠 때 토큰 파일의 «거리» 판을 함께 옮긴다.

**R4(낮음):** 서버가 프로젝트 이름을 NFC 로 펴지 않아 조합형으로 붙여 만든 이름은 완성형 입력으로 못 지운다(붙여 넣으면 된다 — 안전 쪽 실패). 고칠 방향: 두 쪽을 NFC 로 편 뒤 견준다 — 지우는 대상은 이름이 아니라 id 라 편다고 다른 프로젝트를 지우지 않는다. 그렇게 고치면 새 케이스의 NFC 판을 뒤집는다(지금 동작을 잠근 케이스다).
