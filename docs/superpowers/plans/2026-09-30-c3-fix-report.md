## R2 — 옛 비밀번호로 견준 로그인이 바꾸기 뒤에 산다

### 재현

리뷰 케이스 그대로: 로그인 200 · 그 쿠키 `/me` 200 · 세션 2(`expected 200 to be 401`).

### 고침 — 두 방향 가운데

리뷰의 두 방향(`INSERT … SELECT … WHERE password_hash = $견준해시` · 삽입 트랜잭션에서 사용자 행을 `KEY SHARE` 로 다시 읽어 견줌) 가운데 **첫째 꼴을 `FOR SHARE` 로 잠가** 골랐다(`createLoginSession` — 한 문장).

- **`KEY SHARE` 는 창을 남긴다.** 바꾸기의 `UPDATE`(`FOR NO KEY UPDATE`)와 안 부딪혀, 바꾸기가 세션 `DELETE` 를 마친 뒤 · 커밋 앞에 로그인 삽입이 돌면 스냅숏의 옛 해시와 맞아 넣고 먼저 커밋한다 — 그 세션은 `DELETE` 가 못 본 행이라 남는다. 변조 M-b(아래)가 값으로 쟀다: 창 판에서 로그인 200 · `/me` 200.
- **`FOR SHARE` 는** 커밋 안 된 `UPDATE` 를 기다린 뒤 바뀐 행으로 조건을 다시 보고 0 행이 된다(창 판 `waited queued` 뒤 401). 로그인이 먼저 잡으면 바꾸기의 `UPDATE` 가 그 커밋을 기다리고 그 뒤의 `DELETE` 가 새 세션을 본다.
- 한 문장이라 리뷰의 붙잡는 자리(`insert into "sessions"` 앞)가 그대로 «견준 뒤 · 확인 앞» 이다.
- 잠그는 것은 사용자 행 하나이고 기존 세션 행은 안 잡는다 — R1 의 표에 «로그인 삽입» 줄로 넣었다.

### 응답 · 한도

- **같은 코드 · 문장:** 틀린 비밀번호와 같은 401 `unauthenticated` · `이메일 또는 비밀번호가 올바르지 않습니다`(케이스가 틀린 로그인의 본문과 글자로 견준다). 없는 계정도 같은 봉투다(`dummyHash` 머리말).
- **시간대:** 같지 않다 — 이 판은 성공과 같은 길(관리자 표시 읽기 · 삽입 문장)을 더 돌아 틀린 비밀번호보다 질의 둘만큼 늦다(재지 않았다 — 붙잡는 판이라 자연 시간이 안 나온다). 그 차이가 말하는 것은 «견줄 때는 맞았다» 뿐이고 200 이 말할 것 이상을 새지 않는다 — 없는 계정 · 있는 계정은 그 전에 갈리지 않는다. `routes/auth.ts` 의 `dummyHash` 머리말에 적었다.
- **한도: 실패로 남긴다**(브리프 기본값). `admission.succeeded()` 를 세션이 선 뒤로 옮겼고, 0 행이면 아무것도 안 불러 실패로 남는다. 그 사이 DB 오류는 `abandoned()`(전처럼 자리를 걷음). 까닭: 낸 비밀번호가 세션을 낼 때 이미 그 사람의 것이 아니고, 성공으로 세면 옛 비밀번호를 쥔 쪽이 바꾸기와 겹쳐 되풀이하는 시도가 한도에 안 걸린다.
