## 바꾼 것

- **api** — 새 프레임 `comments-changed { projectId, pageId }`(`apps/api/src/ws/protocol.ts` · `ws/notify.ts` 의 `notifyCommentsChanged`). 코멘트 쓰기가 커밋 뒤 보낸다
  (`routes/comments.ts`): 게시 201 · 본문 고침 · 삭제는 낸 연결을 빼고(`broadcastOrigin`), 같은 키의 재생(가드 앞 · 잠금 안)은 빼지 않는다. 가드 앞 재생은
  `passesPostGuardNow` 안에서만 낸다(번호 프레임과 같다). 재번호는 안 낸다(행이 그대로다). `apps/api/README.md` 프레임 표에 한 줄.
- **web** — `realtime/comment-signals.ts`(소켓 → 목록 신호 통로, `RealtimeSetup.comments` · `main.tsx` 가 만든다). `use-realtime.ts` 가 `comments-changed` ·
  `page-stale` · 다시 붙음(둘째 `open` 부터 — «어느 페이지든»)에 낸다. `panels/comment-panel.tsx` 의 `reread`: 신호를 200ms 창(`REREAD_BATCH_MS`)에 묶어
  조회 하나, 답은 `answered`(늦게 낸 조회만), 도는 동안 말 없음 · 실패는 `REFRESH` 칸의 «목록을 다시 불러오지 못했습니다». «컴포넌트» 탭은 다른 노드를 고르면
  같은 `reread` 를 부른다(처음 고른 노드는 마운트 조회가 읽는다).
- 정본 설계서 §7 «코멘트 목록도 실시간이다» 절 · «컴포넌트» 탭 문장. `component-tab.test.ts` 머리말 한 줄.

## 결정

1. **새 프레임을 둔다.** 이미 오는 신호로 셌다: 코멘트 쓰기가 내는 것은 번호가 바뀔 때의 `page-changed`(첫 말 · 마지막 삭제 · 재번호)뿐이다 — 둘째 말 · 본문 고침 ·
   마지막이 아닌 삭제는 아무 신호도 없다. `page-changed` 에 목록 다시 읽기를 걸어도 다섯 걸음 중 셋이 안 선다. api · web 를 이 브랜치에서 함께 넣었다
   (웹이 모르는 프레임은 `parseServerFrame` 이 버리므로 한쪽만 병합돼도 깨지지는 않는다 — 안 설 뿐이다).
2. **본문 없는 신호.** 룸의 연결은 모두 viewer 이상(목록을 읽을 수 있다)이지만 다시 읽기는 REST 가드를 탄다 — 강등 · 제외와 겹친 판도 조회가 가른다.
3. **낸 연결은 뺀다 · 재생은 안 뺀다.** 낸 화면은 쓰기 뒤 `refresh` 로 읽는다(빼지 않으면 조회 하나가 더). 재생은 앞 요청이 답을 잃었으면 신호가 아무 데도 안
   갔으므로 번호 프레임(`rebroadcastPostRevision`)과 같은 판정이다.
4. **«해결한다» 는 없다.** 브리프의 «해결하면» 에 해당하는 쓰기(코멘트 해결 상태)가 저장소에 없다(`git grep -n -i 'resolve\|해결' -- apps/api/src/routes/comments.ts` 0) —
   잴 것이 없어 단다 · 고친다 · 지운다만 쟀다.
5. **다시 읽는 동안 앞 목록 그대로 · «불러오는 중» 없음 · 실패는 앞 목록 + 문장** — 이월 문장 그대로 두었다(신호 다시 읽기도 같은 꼴). 남이 쓸 때마다 «다시 불러오는 중»
   이 깜박이면 거짓 경보라 신호 다시 읽기는 도는 동안 말하지 않는다.
6. **묶음 = 고정 창(200ms).** 첫 신호가 창을 열고 그 안의 신호는 그 조회 하나다(뒤로 밀지 않는다 — 신호가 끝없이 와도 창마다 하나). 겹친 조회는 막지 않고 `answered`
   로 가른다 — 앞 조회가 매달려도 뒤 조회가 선다.
7. **늦은 커밋의 `page-stale` 에도 다시 읽는다.** 답을 잃은 게시 · 삭제가 늦게 커밋되면 서버는 `page-stale` 만 낸다(`runWrite`). 편집의 늦은 커밋에도 조회 하나가
   는다(목록이 열려 있을 때만).

## 남은 것

- **본문 고침의 COMMIT 답을 잃으면 남에게 신호가 없다.** `PATCH …/comments/:id` 는 `runWrite`(늦은 커밋 지켜보기)를 안 타고 `withTransaction` 이라 답을 잃은 고침이
  커밋돼도 `comments-changed` · `page-stale` 둘 다 안 간다. 남의 목록은 다음 신호 · 노드 바꿈 · 탭 다시 열기에 선다. 같은 꼴로 마지막이 아닌 삭제의 늦은 커밋도
  신호가 없다(정본 §7 «문서를 안 바꾼 쓰기 … 커밋돼도 신호가 없다» 와 같은 판).
- **늦은 편집 커밋의 `page-stale` 도 목록 조회 하나를 낸다**(결정 7) — 목록이 열려 있을 때만.
- 묶음 창 200ms 는 몰아친 REST 여섯(이 기계 · 로컬)에서 조회 1 로 잰 값이다. 신호가 창보다 드물게 오면 신호마다 조회 하나다.
- 병합 충돌 자리: 정본 설계서 §7(«메뉴 트리도 실시간이다» 바로 앞에 절 하나) · «컴포넌트» 탭 문장(811행 근처) — ms 트랙도 정본을 고칠 수 있다.

## 지침

- **무엇이 틀렸나(비었나):** api 케이스 파일을 새로 세울 때 «청소는 `beforeEach(resetRealData)` · `afterEach(resetRealData)` 두 줄을 그 글자 그대로» 라는 것이
  인구조사(`apps/api/test/real-api-harness.test.ts`)에만 있다 — 지침 «검증 — wirebound» 는 «`withRealApi` 케이스는 `beforeEach/afterEach(resetRealData)` 를 둔다» 고만 적어
  `afterEach(async () => { await resetRealData() })` 꼴(기존 `comment-replay-broadcast.test.ts` 가 쓰는 꼴 — `withProxiedRealApi` 라 인구조사 밖)을 베끼면 전량에서야 걸린다.
  **어디:** `.ruler/` 소스의 «검증 — wirebound» 「목 · 계측은 불린 수를 값으로 확인하고 …」 절의 `withRealApi` 문장. **넣을 문장:** «청소는 글자 그대로
  `beforeEach(resetRealData)` · `afterEach(resetRealData)` 로 건다 — 인구조사(`apps/api/test/real-api-harness.test.ts`)가 그 글자를 센다. `withProxiedRealApi` 파일의
  `afterEach(async () => …)` 꼴을 베끼면 `withRealApi` 를 쓰는 순간 전량에서 빨강이다.»
- **무엇이 틀렸나:** api WS 케이스에서 «걸음 뒤 `probe.quiet()`» 로 받은 프레임을 세면, 방송이 응답을 기다리지 않아 응답보다 먼저 닿은 프레임을 못 센다(`quiet` 는 부른 뒤 온
  것만 낸다) — 한 판에서 1 개를 놓쳐 «2 가 아니라 1» 로 거짓 빨강이었다. **어디:** 같은 절(`WsProbe.waitForCount` 문장 옆). **넣을 문장:** «`WsProbe.quiet()` 는
  부른 뒤에 온 프레임만 낸다 — 걸음 **앞에** `received.length` 를 적어 두고 창 뒤에 그 뒤를 센다(`apps/api/test/comments-changed.test.ts` 의 `mark`).»
