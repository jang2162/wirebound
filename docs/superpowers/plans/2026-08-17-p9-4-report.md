### 1.2 #2 — SDK가 끌고 오는 것 (**판정을 다시 했다**)

**잰 방법:** 스크래치패드에 빈 패키지를 만들어 `pnpm add @modelcontextprotocol/sdk@1.30.0
--ignore-workspace`를 돌리고, ① `.pnpm` 아래 디렉터리 수 ② `du -sk` ③ **ESM resolve 훅으로
stdio 서버가 실제로 로드하는 패키지**를 각각 쟀다.

| 축 | 값 |
|---|---|
| 설치되는 패키지 | **92개** |
| 디스크 | **24MB** |
| 그중 이 저장소가 이미 쓰는 것 | `zod@4.4.3` **6.4MB** (SDK가 `^3.25 \|\| ^4.0`을 받는다 — 새 판이 안 온다) |
| **stdio 경로에서 실제로 로드되는 것** | **5개** — `@modelcontextprotocol/sdk` · `ajv` · `ajv-formats` · `zod-to-json-schema` · `zod` |
| 로드되지 않는 것(설치만 된다) | `express@5.2.1` · `hono@4.13.2` · `@hono/node-server` · `cors` · `jose` · `eventsource` · `eventsource-parser` · `express-rate-limit` · `pkce-challenge` · `cross-spawn` · `raw-body` · `content-type` … |
| 로드 시 힙 증가 | **9.2MB** |

**`export-zip.ts`가 zip 라이브러리를 고를 때 쓴 표의 형식으로 다시 판정한다.**

| 길 | 대가 |
|---|---|
| **공식 SDK**(고른 것) | 안 쓰는 HTTP 서버 셋(`express`·`hono`·`cors`·`jose`·`express-rate-limit`)이 **`dependencies`로 딸려 온다** — optional peer가 아니라 하드 의존이라 `pnpm install`이 무조건 끌어온다. 92개·24MB |
| stdio JSON-RPC를 손으로 짠다 | 의존 0. **그러나 남이 정한 계약의 두 벌이 된다** — 프로토콜 버전 협상 · `initialize` 핸드셰이크 · capability 선언 · 요청/응답 스키마 · 알림 프레임을 전부 우리가 유지해야 하고, 계약이 바뀔 때 우리가 못 따라가면 **호스트가 안 붙는다** |

**판정: SDK를 유지한다.** 갈림은 `fflate`와 **반대 방향**이다 — zip은 우리가 *만드는* 형식이라
의존 0이 이겼지만, MCP는 우리가 *맞춰야 하는* 계약이다. 24MB는 개발 의존 트리에 들어가는
값이고(`packages/*`가 전부 `private: true`라 배포되지 않는다), **실행 시 로드되는 것은
다섯이라 기동 비용이 그 24MB에 비례하지 않는다.**

**그러나 계획서의 문장 *"의존이 감당할 만하다"*는 재기 전에는 근거가 없었다.** 92개 중 87개가
안 쓰이는 것이 값이고, 그것을 이월에 적는다.

### 1.3 #3 — 도구 실패와 결과를 무엇으로 가르나 (**D8이 걸린다**)

**잰 방법:** stdio 서버 하나와 진짜 `Client` 하나를 띄워 네 갈래를 실제로 불렀다.

| 서버가 한 것 | 클라이언트가 본 것 |
|---|---|
| `{ content: [...] }` | `isError=undefined`, 본문 그대로 |
| `{ content: [...], isError: true }` | **`isError=true`, 본문 그대로** — 예외가 아니다 |
| `throw new Error('평범한 예외')` | **던진다** — `McpError code=-32603` |
| `throw new McpError(InvalidParams, …)` | **던진다** — `McpError code=-32602` |
| 모르는 도구 이름 | 던진다 — `McpError code=-32601` |

**갈래가 둘이 아니라 셋이다.** 계획서 D8은 *"붙지 못한 것"*과 *"결과를 낸 것"* 둘로 적었는데,
MCP에는 **JSON-RPC 오류**(프로토콜 층)와 **`isError: true` 결과**(도구 층)와 **정상 결과** 셋이 있다.

**판정 — CLI 종료 코드 표를 셋에 나눠 싣는다.**

| CLI 코드 | MCP | 왜 |
|---|---|---|
| 1 (**명령을 잘못 썼다**) | **JSON-RPC 오류** (`InvalidParams` / `MethodNotFound`) | 부르는 쪽이 요청을 잘못 만든 것이다. 에이전트가 아니라 **도구 스키마**가 답을 갖고 있다 |
| 2·3·4 (**설정·자격·서버**) | **`isError: true` 결과** | 에이전트가 **문장을 읽고 사람에게 옮기거나 `wireb init`을 치게** 해야 한다(D4). JSON-RPC 오류로 내면 많은 호스트가 그것을 모델에 안 보이고 *"도구가 고장났다"*로 접는다 |
| 0·10 (**제대로 서서 결과를 냈다**) | **정상 결과** | `validate`가 결함을 찾은 것은 오류가 아니다(D8) |

**응답에 CLI 종료 코드를 싣는다.** `[wireb 코드 2]`가 문장 앞에 붙으므로 **같은 상태를 두 도구가
같은 값으로 말한다** — 그것이 *"같은 함수를 부른다"*를 눈에 보이게 만드는 자리다.

**덧 — SDK가 `McpError`의 문장을 두 번 싣는다.** 서버가 `new McpError(-32602, '인자가 틀렸다')`를
던지면 클라이언트가 받는 문장이 `MCP error -32602: MCP error -32602: 인자가 틀렸다`다(실측).
`McpError.message`가 이미 접두를 갖는데 클라이언트가 한 번 더 붙인다. 우리 쪽에서 고칠 자리가
아니므로 적어만 둔다.

### 1.4 #4 — stdio로 충분하다

§12.1이 *"리포에서 `wireb`나 MCP를 쓰면"*이라고 적었고 **프로젝트를 정하는 것이 리포의
`.wirebound.json`이다**(D4). 그 파일을 찾으려면 서버가 **에이전트의 cwd에서 도는 로컬
프로세스**여야 한다 — HTTP 전송이면 서버가 남의 기계에 있어 `io.cwd`가 무의미해진다.
**전송을 고르는 것이 아니라 D4가 전송을 정한다.**

### 1.5 #5 — `packages/cli`가 subpath를 내준다

선례는 `packages/exporter`의 `"./test-support": "./test-support/index.ts"`다(조건 없이 소스를
직접 가리킨다 — `dist`에 안 들어간다. `files`가 `dist`뿐이다).

**두 가지를 함께 확인했다.**

1. **런타임 subpath**는 조건부여야 한다. `packages/cli`의 `.`이 이미
   `{ development, types, import, default }` 네 조건을 쓰고 `tsconfig.base.json`이
   `customConditions: ["development"]`를 걸어 **`tsc`가 소스를 직접 본다**. 같은 모양으로
   `./embed`을 냈다.
2. **vitest는 조건 해석에 안 기댄다.** 루트 `vitest.config.ts`가 alias로 소스를 직접 가리키고
   (*"조건 해석에 기대지 않아 결정적이다"*), 그 파일이 **좁은 것을 먼저 두라**고 적어 뒀다
   (rollup alias가 `id === find || id.startsWith(find + '/')`로 맞추고 앞의 것이 이긴다).
   `@wirebound/cli/embed`·`@wirebound/cli/test-support`를 `@wirebound/cli`보다 **앞에** 뒀다.

**tsdown이 진입점을 나눠도 모듈이 두 벌이 되지 않는다.** 오늘 `index.js`(294B)와 `bin.js`(1088B)가
공유 청크 `node-io-*.js`(65KB) 하나를 함께 import한다 — 세 번째 진입점도 같은 청크를 본다.
**`CliError`의 identity가 진입점마다 갈리지 않는다**는 뜻이고, `instanceof`로 갈래를 만드는
`run.ts`·`outcome.ts`가 그것에 기댄다.

### 1.6 #6 — `io-boundary`의 분모는 `packages/cli`만 본다 (**지적이다**)

`packages/cli/test/io-boundary.test.ts:16`이 `SRC = new URL('../src', import.meta.url)`이다.
**`packages/cli/src` 하나다.** 그러므로 계획서 D3의 마지막 줄대로 **`packages/mcp`가 `node:*`를
직접 불러도 그 자는 아무것도 안 죽는다.**

**닫았다.** `packages/mcp/test/io-boundary.test.ts`가 같은 술어로 `packages/mcp/src`를 훑는다.
목록은 `bin.ts` 하나다 — 서버 자체는 `io`를 인자로 받는다(§3.3).

### 1.7 #7 — `GET .../snapshot`은 잠금에 안 막힌다

**잰 방법:** 호출자 인구조사. *"이 자리가 남의 잠금 안인가"*를 정하는 것은
`apps/api/src/lock/check.ts`의 `lockConflictError` 하나이고(P3-3 이월 §4의 계약),
그것을 부르는 자리는 **셋뿐이다** — `routes/pages.ts:424` · `routes/pages.ts:503` · `ws/patch.ts:70`.
**전부 쓰기다.** `routes/snapshots.ts`는 `lock/check`를 import조차 안 한다.

계획서 사실 8과 P9-3 이월 §4가 그렇게 적었고, **그 근거가 무엇인지는 안 적혀 있었다.**
근거는 이것이다.

### 1.8 #8 — `pageView`도 카탈로그를 필요로 한다 (**축은 하나뿐이다**)

**잰 방법:** `installCatalog()` 전후로 같은 픽스처를 `pageView`에 넣고 세 축을 찍었다.

| 축 | 설치 전 | 설치 후 |
|---|---|---|
| `interactions[].text` | `① 검색 버튼 클릭 시 ② 목록이 **loading**로 바뀝니다` | `… ② 목록이 **로딩 상태**로 바뀝니다` |
| `nodes[].name` | `페이지` · `① 검색 버튼` · `② 목록` | **같다** |
| `comments[].nodeName` | `② 목록` | **같다** |

**필요로 한다. 다만 걸리는 축은 상호작용 문장 하나다** — 노드 이름과 코멘트 노드 이름은
카탈로그와 무관하다(`describeNode`가 `marker`·`props.label`을 본다). **던지지 않는다.**

**`lint` 쪽은 훨씬 크다** — 같은 픽스처로 다시 쟀다(P9-3 이월 §1의 값을 독립적으로 재현했다).

| | 이슈 |
|---|---|
| `installCatalog()` 전 | **5건** — 전부 `document-invalid:error` (`알 수 없는 컴포넌트 타입: Page`·`Button`·`List`·`Page`·`Page`) |
| 〃 후 | **0건** |

**그러므로 `installCatalog`를 부르는 자리를 하나로 둔다**(§3.2).

## 2. T1 — CLI가 무엇을 어느 순서로 부르나 (D1)

`packages/cli/src/commands/page-get.ts`·`lint.ts`를 읽고 적는다. **이 표가 MCP가 다시 짜면
안 되는 것의 목록이다.**

| # | `wireb page get <경로>` | `wireb lint [경로]` |
|---|---|---|
| 1 | 경로 인자가 비면 `usageError` | `--fail-on` 값을 읽는다 |
| 2 | `requireProject(io)` | `requireProject(io)` |
| 3 | — | **`readLintConfig(access.binding)`** |
| 4 | `fetchSnapshot(io, access)` | `fetchSnapshot(io, access)` |
| 5 | **`installCatalog()`** | **`installCatalog()`** |
| 6 | `targetedPages({ menu, pages })` | `snapshotToLintInput(payload, config)` → `lintProject(plan.input)` |
| 7 | `matchPageTargets(ordered, path)` | `targetedPages({ menu, pages })` → `pageTargetPath`로 id→경로 지도 |
| 8 | **0건·2건 이상을 갈라 말한다**(둘 다 코드 1) | 경로가 있으면 `matchPageTargets` → **0건이면 코드 1** |
| 9 | `pageView({ … comments 걸러 넣기 … })` | `filterLintIssues(all, { pageIds })` |
| 10 | 글자로 바꾼다 (`renderPageView`) | `notes` → 이슈 줄 → 요약 → **경로 밖 `error` 개수** |
| 11 | — | 종료 코드는 **걸러진 것**에서 낸다(P9-3 리뷰 N1) |

**2·4·5는 완전히 같고 6~9가 도구별로 갈린다.** 그 6~9가 *"조립"*이고, MCP가 그것을 다시
쓰면 **두 벌**이 된다 — 계획서 D1이 막으라고 한 것이 이것이다.

**그래서 6~9를 `packages/cli/src/read/`로 옮기고 CLI와 MCP가 그것을 함께 부른다**(§3.2).
`page-get.ts`·`lint.ts`에는 **10·11만 남는다** — 그 파일들의 머리말이 원래 *"이 파일에는 글자만
있다"*라고 적어 둔 상태에 실제로 도달한다.
