### 1.2 #2 — SDK가 끌고 오는 것 (**판정을 다시 했다**)

**잰 방법:** 스크래치패드에 빈 패키지를 만들어 `pnpm add @modelcontextprotocol/sdk@1.30.0
--ignore-workspace`를 돌리고, ① `.pnpm` 아래 디렉터리 수 ② `du -sk` ③ **ESM resolve 훅으로
stdio 서버가 실제로 로드하는 패키지**를 각각 쟀다.

| 축 | 값 |
|---|---|
| 설치되는 패키지 | **92개** |
| 디스크 | **24MB** |
| 그중 이 저장소가 이미 쓰는 것 | `zod@4.4.3` **6.4MB** (SDK가 `^3.25 \|\| ^4.0`을 받는다 — 새 판이 안 온다) |
| **stdio 경로에서 실제로 로드되는 것** | **5개** — `@modelcontextprotocol/sdk` · `ajv` · `ajv-formats` · `zod-to-json-schema` · `zod` |
| 로드되지 않는 것(설치만 된다) | `express@5.2.1` · `hono@4.13.2` · `@hono/node-server` · `cors` · `jose` · `eventsource` · `eventsource-parser` · `express-rate-limit` · `pkce-challenge` · `cross-spawn` · `raw-body` · `content-type` … |
| 로드 시 힙 증가 | **9.2MB** |

**`export-zip.ts`가 zip 라이브러리를 고를 때 쓴 표의 형식으로 다시 판정한다.**

| 길 | 대가 |
|---|---|
| **공식 SDK**(고른 것) | 안 쓰는 HTTP 서버 셋(`express`·`hono`·`cors`·`jose`·`express-rate-limit`)이 **`dependencies`로 딸려 온다** — optional peer가 아니라 하드 의존이라 `pnpm install`이 무조건 끌어온다. 92개·24MB |
| stdio JSON-RPC를 손으로 짠다 | 의존 0. **그러나 남이 정한 계약의 두 벌이 된다** — 프로토콜 버전 협상 · `initialize` 핸드셰이크 · capability 선언 · 요청/응답 스키마 · 알림 프레임을 전부 우리가 유지해야 하고, 계약이 바뀔 때 우리가 못 따라가면 **호스트가 안 붙는다** |

**판정: SDK를 유지한다.** 갈림은 `fflate`와 **반대 방향**이다 — zip은 우리가 *만드는* 형식이라
의존 0이 이겼지만, MCP는 우리가 *맞춰야 하는* 계약이다. 24MB는 개발 의존 트리에 들어가는
값이고(`packages/*`가 전부 `private: true`라 배포되지 않는다), **실행 시 로드되는 것은
다섯이라 기동 비용이 그 24MB에 비례하지 않는다.**

**그러나 계획서의 문장 *"의존이 감당할 만하다"*는 재기 전에는 근거가 없었다.** 92개 중 87개가
안 쓰이는 것이 값이고, 그것을 이월에 적는다.

### 1.3 #3 — 도구 실패와 결과를 무엇으로 가르나 (**D8이 걸린다**)

**잰 방법:** stdio 서버 하나와 진짜 `Client` 하나를 띄워 네 갈래를 실제로 불렀다.

| 서버가 한 것 | 클라이언트가 본 것 |
|---|---|
| `{ content: [...] }` | `isError=undefined`, 본문 그대로 |
| `{ content: [...], isError: true }` | **`isError=true`, 본문 그대로** — 예외가 아니다 |
| `throw new Error('평범한 예외')` | **던진다** — `McpError code=-32603` |
| `throw new McpError(InvalidParams, …)` | **던진다** — `McpError code=-32602` |
| 모르는 도구 이름 | 던진다 — `McpError code=-32601` |

**갈래가 둘이 아니라 셋이다.** 계획서 D8은 *"붙지 못한 것"*과 *"결과를 낸 것"* 둘로 적었는데,
MCP에는 **JSON-RPC 오류**(프로토콜 층)와 **`isError: true` 결과**(도구 층)와 **정상 결과** 셋이 있다.

**판정 — CLI 종료 코드 표를 셋에 나눠 싣는다.**

| CLI 코드 | MCP | 왜 |
|---|---|---|
| 1 (**명령을 잘못 썼다**) | **JSON-RPC 오류** (`InvalidParams` / `MethodNotFound`) | 부르는 쪽이 요청을 잘못 만든 것이다. 에이전트가 아니라 **도구 스키마**가 답을 갖고 있다 |
| 2·3·4 (**설정·자격·서버**) | **`isError: true` 결과** | 에이전트가 **문장을 읽고 사람에게 옮기거나 `wireb init`을 치게** 해야 한다(D4). JSON-RPC 오류로 내면 많은 호스트가 그것을 모델에 안 보이고 *"도구가 고장났다"*로 접는다 |
| 0·10 (**제대로 서서 결과를 냈다**) | **정상 결과** | `validate`가 결함을 찾은 것은 오류가 아니다(D8) |

**응답에 CLI 종료 코드를 싣는다.** `[wireb 코드 2]`가 문장 앞에 붙으므로 **같은 상태를 두 도구가
같은 값으로 말한다** — 그것이 *"같은 함수를 부른다"*를 눈에 보이게 만드는 자리다.

**덧 — SDK가 `McpError`의 문장을 두 번 싣는다.** 서버가 `new McpError(-32602, '인자가 틀렸다')`를
던지면 클라이언트가 받는 문장이 `MCP error -32602: MCP error -32602: 인자가 틀렸다`다(실측).
`McpError.message`가 이미 접두를 갖는데 클라이언트가 한 번 더 붙인다. 우리 쪽에서 고칠 자리가
아니므로 적어만 둔다.

### 1.4 #4 — stdio로 충분하다

§12.1이 *"리포에서 `wireb`나 MCP를 쓰면"*이라고 적었고 **프로젝트를 정하는 것이 리포의
`.wirebound.json`이다**(D4). 그 파일을 찾으려면 서버가 **에이전트의 cwd에서 도는 로컬
프로세스**여야 한다 — HTTP 전송이면 서버가 남의 기계에 있어 `io.cwd`가 무의미해진다.
**전송을 고르는 것이 아니라 D4가 전송을 정한다.**

### 1.5 #5 — `packages/cli`가 subpath를 내준다

선례는 `packages/exporter`의 `"./test-support": "./test-support/index.ts"`다(조건 없이 소스를
직접 가리킨다 — `dist`에 안 들어간다. `files`가 `dist`뿐이다).

**두 가지를 함께 확인했다.**

1. **런타임 subpath**는 조건부여야 한다. `packages/cli`의 `.`이 이미
   `{ development, types, import, default }` 네 조건을 쓰고 `tsconfig.base.json`이
   `customConditions: ["development"]`를 걸어 **`tsc`가 소스를 직접 본다**. 같은 모양으로
   `./embed`을 냈다.
2. **vitest는 조건 해석에 안 기댄다.** 루트 `vitest.config.ts`가 alias로 소스를 직접 가리키고
   (*"조건 해석에 기대지 않아 결정적이다"*), 그 파일이 **좁은 것을 먼저 두라**고 적어 뒀다
   (rollup alias가 `id === find || id.startsWith(find + '/')`로 맞추고 앞의 것이 이긴다).
   `@wirebound/cli/embed`·`@wirebound/cli/test-support`를 `@wirebound/cli`보다 **앞에** 뒀다.

**tsdown이 진입점을 나눠도 모듈이 두 벌이 되지 않는다.** 오늘 `index.js`(294B)와 `bin.js`(1088B)가
공유 청크 `node-io-*.js`(65KB) 하나를 함께 import한다 — 세 번째 진입점도 같은 청크를 본다.
**`CliError`의 identity가 진입점마다 갈리지 않는다**는 뜻이고, `instanceof`로 갈래를 만드는
`run.ts`·`outcome.ts`가 그것에 기댄다.

### 1.6 #6 — `io-boundary`의 분모는 `packages/cli`만 본다 (**지적이다**)

`packages/cli/test/io-boundary.test.ts:16`이 `SRC = new URL('../src', import.meta.url)`이다.
**`packages/cli/src` 하나다.** 그러므로 계획서 D3의 마지막 줄대로 **`packages/mcp`가 `node:*`를
직접 불러도 그 자는 아무것도 안 죽는다.**

**닫았다.** `packages/mcp/test/io-boundary.test.ts`가 같은 술어로 `packages/mcp/src`를 훑는다.
목록은 `bin.ts` 하나다 — 서버 자체는 `io`를 인자로 받는다(§3.3).

### 1.7 #7 — `GET .../snapshot`은 잠금에 안 막힌다

**잰 방법:** 호출자 인구조사. *"이 자리가 남의 잠금 안인가"*를 정하는 것은
`apps/api/src/lock/check.ts`의 `lockConflictError` 하나이고(P3-3 이월 §4의 계약),
그것을 부르는 자리는 **셋뿐이다** — `routes/pages.ts:424` · `routes/pages.ts:503` · `ws/patch.ts:70`.
**전부 쓰기다.** `routes/snapshots.ts`는 `lock/check`를 import조차 안 한다.

계획서 사실 8과 P9-3 이월 §4가 그렇게 적었고, **그 근거가 무엇인지는 안 적혀 있었다.**
근거는 이것이다.

### 1.8 #8 — `pageView`도 카탈로그를 필요로 한다 (**축은 하나뿐이다**)

**잰 방법:** `installCatalog()` 전후로 같은 픽스처를 `pageView`에 넣고 세 축을 찍었다.

| 축 | 설치 전 | 설치 후 |
|---|---|---|
| `interactions[].text` | `① 검색 버튼 클릭 시 ② 목록이 **loading**로 바뀝니다` | `… ② 목록이 **로딩 상태**로 바뀝니다` |
| `nodes[].name` | `페이지` · `① 검색 버튼` · `② 목록` | **같다** |
| `comments[].nodeName` | `② 목록` | **같다** |

**필요로 한다. 다만 걸리는 축은 상호작용 문장 하나다** — 노드 이름과 코멘트 노드 이름은
카탈로그와 무관하다(`describeNode`가 `marker`·`props.label`을 본다). **던지지 않는다.**

**`lint` 쪽은 훨씬 크다** — 같은 픽스처로 다시 쟀다(P9-3 이월 §1의 값을 독립적으로 재현했다).

| | 이슈 |
|---|---|
| `installCatalog()` 전 | **5건** — 전부 `document-invalid:error` (`알 수 없는 컴포넌트 타입: Page`·`Button`·`List`·`Page`·`Page`) |
| 〃 후 | **0건** |

**그러므로 `installCatalog`를 부르는 자리를 하나로 둔다**(§3.2).

## 2. T1 — CLI가 무엇을 어느 순서로 부르나 (D1)

`packages/cli/src/commands/page-get.ts`·`lint.ts`를 읽고 적는다. **이 표가 MCP가 다시 짜면
안 되는 것의 목록이다.**

| # | `wireb page get <경로>` | `wireb lint [경로]` |
|---|---|---|
| 1 | 경로 인자가 비면 `usageError` | `--fail-on` 값을 읽는다 |
| 2 | `requireProject(io)` | `requireProject(io)` |
| 3 | — | **`readLintConfig(access.binding)`** |
| 4 | `fetchSnapshot(io, access)` | `fetchSnapshot(io, access)` |
| 5 | **`installCatalog()`** | **`installCatalog()`** |
| 6 | `targetedPages({ menu, pages })` | `snapshotToLintInput(payload, config)` → `lintProject(plan.input)` |
| 7 | `matchPageTargets(ordered, path)` | `targetedPages({ menu, pages })` → `pageTargetPath`로 id→경로 지도 |
| 8 | **0건·2건 이상을 갈라 말한다**(둘 다 코드 1) | 경로가 있으면 `matchPageTargets` → **0건이면 코드 1** |
| 9 | `pageView({ … comments 걸러 넣기 … })` | `filterLintIssues(all, { pageIds })` |
| 10 | 글자로 바꾼다 (`renderPageView`) | `notes` → 이슈 줄 → 요약 → **경로 밖 `error` 개수** |
| 11 | — | 종료 코드는 **걸러진 것**에서 낸다(P9-3 리뷰 N1) |

**2·4·5는 완전히 같고 6~9가 도구별로 갈린다.** 그 6~9가 *"조립"*이고, MCP가 그것을 다시
쓰면 **두 벌**이 된다 — 계획서 D1이 막으라고 한 것이 이것이다.

**그래서 6~9를 `packages/cli/src/read/`로 옮기고 CLI와 MCP가 그것을 함께 부른다**(§3.2).
`page-get.ts`·`lint.ts`에는 **10·11만 남는다** — 그 파일들의 머리말이 원래 *"이 파일에는 글자만
있다"*라고 적어 둔 상태에 실제로 도달한다.

## 3. 판정 — 계획서가 정하지 않은 자리

### 3.1 조립을 `packages/cli/src/read/`로 옮겼다 (D1)

**계획서는 *"오늘 자리가 하나여도"*라고 적었다. 아니었다.**

§2의 표 6~9(무엇을 어느 순서로 엮는가)는 P9-3에서 **명령 파일 안에** 있었다. MCP가 같은
도구를 내려면 그것을 다시 써야 하고, 그러면 두 벌이 된다. **`page-get.ts`의 머리말이 그
사고를 미리 적어 뒀다** — *"§12.2의 MCP `get_page`가 같은 것을 내야 하므로 조립을 여기 두면
P9-4가 두 벌을 만든다."*

**옮긴 것:**

| 새 자리 | 무엇 |
|---|---|
| `read/catalog.ts` | `installCatalog()`를 부르는 **한 자리** |
| `read/page.ts` | `targetedPages`→`matchPageTargets`→0·1·다 갈래→`migrateDocument`→`pageView` |
| `read/lint.ts` | `snapshotToLintInput`→`lintProject`→`filterLintIssues`와 **범위 밖 개수 세기** |

`commands/page-get.ts`·`commands/lint.ts`에는 **글자와 종료 코드만** 남았다 — 그 파일들의
머리말이 원래 *"이 파일에는 글자만 있다"*라고 적어 둔 상태에 실제로 도달했다.

**`installCatalog`를 읽기 층이 부른다.** P9-3 이월 §1의 넷 중 첫째가 *"소비자가 부른다"*인데
**소비자가 둘이 된 순간 그 규칙이 위험해진다** — 하나를 빠뜨린 소비자가 조용히 거짓을 낸다.
순수 패키지는 여전히 안 부르고, 부르는 것은 읽기 층 하나다.

### 3.2 조립이 두 벌이 되는 길을 **둘로** 막았다

| 층 | 어디 | 무엇 |
|---|---|---|
| 구조 | `packages/mcp/package.json` | 런타임 의존이 `@wirebound/cli`와 MCP SDK **둘뿐이다.** `@wirebound/schema`를 import하는 줄이 애초에 해석되지 않는다 |
| 자 | `packages/cli/test/assembly-census.test.ts` | 조립 원시를 부르는 자리가 `read/` **셋**으로 고정 |
| 자 | `packages/mcp/test/assembly-census.test.ts` | 이 패키지에는 **하나도 없다** + 의존 목록이 둘이다 |
| 값 | `packages/mcp/test/read-tools.test.ts` | `wireb page get --json`과 `get_page`가 **같은 값**을 낸다 |

**마지막 줄이 따로 있는 이유:** 자만 있으면 읽기 층 **안에서** 갈래를 나눠도 안 걸린다
(`if (forMcp)`). 값을 맞대는 케이스가 그것을 잡는다.

### 3.3 D8을 셋으로 나눴다 — 계획서는 둘로 적었다

§1.3의 표가 판정이다. **인자 모양 오류만 JSON-RPC 오류이고, 못 붙은 것은 `isError` 결과다.**

계획서 D8이 *"자격이 없다·서버에 못 닿는다·프로젝트를 못 찾는다는 도구가 서지 못한 것이다"*
라고 적었고 그것은 맞다. **다만 그것을 MCP의 어느 갈래에 실을지는 안 적혔고**, JSON-RPC
오류에 실으면 D4가 원하는 것(*"에이전트가 그 문장을 읽고 `wireb init`을 치게 해야 한다"*)이
깨진다 — 호스트가 프로토콜 오류를 모델에 안 보이고 접는 판이 있다.

### 3.4 `get_page`·`validate`가 *"경로를 못 찾았다"*를 **결과로** 낸다

`wireb page get`은 그것을 코드 1로 끝낸다. **여기서는 다르게 정했다.**

**근거: 받는 쪽이 다르다.** 셸은 종료 코드를 읽고 에이전트는 값을 읽는다. 경로가 틀린 것은
**에이전트가 스스로 고칠 수 있는 상태**이고 고치려면 후보 목록을 읽어야 하는데, JSON-RPC
오류로 내면 그 목록이 *"도구가 고장났다"*와 함께 실려 나간다. 그래서 `found: false` ·
`reason` · `candidates`가 값이다.

**어긋남이 아니다:** `wireb`의 코드 1은 *"사람이 인자를 고쳐야 한다"*이고 여기 `found: false`도
같은 말이다. 다른 것은 **그 말을 나르는 통로**뿐이다.

### 3.5 `migrateDocument` — P9-3의 구멍을 **닫았다** (T4의 판정)

계획서가 *"`get_page`가 같은 구멍을 물려받을지 판정하라 — 둘이 갈리면 더 나쁘다"*고 물었다.

**판정: 물려받지 않는다. 읽기 층이 지난다.**

- **갈릴 수 있는 짝이 둘이었다.** ⓐ `wireb page get` ↔ `get_page`, ⓑ `page get` 계열 ↔
  `lint` 계열. 조립을 하나로 만들면서 ⓐ는 **구조적으로 사라졌고**, ⓑ는 한 줄로 닫혔다.
- **태도를 `snapshotToLintInput`에서 가져왔다** — *"못 올리면 그대로 쓰고 말한다."* 막으면
  옛 문서 하나가 페이지 조회 전체를 막고, 조용히 넘어가면 lint와 이 도구가 같은 페이지를
  다르게 읽는다.
- **오늘도 잴 수 있다.** `MIGRATIONS = []`이라 올릴 것은 없지만 `migrateDocument`가
  `version > CURRENT`에서 던지므로 **못 올리는 문서는 오늘 만들 수 있다.** 케이스가 그것을 든다.
- **남는 것:** *"못 올렸다"*를 말하는 문장이 두 자리에 있다(`packages/themes`의 `currentDocument`와
  `read/page.ts`). 합치려면 `packages/themes`가 그 판정을 함수로 내줘야 하고 그것은 이
  슬라이스 밖이다 — 이월에 적는다.

### 3.6 `.wirebound.json`을 못 찾았을 때 **찾은 자리**를 덧붙인다 (D4)

`wireb`의 문장은 *"리포 뿌리에서 `wireb init`을 먼저 실행하세요"*다. **사람에게는 충분하다** —
자기가 어느 디렉터리에서 쳤는지 안다. **에이전트는 모른다:** 이 서버를 띄운 것은 호스트이고
그 작업 디렉터리는 에이전트가 고른 것이 아니다.

**문장은 다시 쓰지 않았다.** `wireb`의 문장을 그대로 옮기고 `(MCP 서버가 <cwd> 에서부터 위로
찾았습니다)` 한 줄을 덧붙인다 — 두 도구가 다른 말을 하면 사람이 원인을 둘로 센다.

### 3.7 응답 형식은 **텍스트 안의 JSON**이다 — `structuredContent`를 안 쓴다

SDK가 `outputSchema` + `structuredContent`를 지원하지만 **안 썼다.**

- **호환이 갈린다.** 그 필드를 읽는 것은 최근 프로토콜 판의 클라이언트뿐이고, 안 읽는
  호스트에는 `content`를 **또** 실어야 한다 — 같은 값이 두 자리에 실린다.
- **`LintIssue`가 평평해서 접을 것이 없다**(P9-1 이월 §7). JSON 하나면 충분하다.
- **여는 날의 조건:** 응답 스키마를 표에 적게 되는 날이다. 그때 `TOOLS`에 `outputSchema`를
  더하고 `toolResult`가 두 자리에 같은 값을 싣는다.

## 10. `pnpm test`가 한 번 빨갰다 — **이 슬라이스와 무관한 흔들림이다**

**보고서 §5의 게이트를 다시 돌리다가 한 번 실패했다.** 그대로 적는다.

```
apps/api/test/comments-concurrency.test.ts
  × 코멘트 삭제의 동시성 > 409를 받은 삭제는 행을 남기지 않는다 (리뷰 B5)
    → expected [ 200, 200 ] to deeply equal [ 200, 409 ]
```

**쟀다.**

| 무엇 | 값 |
|---|---|
| `pnpm test` 전체 | **4번 초록 · 1번 빨강** (같은 트리·같은 커밋) |
| 그 파일만 따로 | **5번 전부 초록** |
| 이 슬라이스가 `apps/` 아래를 건드렸나 | **한 파일도 안 건드렸다** (`git diff --name-only 3b58936..HEAD -- apps/`가 비어 있다) |

**진단.** 그 케이스는 서로 다른 노드의 마지막 코멘트를 **동시에** 지워 하나가 `stale`로
409를 받는 것을 잰다. 그런데 *"실제로 겹쳤는가"*를 케이스가 **강제하지 않는다** —
`Promise.all`로 던질 뿐이다. 앞선 요청이 커밋을 마친 뒤에 뒤엣것이 seq를 읽으면 **둘 다
200이 되고 그것이 옳은 동작이다.** 전체 실행은 파일 256개가 함께 도는 부하 아래라
그 직렬화가 일어날 수 있고, 파일 하나만 돌리면 안 일어난다 — 관측이 그 모양이다.

**단정하지 않는다.** 부하가 원인이라는 것은 위 두 줄의 관측과 일치할 뿐이고, 스케줄러·
Postgres의 잠금 대기 중 무엇이 갈랐는지는 안 쟀다. **고치지 않았다** — `apps/api`는 이
슬라이스가 안 건드리는 자리이고, 고치려면 *"두 요청이 실제로 겹쳤다"*를 케이스가 확인하는
이음매가 필요하다(그것이 `apps/api`의 판정이다). 이월에 적는다.

### 11.2 R2 — 표준출력을 **날 스트림에서** 잰다

리뷰어가 짚은 둘을 다 고쳤다.

1. **자를 세웠다.** `build-test/dist-smoke.test.ts`에 절을 하나 더했다. `Client`를 안 쓰고
   `spawn`으로 직접 띄워 `initialize`·`notifications/initialized`·`tools/call`을 손으로 써
   넣은 뒤 **표준출력 전문**을 읽어 *"모든 줄이 `jsonrpc: '2.0'`인 JSON이다"*를 잰다.
   `StdioClientTransport`가 그 스트림을 독점하므로 진짜 클라이언트로는 못 재는 자리다.
   - **술어를 보정한다** — 이물 줄·개행 없는 조각·JSON이지만 JSON-RPC가 아닌 줄을 직접 먹여
     본다. 늘 `[]`를 내면 위가 아무것도 안 잰다.
   - **붙지 못한 갈래도 잰다** — 자격이 없을 때 `wireb login` 문장이 표준출력으로 안 새는지.
2. **이름이 말하는 것을 안 재던 케이스의 이름을 내렸다.**
   `서버가 표준출력을 더럽히지 않는다 — payload 경고가 프레임을 안 깬다` →
   `payload 형식이 높아도 응답이 온다 — 경고가 읽기를 막지 않는다`. 그 경고는 이미 `io.err`로
   가므로 그 케이스가 재던 것은 *"응답이 온다"*뿐이었다.

**리뷰어의 부수 관측도 옮겼다**(귀속: 리뷰어): SDK 1.30.0의 `StdioClientTransport`는
**개행으로 끝나는 이물 한 줄에 안 끊긴다.** 그래서 술어를 그 관대함에 안 맞췄다 — 개행 없는
조각은 다음 프레임을 깨고, 관대함은 이 클라이언트의 것이지 계약이 아니다. `bin.ts`의
머리말도 그 값으로 고쳤다(덤으로 *"`out`이 `console.log`"*라는 사실 오류도 — 실제는
`process.stdout.write`다).

## 12. 델타 리뷰 대응 — 자의 경계 둘을 닫았다

> 델타 리뷰: `2026-08-17-p9-4-review.md` §10. **판정은 병합 가능**이었고 D-1·D-2는

### 12.1 D-1 — 새 stdout 자가 **응답 뒤**를 못 봤다

리뷰어가 실측했다(귀속: 리뷰어 D-1): 리다이렉트를 지우고
`setTimeout(() => io.out("late log line"), 1500)`을 심으면 `test:build` **14/14 초록**.
원인은 `rawStdout`이 *"`id`를 든 요청 수만큼 프레임이 오면"* 곧바로 resolve한 것이다.

**창을 넓혔다.** 프레임을 다 받으면 **표준입력을 닫고**(stdio 전송이 EOF로 끝난다) 프로세스가
죽을 때까지 읽는다. 안 죽으면 `GRACE_MS`(3초)까지 기다린다. 그 명제를 이름으로 든 케이스도
하나 뒀다(`응답 뒤에도 읽는다 — 서버가 끝까지 산 뒤에 창이 닫힌다`).

### 12.2 D-2 — `io-boundary` 술어에 **`console.`이 없었다**

리뷰어가 실측했다(귀속: 리뷰어 §10.3·D-2): `console.log`를 `packages/mcp/src`에 심어도
`pnpm test`가 **0 사망**이었다(`test:build`가 2건으로 잡았을 뿐이다). `EFFECTFUL`이 보는
것이 `node:*` 지정자·`process.`·전역 `fetch(` 셋뿐이었다.

**술어에 `console.`을 더했다 — `packages/mcp`와 `packages/cli` 양쪽이다**(리뷰어가
*"같은 물음이 선다"*고 적은 자리). **P9-3 리뷰 N4와 같은 부류다** — 술어가 모양 하나만
전제하면 우회가 실재한다.

**술어 배열 전체를 재는 케이스도 세웠다.** `packages/cli` 쪽에는 그것이 아예 없었다 —
계량 케이스가 `EFFECTFUL_SPECIFIER` 하나만 재고 있어서 `process.`·`fetch(`·`console.`이
조용히 빠져도 안 보였다. 반대편(`io.fetch` · `consoleWidth` 같은 이름 겹침)도 함께 든다.
