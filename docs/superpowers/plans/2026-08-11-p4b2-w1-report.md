| 컴포넌트 | 전 | 후 | 왜 |
|---|---|---|---|

## 4. 재라 #7의 답 — **등급이 셋이다**

계획서는 *"구조인가 스킨인가"*를 둘로 물었다. **재 보니 셋이었다.**

| 등급 | 무엇 | 이 그룹의 구조 |
|---|---|---|
| **A. 조각이 없으면 표현 자체가 불가능** | 테마가 겨냥할 상자가 DOM에 없으면 어떤 CSS로도 못 만든다 | `Section:splitBg`(`band`) · `Card:mediaTop`(`media`) · `Card:horizontal`(`content`) · `Section:fullBleed`(조각이 **없어야** 한다) |
| **B. 테마는 CSS로 할 수 있지만 렌더러는 못 한다** | 도구의 제약이다 — `partRule`이 구조 이름을 못 넣으므로 *"이 구조의 이 조각만"*이라는 규칙을 렌더러가 낼 수 없다 | **`Tabs:vertical`** |
| **C. DOM이 같다 — 스킨이다** | 갈리는 것이 §6.8에 이미 있는 어휘로 전부 표현된다 | `Card:bordered`·`Card:elevated` · `Tabs:pill`·`Tabs:enclosed` |

**B의 근거를 적어 둔다** — 세로 탭에 필요한 것이 둘인데 (가) 루트를 가로로 세우는 것은
`componentRule`로 되고, (나) 목록 안의 탭을 세로로 쌓는 것은 **조각 규칙이라 안 된다.**
`partRule`이 구조 이름을 빼는 것은 테마의 조각 규칙(특이도 0,2,0)을 이기지 않기 위해서이고
(`structure-css-tools.ts`), 넣으면 0,3,0이 되어 그 컴포넌트에서 **테마가 진다.** 구조 이름
없이 달면 `underline`의 `list`까지 받아 **오늘 화면이 바뀐다**(D5). 그래서 (나)를 DOM으로
풀었다 — 탭이 `<span>`(인라인)이 아니라 `<div>`(블록)이라 **선언 하나 없이 쌓인다.**

**그러나 테마는 같은 것을 CSS로 할 수 있다** — `Tabs.base { display: flex }` +
`Tabs.parts.list { display: flex, direction: column }`이 오늘 어휘로 전부 표현된다.
즉 `vertical`은 *"CSS로 불가능한 구조"*가 아니라 **"렌더러가 스스로 세우려면 DOM이 갈려야
하는 구조"**다. **P4b-3이 알아야 할 것이 이 등급 차이다** — C의 넷은 `parts` 차이가 아니라
`base` 스킨 차이로 갈라야 하고, B는 테마가 굳이 `vertical`을 안 골라도 흉내 낼 수 있다.

**계획서가 `Section:splitBg`와 `Tabs:vertical`을 같은 물음으로 묶었는데 둘은 등급이
다르다**(A와 B). 계획서를 고치지 않고 여기 적는다.

## 5. 구조 기본 CSS가 얼마나 커졌나 (재라 #5)

**789바이트 · 규칙 5** → **1139바이트 · 규칙 9**. 이 그룹이 더한 것은 넷이다.

```css
[data-wb-component="Section"][data-wb-structure="splitBg"] { display: grid; grid-template-columns: 1fr 1fr; }
[data-wb-component="Card"] [data-wb-part="media"]          { aspect-ratio: 16 / 9; }
[data-wb-component="Card"][data-wb-structure="horizontal"] { display: flex; }
[data-wb-component="Tabs"][data-wb-structure="vertical"]   { display: flex; }
```

**어휘를 골라 썼다.** `display`·`gridColumns`·`aspectRatio` 셋 다 `STYLE_PROPERTIES`에 있어
**테마가 네 규칙을 전부 덮을 수 있다.** `flex-grow` 같은 것으로 갈랐으면 대응 어휘가 없어
되돌릴 길이 없는 선언이 됐다 — 그것은 구조가 아니라 강요다.

**조각 규칙은 하나뿐이고 구조 이름이 안 들어간다**(`Card`의 `media`). `media`를 내는 구조가
`mediaTop`·`horizontal` 둘뿐이고 둘 다 같은 것을 원하므로 의도한 것이다. **D5(화면이 바뀌면
안 된다)에 걸리지 않는다** — `admin`이 고르는 `Card:plain`은 `media`를 내지 않는다.

## 8. 다른 워커·통합이 알아야 할 것

- **`partRule`은 구조 이름을 못 넣는다 — 이것이 구조를 만들 때 가장 자주 걸리는 벽이다.**
  *"이 구조의 이 조각만"*이라는 규칙은 낼 수 없다. 낼 수 있는 것은 (가) 루트 + 구조 이름
  (`componentRule`), (나) 조각 (구조 무관, `partRule`) 둘뿐이다. **(나)는 그 조각을 내는
  구조가 하나뿐일 때만 안전하다** — 아니면 남의 구조가 받아 D5가 깨진다.
- **그 벽에 부딪히면 DOM으로 푸는 길이 있다.** 태그를 바꾸면(인라인 ↔ 블록) 선언 없이
  배치가 갈린다. `Tabs:vertical`이 그 예다.
- **`Card.parts`에 `media`·`content`가, `Section.parts`에 `band`가 생겼다.** W2가 `List`에
  `media`를 쓸 때 이름이 겹치지만 **컴포넌트가 다르므로 셀렉터도 다르다** — 문제 없고,
  오히려 이름을 맞추는 편이 낫다.
- **D5:** 이 그룹은 기존 구조 일곱의 DOM을 **한 글자도** 바꾸지 않았고, 더한 CSS 넷 중
  셋은 구조 이름으로 막혀 있다. 남은 하나(`Card`의 `media`)는 `plain`이 그 조각을 안 내므로
  `admin`에 닿지 않는다.
- **D4:** 이 그룹이 더한 손잡이는 **0개**다.
- 새 케이스는 `packages/renderer/test/structures-section-card-tabs.test.tsx` 한 파일에 있다
  (44 케이스). 다른 워커가 만질 파일에는 한 줄도 안 썼다.
