# P5-3 뷰 모드 · 상호작용 런타임 구현 계획

> **에이전트에게:** 태스크 단위로 실행한다. 각 태스크는 실패하는 케이스 → 최소 구현 →
> 통과 → 커밋의 순서를 지킨다.

**목표.** §8.3의 상호작용 런타임과 §9의 뷰 모드를 세운다. **P5의 마지막 조각이고, 이것으로
로드맵의 *"설계서로서 완성된다"*에 닿는다.**

**§8.3:** *"편집 모드에서는 상호작용이 동작하지 않는다(노드 선택이 우선). **뷰 모드 토글 시
`renderer`의 상호작용 런타임이 활성화되어 실제로 동작한다.** 내보낸 HTML 번들은 항상
뷰 모드다."*

**§9:** 뷰 모드에서 **구조 트리가 접혀 메뉴 트리가 전체를 쓰고**, 우측 탭이
**페이지 설명 / 코멘트 / 상호작용**이 된다.

**스택.** `packages/renderer`(런타임) · `apps/web`(셸·탭·모드) · vitest.

---

## 전역 제약

- **워크트리 안에서만 작업한다.**
- `pnpm test` · `pnpm typecheck` · `pnpm build`가 마지막에 전부 통과해야 한다.
  **종료 코드는 파이프 없이 따로 찍어라** — P5-2에서 **테스트는 초록인데 typecheck가
  exit 2**인 것을 그 규칙이 잡았다(그쪽이 쟀다).
- **api 테스트는 Postgres 하나(포트 5433)를 공유한다.**
- **`git checkout --`을 쓰지 마라.** python 치환으로 심고 복구하고 `git status`.
  **`git diff`로 심어졌는지 확인하지 마라** — 새 파일은 untracked라 늘 비어 있다.
  **파일 내용으로 확인하고 하네스는 원본 전문을 먼저 들고 `finally`에서 되쓴다.**
- **측정이 예상과 다르면 대상이 아니라 측정 장치를 먼저 의심하라** — **열두 번** 걸렸다.
  **의심했으면 같은 장치를 다시 돌리지 말고 다른 장치로 재라.** **한 번 관측한 것이
  flake일 수 있다.**
- **jsdom과 실브라우저가 캐스케이드를 반대로 가른다** — jsdom은 `textContent`를 쓴 순서,
  **실브라우저는 DOM 순서**다(P4c-2의 ①·③이 각각 쟀다).
- **검산 명령이 실제로 도는지, 그리고 *네가 세려는 것을* 세는지 확인하라.**
- **설계 문서(`docs/superpowers/specs/*`)는 고치지 않는다.** 어긋나면 판정해 보고한다.
- **`apps/web`에 새 런타임 의존을 더하지 않는다.**
- **남이 잰 값은 귀속을 붙여 옮긴다.** 표에는 세는 단위·번호·검산 명령 셋.

## 이 계획이 딛고 선 사실 — 전부 P5-2 이월에서 왔다

| # | 사실 | 누가 쟀나 |
|---|---|---|
| 1 | **런타임이 *깨진 규칙*을 만난다.** severity가 `warning`이라 **끊긴 타겟·잘못된 prop이 문서에 남은 채 저장된다** | P5-2 |
| 2 | **그것을 읽는 코드가 한 곳도 없다** — `PatchResult`에 `warnings` 키 **선언조차 없다.** 셋 다 0건(선언 · 읽는 코드 · 저작 화면의 자기 검증) | 리뷰가 찾고 P5-2가 셌다 |
| 3 | **`RightPanel`이 `mode`를 안 읽는다** — P5-1 이월 §5가 지목한 자리가 **그대로 남아 있고** 본문만 삼항에서 표로 바뀌었다 | P5-2 |
| 4 | ***"실패했다고 말하는데 남는다"*가 다섯째이고 층이 갈렸다** — 앞 넷은 *조작*, 다섯째는 *화면 상태*. **새 실패 갈래마다 *"이 갈래는 무엇을 되돌리는가"*를 물어라** | P5-2·리뷰 |

**그리고 `RenderOptions`가 이미 있다**(`structures` · `slot` · `onNodeError`) — 런타임은
**그 자리에 얹힌다**(내가 확인했다. 워커가 다시 확인하라).

## 확정한 결정

### D1. **런타임 상태는 문서를 바꾸지 않는다** — 이 슬라이스의 핵심

뷰 모드에서 버튼을 눌러 `setProp`이 돌면 **그것은 시연이지 편집이 아니다.**

- **문서를 건드리면** revision이 쌓이고 남의 화면이 바뀌고 undo 스택에 섞인다.
  **§8.3이 *"동작한다"*고 한 것은 그 뜻이 아니다.**
- **그러므로 런타임은 별도의 겹layer 상태를 든다** — `nodeId → { prop: value }`.
- **뷰 모드를 나가거나 페이지를 옮기면 사라진다.** 되돌리기 버튼이 아니라 **모드가 리셋이다.**

**§11.3의 정적 번들도 같다** — 거기엔 문서를 바꿀 서버가 아예 없다.

### D2. **런타임은 `renderer`가 소유한다**

§8.3이 이름으로 지목했고(*"`renderer`의 상호작용 런타임"*), §11.3이 그 이유를 적었다 —
*"`exporter`가 `renderer`를 서버에서 실행해 정적 HTML을 만든다. **렌더러가 하나뿐이라 결과가
어긋날 수 없다.**"*

**`apps/web`에 두면 P8의 번들이 다른 런타임을 갖게 된다.**

- **`RenderOptions`에 얹는다** — 새 진입점을 만들지 마라.
- **끄는 것이 기본이다.** 오늘 `renderDocument`를 부르는 모든 자리(캔버스·갤러리·테스트)가
  **상호작용 없이 그대로 돌아야 한다.**

### D3. **깨진 규칙을 만나면 조용히 지나가지 않는다** — 사실 1·2

**런타임이 끊긴 타겟을 만나는 것은 예외가 아니라 예상된 상태다**(severity가 `warning`이라
저장이 통과한다).

**그때 무엇을 하는가가 이 슬라이스의 두 번째 결정이다.** 후보 셋:

| 후보 | 무엇 |
|---|---|
| 조용히 무시 | **안 된다.** *"눌렀는데 아무 일도 안 일어난다"*가 되고 그것이 이 저장소의 반복 부류다(사실 4) |
| `onNodeError`처럼 콜백 | **`RenderOptions`에 이미 그 형식이 있다.** 앱이 배너로 알린다 |
| 화면에 직접 표시 | 렌더러가 UI 결정을 하게 된다 |

**나는 둘째를 권한다** — 그러나 **워커가 판정하고 근거를 적어라.** `onNodeError`의 주석이
*"이 콜백 안에서 `setState`를 부르지 마라"*와 그 이유를 이미 적어 두었다 — **읽고 같은
함정을 피하라.**

### D4. **`navigate`·`openModal`은 렌더러 밖이다**

둘의 타겟은 `"page:관리자/회원/상세"`이고 **다른 페이지**다. 렌더러는 페이지를 모른다
(P5-2가 그래서 그 둘을 검증하지 못했다).

**그러므로 런타임은 그 둘을 *실행*하지 않고 *알린다*** — 앱이 라우팅하고, 정적 번들은
링크로 바꾼다. **경계를 그 자리에 두어라.**

### D5. **뷰 모드가 셸을 바꾼다** — §9

| 무엇 | 편집 모드 | 뷰 모드 |
|---|---|---|
| 좌측 하단 **구조 트리** | 보인다 | **접힌다** — 메뉴 트리가 전체를 쓴다 |
| 우측 탭 | 속성 / 코멘트 / 상호작용 | **페이지 설명** / 코멘트 / 상호작용 |
| 캔버스 | 선택 아웃라인 · 번호 마커 | **마커만**(P5-1의 D8) |
| 상호작용 | 안 돈다 | **돈다** |

**사실 3이 그 자리다** — `RightPanel`이 `mode`를 안 읽는다. **P5-1 이월이 지목하고 P5-2가
안 고친 것을 여기서 닫는다.**

**"페이지 설명"은 §9가 이렇게 적었다:** *"페이지 설명은 편집 모드에서 페이지 자체를
선택했을 때 속성 탭에 나타난다."* — **즉 새 데이터가 아니라 이미 있는 것의 다른 자리다.**

### D6. **`warnings`를 읽는 코드를 만든다** — 사실 2

**셋 다 0건이다.** 최소한 **`PatchResult`에 키를 선언하고 편집 경고를 화면이 받게 하라** —
그것이 P5-2가 만든 이슈 셋이 **처음으로 사람에게 닿는 자리**다.

**어디에 보이는가는 재라 #3.** 상호작용 탭이 자연스럽지만 **페이지 편집 경고는 상호작용만이
아니다**(P4a-2의 `ignored-variant`도 그 채널이다).

### D7. **렌더 결과가 안 바뀌어야 하는 것**

**상호작용을 끈 렌더는 오늘과 글자까지 같아야 한다.** 켠 렌더가 **속성을 더하는 것은
괜찮지만**(§6.11의 여섯 속성 계약을 깨지 않는 선에서) **끈 것이 바뀌면 고장이다.**

**P4c-2 ③의 DOM 순서 케이스 · P5-1의 마커 케이스 · P5-2의 문장화 케이스가 죽으면 멈춰라.**

> **§6.11이 *"이 여섯이 전체 계약"*이라고 못박았다.** 런타임이 일곱째 데이터 속성을
> 만들어야 한다면 **그것은 규격을 넓히는 판단이다 — 멈추고 보고하라.**

## 태스크

### T1. 런타임 — 상태와 실행

**Files:** `packages/renderer/src/interaction/…`(새 파일) · `render.tsx` · 케이스

D1·D2. **`setProp` · `setVisible` · `switchTab` 셋만 렌더러가 실행한다**(D4).

**`switchTab`이 어려운 자리다** — `Tabs`의 활성 탭은 오늘 `props.active`이고 구조 구현체가
그것을 읽는다. **런타임의 겹layer가 그것을 덮는 경로가 있는지 재고 판단하라.**

D3. **끊긴 타겟 · 없는 prop · 범위 밖 탭**을 각각 만들어 무엇이 일어나는지 재라.

### T3. 뷰 모드 — 셸

D5. **사실 3의 자리를 닫는다.**

### T4. `warnings`를 읽는다

D6. **셋 중 최소한 둘**(선언 · 읽는 코드)을 닫아라.

## 재라

1. **깨진 규칙을 어떻게 알리는가**(D3의 후보 셋).
2. **`navigate`·`openModal`을 앱이 어떻게 받는가**(D4). 오늘 페이지 경로를 id로 푸는 수단이
   있는지 재고 판단하라 — 없으면 **알리기만 하고 안 움직이는 것도 답이다.**
3. **편집 경고가 어디에 보이는가**(D6).
4. **런타임 상태가 언제 리셋되는가.** 모드 전환·페이지 이동은 확실하고, 그 밖은?
5. **같은 `on`이 여럿일 때 순서.** P5-2의 재라 #4가 넘긴 것이다.
6. **뷰 모드에서 노드를 클릭하면?** §8.3이 *"편집 모드에서는 노드 선택이 우선"*이라고만
   적었다 — 뒤집으면 **뷰 모드에서는 상호작용이 우선**인데 선택이 아예 없는지는 안 적혔다.

## 계획이 재지 않은 것

1. **P8의 정적 번들이 이 런타임을 싣는 것**(§11.3의 `runtime.js`). **여기서는 렌더러가
   그것을 소유하게 하는 데까지**이고, 번들로 나가는 것은 P8이다.
2. **실브라우저 확인.** P4c-3·P5-1·P5-2가 전부 0건으로 남겼다. **이 슬라이스는 클릭이
   실제로 도는 것을 다루므로 그 사각이 가장 아픈 자리다** — 재면 적고, 못 재면 그렇다고 적어라.
3. **P5-1·P5-2가 남긴 것과 P4c가 넘긴 것들.** 벽 1·2 · `placeholder.style` ·
   `suspicious-literal` severity · 정렬 버튼 · `onSelectPath` · `inverse-bench` ·
   §8.2의 둘째 예 · 비대칭의 나머지 반. **전부 그대로 남는다.**
