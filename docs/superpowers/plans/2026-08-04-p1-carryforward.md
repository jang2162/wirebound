# P1 이월 사항

P1(서버 API) 구현 중 발견됐으나 그 단계에서 고치지 않기로 판정한 항목들이다. 각 항목에 어느 단계가 받아야 하는지가 붙어 있다. 다음 단계의 계획을 쓸 때 반영한다.

관련 문서: 설계 `docs/superpowers/specs/2026-08-03-wirebound-design.md`, 구현 계획 `docs/superpowers/plans/2026-08-03-p1-api.md`

P1 최종 상태: 브랜치 `feat/p1-api`, 578 tests / 33 files 통과, `pnpm typecheck` exit 0.

---

## P2 시작 전 확인할 것

없다. P1은 스스로 닫혔다 — 최종 브랜치 리뷰가 인가 표면을 전수 감사해 18개 라우트 전부 적절한 가드를 갖고 프로젝트 범위 확인 없이 id를 신뢰하는 곳이 없음을 확인했고, 병합 전 수정으로 지적 사항을 모두 닫았다.

아래는 전부 "언젠가" 항목이며, 대부분은 해당 코드를 다시 만질 때 함께 처리하는 것이 싸다.

## P3 (WebSocket 실시간 동기화)가 받을 것

### 1. `findMembership`을 `repos/`로 옮긴다

`auth/roles.ts`가 raw SQL을 직접 돈다. 계획이 그렇게 지정했고 P1에서는 문제없지만, P3의 WebSocket 가드가 같은 조회를 필요로 하므로 그때 `repos/members.ts`로 옮긴다. 지금 옮기면 이미 리뷰를 통과한 129줄을 흔들 뿐이다.

### 2. 진짜 경합 테스트

P1의 테스트 하네스(`withApi`)는 각 테스트를 **하나의 커넥션, 하나의 트랜잭션** 안에서 돌린다. 그래서 `Promise.all`로 요청을 겹쳐도 직렬화되고, 그런 테스트는 잠금이 있든 없든 통과한다 — 실패할 수 없는 테스트다. P1은 이 사실을 인지하고 동시성 테스트를 **의도적으로 만들지 않았다**:

- 마지막 owner 불변식은 **순차** 테스트로 고정했다.
- 잠금(`SELECT ... FOR UPDATE`, `repos/members.ts`의 `lockOwnerIds`)은 **리뷰어가 SQL에서 확인하는 코드 요구사항**으로 뒀다.

P3는 실제 커밋이 필요하므로 다른 격리 전략(테이블 TRUNCATE)을 쓰게 된다. 그때 다음을 진짜 경합으로 검증한다:

- owner 둘이 서로를 동시에 강등 → owner가 최소 한 명 남는가
- 자식 없는 메뉴를 삭제하는 사이 다른 트랜잭션이 자식을 넣는 경우 (`repos/menu.ts`의 FK 위반 catch 분기는 P1에서 도달 불가라 미검증이다)
- 페이지 스키마 동시 저장

### 3. `withTransaction`의 잔여 성질

`db/tx.ts`: savepoint 롤백 자체가 던지면 원본 에러가 대체된다. 커넥션이 이미 쓸 수 없는 상태라 실무적으로는 대체된 쪽이 더 유용하지만, P3가 이 경로를 훨씬 자주 타게 되면 재검토한다.

## P2 (에디터) 또는 그 근처에서 처리할 것

### 4. 응답 형태의 두 관용구

`GET /api/projects`, `/members`, `/menu`는 배열을 그대로 내고 `/tree`는 `{ menu: [...] }`를 낸다. 후자는 의도적이고 문서화되어 있으나, 클라이언트 입장에서는 두 번째 관용구다.

더 껄끄러운 것: `MenuTreeNode`(`/menu`)와 `TreeMenuNode`(`/tree`)가 `pages` 유무만 다른 거의 같은 형태다. P2가 두 엔드포인트를 다 쓰게 되면 하나로 합치는 편이 낫다.

### 5. `buildMenuTree`의 위치

`repos/menu.ts` 안에 있으나 SQL이 없는 순수 인메모리 조립 함수다. "라우트는 SQL을 쓰지 않는다" 규칙을 만족시키려고 거기 들어갔는데, SQL이 없으므로 그 규칙이 애초에 적용되지 않았다. 자기 모듈로 빼는 것이 맞다.

### 6. `invitedAt` 직렬화 형식

`members.test.ts`가 키 존재만 단언하고 형식(ISO 문자열 여부)은 보지 않는다. P2가 파싱할 값이므로 그때 고정한다.

## 테스트 부채 (아무 때나, 해당 코드를 만질 때)

### 7. `packages/schema`: `assertValidLayout`에 테스트가 없다

`assertValidPage`에는 있다. 검증된 `validateLayout`에 3줄 위임하는 함수이고 새로 붙은 팬텀 브랜드가 오용을 컴파일 오류로 만들므로 위험은 낮다.

### 8. `dist-loadable.test.ts`가 기본 테스트 실행을 pnpm에 결합한다

`beforeAll`에서 `pnpm`을 셸아웃해 두 패키지를 재빌드한다(타임아웃 300초). 검증하는 대상(번들러 없는 순수 Node 로드 가능성)은 실재하지만, `pnpm test`가 PATH의 pnpm과 전체 재빌드에 묶인다. **빌드/CI 전용 프로젝트로 분리하는 것이 맞다.**

### 9. 로그인 타이밍 방어가 코드 읽기로만 보장된다

없는 이메일로 로그인해도 더미 해시를 검증해 응답 시간을 맞추는데, 그 호출이 실제로 도는지 증명하는 테스트가 없다 — 그 줄을 지워도 스위트는 초록이다. 타이밍 단언은 flaky하지만, 그 경로에서 `verifyPassword`가 불리는지 확인하는 스파이는 아니다. 인증 코드를 다음에 만질 때 넣는다.

### 10. `password_hash` 부재 단언이 signup 응답에만 있다

login과 `/me`는 명시적 3컬럼 select로 **구조상 안전**하지만, 누군가 `selectAll()`로 바꾸는 순간을 잡는 것은 `Object.keys` 단언이다. 세 곳 다 거는 것이 싸다.

### 11. `hashPassword` 대칭 테스트의 `N=1000` 행이 비판별

Node가 2의 거듭제곱이 아닌 `N`을 자체적으로 거부하므로, 그 행은 `validateScryptParams`가 돌았다는 것을 증명하지 못한다. 나머지 행(`r`/`p`/메모리 상한)은 증명한다. 그 행은 빼거나 교체한다.

### 12. 메뉴 FK 위반 catch 분기가 미검증

`repos/menu.ts`의 `deleteMenuNode`가 앱 레벨 검사를 먼저 하므로 DB RESTRICT 폴백에 도달할 수 없다. TOCTOU 가드로서 옳고 유지해야 하지만, 검증은 P3의 경합 테스트를 기다린다(위 2번).

## 명시적으로 "그대로 둔다"고 판정한 것

다시 논의하지 않도록 근거와 함께 남긴다.

- **`auth/password.ts`의 `p`가 무제한이다.** 메모리 상한 `128*N*r`에 `p`가 없어 CPU 시간 레버가 남는다(실측 `p=2000` → 6.23ms). 그러나 `p`는 **저장된 해시에서만** 읽히고 유일한 프로덕션 호출자가 `p: 1`을 하드코딩한다. 악용하려면 DB 쓰기 권한이 필요하다. `MAX_P`를 되살리지 않는다.
- **대소문자 무시 로그인 테스트가 상태 코드만 단언한다.** 그 200이 판별 신호다 — 사용자가 하나뿐이라 정규화가 깨지면 null → 401이 된다.
- **`signup()` 픽스처에 직접 테스트가 없다.** 201이 아니거나 쿠키가 없으면 설명적 에러를 던지므로 자기 검증한다.
- **`withApi`가 `fn`과 `close`가 동시 실패할 때 close 에러를 버린다.** `fn`이 이미 실패했을 때만 버리며, 그것이 올바른 우선순위다.
- **페이지 앱 레벨 precheck의 독립적 필요성이 미검증.** 그 가치는 에러 *품질*(문장을 내기 전에 409 + 구체적 메시지)이고, RESTRICT 단독은 별도로 검증되어 있다.
- **`buildMenuTree`의 `as TreeMenuNode` 단언.** 바로 앞 루프에서 같은 배열로 채운 Map을 조회한다.
- **이메일 열거 트레이드오프.** 로그인만 감추고 회원가입 409와 멤버 초대 404/409는 드러낸다. 인지된 결정이며 설계 §10에 근거와 재검토 조건을 기록했다.

## 프로세스 관찰 — 다음 단계 계획을 쓰는 사람에게

P0의 교훈("계획이 리터럴 구현 코드를 지정하면 그 결함이 그대로 코드가 된다")에 대응해 P1 계획은 세 층으로 썼다: 설정·SQL·타입 정의와 성질이 미묘한 테스트는 리터럴, 반복적인 라우트 테스트는 **행 하나 = `it` 하나**인 케이스 표, 핸들러 본문은 계약과 규칙만.

**케이스 표 형식은 통했다.** 태스크 10~14에서 리뷰어가 행별 매핑표를 내놓았고 누락도 들러리 테스트도 없었다. 계속 쓸 것.

**그러나 이 단계의 지배적 실패는 다른 종류였다.** 리뷰가 잡은 것의 대부분이 "코드가 틀렸다"가 아니라 **"테스트가 이름이 주장하는 것을 검사하지 않는다"**였다.

| 태스크 | 초록이던 것 | 실제로 검사하지 않던 것 |
|---|---|---|
| 2 | 테스트 50개 | `nodeId`를 한 번도 단언 안 함 — 결함이 그 필드에 있었다 |
| 4 | 로그 리다크션 테스트 | 빈 버퍼에서 통과할 뻔했다(레벨이 `silent`) |
| 6 | 형식 오류 14개 | 전부 "모양이 틀린" 것뿐 — **인증 우회가 44개 초록 뒤에 숨었다** |
| 7 | try/catch를 겨냥한 테스트 | 그 분기에 도달조차 안 함(지워도 통과) |
| 8 | 중복 이메일 409 | 409에서 멈춰 savepoint 누락을 탐지 불가 |
| 12 | 재번호 테스트 전부 | `openGap`의 행 이동 분기가 스위트 전체에서 한 번도 실행 안 됨 |
| 12 | 세 테스트의 주석 | "세이브포인트 없으면 25P02" — 그 경로엔 실패하는 SQL이 없다 |

**거의 전부 계획이 쓴 테스트에서 왔다.** 효과가 있었던 대응책 둘:

1. **모든 디스패치에 이 실패 이력을 구체적으로 적고**, 각 테스트마다 "이름이 가리키는 것이 깨져도 통과할까"를 묻게 하고, 약하면 솔직히 보고하게 했다. 태스크 8부터 구현자들이 실제로 약한 테스트를 자진신고하기 시작했다.
2. **구현자가 변이 테스트를 선제적으로 돌리게 했다**(깨뜨림 → 실패 확인 → 되돌림). 태스크 10·11에서 정착했고 **그 두 태스크는 수정 라운드 0으로 통과했다**.

다음 단계에서도 이 둘을 디스패치 표준으로 유지할 것. 그리고 **테스트 통과 개수는 커버리지의 증거가 아니다** — 특히 케이스 목록이 한쪽으로 쏠려 있으면 그 편향이 곧 사각지대다.

한 가지 더: 리뷰어에게 "보고서를 믿지 말라"고만 하지 말고 **무엇을 어떻게 확인할지 지목**했을 때 결과가 훨씬 좋았다. 태스크 5의 하네스 격리, 태스크 6의 형식 오류 경로, 태스크 12의 손자 순환, 최종 리뷰의 인가 표면 전수 감사가 그렇게 나왔다.
