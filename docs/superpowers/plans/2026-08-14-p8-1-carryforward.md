## 1. `exportPage`가 무엇을 내고 무엇을 안 하나

```ts
exportPage({ document, title, theme?, lang? }): { html, css, errors }
```

| 것 | 값 |
|---|---|
| `document` | **`PageDocument`다.** `AnyDocument`가 아니다 — D3의 판정이 타입에 박혀 있다(§4) |
| `title` | **필수다.** 문서가 제목을 안 든다 — `pages.title`(§4.2)과 §11.2 봉투의 `page.title`에 산다. 기본값을 두면 *"빠뜨린 것"*과 *"이름이 없는 것"*이 같은 값이 된다 |
| `theme` | `ResolvedTheme \| null`. **없는 것이 정상이다**(`layouts.theme_id`가 `NULL`을 받는다 — P6-1이 쟀다) |
| `lang` | 기본 `'ko'` |
| `html` | `<!doctype html><html lang><head><meta charset><title></head><body>문서</body></html>`. **그것뿐이다** |
| `css` | 구조 기본 CSS + 테마 CSS **한 장**. §11.3의 `assets/theme.css`가 될 값 |
| `errors` | 그리지 못한 노드. 캔버스가 배너로 알리는 것과 같은 값이다 |

**안 하는 것:** 파일을 쓰지 않는다(D1) · 레이아웃을 합성하지 않는다(D3) · 셸을 만들지
않는다(D7) · CSS를 HTML에 넣지 않는다.

**`<head>`에 `style`·`script`·`link`가 0개인 것을 케이스가 지킨다.** P8-2가 거기 무엇을
넣으면 그 케이스가 죽는다 — **그것이 알림이지 사고가 아니다.** 죽으면 고쳐라.

## 2. **`themeStructures`를 `apps/web`에서 `packages/themes`로 옮겼다**

화면이 테마→구조를 고르는 함수다. `apps/web/src/theme/theme-structures.ts`에 있던 것을
`packages/themes/src/resolve/structures.ts`로 옮기고 공개 표면에 냈다.

**왜.** 두 경로가 **같은 구조 선택**을 써야 *"화면과 번들이 같다"*가 성립하는데
`packages/exporter`는 `apps/web`을 볼 수 없다. 사본을 두면 P8-3의 api 라우트에서 셋째가
된다 — P7-3 이월 §8.2 규칙 1이 이름 붙인 자리다.

**P8-2·P8-3에게:** 셸이나 라우트가 구조 선택을 만들어야 하면 **그 함수를 부르고 새로 짜지
마라.** 정의는 하나다:

```
$ grep -rn 'function themeStructures' apps packages --include='*.ts' --include='*.tsx'
packages/themes/src/resolve/structures.ts:38
```

**의존 방향은 그대로다** — 그 함수는 `ResolvedTheme`을 받아 평범한 레코드를 낸다.
`themes`는 `renderer`도 `react`도 보지 않고, `public-api.test.ts`의 경계 검사가 그것을 지킨다.

**공개 표면 목록은 손으로 적혀 있다**(`packages/themes/test/public-api.test.ts`의
`CONTRACT`). 그 목록이 실제 수출과 어긋나면 죽는 것을 양방향으로 확인했다 — 이름을 더해도,
수출을 지워도 같은 케이스가 죽는다. **themes에 무엇을 더하려거든 거기 이름을 함께 적어라.**

## 3. **갈림 셋** — P8-2가 셸을 만들면 다시 만난다

보고서 §1에 원문과 판정이 있다. 요지:

| 갈림 | 화면 | 번들 | 원인 |
|---|---|---|---|
| ㉠ `style` 속성의 적는 꼴 | `--wb-node-grid-columns: 3;` | `--wb-node-grid-columns:3` | React 클라이언트는 CSSOM에 얹고, 파서는 원문을 보관한다. **선언은 같다** |
| ㉡ 텍스트 노드 경계 | `"구획 "` + `"1"` | `"구획 1"` | HTML이 경계를 적을 수 없다. `renderToStaticMarkup`은 `<!-- -->`를 안 넣는다 |
| ㉢ **선언 없는 `style` 속성** | `style=""` | 속성이 **없다** | **React의 재조정.** 구조가 바뀌면 같은 원소를 재사용하고 선언만 지운다 |

**P8-2에게 이것이 왜 중요한가.**

1. **번들과 화면을 다시 견주는 검사를 만들면 같은 세 축을 만난다.**
   `@wirebound/exporter/test-support`의 `describeTree`가 그 셋만 접고, **접는 축만 접는지
   양방향으로 재는 케이스**가 옆에 있다. **새로 짜지 말고 그것을 불러라**(§3.1).
2. **㉡은 다섯 테마 중 `portal` 하나에서만 났다.** 그 테마만 `EntryForm:sectioned`를
   고른다. **테마 하나·문서 하나로 재면 못 본다.**
3. **㉢은 진짜 캔버스에서만 난다.** 한 번만 그리는 견주기로는 그 상태를 만들 수 없다 —
   캔버스는 테마를 **서버에서 늦게** 받아 구조가 한 번 갈아엎인다. **셸이 무엇을 언제
   그리는지 바뀌면 이 축이 다시 흔들린다.**

   > **㉢은 오늘 노출이 없지 셀렉터에 안 잡히는 것이 아니다** — 델타 리뷰가 덧붙인 사실이다.
   > **빈 `style` 속성은 `[style]` 셀렉터에 매칭된다**(재서 확인했다: `style=""`인 원소가
   > `matches('[style]')`에 `true`, 속성이 없는 원소는 `false`). 오늘 저장소에 `[style]`
   > 셀렉터가 **0건**이고 `compileTheme`이 낼 수 있는 셀렉터 어휘도 §6.11의 여섯
   > `data-wb-*`뿐이라 닿는 규칙이 없을 뿐이다.
   >
   > **P8-2·P8-3이 뷰어 셸 CSS에 `[style]`을 하나 더하는 순간 그 갈림이 화면으로 보인다** —
   > 캔버스의 노드에는 걸리고 번들의 같은 노드에는 안 걸린다. 그때는 접기를 다시 판정해야
   > 한다(견주는 자가 접는 것은 *"선언이 0개"*라는 근거였고, 셀렉터는 선언 수를 안 본다).
4. **`admin`은 카탈로그의 첫 구조와 다른 것을 하나도 고르지 않는다**(보고서 §7.2에 다섯
   테마의 표가 있다). 그래서 **구조 배선이 끊겨도 `admin`으로는 안 죽는다.** 테마를 하나만
   골라 재려거든 `admin`을 고르지 마라 — 캔버스 견주기가 `portal`을 쓰는 이유다.

### 3.1 견주는 자와 픽스처는 **패키지가 낸다**

```ts
import { describeTree, broadFixture, variantFixture } from '@wirebound/exporter/test-support'
```

`packages/exporter/test-support/`에 있고 패키지의 `exports` 서브패스로 나간다. `dist`에는
안 들어간다(`files`가 `dist` 하나다 — 케이스가 그것을 지킨다).

**왜 `test/`가 아닌가.** `apps/web`이 import해야 하기 때문이다 — 캔버스↔번들 견주기가
거기 산다. **`apps/web`만 캔버스·렌더러·exporter를 동시에 본다**(`themes`의 어휘를
`renderer`와 대조하는 케이스가 이미 같은 이유로 거기 있다).

**루트 `vitest.config.ts`의 alias에서 더 좁은 것이 먼저 온다** — rollup의 alias는
`id === find || id.startsWith(find + '/')`로 맞추고 앞의 것이 이기므로, 순서를 뒤집으면
서브패스가 `…/src/index.ts/test-support`로 바뀐다.

### 3.2 화면 경로가 둘이고 **재는 것이 다르다**

| 어디 | 화면 경로 | 무엇을 재나 |
|---|---|---|
| `packages/exporter/test/parity.test.tsx` | `renderDocument`를 직접 부른다 | exporter가 렌더 경로에 무엇을 더하거나 뺐는가 |
| `apps/web/test/canvas/bundle-parity.test.tsx` | **진짜 `<App/>`** | 캔버스가 그 경로에서 벗어났는가 |

**뒤쪽이 없으면 캔버스 변이가 안 죽는다** — P8-1 리뷰가 그 구멍을 짚었고, 그것을 메우다
㉢이 나왔다. **그리고 감싸개는 견주기로 안 잡힌다**(견주기는 문서 뿌리 **아래**만 잰다).
그래서 *"문서 뿌리를 아무것도 감싸지 않는다"*를 따로 든다 — **P8-2가 셸을 문서 위에 두면
그 케이스가 먼저 죽는다. 그것이 알림이지 사고가 아니다.**

## 4. `Slot`과 레이아웃 — **P8-1이 지나지 않은 자리**

D3대로 `renderDocument`만 썼고 `exportPage`의 인자 타입이 `PageDocument`다. 그래서
레이아웃을 넣으려면 **P8-2가 타입을 넓히며 판정하게 된다** — 그 판정에 필요한 사실 셋을
이번에 재서 적는다.

1. **`Slot`은 페이지 문서에 둘 수 없다.** `validatePage`가 `error`를 낸다:
   `/root: 페이지에는 Slot을 둘 수 없습니다 (1개 발견)`. 그래서 견주기 픽스처가 둘로
   갈려 있고(본 픽스처 + `slotFixture`), **그 갈림이 편의가 아니라 강제라는 것**을 케이스가
   그 이슈 문장으로 든다.
2. **그래도 렌더 경로는 `Slot`을 그린다** — 검증을 지나지 않기 때문이다. 화면과 번들이
   `Slot`을 든 문서에서도 같은 DOM을 낸다(케이스가 있다).
3. **`renderComposed(layout, page)`는 `renderDocument(page)`와 같지 않다** — 남에게서 받은
   사실이다(P4a-3 이월의 D6 반증, P7-3 이월 §5가 다시 지목). `Slot`이 구멍이 아니라 그려지는
   노드라 합성이 노드 둘을 더한다. **이 슬라이스에서 다시 재지 않았다.**

**판정할 것:** 번들의 페이지가 레이아웃 셸 안에 들어가는가. 들어간다면 §11.2가 가정한
*"페이지마다 다른 레이아웃"*이 오늘 성립하지 않는다는 것(P7-3 이월 §5 — `pages`에 레이아웃
컬럼이 없다)까지 함께 판정해야 한다.

## 5. CSS — 한 장이고 순서가 계약이다. **인라인하려면 §5.1을 읽어라**

`css`는 `구조 기본 CSS + "\n" + compileTheme(theme)`이다.

- **순서가 곧 *"테마가 이긴다"*이다.** 같은 특이도에서 나중에 온 규칙이 이긴다. 화면은
  같은 순서로 `<style>` **둘**을 건다(`apps/web/src/theme/use-theme-css.ts`의 D5).
  **한 장으로 합쳐도 문서 순서가 그대로라 캐스케이드가 같다.**
- **테마가 없으면 구조 기본 CSS만이다 — 빈 문자열이 아니다**(재라 #5를 재서 참).
  케이스가 `css === structureBaseCss()`라는 항등을 든다.

### 5.1 `<style>`로 인라인해도 되는가 — **오늘의 답은 "된다"이고 근거가 있다**

`</style>`이 CSS 값에 들어가면 인라인이 깨진다. **그 길이 `themes`에서 막혀 있다:**

| 넣어 본 자리 | 결과 |
|---|---|
| `primitives.container.maxWidth`에 `</style><script>…` | `bad-style-value` **error** → `resolveTheme`이 `null`을 낸다 |
| `assets.fonts[0].src`에 같은 것 | 같다 |

문장: *"`primitives.container.maxWidth`에 CSS 문법을 끊는 문자가 있습니다: `<`"*.

**케이스 둘이 `packages/exporter/test/escape.test.ts`에 있다.** P8-2가 인라인하기로 하면
그 케이스가 근거이고, **`themes`가 그 검사를 느슨하게 하는 날 먼저 죽는다.**

> **다만 이것은 *"오늘 그 길이 없다"*이지 *"영원히 없다"*가 아니다.** 링크(`<link>`)로
> 걸면 이 물음 자체가 없어진다 — §11.3의 예시가 `assets/theme.css`인 것도 그쪽이다.

## 6. 카탈로그 설치는 **`exportPage`가 한다**

`exportPage`가 부를 때마다 `installCatalog()`·`installStructures()`를 부른다(멱등이라 이미
등록된 것을 건너뛴다). **P8-2·P8-3이 그것을 따로 부를 필요가 없고, 불러도 해가 없다.**

**설치 없이 부르면 무엇이 관찰되는지 케이스가 값으로 든다**(보고서 §3의 표). 요지: 렌더
경로는 **시끄럽다** — 노드마다 폴백이 뜨고 `errors`가 찬다.

**`validatePage`도 시끄럽다** — 카탈로그가 없으면 **노드마다 `unknown-type`**을 낸다.
조용해지는 것은 **`invalid-props` 한 종뿐이고**, 그것도 사라지는 이유가 *"props 스키마를
아는 것이 카탈로그"*라 물음 자체가 성립하지 않아서다. (앞 판이 그것을 침묵 쪽에 넣었는데
거짓이었다 — P8-1 리뷰가 잡았고 케이스가 두 방향의 차집합을 든다.)

**사실 5(P5-3 이월 §3.2)가 잰 진짜 침묵은 상호작용 판정(`checkNodeAction`)의 것이고,
P8-3이 상호작용 런타임을 붙이면 그때 돌아온다.**

## 7. P8-3(내보내기 경로)에게

- **테마를 무엇으로 넘길지는 라우트가 판정한다**(D5). P6-2 이월 §3의 *"payload에서 읽어라"*는
  **스냅샷을 내보낼 때의 정책**이고, 라이브 페이지를 내보내면 라이브 테마가 맞다. 순수
  패키지는 그 정책을 갖지 않는다.
- **`errors`를 버리지 마라.** 폴백이 든 HTML도 눈으로는 그럴듯한 한 장이고 번들은 그것을
  남에게 전달한다. P7-3 이월 §8.2 규칙 2(*"화면이 못 보는 것을 세어 적고 화면이 그것을
  말하게 하라"*)가 여기 걸린다.
- **`javascript:` URL을 React가 막지 않는다.** 막는 것은 `structures/action.tsx`가
  `Link.target` 앞에 붙이는 `#`이다 — 검사가 아니라 접두어다. 내보내기 경로가 URL을 새로
  만드는 자리를 두면 **그 안전이 따라오지 않는다.**
- **api 테스트를 도는 워커는 동시에 하나만.** P7-3 이월 §10의 실측이고 이번에도 게이트
  전에 `ps`로 확인하고 돌렸다.

### 7.1 **`runtime.js`에 데이터를 심을 때 — `scriptJson`을 불러라. 규칙을 베끼지 마라**

```ts
import { scriptJson } from '@wirebound/exporter'

const html = `<script>window.wb = ${scriptJson(data)}</script>`
```

**여기 스니펫을 두지 않는 것이 판정이다.** 앞 판은 여기 코드를 적어 넘겼는데 **그 코드가
틀려 있었다** — 델타 리뷰가 잡았다. 아래 §7.1.1이 그 사고이고, 고친 규칙은 이제
`packages/exporter/src/script-json.ts`에 있고 `test/script-json.test.ts`가 잡는다.

#### 7.1.1 앞 판의 스니펫이 무엇을 놓쳤나 — **막을 필요 없는 것을 막고, 깨지는 것을 놓쳤다**

그 코드는 `JSON.stringify` 뒤에 **U+2028·U+2029만** 이스케이프했다.

| 무엇 | 앞 판 | 실측 |
|---|---|---|
| U+2028·U+2029 | 이스케이프했다 | **막을 필요가 없다.** ES2019가 그 둘을 문자열 리터럴에서 합법으로 만들었다 — 날 분리자를 넣은 리터럴이 그대로 파싱되고 가운데 코드가 `2028`로 남는다 |
| `</script>` | **그대로 통과** | **깨진다.** 그 리터럴을 `<script>`에 넣으면 스크립트가 `window.wb = {"note":"`에서 끊기고, 뒤따르는 글자가 마크업이 되어 `img` 하나가 `onerror`를 달고 생긴다 |

**원인은 HTML 파서가 문자열 안을 보지 않는다는 것이다.** `<script>`는 **raw text 요소**라
파서가 자바스크립트를 이해하지 않고 **종료 태그만 찾는다.** 데이터 안의 `</script>`는
*"문자열 안이니 괜찮다"*가 아니라 **그 자리에서 스크립트를 끝낸다.**

#### 7.1.2 `scriptJson`이 무엇을 하나

**`<` 하나를 `\u003c`로 바꾼다.** JSON에서 같은 값이라 `JSON.parse`가 원래 문자열을 그대로
돌려주고(케이스가 왕복을 잰다), `<` 하나를 막으면 `</script>`·`<script`·`<!--`가 함께
닫힌다 — 셋 다 raw text 안에서 뜻을 갖는 자리다.

**바꾸지 않는 것 둘도 재서 정했다:** `&`는 raw text 안에서 문자 참조로 **해석되지 않으므로**
바꾸면 오히려 값이 달라진다. U+2028·U+2029는 위 표대로 막을 필요가 없다.

**JSON이 아닌 값(`undefined`·함수·심볼)은 던진다** — 조용히 `null`로 삼키면 부르는 쪽의
실수가 값의 변화로 위장되고, 번들에 실려 오래 산다.

#### 7.1.3 **왜 문서가 아니라 함수인가** — 판정과 근거

이 저장소가 네 번 이름 붙인 부류가 *"이월의 문장은 어떤 검사도 지키지 않는다"*이고,
**이번 것은 문장이 아니라 실행되는 코드였다.** 다음 사람은 그것을 읽는 것이 아니라
**복사한다.**

- **스니펫으로 남기는 쪽**을 고르면 그 코드가 검사 밖에 그대로 남는다. *"무엇이 그것을
  지키는가"*를 적어도, 지키는 것은 여전히 없다 — 앞 판이 정확히 그 상태였다.
- **함수로 옮기면** P8-3이 복사하는 대신 부르고, 규칙이 바뀌면 한 자리만 바뀐다. 그리고
  `<script>`를 실제로 만드는 것은 P8-3이지만 **번들을 만드는 것은 exporter**다.

**소비자가 아직 없는데 미리 두는 배치는 이 저장소의 선례다** — `packages/themes`의
`expandPattern`을 P7-1이 P8을 이름으로 들어 미리 뒀다. `exportPage`가 오늘 `<script>`를
하나도 안 내는 것은 케이스가 지킨다.

### 7.2 **NUL은 저장 경계가 막는다 — 저장을 안 지나는 경로가 그 밖이다**

`apps/api/src/db/nul-guard.ts`가 문서 트리를 훑어 막고, 그 자리를 고른 근거가 그 파일에
있다(Postgres 제약이라 브라우저에서도 도는 `schema`가 아니라 Postgres를 아는 계층에 뒀다).
**exporter는 통과시킨다 — 두 벌로 두지 않으려고 그렇게 뒀다.**

**P9의 CLI가 파일에서 읽은 문서를 바로 내보내면 그 방벽을 지나지 않는다.** 그 경로를
만드는 쪽이 *"어디서 막을 것인가"*를 판정할 자리다.

## 9. 새 패키지의 설정에서 알아 둘 것

- **`tsconfig.json`(src)에 `DOM` lib이 없다.** 일부러다 — 이 패키지의 본체는 서버에서
  돌고, DOM 타입이 보이면 브라우저 API를 쓰고도 컴파일이 통과한다. **케이스 쪽
  (`tsconfig.test.json`)만 `DOM`·`DOM.Iterable`을 받고, 거기에 `test-support`도 들어간다.**
  **`test/public-api.test.ts`가 그 설정과 경계 여섯을 지킨다** — 그 설정이 실제로 막는
  것도 양방향으로 쟀다(`document.title`을 적으면 `TS2584`, `lib`에 `"DOM"`을 되넣으면
  그 줄의 오류가 사라진다).
- **`unit` 프로젝트에는 DOM 환경이 없다.** `page.test.ts`가 그 전제를 **카나리아로**
  지킨다(`typeof document === 'undefined'`) — 누가 `unit`에 jsdom을 걸면 거기가 먼저 죽는다.
  DOM이 필요한 파일은 `// @vitest-environment jsdom` 도크블록을 자기 머리에 단다
  (`parity.test.tsx`·`escape.test.ts`).
- **루트 `vitest.config.ts`의 alias에 둘을 더했다** — `@wirebound/exporter`와
  `@wirebound/exporter/test-support`이고 **좁은 것이 먼저다**(§3.1). include는 안 고쳐도
  됐다 — `unit` 프로젝트가 각 패키지의 `test` 디렉터리를 이미 본다.

  > **그 include 패턴을 블록 주석에 그대로 적지 마라.** `packages` 뒤의 별표와 빗금이
  > 주석을 거기서 닫고 뒤따르는 글자가 코드가 된다 — 실제로 `ReferenceError`로 죽었다.
  > 요란하게 죽으므로 검사를 세울 자리는 아니다.

- **`apps/web`이 `@wirebound/exporter`를 devDependency로 든다.** 캔버스↔번들 견주기 때문이고
  **런타임 의존이 아니다** — 웹 번들에 `react-dom/server`가 실리지 않는다.
- **루트 `tsconfig.json`의 references에 둘을 더했다**(`./packages/exporter`와 그 test).
  `pnpm typecheck`는 글롭(`packages/*/tsconfig*.json`)으로 집으므로 없어도 돌지만,
  솔루션 파일의 목록을 실제와 맞춰 둔다.
- **제어 바이트 census가 이 패키지도 훑는다**(재라 #6을 재서 참). **이 문서도 훑는다** —
  `docs/**`가 분모에 있다.
