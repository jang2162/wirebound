## 사용자 결정 후보의 권고

**L-243 — 뷰 모드의 빈 가지에 자리표 «여기 비어 있음» + 단추를 둘지.** 권고: **두지 않는다(현 설계 유지).**
- 뷰 모드는 설계서를 «완성된 화면처럼» 읽는 자리라 «비어 있음» 은 저작 정보이고 읽는 사람에게는 잡음이다. 빈 가지의 상태는 머리 전환기로 고를 수 있어 **고르는 길이 막히지 않았다**(막힌 것은 영역에서 바로 고르는 편의뿐).
- 자리표를 두면 뷰 모드의 표지(점선 · 단추)가 그려진 자식의 상자를 합친 상자라는 현 규칙이 «자리표 상자» 라는 둘째 갈래를 얻고, 자리표가 문서 레이아웃을 안 민다는 편집 모드의 약속(셸 겹)을 뷰 모드도 지켜야 한다. 이득(빈 가지 전환의 편의) 대비 규칙 비용이 크다.
- 바꾼다면 «단추만»(자리표 없이 표지 줄 하나)이 가장 작다 — 그래도 L-244 의 겹침 한계(N19-1)가 먼저 정리돼야 같은 자리에 표지가 쌓이지 않는다.

**L-250(참고).** 한도 문장을 «답을 모름» 으로 바꿀 때를 정하려면 쓰기 답의 시간 한도를 설계해야 한다(읽기 한도 `READ_DEADLINE_MS` 와 같은 값이어야 한다 — 쓰기는 서버에 닿았을 수 있어 «취소됐다» 로 못 말한다). 권고: 지금 문장(사실)을 유지하고 따로 두지 않는다.

**L-113 (a) 완전판.** 어느 링크가 끊기는지를 상자에 말하려면 서버 질의(지울 페이지 id 들을 가리키는 `navigate` · `openModal` 의 수)를 새로 세워야 한다 — 프로젝트의 모든 페이지 문서를 읽는 비용이 상자를 여는 순간 든다. 권고: 한 줄 + `wireb lint` 안내(이번)로 두고, 필요가 확인되면 api 트랙에서 `page-target-missing` 을 «삭제 전 미리보기» 로 부르는 것을 따로 결정한다.
