## N1 — 하트비트마다 남의 잠금 수에 곱으로 느는 동기 판정(높음 · 새 길: 빈도)

**판정 한 번의 값**(api · `hb-judge-cost.probe.ts`). 문서: 뿌리 아래 Section 하나 + Text N 개(평평). 다혜가 `n_sec` 를 쥐고 남 K−1 명이 Text 200 개씩, 보라가
Text 200 개를 쥐고 같은 집합을 10 번 다시 보낸다(하나씩). `liveIn` · `hold` 를 감싸 «보낸 순간 → `hold`»(full) · «마지막 `liveIn` → `hold`»(판정)을 재고,
1ms `setInterval` 의 가장 긴 틈(이벤트 루프 멈춤 — 끝에서 한 번 더 잼)을 함께 적었다. `SWAP=1` 은 같은 집합 대신 두 집합(앞 200 · 끝 200)을 번갈아
보낸다 — 매번 «새로 드는 200 개»다.

거절(`lock-denied`)은 모든 판에서 0 이다(카나리아: 판정이 실제로 돈다 — 겹침이 없어 다 받는다).

**원인.** `ws/lock.ts` 의 `settle` 이 프레임의 노드 **전부**를 `lock/check.ts` 의 `selectionVerdict` 에 넣고, 그 함수는 노드마다
`findLockConflict({ pointers: [path] })` 를 부르며, `packages/schema/src/lock.ts` 의 `findLockConflict` 는 **남의 잠금마다 `findNodePath(root, lock.nodeId)`**
로 문서를 다시 훑는다 — 고른 수 × 남의 잠금 수 번의 경로 찾기다. `settle` 은 동기라 그동안 **이벤트 루프 전체**(다른 프로젝트의 요청까지)가 서고, 그 판정은
`handleLockFrame` 의 트랜잭션 안(페이지 행 `FOR KEY SHARE` 를 쥔 채)이라 **같은 페이지의 편집(`FOR UPDATE`)도 그만큼 줄 선다.** 대응 전에는 같은 비용이
«새로 드는 노드»에만 났다(`SWAP` 줄 — 선택을 바꿀 때 한 번). 고친 뒤에는 웹이 **편집마다** 보내는 하트비트(`use-edit-commit.tsx` 의 전송 루프 `lockChannel?.refresh()`)가
그 값을 낸다. 503 은 루프가 막힌 사이 풀 대기(5s)나 트랜잭션 안 유휴 한도(10s)가 지나 `db/connection-loss.ts` 의 `classifyConnectFailure` · `classifyQueryFailure`
가 «연결 잃음»으로 가른 것으로 읽힌다(코드로 판단 — 어느 한도인지는 안 갈랐다).

**대응 보고의 비용 표가 이것을 못 본 까닭.** 그 벤치(`fx-e2/api/bench.probe.ts`)는 남의 잠금을 **하나**만 두어 판정 1.5–3ms 를 적었다 — 비용의 축(남의 잠금 수)이
1 에 묶였다. 이 리뷰의 K 1 줄이 같은 값이다.

**닿는 길.** 큰 페이지에서 두 사람 이상이 노드 여럿을 고르고 편집하면 선다 — 한 사람이 200 개(Cmd+A)를 고르고 다른 사람이 200 개를 고른 판이 하트비트마다
0.55s, 다섯이면 4.2s 다. 고른 수가 작으면 작다(50 개 둘: 차이 없음).

**고칠 방향.** 판정을 프레임마다 «남의 잠금 → 경로» 한 번으로 줄인다(문서를 한 번 훑어 id → 경로 표 · 남의 잠금 경로를 미리 짓고 대상마다 접두 견줌) — 그러면
하트비트도 선택 바꿈도 함께 싸진다. 또는 리뷰가 적은 대안(쥘 때의 `head_seq` 를 집합에 적고 다를 때만 남는 것을 판정)으로 빈도를 되돌린다. 어느 쪽이든 판정을
트랜잭션 밖 동기 구간으로 길게 두지 않는다.

## N2 — 브라우저 기록으로 페이지를 옮기면 친 글이 말없이 사라진다(낮음 · 원래 길 · 장치가 약속한 통지가 빠짐)

**판**(실브라우저 · `h2-leave.bprobe.ts` «P1»). 페이지 A · B(같은 메뉴 · **같은 노드 id** `n_t00…02` — 엉뚱한 페이지에 쓰이면 보이게). A 에서 메뉴 링크로 B 에 갔다가
`goBack` 으로 A 에 돌아와 `n_t00`(하나) · `n_t00`+`n_t01`(여럿)을 고르고 «내용»에 «앞 페이지 글»을 친다(`fill` — 포커스는 칸 · blur 없음). `goForward`(popstate)로 B.

| | 하나 | 여럿 |
|---|---|---|
| E2 — A · B 서버 | 그대로(revision 0 · 0) | 그대로 |
| E2 — 나간 `patch` | 0 | 0 |
| E2 — 하단 바(선 적이 있는 글 전부) | **없음** | **없음** |
| E2 — 그 탭으로 A 에 다시 돌아온 화면 | 하단 바 없음 · A 그대로 | 같음 |
| 대응 전 | 같은 값(버림 · 말 없음) | 같은 값 |
| 대조 — 같은 판을 **메뉴 링크 클릭**으로(P1h) | A 에 «클릭 전 글»(revision 1 · `patch` 1 이 A 의 id) · B 그대로 | A 둘에 같은 값 · revision 1 |

**원인**(진단 변조 — `useLeftoverCommit` 에 `console.log` 두 줄). 떠나는 순간의 값: `{"canEdit":true,"atPage":"<A>","openPageId":"<A>","hasDoc":true}` →
`LEFTOVER-COMMIT {"sentOk":false}`(하나 · 여럿 같음). 위젯의 정리가 도는 때 **스토어는 아직 A** 라 대상이 서지만, `latest.current.commitOps` 는 다시 그린 패널의
것 — 주소가 B 로 바뀐 판이라 `useEditCommit` 의 `open` 이 `null` 이고 `commitOps` 가 `false` 를 돌려준다(그 가드는 «앞 페이지의 ops 를 다음 페이지 경로로 내지
않는다» — 그것은 지켰다: B 에 쓰인 것 0). `useLeftoverCommit` 은 그 반환을 안 보고 끝나 `DROPPED_DRAFT_NOTICE` 도 안 선다. 머리말 표의 «다른 페이지로 옮겨
갔다 → 하단 바 한 줄»은 «스토어가 이미 B» 판만 덮는다.

**닿는 길.** 칸에 친 채 브라우저의 뒤로 · 앞으로(단추 · Cmd+[ · 마우스 옆 단추) — 포커스가 칸에 있어 blur 가 안 난다. 사람의 클릭(메뉴 링크)은 누름이 먼저
blur 로 A 에 쓴다.

**고칠 방향.** `commitOps` 의 `false` 를 «못 썼다»로 읽어 하단 바에 한 줄(또는 `at.pageId` 를 패널이 지금 그리는 `pageId` 와 먼저 견줘 다르면 말한다). I1 과 한
규칙으로 맞출 것(아래).

## N3 — 다른 탭이 로그아웃하면 내려가는 칸이 끝난 세션으로 쓰기를 낸다(낮음 · 새 길)

**판**(실브라우저 · `h2-leave.bprobe.ts` «P4» · `p4-logout.bprobe.ts`). alice 의 탭1 이 `n_t00`(+`n_t01`)을 고르고 «내용»에 친다(blur 없음). 같은 브라우저 문맥의
탭2 가 «더 보기 → 로그아웃».
