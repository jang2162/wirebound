# P4b-2 구조 구현체 확장 구현 계획

> **에이전트에게:** 태스크 단위로 구현한다. 각 태스크는 실패하는 테스트 → 최소 구현 →
> 통과 → 커밋의 순환을 하나씩 갖는다.

**목표:** 카탈로그가 선언한 구조 **45개 중 19개만 구현돼 있다. 나머지 26개를 만든다.**
그래야 §6.0의 약속 — *"같은 `List` 노드가 관리자 테마에서는 테이블로, 마케팅 테마에서는
카드 그리드로"* — 가 성립하고, P4b-3의 시스템 테마 다섯이 서로 달라 보인다.

**진행 방식이 다르다 — 이 슬라이스는 병렬이다.**

```
① 준비(순차, 워커 하나)  →  ② 구현(병렬, 워커 넷)  →  ③ 통합·리뷰
   충돌 지점을 미리 가른다      그룹별로 독립 워크트리
```

CLAUDE.md가 *"구조 구현체를 그룹별로 나눠 구현할 때"*를 병렬화가 잘 맞는 지점으로 지목한다.
다만 오늘 코드에는 **네 워커가 동시에 만질 파일이 둘** 있어서 그것을 먼저 가른다.

## 전역 제약

- **설계 문서를 고치지 않는다.** 예시가 규격과 어긋나면 규격이 이기고, 어긋난 사실을 보고한다.
  규격끼리 부딪히면 P4a-3의 기준 — *"어느 규격이 다른 규격을 실행 불가능하게 만드는가."*
- **§6.11의 여섯 속성 계약을 넓히지 않는다.**
- **`style=`에는 커스텀 프로퍼티만.** 일반 선언 0개(P4a-2의 D2).
- **시스템 테마를 만들지 않는다** — P4b-3이다. `admin`은 기본 구조를 고르므로 이 슬라이스가
  화면을 바꾸지 않아야 한다.
- **`packages/schema`는 zod 외의 런타임 의존을 갖지 않는다.**
- **api 테스트는 Postgres 하나(포트 5433)를 공유한다.** 병렬 워커가 **동시에 `pnpm test`
  전체를 돌리지 않는다** — 아래 D4.

---

## 확정한 결정

### D1. 준비 웨이브가 충돌 지점을 먼저 가른다

네 워커가 동시에 만질 파일이 둘이다.

| 파일 | 무엇이 충돌하는가 |
|---|---|
| `packages/renderer/src/structures/index.ts` | `DEFAULTS` 배열 하나에 26줄이 들어온다 |
| `packages/renderer/src/structure-css.ts` | `structureBaseCss()`가 규칙 배열 하나를 만든다 |

**그룹별 모듈로 가른다.** 등록도 CSS도 그룹이 소유하고 `index.ts`·`structure-css.ts`는
그것들을 모으기만 한다. 그러면 각 워커가 **자기 파일만** 만진다.

### D2. 그룹 넷으로 나눈다

| 워커 | 그룹 | 만들 구조 | 수 |
|---|---|---|---|
| **W1** | 구조 | `Section` fullBleed·splitBg · `Card` bordered·elevated·mediaTop·horizontal · `Tabs` pill·enclosed·vertical | **9** |
| **W2** | 데이터 | `List` cardGrid·stackedList·mediaList · `Tree` accordion · `KeyValue` definitionList·cardGrid | **6** |
| **W3** | 입력 | `SearchForm` stacked·collapsible · `EntryForm` labelTop·sectioned · `Field` filled·underlined | **6** |
| **W4** | 액션·문서 | `Button` outline·text · `Media` video·illustration·chart | **5** |

**카탈로그 파일이 이미 이 경계로 갈려 있다**(`catalog/structure.ts`·`data.ts`·`input.ts`·
`action.ts`·`document.ts`). 그래서 `parts`를 넓혀야 할 때도 서로 안 겹친다.

### D3. `Media.kind` 판정은 W4가 한다

P4b-1이 *"`MediaImage`가 `kind`를 한 번도 읽지 않는다 — 죽어 있는 prop이고 '조용히 틀린다'
부류다"*를 케이스로 고정하고 **답을 이 슬라이스로 넘겼다.**

**W4가 `MediaVideo`·`MediaIllustration`·`MediaChart`를 만든 뒤 판정한다** — 넷이 서로 다르게
그리면 `kind`는 구조와 중복이고, 구조들이 `kind`를 읽을 일이 있으면 남는다. **구조를 만들기
전에 정하지 마라.**

지우기로 하면 **`z.strictObject`라 문서 마이그레이션이 필요하다**(§13.1). 그 비용을 재고
**이 슬라이스에서 할지 P4b-3으로 넘길지 판정하라.**

### D4. 손잡이 부류는 **26개가 다 만들어진 뒤** 판정한다

P4b-1 이월이 남긴 것 — 구조 기본 CSS가 노드 변수를 읽는 손잡이가 테마 어휘로 **침묵 덮어쓰기**
되고, 원인은 `STYLE_PROPERTIES`에 **컴포넌트 범위 개념이 없다**는 것이다.

**구조를 만들 때마다 손잡이가 는다.** 그래서 ③ 통합 단계에서 **전체 목록을 놓고** 판정한다.
후보 둘 — 어휘에 컴포넌트 범위를 준다 / 노드에서 스타일 prop을 걷어낸다.

**병렬 워커는 손잡이를 새로 만들 때 그 사실만 보고한다. 부류를 고치지 마라.**

### D5. 화면이 바뀌면 안 된다

`admin`이 고르는 것은 **각 컴포넌트의 첫 구조**이고 그것들은 이미 있다. 26개를 더해도
**오늘 화면은 그대로여야 한다.** ③ 통합이 그것을 판정한다.

## 구조 구현체 작성 계약 — **네 워커가 똑같이 지킨다**

새 구조는 전부 이 여섯을 지킨다. **가드가 이미 셋 있고 어기면 그 자리에서 죽는다.**

1. **`attrs`를 루트 엘리먼트에 편다.** `{...attrs}` 하나로 여섯 속성이 나간다.
2. **내부 조각은 `part('name')`.** 그 이름이 **카탈로그의 `parts`에 선언돼 있어야 한다** —
   없으면 `structures.test.tsx`의 part 이름 계약이 죽는다. 필요하면 **자기 그룹의 카탈로그
   파일**에 이름을 더해라.
3. **`style=`에는 커스텀 프로퍼티만.** 일반 선언은 0개다. 노드마다 달라지는 값은
   `nodeVar('component', 'prop')`으로 내고 **자기 그룹의 구조 기본 CSS**가 `var()`로 읽는다.
4. **계약 밖 `data-*` 금지.** `data-wb-role` 같은 것을 만들지 마라 — enum prop에서 파생되는
   표현 변형은 `variantFrom`(P4a-2)이 이미 채널이다.
5. **조건부 조각도 가드가 본다.** P4b-1이 순회를 **수 prop 갈래와 두 prop 동시 조건**까지
   넓혔다. 셋 이상 동시 조건은 아직 못 보므로 **만들지 마라**(만들었으면 보고하라).
6. **카탈로그의 도달성 검사를 어기면 `import`가 던져 파일 65개가 멈춘다.** `states`를 더하면
   `editor`에도 항목을 더해라. `variants`는 enum과 정확히 같아야 한다(`variantFrom`이 있을 때).

**구조는 와이어프레임이다.** 실제 데이터도 상호작용도 없다 — DOM 구조와 조각 이름이 전부이고
외형은 테마가 준다. 구현체 안에서 색·여백을 정하지 마라.

## ② 구현 웨이브 (병렬, 워커 넷)

각 워커는 **자기 그룹의 구조를 하나씩** 만든다. 구조 하나가 태스크 하나다:

- [ ] **Step 1** 그 구조가 그리는 DOM과 조각 이름을 정한다. 카탈로그의 `parts`에 없으면 더한다.
- [ ] **Step 2** 실패하는 테스트를 쓴다 — 조각이 나오는가, 계약 밖 속성이 없는가,
      조건부 조각이 조건에서 나오는가.
- [ ] **Step 3** 실패를 확인한다.
- [ ] **Step 4** 구현하고 등록한다.
- [ ] **Step 5** 구조가 서기 위한 선언이 필요하면 **자기 그룹의 구조 기본 CSS**에 넣는다.
      **손잡이(노드 변수)를 새로 만들었으면 보고에 적어라**(D4).
- [ ] **Step 6** 통과를 확인하고 **구조 하나마다 커밋**한다.

**`pnpm test` 전체를 돌리지 마라** — 다른 워커가 동시에 돌면 Postgres 하나를 두고 부딪힌다.
`pnpm vitest run --project unit`과 `--project web`만 돌려라. **api 프로젝트는 통합 단계에서
한 번만 돈다.**

## 재라 — 이 계획이 정하지 않고 넘기는 것

| # | 무엇 | 누가 |
|---|---|---|
| 1 | 각 구조가 실제로 어떤 DOM인가 | 설계가 이름만 준다. 각 워커가 정하고 **왜 그렇게 그렸는지**를 주석에 남긴다 |
| 2 | `parts`를 얼마나 넓힐 것인가 | 조각 이름은 **테마의 어휘**다(§6.5). 늘리면 테마가 쓸 수 있는 것이 늘지만 계약도 는다 |
| 3 | `Media.kind` | W4 (D3) |
| 4 | 손잡이 부류 | ③ 통합 (D4) |
| 5 | 구조 기본 CSS가 얼마나 커지는가 | P4b-1이 *"19개 중 5개만 규칙을 갖는다"*고 쟀다. 26개가 늘면 다시 재야 한다 |
| 6 | 셋 이상 동시 조건이 필요한 구조가 있는가 | 있으면 가드가 못 본다 — 만들지 말고 보고하라 |
| 7 | `Tabs.vertical`·`Section.splitBg` 같은 것이 **구조인가 스킨인가** | 세로 탭이 DOM 차이인지 CSS 차이인지에 따라 갈린다 |

## 계획이 재지 않은 것

| # | 무엇 |
|---|---|
| 1 | **병렬 워커가 정말 안 부딪히는지** 재지 않았다. 준비 웨이브가 가르는 파일 둘 말고 다른 공유 지점이 있을 수 있다 |
| 2 | 26개가 늘면 **전수 가드의 순회가 얼마나 커지는지**. P4b-1이 4224 렌더·86ms를 쟀고 구조가 19 → 45가 된다 |
| 3 | **`admin`이 새 구조를 하나도 안 고르므로 26개가 화면에서 안 보인다.** P4b-3까지 눈으로 확인할 길이 없다 |
| 4 | 조각 이름이 그룹마다 따로 정해지면 **테마 작성자가 외울 것이 는다.** 이름 규칙을 세우지 않았다 |
| 5 | `Field`의 세 구조(outlined·filled·underlined)가 **DOM이 같고 CSS만 다를** 수 있다 — 그러면 구조가 아니라 변형이다(재라 #7과 같은 부류) |
