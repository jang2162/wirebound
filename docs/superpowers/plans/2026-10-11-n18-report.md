## 항목마다

### L-101 — 하트비트 도장의 문서 축을 «구조가 바뀔 때만 오르는 수» 로

**재현(실서버).** Text 7000(538KB) · 쥔 사람 5(고른 200 씩) · 남의 잠금 801 인 한 페이지에서 보라가 **제 노드의 props 를 `PATCH …/ops` 로 고친 뒤 같은 집합의 `lock` 프레임(하트비트)**을 보내는 흐름 10번(웹이 실제로 내는 순서).

| | 건너뜀 | «보낸 순간 → `hold`» p50 |
|---|---|---|
| 고치기 전(도장 = `head_seq`) | **0 / 10** | 15.4ms |
| 고친 뒤(도장 = `structure_seq`) props 만 고친 편집 | **10 / 10**(두 번 돌려 둘 다) | 5.0 · 5.3ms |
| 고친 뒤 구조를 바꾼 편집(노드 더하기) | 0 / 5(다시 판정 — 의도) | 23.3 · 25.3ms |

편집 없는 하트비트(기존 케이스) 열 번은 전과 같이 10/10 건너뜀 · p50 2.8 → 4.6 · 5.2ms(붐빔 범위). **구조 번호를 올리는 비용** `sameStructure` — Text 7000 한 문서 쌍 비교 0.30ms/호출(스크래치, 200번 p50 — 편집 요청 p50 38ms 안의 몫).

**무엇을 했나.** 도장의 문서 축을 `head_seq` → `pages.structure_seq`(새 칸 · 마이그레이션 `0023-pages-structure-seq` — 이미 있는 행은 `head_seq` 와 같게 채움 = 다시 판정하는 쪽으로 틀림). 편집 파이프라인이 `sameStructure(before.root, after.root)`(전위 순회의 (id · 부모 자리) 열 비교 — 스택으로 돈다)가 다를 때만 `seq` 로 올린다. 판정 입력(`selectionConflicts`)이 노드의 부모 사슬뿐이라 구조가 같으면 판정이 같다. 되살린 페이지(`insertPageWithId`)는 `structure_seq` 도 `head_seq` 와 같은 값에서 시작한다.

**소비자 세기(`git grep`).** 도장을 읽는 자리는 `lock/store.ts` 의 `isJudged` 하나이고 부르는 곳은 `ws/lock.ts` 의 `settle` 하나다. 웹 · CLI · MCP 는 도장을 안 읽는다(프레임에 안 실린다).

**e2 반증의 미재측 값**(«5 연결 · 1s 30 편집이 600s 안에 안 끝남»). 같은 모양의 기존 케이스(`ws-lock-cost.test.ts` 둘째 단계 — 쥔 사람 다섯이 1s 마다 하트비트 · 남의 편집 20)가 통과한다: EDITS p50 82 · 105.8 · 202.6ms(붐빔 · 최대 138 · 623ms). 600s 안에 안 끝나는 값은 안 나왔다 — 같은 부하의 «편집 직전 하트비트» 흐름(위 표)은 따로 재지 않았다.

### L-254 — 세대 표

**재현(스크래치 케이스 = 변조 M5 의 값).** 놓기 · 만료 · 빈 집합 · 지운 페이지 어느 길로 놓아도 `generations` 에 그 프로젝트 항목이 1 개 남는다(변조 M5 가 `expected 1 to be 0`). **고침:** 공개 연산 끝마다 `tidy` — 그 프로젝트에 잠금이 하나도 없으면 세대를 지움. 지워도 되는 까닭: 세대를 읽는 자리는 도장을 쥔 잠금과 새 `hold` 뿐이라 잠금이 없으면 읽을 도장이 없고, 새 `hold` 는 `bump` 로 다시 시작한다(케이스 «지운 뒤 다시 잡아도 옛 도장이 맞지 않는다»). `LockStore.generationCount()` 를 더했다(누수 재는 자리 — `liveCount` 와 같은 자세).

### L-255 — 잃은 삭제 COMMIT 이 늦게 커밋되면 지운 페이지의 잠금이 남는다

**재현(실서버 · `withProxiedRealApi` — COMMIT 3s 늦춤 + api 쪽 연결만 끊음).** 페이지 삭제 · 메뉴 연쇄 삭제 둘 다 503 «모름» → 3s 뒤 커밋 → 룸은 `menu-changed`(rev 4)를 받았지만 `locks` 목록은 **두 잠금 그대로**(케이스가 «locks 프레임이 4 개까지 차지 않았습니다» 로 3s 시간 초과 — 기다린 변화가 안 왔다).

**고침.** `runTreeTransaction(…, goneOf)` — 지운 페이지 id 를 내는 함수를 받아 **제때 커밋된 판 · 늦게 커밋된 판 모두 같은 자리에서** 놓는다(신호 앞). 라우트가 따로 부르던 `releaseLocksOnPages` 줄(페이지 삭제 · 연쇄 삭제)은 걷었다 — 둘이 갈리지 않게. 복원의 놓기는 그대로(답을 잃은 복원은 방송이 번호 프레임이라 늦게 안 낸다 — 아래 L-106).

### L-253 — 외짝 서로게이트 가드가 문서 전체를 훑는다

**재현(스크래치 · Text 7000 한 문서).** 가드 `containsLoneSurrogate(ops) || (inverse) || (after)` p50 **2.57ms**(최대 8.79) — NUL 가드는 p50 2.67ms. 장부의 5.08ms 는 api 안(붐빔 포함)의 값이다. **고침:** `ops` 만 훑는다 — 앞 문서는 jsonb 에서 와 외짝이 없고 `inverse` · `after` 의 새 글자는 전부 `ops` 의 값 · 경로에서 온다. 훑는 비용 p50 0.00ms(최대 0.025). NUL 가드는 장부 밖이라 안 바꿨다. 기존 6 케이스(PATCH · WS `patch` · PUT · 프리셋 …)가 그대로 통과.

### L-252 — 깊은 중첩 본문 500

**재현.** (스크래치) `applyOps` · `invertOps` 가 노드 **1500 단계에서** 스택이 넘친다(1000 은 통과) — 장부의 3000 · 8000 보다 앞이다. 가드(`containsNulByte` · `containsLoneSurrogate`)는 3000 단계에서 넘친다(2000 은 통과). (실서버 · 변조 M10 + M11 을 함께 떼어 «고치기 전» 을 만든 값) REST ops 3000 · 8000 → **500 · 500**, 350 단계 → **200**(한도 밖이 통과), PUT 3000 → 500, 프리셋 3000 → 500, WS `patch` 3000 → patch-error **500**.

**고침.** 본문 JSON 중첩 상한 `MAX_JSON_NESTING = 600`(노드 300 단계 · 반복문 훑기 — `services/nesting.ts`) — HTTP `preValidation` 훅(PUT · 가져오기 · 프리셋 · REST ops 모두) + 편집 파이프라인의 `ops`(WS `patch` · 코멘트 · 복원). 넘으면 400 «본문의 중첩이 너무 깁니다(객체 · 배열 600 단계까지)». **기술 한도다 — 제품 규칙이 아니다**(재귀를 반복문으로 바꾸는 쪽이 먼저). 값 600 의 근거: 노드 300 단계는 `applyOps` 가 넘치는 1500 의 1/5.

**편집 뒤 문서의 깊이는 따로 안 본다 — 실증으로 걷었다.** 처음에 «한도 안의 편집을 되풀이해 깊이를 쌓으면 다음 적용이 넘친다» 를 막으려고 편집 뒤 노드 깊이 검사를 달았다. 변조 M12(그 줄을 뗌)가 **살아남았다** — 케이스의 셋째 편집이 400 이었는데 원인이 그 검사가 아니라 **경로 길이 한도(2000 글자 · `http/patch-ops.ts`)** 의 `ops.0.path` «경로가 너무 깁니다» 였다. 경로로 닿는 깊이가 노드 190 단계 안팎이라 편집으로는 더 못 쌓는다(편집 하나 = 경로 깊이 ≤ 190 + 값 ≤ 300 → 문서 ≤ 500 단계 < 1500). 쓸모없는 검사라 걷었고(`MAX_NODE_DEPTH` 포함), 그 성질은 케이스(«한도 안의 편집을 되풀이해 … 경로 길이 한도에서 400 으로 멈추고 그 뒤에도 편집이 선다»)가 잠그며 경로 한도를 올리는 변조 M14 에 죽는다.

### L-256 — 입구 표 밖의 json 칸 `projects.theme_tokens`

**재현 — 재현 안 됨(닫힘).** `psql`: `'{"a":"x\ud800y"}'::json` 은 통과, `->>` · `::jsonb` 는 22P02 — 장부 서술대로다. 그러나 API 로 닿는 길(`PUT …/theme`)은 값 · 키 모두 거절된다: 값은 `checkTokenValue` 의 `BAD_CHAR`(422 `token-value-char`), 키는 manifest 에 없는 키(422). 케이스 4 개(값 외짝 · 값 NUL · 키 외짝 · 키 NUL → 422 · `theme_tokens` `{}` 그대로)를 `project-theme-review.test.ts` 에 더했다 — 변조 M13(`BAD_CHAR` 검사를 뗌)에 값 케이스 둘 + 기존 «스냅샷 · 복원» 둘이 죽는다. **키 케이스는 이 변조에서 안 죽는다**(키는 다른 판정이 막는다 — 아래 변조 표 M13). `layouts.schema` 를 쓰는 라우트는 `git grep` 으로 0(`routes/layouts` 없음).

### L-106 — 늦은 COMMIT 의 신호(편집 · 복원 · 게시) — 열림

**재현(실서버 — 편집).** 같은 장치(COMMIT 3s 늦춤 + api 쪽 연결 끊음)로 `PATCH …/ops` 를 보내면 응답 **503**, 3s 뒤 `head_seq` **0 → 1**(커밋됨), 구경꾼 연결이 받은 프레임 `joined · presence · locks` 뿐 — **`page-changed` 0 건**. 트리 쓰기는 전 차수에서 닫혔다(`LOST_COMMIT_LATE_MS` 지켜보기).

**왜 안 고쳤나.** 편집 · 복원 · 게시의 방송은 `seq` 이음이라 늦게 옛 번호를 내면 받는 쪽이 «다음 번호» 로 얹어 뒤 revision 이 빠진 화면을 최신으로 둔다(`services/lost-commit.ts` 머리말 표). **안전한 늦은 신호는 번호를 안 싣는 새 프레임**(예: `page-stale { pageId }` → 웹이 «다시 불러오기» 경보)인데, 웹의 파서(`apps/web/src/realtime/protocol.ts`)는 모르는 프레임을 `null` 로 버리고 경보 표면은 N19(통지) 트랙의 땅이다 — **서버만 병합하면 아무 효과가 없고 웹만 병합하면 서버가 안 보낸다**(트랙 경계를 넘는 원자적 변경). **권고:** N19 병합 뒤 서버 + 웹을 한 브랜치로 «늦은 커밋 → `page-stale`» 한 차수. 그 전까지 현상은 남의 화면이 다음 변경의 `seq` 이음 어긋남(«연결이 끊긴 사이…») 때 낡음을 안다.

### L-251 — 텍스트 칸의 외짝 서로게이트 — 구현 안 함

**값(실서버 · HEAD).** 페이지 제목 · 프로젝트 이름 · 메뉴 제목 PATCH → **200**, 스냅샷 태그 · 프리셋 이름 POST → **201**, 응답의 글자 `a�b` 처럼 **U+FFFD 로 조용히 바뀐 채 저장된다**(코멘트 본문은 같은 `pg` 경로 — 안 쟀다). 사용자 결정 항목이라 코드는 안 바꿨다.

**권고 — (나) 안 바꿈(U+FFFD 치환 유지).** 근거: (1) NUL 은 Postgres 가 **저장 자체를 못 해서** 거절한다 — 외짝 서로게이트는 치환으로 저장이 되고 잃는 것은 깨진 글자 하나다. (2) 외짝은 사용자가 이모지 중간을 잘라 붙이는 데서 생기는데, 400 으로 거절하면 화면은 «왜 안 되는지» 모르는 실패 줄만 낸다 — 치환은 눈에 보이는 `�` 로 스스로 드러난다. (3) 400 을 고르면 «칸 목록 표» 를 `NulByteError` 와 한 벌 더 만들어 입구마다(라우트 · 저장소 방벽) 달아야 한다 — 같은 규칙이 두 벌이 된다. **(가)로 가면:** `NulByteError` 표의 칸 목록에 `containsLoneSurrogate` 를 같이 건다(저장소 쓰기 함수가 지키는 자리 — `repos/projects.ts` · `menu.ts` · `pages.ts` · `comments.ts` · `presets.ts` · `snapshots.ts`) + 웹이 400 문장을 보이는지 확인.

### L-036 — 스키마 `nested-page` — 구현 안 함

**값(스크래치).** `validatePage` 가 `Page` 안의 `Page` 를 **오류 0 건으로 통과**시킨다(루트 `Page` 의 자식으로 `Page` 하나 — 이슈 없음). N6 이 닫은 것은 선택기 목록뿐이다. 스키마에 `nested-page` 오류를 더하면 **이미 저장된 문서가 편집(6단계 검증)에서 422 로 막힌다** — 그래서 사용자 DB 를 먼저 훑어야 한다. **읽기 전용 훑기 SQL**(사용자 DB 5433 에서 사용자가 돌린다 — 이 세션은 안 읽었다. 문법은 이 워크트리 자기 DB(5521)로만 확인했다):

```sql
-- 페이지: 루트 아래에 Page 가 든 문서
select id, title, jsonb_array_length(jsonb_path_query_array(schema, 'strict $.root.**.children[*] ? (@.type == "Page")', '{}', true)) as nested
from pages
where jsonb_path_exists(schema, 'strict $.root.**.children[*] ? (@.type == "Page")', '{}', true);

-- 프리셋: nodes 배열 안
select id, name from presets
where jsonb_path_exists(nodes, 'strict $[*].**.children[*] ? (@.type == "Page")', '{}', true);
```

(스냅샷 payload 안의 문서는 `snapshots.payload` 의 `pages[*].schema` — 같은 식을 `strict $.pages[*].schema.root.**…` 로 건다. `**` 앞에 `strict` 를 안 주면 lax 가 배열을 자동으로 풀어 같은 노드를 두 번 센다 — 스크래치로 확인했다.) **권고:** 0 건이면 스키마에 `nested-page`(오류)를 더하고, 있으면 그 문서를 먼저 고치거나 «경고» 로 시작한다.

### L-104 · L-112 · L-114 · L-115 — 값만(코드 안 바꿈)

장부 열에 넣을 문장:

- **L-104** 마이그레이션 `0020` 의 `down` 은 `project_menu_revs` 표를 `dropTable` 한다(코드) → 다시 올리면 `rev` 가 0 부터. 내려갔다 올라가는 길은 개발 · 복구뿐이고 열린 탭의 «더 큰 번호» 는 다음 변경이 그 번호를 넘을 때까지 신호를 버린다. 안 바꿈(Q-B (a)).
- **L-112** `CASCADE_ID_LIMIT = 10_000`(`routes/menu.ts`) — 넘으면 **400** `id는 10000개 이하여야 합니다`(`menu-cascade-delete.test.ts` 가 이미 잠금). 상자가 상한을 미리 말하지 않는다. 안 바꿈(Q-C (a)).
- **L-114** 프레임 `actor`(`{ type: 'user' | 'mcp' | 'cli', label }` — `label` 은 사람 이름 · 토큰 이름)는 `page-changed` · `restored` · `theme-changed` · `menu-changed` 에 실려 viewer 까지 간다. **읽는 자 0**: `git grep -n '\.actor\b' -- apps/web/src packages/cli/src packages/mcp/src` 결과가 웹 `realtime/protocol.ts` 의 **파싱 줄(`isRecord(value.actor)` 검증 + 옮겨 담기)뿐**이다. **서버에서 뺄 수 없다** — 웹 파서가 `isRecord(value.actor)` 가 아니면 `page-changed` · `restored` · `theme-changed` 를 `null` 로 버린다. 빼려면 웹 파서와 같은 브랜치(L-106 과 같은 «서버 + 웹» 차수). viewer 는 `presence` 로 이미 사람 이름을 보므로 새 노출은 **토큰 이름뿐**이다. 안 바꿈.
- **L-115**(실서버) 저장된 문서의 노드에 모르는 키를 DB 에서 직접 넣고 `POST …/snapshots` → **500**, 같은 페이지의 `GET …/pages/:id` → 200(조회는 봉투를 안 본다). 원래 길(안전망 스냅샷 · `GET …/snapshot` 도 같은 `PageSchema` 를 지난다). 안 바꿈(Q-D (a)).

## 변조 표(구분력)

모든 변조는 `백업(경로 전체 이름) → 한 곳 치환(맞은 수 1) → 해당 파일만 돌림 → cmp 복원`(스크립트가 `finally` 에서 복원하고 `cmp` 결과 `True` 를 적는다). 변조마다 전량은 안 돌렸다. 죽은 케이스는 **실패 값**으로 적었다(시간 초과 아님 — 아래 «시간 초과로 죽은 것» 참고).

| # | 변조 | 죽은 케이스 · 값 |
|---|---|---|
| M1 | `isJudged` 가 구조 번호를 안 본다 | 저장소 «구조 번호가 달라졌으면 거짓» (`expected true to be false`) · 웹 흐름 «구조를 바꾼 편집 뒤는 다시 판정» (`skipped 5 → 기대 0`) |
| M2 | 파이프라인이 구조 번호를 안 올린다 | `page-structure-seq`(`{head:1, structure:0}` ≠ `{1,1}`) · 웹 흐름(`skipped 5`) |
| M3 | 파이프라인이 늘 올린다 | `page-structure-seq`(`structure 3 ≠ 2`) · 웹 흐름 «props 만 고친 편집은 건너뜀» (`skipped 0 → 기대 10`) |
| M4 | `sameStructure` 가 부모를 안 본다 | `lock-structure` «다른 부모로 옮기면» · `page-structure-seq`(`structure 2 ≠ 4`) |
| M5 | `tidy` 가 아무것도 안 한다 | 세대 표 «놓으면 · 만료되면 …» (`expected 1 to be 0`) — **혼자** |
| M6 | `tidy` 가 잠금이 남아도 지운다 | 세대 표 «잠금이 남아 있으면 안 지운다» (`expected 0 to be 1`) — **혼자** |
| M7 | 늦은 커밋 갈래의 놓기를 뗌 | 「답을 잃은 삭제 COMMIT」 **둘**(`locks 프레임이 4 개까지 차지 않았다`) — 제때 커밋 케이스는 산다 |
| M8 | 제때 커밋 갈래의 놓기를 뗌 | 「페이지 삭제」 · 「연쇄 삭제」 · 「남은 페이지」 · 「같은 집합을 다시 보내도」 **넷** |
| M15 | 페이지 삭제 라우트가 `goneOf` 를 안 넘김 | 「페이지 삭제」 · 「남은 페이지」 · 「같은 집합」 · 늦은 커밋의 페이지 삭제 **넷** |
| M16 | 연쇄 삭제 라우트가 `goneOf` 를 안 넘김 | 「연쇄 삭제」 · 늦은 커밋의 연쇄 삭제 **둘** |
| M17 | `handleLockFrame` 의 «없는 페이지» 갈래를 뗌 | 「같은 집합을 다시 보내도」 **혼자**(`pages` 가 `[keep]` 이어야 하는데 지운 페이지가 다시 섬) |
| M9 | `ops` 서로게이트 훑기를 뗌 | `lone-surrogate-inputs` «PATCH …/ops» (`500 ≠ 400`) · «편집 patch 프레임» (`500 ≠ 400`) |
| M10 | HTTP `preValidation` 훅을 뗌 | 「PUT …/schema 3000」 · 「POST …/presets」 (`500 ≠ 400`) — REST ops 는 파이프라인이 막아 안 죽는다 |
| M11 | 파이프라인 `ops` 중첩 검사를 뗌 | 「편집 patch 프레임」 **혼자**(`500 ≠ 400`) — REST ops 는 훅이 막는다 |
| M10+M11 | 둘 다 뗌 | 7 / 9 죽음(REST ops 3000 · 8000 · 350 · PUT 3000 · 350 · 프리셋 · WS) — **REST ops 는 두 겹이 함께 막아 한 겹씩 떼면 초록** |
| M12 | 편집 뒤 노드 깊이 검사를 뗌 | **안 죽었다** → 쓸모없는 검사라 걷음(위 L-252) |
| M14 | 경로 길이 한도 2000 → 200000 | 「되풀이해 … 경로 길이 한도에서 400 으로 멈춘다」 **혼자**(`200 ≠ 400`) |
| M13 | `checkTokenValue` 의 `BAD_CHAR` 를 뗌 | 값 케이스 둘 + 기존 «스냅샷 · 복원» 둘(`put 200 · snapshot 500 · restore 500`) — **키 케이스 둘은 안 죽는다**(키는 manifest 에 없는 키라는 다른 판정이 막는다. 키 케이스는 «막힌다» 의 대조를 잠그되 `BAD_CHAR` 를 소유하지 않는다) |

**시간 초과로 죽은 것.** M7 · M8 · M15 · M16 의 «locks 프레임이 4 개까지 차지 않았다» 는 `waitForCount` 의 3s 시간 초과다 — 그러나 **기다린 변화(목록이 줄어듦)가 안 온 것을 재는 케이스**이고, 짝 대조군(M7 에서 제때 커밋 케이스, M8 에서 «남은 페이지» 가 아닌 둘)이 같은 변조에서 살아 있어 시간 초과가 구분력을 소유한다 — 그래도 단언 값(잠금 목록)으로 죽은 것이 아니라는 점은 적어 둔다.
