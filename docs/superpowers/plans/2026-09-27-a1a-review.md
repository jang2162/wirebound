## 1. 호스트 리스너가 iframe 안의 이벤트를 못 받는다 — 결함(중간), 이 브랜치가 연 길

**센 자리.** `git grep -nE "(document|window)\.addEventListener" -- apps/web/src packages/renderer/src`:

| 자리 | 무엇 | 캔버스 위 조작에 닿나 |
|---|---|---|
| `src/shell/use-popover-dismiss.ts` — `document` 의 `mousedown` · `keydown` | 팝오버 둘(`git grep usePopoverDismiss`: `export-panel.tsx` · `snapshots-panel.tsx`)을 바깥 누름 · Escape 로 닫는다 | **안 닿는다** |
| `src/shell/shell-resizer.tsx` — `window` 의 `pointermove` · `pointerup` · `pointercancel` | 손잡이 둘(`routes/editor.tsx` — 사이드바 폭 `wb-shell-side-resizer` · 좌측 배분 `wb-shell-region-resizer`). 캔버스 위를 지나는 것은 폭 손잡이. 배분 손잡이도 같은 코드라 옆으로 끌어 캔버스 위에 서면 같다 | **안 닿는다.** `setPointerCapture` 는 안 쓴다(머리말: jsdom 에 없어서 `window` 리스너) |
| `src/shell/sidebar-layout.ts` — `window` 의 `resize` | 창 크기 | 무관 |
| `src/canvas/canvas-iframe.tsx` — iframe 창의 `wb-canvas-measure` · 문서의 `click` | iframe 자기 것 | 무관 |

React `onKeyDown` 을 호스트 요소에 건 자리(`panels/structure-tree.tsx` · `panels/menu-tree.tsx` 등)는 **원래 있던 길**이다 — main 에서도 캔버스 노드를 누르면 초점이 `BODY` 로 가서(아래 표 `activeAfterCanvasClick`) 트리의 `onKeyDown` 에 키가 안 닿았다. 전역 키 단축키(`metaKey` · `ctrlKey`)는 `apps/web/src` 에 없다.

**값**(탐침 · 조작 같음, 운영 번들도 브랜치 값 같음):

| 조작 | main | 브랜치 |
|---|---|---|
| 내보내기 · 스냅샷 팝오버를 열고 캔버스 노드를 누름 → 팝오버 수 | 0 · 초점 `BODY` | **1** · 초점 `IFRAME` |
| 이어서 Escape → 팝오버 수 | 0 | **1** |
| 폭 손잡이를 잘게(한 이벤트 30px) 오른쪽으로 — 포인터가 손잡이를 앞질러 캔버스 위로 | 폭이 포인터를 따라 811 까지 | **214 에서 멈춤** — 포인터 아래가 `IFRAME` 이 된 순간부터 |
| 캔버스 위에서 놓고 손잡이 쪽으로 60px 되돌아감(버튼 안 누름) | 폭 그대로 | **폭이 바뀜(214 → 204)** — `pointerup` 을 못 받아 드래그가 붙은 채 남는다 |
| 한 이벤트에 500px 뛰어 캔버스 한가운데 | 764 | **264(움직이지 않음)** |

**케이스**(`apps/web/build-test/canvas-iframe-host-events.test.ts`) — main 사본 6/6 초록, 브랜치 dev · build 둘 다 5 빨강 · 1 초록:

| 케이스 | 브랜치 실패 값 |
|---|---|
| «내보내기 팝오버를 연 채 캔버스의 노드를 누르면 닫힌다» · «스냅샷 …» | `afterCanvasClick: 1`(기대 0) |
| «내보내기 팝오버 — 초점이 캔버스 안의 요소에 있어도 Escape 가 닫는다» · «스냅샷 …» | `afterEscape: 1`(기대 0) — 누르지 않고 `focus()` 로 초점만 옮겨 누름 갈래와 떼어 잰다(`focusedInCanvas: true` 를 함께 단언) |
| «사이드바 폭 손잡이를 캔버스 위로 끌어도 폭이 따라오고, 캔버스 위에서 놓으면 드래그가 끝난다» | `dragged: 264`(기대 414) · `afterRelease: 204`(기대 414), 놓은 자리 `wb-shell-canvas-iframe` |

- **원인:** 캔버스 문서가 별도 `Document`(iframe)가 되어 그 안의 마우스 · 키 · 포인터 이벤트가 호스트 `document` · `window` 로 올라가지 않는다. React 합성 이벤트는 portal 로 호스트 트리에 닿지만(구현 보고 Task 7) 네이티브 전역 리스너는 아니다.
- **고칠 방향:** 팝오버는 캔버스 iframe 문서에도 `mousedown` · `keydown` 을 건다(또는 호스트 `window` 의 `blur` 에서 `document.activeElement` 가 캔버스 iframe 이면 바깥 누름으로 본다 — Escape 는 iframe 문서의 `keydown` 이 따로 필요). 손잡이는 `setPointerCapture`(jsdom 판은 `window` 리스너를 남겨 둔다) 또는 드래그 동안 iframe 에 `pointer-events: none`.
- **한계:** Chrome 만 쟀다(Firefox · Safari 의 iframe 경계 포인터 라우팅은 안 쟀다). 실제 하드웨어 마우스가 아니라 CDP 입력이다. 배분 손잡이(`wb-shell-region-resizer`)는 코드로만 같다고 봤고 따로 재지 않았다.

## 2. 캔버스 위 휠 스크롤 — 재현 안 됨

- **판:** Text 150 개 페이지, 줌 1 · 0.5. 캔버스 문서 위(포인터 아래 요소: main `P` · `DIV`, 브랜치 `IFRAME`)에서 `wheel(0, 300)` 세 번 → `.wb-shell-canvas` 의 `scrollTop`. 대조로 캔버스 여백(프레임 밖) 위에서 한 번 더.
- **값:** main · 브랜치 모두 줌 1 · 0.5 에서 `0 → 900 → 1200`(문서 위 세 번 · 여백 위 한 번). iframe 이 안쪽 스크롤이 없어 휠이 호스트 스크롤러로 이어진다.
- **한계:** Chrome 의 이산 휠만(트랙패드 관성 · Safari 의 iframe 스크롤 체이닝은 안 쟀다).

## 3. 빈 자리 클릭 — 재현 안 됨(옳다), 실브라우저 케이스로 잠금

- **판:** `Page > [Button(click → navigate), Text × 2]`. 편집 모드: 노드를 누른 뒤 프레임 아래끝 12px 위(문서가 최소 높이 320px 보다 짧아 빈 자리 — 브랜치의 적중 요소 `HTML`, main `DIV.wb-shell-canvas-surface`)를 누름. 뷰 모드: 단추로 알림을 세운 뒤 빈 자리를 누르고 편집 모드로 돌아와 선택을 본다.
- **값:** main · 브랜치(dev · build) 모두 `{ selected: n_text0000001, afterEmpty: null, noticeShown: 1, noticeAfterEmpty: 0, selectedAfterView: n_text0000001 }`.
- **케이스:** «빈 자리 클릭 — 편집 모드는 선택을 풀고, 뷰 모드는 알림만 걷고 선택은 그대로다»(같은 파일, 초록). **구분력:** `CanvasIframe` 의 `doc.addEventListener('click', listener)` 를 걷은 변조(백업 → 바이트 비교 복원)에 죽었다 — `afterEmpty: "n_text0000001"`(기대 null) · `noticeAfterEmpty: 1`(기대 0).
- **한계:** 편집 갈래와 뷰 갈래를 한 케이스가 함께 잰다 — `onBackgroundClick` 의 두 갈래(`canvas.tsx`)를 따로 떼는 변조는 돌리지 않았다.

## 4. 뷰 모드 상호작용이 iframe 안에서 도는가

- **클릭 규칙:** 돈다(항목 3 의 `noticeShown: 1`).
- **알림 줄이 떴을 때 마커 자리**(`frameOffset`): 뷰 모드에서 단추로 알림을 세운 뒤 코멘트 마커 중심 − 노드 왼쪽 위. 브랜치 줌 1 `(0, 0)` · 줌 0.5 `(0, 0)`. main 줌 1 `(0, −2.03)` · 줌 0.5 `(0, 0)` — main 의 2px 어긋남은 이 브랜치에 없다.
- **submit** — 폼(`SearchForm`)에 `<button type="submit">` 을 심어 눌렀다(`render.tsx` 의 `handlersFor` 머리말 A/B 판을 따름):

| 판 | main | 브랜치 |
|---|---|---|
| 뷰 모드 · submit 규칙 있는 폼 | 호스트 URL 그대로 · 규칙 돎(대상 글 숨음) | 같다 — 호스트 URL 그대로 · iframe `about:blank` 그대로 · 노드 5 · 규칙 돎 |
| 뷰 모드 · 규칙 없는 폼 | **호스트가 `…?` 로 이동**(페이지 전체 새로고침) | **iframe 이 `about:blank?` 로 이동 — iframe 문서의 노드 0**(캔버스가 빈다, 호스트 URL 은 그대로) |
| 편집 모드 · 두 폼 다(편집 모드는 핸들러가 없다) | 호스트 `…?` 로 이동 | iframe `about:blank?` · 노드 0 |

- **판정:** 규칙 없는 submit 이 문서를 떠나는 것은 **원래 있던 길**이고, 이 브랜치에서 모양이 «페이지 새로고침» 에서 «캔버스만 빈 채 남음» 으로 바뀌었다. **지금은 사용자 조작으로 닿지 않는다** — 기본 뷰의 폼은 제출 컨트롤이 없다(`SearchFormView` · `EntryFormView` 의 액션은 `<span>`, `ButtonView` 는 `type="button"`, `FieldView` 는 `<div>`). 코드 테마가 폼 안에 진짜 `<button>`(기본 `type=submit`) · `<input>` 을 그리는 순간(A1b 이후) 닿는다. **이월 후보(낮음)** — 케이스는 세우지 않았다.
- **고칠 방향(이월 시):** `CanvasIframe` 이 iframe 문서의 `submit` 을 캡처 단계에서 모드와 무관하게 `preventDefault` 한다(렌더러 핸들러는 규칙이 있을 때만 막는다).
- **한계:** 외곽선 + 오류 배너(`bannerHost`) 판은 재지 않았다 — 배너는 노드 렌더 실패가 있어야 서는데 서버가 카탈로그 오류 문서를 받지 않아 판을 못 세웠다. 외곽선은 알림 줄과 공존하지 않는다(외곽선은 편집 모드, 알림은 뷰 모드). 외곽선 자리는 기존 케이스(`canvas-iframe.test.ts` «캔버스 클릭이 노드를 고르고 외곽선이 …»)가 배너 없는 판만 잰다.

## 5. iframe 수명 — 재현 안 됨(쌓임 없음)

- **세는 법(계측):** `page.addInitScript` 로 호스트의 `HTMLIFrameElement.prototype.contentWindow` 게터를 감싸, 처음 보는 iframe 창마다 ① 그 창의 `ResizeObserver` 를 감싼 생성자로 바꿔 `observe` 에 +1 · `disconnect` 에 −(그 관찰자의 수) 해 **산 관찰 수**를 세고 ② 그 창의 `EventTarget.prototype.addEventListener` · `removeEventListener` 를 감싸 (대상 · 타입 · 캡처 · 함수) 쌍의 **산 리스너 수**를 센다. `CanvasIframe` 이 iframe 창을 `contentWindow` 로 받으므로 첫 리스너 전에 감싸진다. **카나리아:** 재는 동안 산 관찰 1 · 문서 `click` 1 · 창 `wb-canvas-measure` 1 — 0 이 아니다. 스타일은 iframe 문서의 `style[data-wb-style]` 을 차례대로, portal 은 iframe 문서의 `[data-wb-id]` 수.
- **조작 차례:** 열기 → 페이지 전환 왕복 ×3 → 편집/뷰 전환 ×3 → 브라우저 뒤로/앞으로 ×3 → 남(같은 계정 다른 세션)의 스냅샷 복원 + 배너 «다시 불러오기» ×2 → 노드 선택 ×5.
- **값(dev · build 같음):** 모든 단계에서 iframe 1 · 스타일 `base,theme`(한 벌) · 노드 6(Text 5 + Page) · `body` 자식 1 · 산 관찰 1 · 문서 `click` 1 · 창 `wb-canvas-measure` 1. 감싼 창 수(= 만들어진 iframe 수)는 열기 1 → 페이지 왕복 뒤 7 → 뒤로/앞으로 뒤 13 — **페이지를 옮길 때마다 iframe 이 새로 선다**(조회 중 상태가 캔버스를 내렸다 올린다). 옛 창의 관찰 · 리스너는 0 으로 걷혀 있다(산 수가 1 로 유지).
- **한계:** React 가 portal 컨테이너(`body`)에 다는 루트 리스너는 세지 않았다. 복원은 배너 경로만(내 복원 · 되돌리기 복원은 안 쟀다).

## 6. 렌더 비용 — 2 배 미만

- **판:** Text 500 개 페이지 둘, 운영 번들, 같은 기계에서 main → 브랜치 차례로. 탭 3 개 × 조작마다 4 번 = 표본 12. CDP `Performance.getMetrics`(`threadTicks`)의 누적 `TaskDuration` · `ScriptDuration` · `LayoutDuration` · `RecalcStyleDuration` 을 조작 앞뒤(각 300ms 쉼)로 뺐다. 조작: 페이지 전환(링크 클릭 → 500 노드가 설 때까지 — 조회 포함) · 편집/뷰 모드 전환 · 한 글자 편집(노드 250 을 고르고 속성 칸에 `x` 를 친 뒤 blur → 캔버스 글자가 바뀔 때까지).
- **값(중앙값, ms):**

| 조작 | main 작업 / 스크립트 / 레이아웃 / 스타일 | 브랜치 | 스크립트 비 |
|---|---|---|---|
| 페이지 전환 | 24.5 / 8.7 / 4.5 / 2.5 | 28.6 / 14.2 / 3.4 / 1.4 | 1.63 |
| 모드 전환 | 17.9 / 5.1 / 1.1 / 0.5 | 16.7 / 7.0 / 1.2 / 0.5 | 1.37 |
| 한 글자 편집 | 28.0 / 24.6 / 0.2 / 0.1 | 34.6 / 30.5 / 0.2 / 0.1 | 1.24 |

- 벽시계(클릭 → 두 프레임)는 두 판 모두 프레임에 묶였다 — 모드 ≈ 33ms · 페이지 전환 ≈ 49ms. 2 배를 넘은 것이 없어 층을 가르지 않았다. 스크립트가 늘고 레이아웃 · 스타일이 준 것은 노드마다 `ViewHost` · 경계 · 컨텍스트가 붙고 테마 CSS 가 iframe 문서(작은 문서)에서 계산되는 것과 맞는다.
- **한계:** 컴포넌트 한 종류(Text — 기본 뷰가 얇다). 무거운 코드 테마 뷰 · dev 판은 안 쟀다. 표본 12 의 흩어짐은 한 조작 안에서 ±30% 안팎이다.

## 7. `ViewHost` 의 Root 누락 감지

- **판(jsdom — React 의 렌더 · 이펙트 순서는 jsdom 에서도 같다):** `renderDocument` 에 테마 뷰를 주고 그림 → 형제 노드만 고친 문서로 다시 → 그 노드를 고친 문서로 다시. 각 판을 `StrictMode` 안팎에서.

| 뷰 | 처음 | 형제 편집 뒤 | 제 편집 뒤 | «Root» 경고 |
|---|---|---|---|---|
| 뷰 → 내부 컴포넌트 → Root | 테마 뷰 | 테마 뷰 | 테마 뷰 | 0 |
| 뷰 → `memo` 자식(props 받음) → Root | 테마 뷰 | 테마 뷰 | 테마 뷰 | 0 |
| 뷰 → `memo` 자식(props 없음 · 다시 안 그려짐) → Root | 테마 뷰 | 테마 뷰 | 테마 뷰 | 0 |
| **마운트 뒤(`useEffect` 로 상태를 바꿔) Root 를 그리는 뷰** | **기본 뷰** | 기본 뷰 | 기본 뷰 | 1(StrictMode 2) |
| **처음엔 Root 를 빠뜨리고 편집 뒤엔 Root 를 그리는 뷰** | 기본 뷰 | 기본 뷰 | **기본 뷰** | 1(StrictMode 2) |

- `memo` 자식이 안 다시 그려져도 거짓 누락이 안 서는 까닭: `Guarded` 가 렌더마다 새 `binding` 객체를 `NodeContext` 에 싣고 `Root` 가 그 컨텍스트를 읽으므로, `memo` 가 건너뛰어도 컨텍스트 전파로 `Root` 는 다시 그려진다(`markRootRendered` 가 불린다).
- **결함 — 누락 판정이 되돌아오지 않는다.** spec 「뷰 계약」은 «`<Root>` 없이 **반환하면** … 기본 뷰로 대신 그린다» 인데, `Guarded` 의 `missing` 은 한 번 참이 되면 그 노드가 내려가기 전까지 참이다 — 편집으로 Root 를 반환하게 된 뷰도 다시 불리지 않는다(노드 경계의 `resetKey` 는 예외 상태만 되돌린다).
  - **케이스:** `packages/renderer/test/view-path.test.tsx` «Root 를 빠뜨렸던 뷰가 편집으로 Root 를 그리게 되면 테마 뷰로 돌아온다» — 실패 값 `fixed: { className: "", structure: "solid" }`(기대 `{ className: "mine", structure: null }`). renderer + theme-sdk 23 파일 · 395 통과 · 1 실패(이 케이스).
  - **원인:** `ViewHost` 의 `Guarded` 가 `missing` 을 되돌리는 자리가 없다.
  - **고칠 방향:** 뷰 props(`viewProps`)가 바뀌면 `missing` 을 거짓으로 되돌려 테마 뷰를 다시 불러 본다(노드 경계의 `resetKey` 와 같은 축). 이 문장 그대로 짠 판(렌더 중 상태 조정 — 앞 `viewProps` 를 상태로 들고 달라지면 `setMissing(false)`)을 임시로 심어 돌렸다: renderer + theme-sdk **406/406 초록**(새 케이스 · 기존 «Root 를 안 그린 뷰는 기본 뷰로 다시 그리고 console.error 로 말한다» 포함). 바이트 비교로 복원했다.
  - **무게:** 지금은 **낮음** — 캔버스는 `system-admin` v0(기본 뷰 그대로)만 싣고 기본 뷰는 전부 Root 를 그린다. 코드 테마가 들어오면(A1b) **중간** — 데이터는 잃지 않지만 그 노드에서 테마 모습이 페이지를 다시 열 때까지 사라진다.
- **판정 필요 — 마운트 뒤에 Root 를 그리는 뷰.** 첫 반환에 Root 가 없으니 spec 문장대로면 누락이 맞다. 다만 위 고칠 방향으로도 구해지지 않는다(되돌려도 뷰가 새로 마운트되어 다시 첫 반환에 Root 가 없다 — 편집마다 경고). «첫 렌더에 Root 를 반환해야 한다» 를 뷰 계약으로 적을지(spec 「뷰 계약」 · `SKILL.md`), 감지를 한 프레임 미룰지는 코디네이터 판정이다. 케이스는 세우지 않았다.
- **한계:** spec 의 «개발 모드에서 던진다» 는 이 차수에 없다(`view-host.tsx` 머리말 — A2 의 `wb-theme dev` 몫) — 재지 않았다. `Suspense` · `lazy` 로 Root 를 늦게 그리는 뷰는 안 쟀다.
