## 3. 합친 판 게이트 첫 판의 빨강 — 코멘트 목록이 섰다가 빠진다

첫 전량 판(`ba200b16`)의 `pnpm test:build` 실브라우저 갈래에서 `apps/web/build-test/editor-restore-late-commit.test.ts:82` 가 빨강이었다 —
밥이 «코멘트» 탭을 눌러 `li.wb-shell-comment` 가 선 것을 기다린 뒤 센 수가 0(기대 1). 그때 load 20.

**가르기.** 혼자 세 번(load 9–12): 3/3 초록. 같은 파일 넷을 동시에 두 번(load 9–11 에서 시작 · 실행 중 더 오름): **3/8 빨강, 셋 다 같은 줄**.
부하에서만 보이지만 부하 탓이 아니다 — 기전이 섰다:

- CT 가 «컴포넌트» 탭의 «코멘트» 묶음과 «코멘트» 탭이 목록 칸 하나(`panels/comment-panel.tsx` 의 `LIST` — provider 에 든다)를 나눠 쓰게 했다.
  페이지를 열면 «컴포넌트» 탭이 처음 탭이고 루트가 골라져 있어 묶음이 목록을 읽어 둔다.
- «코멘트» 탭을 누르면 그 목록이 첫 렌더에 선다(줄 1) → 본문의 마운트 이펙트가 칸을 `loading` 으로 지운다(«코멘트를 불러오는 중…» · 줄 0) →
  다시 읽기의 답이 다시 세운다(줄 1). 다시 읽기가 느린 판(부하)에서 케이스의 `waitFor` 가 첫 렌더의 줄을 보고 `count()` 가 빈 틈을 읽었다.
- CT 앞에도 «코멘트» 탭을 떠났다 돌아올 때는 같은 깜빡임이 있었다(칸이 탭 밖에 들어 돌아온 첫 렌더에 앞 목록이 선다). CT 가 그것을 **첫 방문**에도
  서게 해, 첫 방문을 기다리던 이 케이스(이 트랙들보다 앞의 것)가 밟았다 — «한 트랙의 동작이 다른 케이스의 판을 바꾼» 꼴이다.

**결정론 판.** `mv-overlaps.test.ts` «… 다시 읽는 동안에도 읽어 둔 목록이 남는다» — 묶음이 읽은 뒤 코멘트 GET 을 1.5s 늦추고 «코멘트» 탭을 눌러
패널의 줄 수가 바뀌는 차례를 `MutationObserver` 로 센다. 고치기 전: `줄 [1, 0, 1] · 불러오는중 1`. 고친 뒤: `줄 [1] · 불러오는중 0 · 끝 1`.

**고침(결정).** 마운트 조회가 칸을 지우지 않는다 — 같은 페이지의 목록이 이미 섰으면 그대로 두고 번호(`at`)만 이 조회의 것으로 올린다(그보다 앞에 낸
다시 받기의 답은 `answered` 가 버린다). 답이 오면 바꾼다. 칸이 비었거나(`loading`) 실패면 지금처럼 «불러오는 중» 이다. 페이지가 바뀌면 provider 가
칸을 처음 값으로 버리므로 남의 페이지 목록이 서는 길은 없다. «남이 단 말은 다시 읽을 때 선다»(설계서 §9)는 그대로다 — 다시 읽기의 답이 선 뒤에 선다.
대안은 케이스를 고치는 것(줄 수가 멎을 때까지 기다림)이었다 — 사람에게도 보이는 깜빡임이라 코드를 고쳤다.
