# N17 — 실브라우저 파일 병렬 연결 · viewer-readonly 쪼개기 보고

변경한 것: `package.json` 스크립트 · `vitest.config.ts`(build 프로젝트 include) · `vitest.browser.config.ts`(워커 3 · export-bundle 제외) · `apps/web/test/routes/viewer-readonly*.tsx`(네 파일 + 헬퍼) · README/CLAUDE.md 의 게이트 문장 · 주석 몇 곳의 명령 이름. 새 케이스는 없다.
원본 JSON · 로그는 이 세션 스크래치패드(`…/scratchpad/m/`)에 있고, 아래 값은 표의 명령에서 나왔다. 덮개 잠듦 없음: `pmset -g log | grep ' Sleep '` 의 마지막 줄이 측정 전(2026-10-09)이다.

## 선택과 이유

**`export-bundle.test.ts` 는 build 프로젝트(직렬)에 남겼다.** `apps/*/build-test/**` 글롭을 `apps/api/build-test/**` + `apps/web/build-test/export-bundle.test.ts` 로 바꾼 한 곳이면 끝나고, 그 파일이 쓰는 `packages/exporter/dist/runtime.js` 재빌드가 직렬 갈래 안에서 다른 파일과 겹치지 않는다. 별도 한 줄 스크립트는 `test:build` 가 세 갈래가 되어 더 복잡하다. 대가: 새 앱의 `build-test` 는 글롭이 아니라 줄을 더해야 build 프로젝트에 든다(주석에 적었다).
**`test:build` 는 두 갈래를 차례로 돈다**(`pnpm test:build:serial; … pnpm test:browser; …` — 앞이 빨강이어도 뒤를 돌고 종료 코드는 앞 → 뒤 순으로 비 0 을 낸다. `sh -c` 로 네 조합을 쳐 0/1/1/1 확인). **`pnpm test:build` 에 `--reporter` 같은 인자를 붙이면 마지막 명령에만 붙는다** — 갈래를 따로 돌려 인자를 준다.

| 실브라우저 갈래 후(워커 3) | `pnpm test:browser` | 538s | 68 · 516 | 0 · 0 | 5.7 |
| 실브라우저 갈래 후 둘째 판 | 같은 명령(아래 붐빔 구간과 겹침) | 523s | 68 · 516 | 0 · 0 | 5.4 |

모든 판은 `--reporter=default --reporter=json --outputFile.json=<경로>` 로 돌렸다. **`test:build` 는 1564s → 687s(−877s)** 다. 직렬 갈래 후 149s 는 build 프로젝트에서 실브라우저 68 파일이 빠진 값이다(N16 보고의 추정 «직렬 ≈1375s» 와 같은 자릿수).

## 파일이 빠지거나 두 번 도는지 — 센 것

- **실행 수(JSON, 두 번):** 전 727 케이스(726 통과 · 1 건너뜀)와 후 211 + 516 = 727(210 통과 · 1 건너뜀 + 516 통과). 케이스를 `(파일 경로, 전체 이름, 상태)` 로 정렬해 견주면 **727 개가 하나도 안 다르다**(파이썬 `sorted(전) == sorted(후)` 참). 건너뛴 한 케이스는 전후 같다 — `packages/theme-kit/build-test/template.test.ts` «스타터 템플릿 zip 저장소 밖에서 설치하고 빌드한다(WB_TEMPLATE_INSTALL=1)»(환경변수를 켜야 도는 케이스).
- **파일 수(`vitest list --filesOnly`, 두 번째 방법):** 전 92 파일의 경로 집합 = 후 `--project build` 24 + `-c vitest.browser.config.ts` 68 이고 겹침 0 · 빠짐 0 · 더함 0.
  - 재는 명령: `pnpm vitest list --filesOnly --project build` · `pnpm vitest list --filesOnly -c vitest.browser.config.ts`(출력 줄 머리의 `[build] ` 는 떼고 센다).
- **구분력(변조 둘 — 파일 수로 센다. 변조 판을 실제로 돌리지는 않았다):**
  - 변조 A — build 프로젝트 include 의 `export-bundle` 줄을 `apps/web/build-test/**/*.test.ts` 로 되돌림: build 24 → **92**, 합 92 → **160**(실브라우저 68 파일이 두 번 돈다).
  - 변조 B — browser 설정에서 `exclude` 줄을 뗌: browser 68 → **69**, 합 92 → **93**(`export-bundle` 이 두 번).
  - 둘 다 백업(`bak/` 의 전체 경로 이름) 후 `cmp` 로 복원했고 복원 뒤 24 + 68 = 92 로 돌아왔다.

## viewer-readonly 쪼개기

- 케이스 넷을 파일 하나씩 `viewer-readonly-reach` · `-viewer` · `-demoted` · `-restored` `.test.tsx` 로 갈랐다. 훑기 도구 · 머리말 · 픽스처는 `viewer-readonly-harness.tsx`(테스트 파일이 아니다)로 옮겼다 — 단언은 한 글자도 안 바꿨고 케이스를 지우지 않았다.
- **케이스 이름 목록:** 전 4 · 후 4 가 같다(`fullName` 정렬 비교 참). web 전체 케이스 3222 · 나머지 3218 개의 이름도 전후 같다(`web-before.json` ↔ `web-after.json`).
- **파일 시간:** 전 `viewer-readonly.test.tsx` 97.5s → 후 reach 42.7s · viewer 12.5s · demoted 12.6s · restored 12.7s. 가장 긴 파일이 절반 이하가 됐다.
- **web 벽시계 108s → 96s**(load 5.9 → 4.1 에서 시작; 실행 중 load 는 앞뒤 값이 다르다). 브리프가 짐작한 «83s → 41s» 만큼은 아니다 — 이 기계의 web 전량은 케이스 합(`tests 237s`)이 워커 몇 개(`--maxWorkers=25%`)로 나뉘는 값이라, 가장 긴 파일이 줄어도 나머지 파일이 길이를 정한다. 쪼갠 효과(최장 파일 97.5s → 42.7s)는 워커를 더 줄 때 더 크다.
- 문서 인용 정리: `fake-realtime.ts` · `viewer-entries.test.tsx` 의 `viewer-readonly…` 가리킴을 새 파일 이름으로 바꿨다.

## 시간 상한 케이스(N16 보고 E 절)

실브라우저 갈래(워커 3, load 5.4 → 8)가 도는 **동안** 같은 기계에서 돌렸다: `pnpm vitest run --project api apps/api/test/edit-lost-commit.test.ts` 3 판(각 12 케이스 통과 · 20.1–20.2s) · `pnpm vitest run --project build apps/api/build-test/screen-chromium.test.ts` 1 판(31 케이스 통과). **거짓 빨강 없음** — 빨강이 없어 «혼자 3번 돌리고 게이트 재실행»은 하지 않았다. 값(경과 · peak)은 계측을 안 심어서 모른다.
`screen-chromium` 은 직렬 갈래 후 판(149s)에서도 통과했다. 실브라우저 갈래 본 판 둘(538s · 523s)은 둘 다 0 실패.
