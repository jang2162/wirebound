## 재현

새 파일 `packages/schema/test/nested-page.test.ts` 를 고치기 전 소스로 돌린 값: 6 케이스 중 **5 빨강 · 1 초록**(«뿌리 Page 하나는 이슈가 아니다» — 대조군). 뿌리의 자식 `Page` · `Flex › Flex › Page` · `Page › Page` · 레이아웃의 `Page` 모두 `expected [] to deeply equal [ObjectContaining{…}]` — **이슈 0 건**. `ISSUE_SEVERITY['nested-page']` 는 `undefined`.

## 고침

- `packages/schema/src/validate.ts`
  - `ValidationCode` 에 `'nested-page'` · `ISSUE_SEVERITY` 에 `error`.
  - `validateTree` 순회에서 `node.type === 'Page' && parent !== null` 이면 `makeIssue('nested-page', node.id, path, 'Page는 루트에만 둘 수 있습니다 — 페이지 안에 Page를 넣을 수 없습니다')`. 다른 이슈와 같은 꼴(노드 id · 노드 경로 · `makeIssue` 가 표에서 severity).
  - **`excuseStandingNestedPages(before, issues)`** — `before` 에서 이미 뿌리 밖에 서 있던 `Page` 의 id 를 모아 그 id 의 `nested-page` 만 걷는다. 이슈에 `nested-page` 가 없으면 `before` 를 검증하지 않는다(평소 편집 비용 0). `before` 봉투가 깨졌으면 걷을 것이 없다.
- `packages/schema/src/lint/design.ts` — `VALIDATION_RULE['nested-page'] = 'document-invalid'`(`Record<ValidationCode, …>` 라 안 넣으면 타입체크가 죽는다) · `test/lint-mapping.test.ts` 표에 한 줄.
- 설계서 §5 카탈로그 표의 `Page` 줄에 규칙과 옛 문서 처리(연대기 없이).

**왜 노드 id 인가(경로가 아니라).** 웹 붙이기 판정은 원래 «넣기 전에 있던 오류»를 `code|path` 로 갈랐다(`paste-ops.ts`). 그 키로는 옛 `Page` **앞에** 붙이는 무관한 편집이 그 `Page` 의 경로를 밀어 «새 오류»가 된다 — 재현: 새 케이스 «옛 문서의 중첩 Page 앞에 붙여도 붙는다»가 고치기 전 `붙이지 못했습니다: Page는 루트에만 둘 수 있습니다 …` 로 빨강. id 는 문서 안에서 겹치지 않으므로(`duplicate-id`) 걷히는 중첩 `Page` 수는 편집 전 수를 못 넘는다 — 옮기기 · 안을 고치기는 되고 늘리기는 안 된다.

2. **`PUT …/schema`** — 3단계 앞 검사에서 `nested-page` 만 빼고 파이프라인 6단계에 맡긴다(편집 전 문서가 그 자리에 있다). 새 중첩은 같은 422 · 같은 문장(`스키마 검증에 실패했습니다`)이다.
3. **복원(create)** — 그 문서 자신을 «편집 전»으로 줘 문서 안의 중첩을 모두 걷는다. payload 는 저장된 행에서 지은 것뿐이다. **가져오기는 조이는 쪽에 둔다** — 파일은 누구나 지을 수 있어 걷으면 새 중첩의 입구가 된다. 옛 문서를 내보낸 파일을 다시 들이면 거절된다(이월 L-new-2).
4. **테마 패턴 검사는 안 조인다** — 내보내기가 저장된 테마 패키지를 `readWbtheme`(→ `validateManifest` → `checkPatterns`)로 다시 읽어(`apps/api/src/services/export-source.ts:121`), 조이면 `Page` 패턴을 실은 옛 패키지의 내보내기가 깨진다. 넣는 순간은 패턴 넣기가 막는다. `patterns.ts` 의 «중첩 `Page` 는 `validatePage` 가 통과시키므로»라는 낡은 주석을 지금 참으로 고쳤다.
5. **lint 는 옛 문서도 error 로 말한다** — lint 는 저장된 문서 하나를 보고 «편집 전»이 없다. 진실을 말하는 쪽이다(저장은 안 막힌다). 그 결과 옛 문서가 든 프로젝트의 `wireb lint` 가 코드 10 이 된다(이월 L-new-3).

## 프리셋 식(고친 것) · 스냅샷 식

`presets` 에 `nodes` 열이 없고 문서는 `schema`(노드 **배열**)다. 배열의 맨 위 노드도 적용 때 뿌리의 자식이 되므로 맨 위 `Page` 도 센다. 워크트리 DB(`5532`)에서 문법과 구분력을 쟀다 — 손으로 지은 값 넷: 맨 위 `Page` 참 · `Flex › Card › Page` 참 · 없음 거짓 · `props` 안의 `"type":"Page"` 거짓.

```sql
begin read only;
select id, project_id, name from presets
 where jsonb_path_exists(schema, 'strict $[*] ? (@.type == "Page")')
    or jsonb_path_exists(schema, 'strict $[*].**.children[*] ? (@.type == "Page")');
-- 스냅샷 — payload 안 페이지마다. 구분력: 중첩 둘인 판 2 · 없는 판 0
select id, tag from snapshots
 where jsonb_path_exists(payload, 'strict $.pages[*].schema.root.**.children[*] ? (@.type == "Page")');
rollback;
```

워크트리 DB 의 실행 값: 두 질의 모두 0 행(빈 DB). 사용자 DB(5433)는 읽지 않았다.
