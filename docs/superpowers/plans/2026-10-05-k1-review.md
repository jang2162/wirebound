## R1 — 번호 경로의 되돌리기가 남의 상태를 지운다(높음 · 새 길)

**판(api · `p9-index.apiprobe.ts`):** 목록 `[관리자]` · 관리자 가지에 `n_ok`. 보라가 `addViewStateOps(…, '손님')` 를 낸다(200 · `inverse = [remove /viewStates/1]`). 다혜가 «손님»을 맨 앞으로(`move /viewStates/1 → /viewStates/0`, 200). 보라가 받은 역연산을 그대로 낸다(REST 되돌리기).

| 무엇 | 값 |
|---|---|
| 다혜 뒤 목록 | `[손님, 관리자]` |
| 웹 리베이스(`anchorOps` → `rebaseAnchored`)가 지은 되돌리기 | `[{"op":"remove","path":"/viewStates/1"}]` — 그대로 |
| 되돌리기 답 | 200 |
| 되돌리기 뒤 목록 | `[손님]` — **보라가 더한 «손님»이 남고 «관리자»가 빠졌다** |
| 관리자 가지 | `["default","s_admin"]` 그대로 — 목록 밖 상태의 가지가 되어 어느 상태에서도 안 그려진다 |

**원인:**
- 연산 — `view-state-ops.ts` 의 `addViewStateOps` · `renameViewStateOps` · `moveViewStateOps` · `removeViewStateOps` 가 목록을 번호(`/viewStates/<i>`)로 가리킨다. 서버 역연산(`invertOps`)도 번호다.
- 웹 — `apps/web/src/store/anchored-ops.ts` 의 `anchorPath` 는 `tokens[0] !== 'root'` 면 `{ kind: 'raw' }` 로 적는다(머리말 «자리의 셋»의 «노드 밖(`/version`)»). 노드는 id 로 붙잡아 남의 편집 뒤 자리를 다시 짓지만 상태 목록은 그 길이 없다 — 리베이스(409 뒤 다시 내기)와 되돌리기(`#startFrom`)가 같은 함수를 쓴다.

**닿는 길:** 오늘 웹은 `/viewStates` 연산을 내지 않는다 — REST 로 `revisions?mine` 의 역연산을 직접 내는 클라이언트가 닿는다(노드 경로도 그 클라이언트에는 원래 같은 위험이다). K2 가 상태 관리 대화 상자를 세우면 웹의 되돌리기 · 리베이스가 그대로 닿는다. 이름 바꾸기 · 순서 바꾸기 · 상태 삭제의 되돌리기(`add /viewStates/<i>`)도 같은 꼴이다(코드로 읽음 — 판은 «상태 추가»만 쟀다).

**고칠 방향:** `anchored-ops.ts` 에 «상태 자리»를 더한다 — `/viewStates/<i>(/…)` 를 만든 문서의 그 자리 상태 id 로 적고, 얹을 문서에서 그 id 의 번호로 다시 짓는다(없으면 못 얹음 · 알림). 넣는 자리(`add /viewStates/<i>`)는 노드의 «넣을 자리»처럼 앞 · 뒤 이웃 id 로 적는다. K2 브리프에 이 판(순서 바꾸기 뒤 되돌리기 · 409 리베이스)을 실브라우저 케이스로 적는다.

## R2 — 목록만 빼면 가지 안 남의 잠금을 지나 그 가지가 사라진다(낮음 · 새 길)

**판(api · `p10-snap.apiprobe.ts`):** 다혜가 관리자 가지 안 `n_ok` 를 잡는다. 보라가 `[remove /viewStates/0]` 만 낸다 → **200 · `warnings: null`**. 이어 `add /viewStates [{ id: 's_other', name: '관리자' }]` 도 200 — 이름은 돌아와도 옛 가지(`s_admin`)는 고아로 남는다. 같은 뜻을 `removeViewStateOps` 로 내면 가지 `remove` 가 `n_ok` 와 겹쳐 423(보고 Task 5 케이스).

**원인:** `lock.ts` 의 `lockConflictOfOps` 는 포인터 겹침으로만 판정한다 — `/viewStates/…` 는 `/root/…` 와 안 겹친다(설계대로). 목록 밖 상태의 가지는 검증 오류가 아니다(`validate.ts` 의 `checkStateRegion` 머리말 — lint 의 몫, K3). 노드 id 바꾸기(`replace /viewStates/0/id`)도 같다.

**고칠 방향(고를 것):** ① 서버 6단계에서 «목록에서 빠지거나 id 가 바뀐 상태의 가지»를 그 묶음이 지우는지 보고, 안 지우면 그 가지 안 남의 잠금으로 판정한다. ② 받아들이고 K3 의 MCP 스킬 문서에 «상태는 `removeViewStateOps` 꼴(가지 `remove` + 목록 `remove`)로 지운다»를 적고, lint `view-state-unknown` 이 그 가지를 보이게 한다. MCP 는 JSON Patch 로 쓰므로(spec 「MCP · CLI · lint」) 목록만 빼는 묶음을 낼 수 있다.

## R3 — 복사 + 편집이 값 안의 노드 id 를 안 옮긴다(낮음 · 새 길)

**판(`p2-fork.probe.ts`):** 기본 가지 안 노드를 통째로 바꾸는 편집(`replace …/children/d/children/<j>` 에 그 노드의 사본 — id 그대로 · 또는 새 id 이되 자식은 그대로)을 `editInForkOps` 에 넣는다. 5000판 가운데 1071판이 `duplicate-id` 검증 오류 — 전부 «노드 통째 바꾸기»가 든 묶음이다. 그 밖의 꼴(값 · 넣기 · 빼기 · 옮기기 · 상호작용 · 별칭)은 오류 0 이고, 새 가지 = 같은 편집을 기본 가지에 바로 낸 결과(id 를 되돌려 견줌)다.

**원인:** `view-state-ops.ts` 의 `retarget` 은 값 안의 `target` 키만 `remap` 으로 바꾼다. 값이 기본 가지의 노드(와 그 id)를 들면 복사 가지에 같은 id 가 다시 선다.

**곁가지:** 기본 가지에 `children` 키가 없으면(검증은 받는다 — API 로 만든 문서) 첫 자식 넣기 `add …/children/d/children [노드]`(`apps/web/src/edit/ops.ts` 의 첫 자식 갈래)는 포인터 길이가 «가지 자신의 필드»와 같아 `null` 이다. 화면이 `null` 을 «영역 밖 평범한 편집»으로 읽으면(보고 이월 4) 기본 가지에 넣는다.

**고칠 방향:** `retarget` 이 `remap` 에 든 `id` 값도 복사 id 로 바꾼다(통째 바꾸기가 «그 노드의 복사를 바꾼다»가 된다). 곁가지는 `inside` 가 `children` 키 자체(`…/children/d/children`)의 `add` 를 받게 한다.

## R4 — 상태를 안 받는 이름 짓는 자리(낮음 · 새 길)

## R5 — 상태 목록 봉투 이슈의 `nodeId` 가 상태 id 다(낮음 · 새 길)

**판(`p7-boundary.apiprobe.ts` 의 스냅샷 복원 «이름 겹침»):** 422 본문 `{"code":"bad-document","nodeId":"s_guest","path":"/viewStates/1/name"}`.

**원인:** `validate.ts` 의 `resolveNodeId` 는 경로를 따라 `id` 를 가진 객체를 노드로 본다 — 상태 항목 `{ id, name }` 도 걸린다.

**고칠 방향:** `resolveNodeId` 가 `root` 아래에서만 id 를 잡는다(`/viewStates/…` 이슈는 `nodeId: null`). 화면이 `nodeId` 로 노드를 찾아 고르는 자리가 없는 노드를 찾지 않게 한다.

- 500 은 0 · 문서 바뀜 0 · WS 연결은 끝까지 열려 있었다.
- **ops 길은 400 이 아니라 422 다** — 본문 계약(`PatchPath` · 연산 모양)은 지켰고 적용한 문서가 검증을 못 지나는 판이라 파이프라인 6단계의 `invalid` 다(노드 편집과 같은 관례). spec 「테스트」의 «비튼 값 → 400»은 PUT · 가져오기에만 맞는 문장이다.
- **프리셋은 구조 위반을 201 로 받는다** — `routes/presets.ts` 머리말 «카탈로그 검증은 여기서 하지 않는다»의 설계대로다(적용 때 결과 문서로 판정). 프리셋 본문은 노드 배열이라 목록을 실을 자리가 없다(spec 의 «프리셋이 `viewStates` 를 싣는다»는 K3).
- **스냅샷 복원** — payload 를 DB 로 비틀어(이름 겹침 · 21개 · 목록 `null`) 복원하면 422 `validation-failed`(`bad-document` · `path: /viewStates…`). 운영에서 payload 는 서버가 짓는다.
- **클립보드** — 봉투(`readNodesEnvelope`)는 노드만 나르고 목록 자리가 없다. 맨 위 가지 · 영역째 봉투의 값은 I5.

## I4 — «스냅샷 payload 는 목록이 있으면 500»(정보)

- **재현(변조 M7):** `packages/themes/src/snapshot/payload.ts` 의 `PageSchema.schema` 를 `DocumentEnvelopeSchema` 로 되돌리고 목록 든 페이지(PUT 200)로 스냅샷을 만들면 **500** `internal`. 고친 판은 201. 원인은 스냅샷 만들기가 제가 지은 payload 를 strict 봉투로 다시 읽는 것이다 — 모르는 키 `viewStates` 에 던진다.
- **이 트랙이 연 길이다:** main `5d365015` 에서는 페이지에 목록을 저장할 길이 없었다 — ops 경로 술어가 `/root` · `/version` 만 받고(`PatchPath` 의 `refine`) · PUT · 가져오기 봉투가 strict 였다(보고 «문서 경로 판정» 표). 저장 길을 연 커밋과 같은 트랙이 봉투를 `PageEnvelopeSchema` 로 바꿔 닫았다. 저장된 페이지 문서를 strict 하게 다시 읽는 다른 자리는 `grep -rn "DocumentEnvelopeSchema" apps/*/src packages/*/src` 에 레이아웃 봉투 · 클립보드(노드만) · `validateLayout` 뿐이다.
- **원래 길(정보):** DB 를 직접 비틀어 저장된 문서가 봉투를 어기면(노드에 모르는 키 `style` · 목록 이름 겹침) 스냅샷 만들기가 500 이다 — 노드 쪽 꼴은 K1 전에도 같다.
