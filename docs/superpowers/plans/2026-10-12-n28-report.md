## 2. 전제 셋(L-292) — 값

- **(a) `restored` 가 `seq` 를 안 싣는다.** 서버 `ws/protocol.ts` 의 `restored` 프레임 = `projectId` · `snapshotId` · `safetySnapshotId` · `actor` · (있으면) `clientRestoreId` — 번호 없음. 웹 파서(`realtime/protocol.ts`)도 그 다섯만 옮긴다. 받는 쪽 `EditorStore.markRestored` 는 `headSeq` 를 건드리지 않고 낡음을 세우고 창(`#windowChanges`)을 버린다 — 늦게 받아도 얹을 것이 없어 이음이 안 틀어진다. 실서버 값: 늦은 꼬리의 `restored` 프레임이 정확히 `{ type, projectId, snapshotId, safetySnapshotId, actor, clientRestoreId }`(`toEqual`).
- **(b) `menu-changed` · `theme-changed` 의 옛 번호는 받는 쪽이 넘긴다.** 웹 `tree/use-tree-commands.tsx` — `if (remoteRev > shownRev.current) void refresh()` · 셸은 가장 큰 번호만 든다(`routes/editor.tsx` 의 `onMenuChanged`). 테마 `theme/project-theme.tsx` 의 `applyFrame` — `if (frame.rev <= held.rev) return`. jsdom 잠금: `apps/web/test/panels/menu-realtime.test.tsx` «제 판보다 큰 번호면 다시 받고, 같거나 작으면 안 받는다»(이 판에서 초록 — 아래 게이트). 실서버 값(전제 (c) 판): 늦은 꼬리는 제 트랜잭션의 번호를 싣는다 — `menu-changed rev 6 → 5` · `theme-changed rev 3 → 2`(둘째 복원의 것이 먼저, 늦은 것이 뒤 — 지켜보기 간격에 달려 차례는 정해지지 않는다).
- **(c) 그사이 다른 복원 · 삭제.** 둘째 복원은 늦은 복원이 쥔 프로젝트 행(`FOR UPDATE`)에 줄 서 그 커밋 뒤에 돈다 — 늦은 꼬리와 둘째 꼬리가 둘 다 나가고(위 값), 받는 쪽은 번호로 옛 트리 · 테마를 넘기며 `restored` 는 배너를 한 번 더 세운다(다시 읽기 하나 — 안전한 쪽). 늦은 꼬리의 잠금 놓기가 둘째 복원이 되살린 페이지의 잠금을 놓을 수 있는데(코드 읽기 값 · 안 쟀다), 쥔 쪽의 다음 하트비트가 되잡는다(`ws/lock.ts` 의 `handleLockFrame` — 지운 페이지가 아니면 잡는다). 프로젝트 삭제는 같은 행에 줄 서 늦은 복원 뒤에 커밋되고, 늦은 꼬리의 방송은 연결마다 자격을 다시 보므로(`ws/broadcast.ts` 의 `stillAllowed`) 멤버가 사라진 연결에는 안 가고 그 연결을 닫는다 — 코드 읽기 값이고 안 쟀다. 전제가 틀린 것은 없어 전부 구현했다.

## 3. 고침

### 서버

- `services/lost-commit.ts` — `runConfirmedTransaction`: 결말이 `committed` 인데 `confirm` 이 `null` 이면(게시 — `revisionOf` 없음 · 머리를 한도 안에 못 읽음 · 문서를 안 바꾼 삭제 · 재번호) `late.onCommit(body.result)` 을 그 자리에서 부르고 원래 오류(503)를 던진다. 실패는 삼킨다(지켜보기와 같다). 머리말 표에 줄을 갈랐다(«커밋됐는데 번호를 모른다» / «결말을 묻지 못했다»).
- `routes/snapshots.ts` — 꼬리를 `announceRestore(app, request, projectId, snapshotId, body)` 로 뺐다(`restored` · `menu-changed` · `releaseLocksOnPages` · 판 3 `theme-changed`). 트랜잭션 본문이 `{ restored, menuRev }` 를 결과로 돌려주고(바깥 변수 아님), 제때 길은 응답 자리에서 · 늦은 길은 `runConfirmedTransaction` 의 `late`(`app.lateCommits`)가 같은 함수를 부른다. 복원이 안 된 판정은 함수 머리에서 돌아간다 — 늦은 길도 같은 판정을 받는다. `actor:` 자리 셋은 그대로 `requestEventActor(request)`(`actor-census` 표 그대로 · 28 초록).
- 정본: `apps/api/README.md` «COMMIT 답을 잃은 편집» 표 · «늦게 커밋된 편집 · 게시 · 복원» 절 · «편집 밖의 쓰기 넷» · 프레임 표(`page-stale` · `restored`) · «트리 쓰기» 의 «한도 안에 결말을 모르면 … 안 낸다» → 지켜보기가 늦게 낸다(`services/tree-write.ts` 의 `late` 가 이미 그렇다 — 문서만 낡아 있었다). 설계서 실시간 절(`page-stale` 항목 · 복원 항목).

### 웹

- `routes/editor.tsx` — 늦은 변경 이펙트의 `catch` 가 `EditorStore.tellLoss` 로 한 줄: `lateReloadFailedNotice(reason)` = «페이지를 다시 불러오지 못했습니다. <까닭> — 화면은 아직 최신이 아닙니다. «다시 불러오기»를 다시 누르세요.»(`RELOAD_FAILED_LEAD` 와 같은 앞머리 · 누가 했는지 없음). `untilLoad: true` 라 판이 실리면 걷힌다. 떠나며 끊은 조회(`!alive`)는 말하지 않고, 세션 끊김은 `setEditFailure` 로 로그인 화면으로(`use-edit-commit.tsx` 의 같은 갈래). 판은 비우지 않는다.
- 옛 문안을 단언한 자리: «조용히 둔다»는 문장이 단언된 곳 없음(`git grep -n "조용히 둔다\|경보가 그대로 선다" -- apps/web/test apps/web/build-test` → `page-stale-alert.test.tsx` 머리말 표 한 줄뿐 — 고쳤다). 새 문안의 조각(«다시 불러오지 못했습니다»)은 `RELOAD_FAILED_LEAD` 를 단언하는 기존 케이스가 있으나 그 문장은 그대로다.

## 10. 못 잰 것

- 전제 (c) 의 «프로젝트 삭제가 끼는 판»과 «둘째 복원이 되살린 페이지의 잠금을 늦은 꼬리가 놓는 판» — 코드 읽기 값(위 2.(c)). 재는 법: 늦은 복원 뒤 `DELETE /api/projects/:id` → 구경꾼이 4403 으로 닫히고 `restored` 0 / 둘째 복원 뒤 그 페이지에 잠금을 쥔 채 늦은 꼬리 → `locks` 에서 빠졌다가 다음 하트비트에 되살아남.
- Chrome 변조는 «신호가 안 온다» 꼴이라 시간 초과로 죽는다(N24 와 같다) — 같은 변조를 값으로 죽이는 소유자는 서버 케이스(M1 · M5)다. Chrome M1 을 한 번 돌려 죽는 방식만 적었다(변조 표).
- 문서를 안 바꾼 삭제 · 재번호의 503 «모름»에 가는 `page-stale`(거짓 경보 하나 — 받는 쪽은 같은 판을 읽어 경보만 푼다)은 케이스로 잠그지 않았다(대가를 동작으로 잠그지 않는다) — README 에 값으로 적었다.

## 11. 새 이월

- **N28-1(낮음)** 문서를 안 바꾼 삭제 · 재번호가 COMMIT 답만 잃으면 `page-stale` 이 하나 간다(거짓 경보 · `GET` 하나). `runRevisionTransaction` 의 `confirm` 이 «revision 없음»과 «모름»을 한 `null` 로 내서다 — `revisionOf` 가 «없음»을 따로 내면 가를 수 있다. 재는 법: 마지막이 아닌 코멘트 삭제에 `dropCommitReplyAfter('delete from "comments"')`.
- **N28-2(정보)** 전제 (c) 의 두 판(프로젝트 삭제 · 되살린 페이지의 잠금) — 위 「못 잰 것」. 코드 읽기로는 안전하다.
- **N28-3(정보)** 늦은 꼬리의 `restored` 는 받는 쪽이 이미 둘째 복원 뒤의 판을 읽었어도 배너를 한 번 더 세운다(L-294 와 같은 뿌리 — 번호가 없다). 안전한 쪽이라 그대로 둔다.

## 12. 지침 보고

1. **틀린 곳.** `apps/api/README.md` «트리 쓰기» 의 «한도 안에 결말을 모르면 503 … 안 낸다»는 `services/tree-write.ts` 의 늦은 커밋 지켜보기(`late`)가 들어온 뒤로 낡아 있었다 — 고쳤다. `services/tree-write.ts` 머리말의 «복원의 늦은 커밋은 신호가 없다» 도 고쳤다.
2. **없는 것(제안 — CLAUDE.md 「워커에게 맡길 때 — wirebound」 경보 문단 끝).** «늦은 커밋의 신호를 내는 자리를 새로 세우면 «한도 안에 커밋이 확인됐는데 번호를 모르는» 갈래(`confirm` 이 `null`)도 센다 — 지켜보기만 세우면 그 갈래는 커밋됐는데 아무 신호도 없다(게시 «모름» 503 이 그랬다). 두 갈래가 같은 `onCommit` 을 부르게 한다.»
3. **없는 것(제안 — 같은 문단).** «여러 자원을 함께 바꾸는 쓰기(복원)의 커밋 뒤 알림은 함수 하나로 두고 제때 · 늦은 길이 그것을 부른다 — 자원 하나짜리 신호(`page-stale`)로 대신하면 단추가 거짓이 되고, 두 벌로 두면 한 자원이 빠진 채 조용히 낡는다(`routes/snapshots.ts` 의 `announceRestore`).»
4. 브리프의 방향 문장을 그대로 짠 판이 기존 잠금을 죽인 것은 없었다(actor-census · lost-commit-writes · edit-lost-commit · broadcast-census 초록).
