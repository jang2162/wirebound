## 잰 값

### 1. 계획에서 벗어난 두 곳(«결정» 2 · 3) — 성질이 지켜진다

파일 `apps/api/test/rv-ac-demote-race.test.ts`(8 케이스 · skip 없음 · 초록).

**재확인을 지난 뒤 · 커밋 전의 강등** — 요청자의 쓰기를 재확인 **뒤** 문장(`insert into "invites"` · `insert into "password_resets"`) 앞에 붙잡고 강등을 보냈다.

| 강등 | 강등이 선 자리 | 결과 |
|---|---|---|
| 다른 관리자의 API 해제 | 요청자 행(`for no key update` — 사슬로 확인) | 초대 201 → 해제 200 · `revokedLinks` 1(그 링크까지 거둠) · 남은 관리자 1 · 교착 0 |
| 서버 명령의 해제(`setInstanceAdmin` — `db/admin.ts` 가 부르는 함수) | 같은 행 | 초대 201 → `changed` · 그 링크 거둠 |
| 다른 관리자의 요청자 비활성화 | 같은 행 | 재설정 링크 201 → 비활성화 200 · `revokedLinks` 1 · 그 링크 404 |
| 반대 차례 — 서버 명령의 해제가 행을 쥔 채(커밋 전) 보낸 쓰기 | 쓰기의 재확인(`… for share`) | 403 · 링크 0 |

보고의 주장(«재확인이 잡은 요청자 행 `FOR SHARE` 가 강등을 커밋 뒤로 미룬다»)이 실측으로 선다. CLI 경로도 같은 행(`lockUserRows` 의 `FOR NO KEY UPDATE`)을 잡는다.

**셋이 고리로 서로를 해제 · 비활성화**(id 순 a < b < c · 한 요청을 재확인 앞에 붙잡고 둘이 그 뒤 사슬로 선 것(`queued` 2)을 본 뒤 놓음):

| 고리 | 붙잡은 것 | 응답 | 남은 관리자 | 교착 |
|---|---|---|---|---|
| a→b · b→c · c→a(해제) | b→c | 200 · 200 · 403 | a | 0 |
| a→c · c→b · b→a(해제) | a→c | 200 · 403 · 200 | b | 0 |
| a⊘b · b→c · c⊘a(섞음) | b→c | 200 · 200 · 403 | a | 0 |
| a⊘c · c⊘b · b⊘a(비활성화) | a⊘c | 200 · 401 · 200 | b | 0 |

넷째 판의 401 은 앞 비활성화가 요청자 c 의 세션을 지운 것이다(재확인이 자격을 관리자 판정보다 먼저 던진다) — 성질의 문제는 아니다. 관리자 0 · 교착
(40P01 → 500) 둘 다 안 났다. 서버 명령의 해제는 마지막 관리자도 거둔다(`db/admin.ts` 머리말 «관리자가 0 명일 때 되살리는 길» — 설계대로라 결함으로 안 셌다).

### 2 · 3. 관리자가 닿는 곳 — 성질이 지켜진다

파일 `apps/api/test/rv-ac-admin-reach.test.ts`(5 케이스 · skip 없음 · 초록).

- **비멤버 프로젝트의 내용 라우트 전부** — 분모는 Fastify 의 라우트 표(`onRoute`)에서 `:projectId` 가 든 줄을 메서드로 편 **48 줄**. 관리자 세션의
  답이 관리자 아닌 비멤버(같은 프로젝트)의 답과 상태 · 몸이 **48/48 같고, 48/48 이 404** 다(`/ws` 도 업그레이드 없는 GET 이라 404). 대조로
  owner 를 넘겨받은 뒤에는 같은 관리자의 트리 읽기가 200 이고 메뉴 표지가 보인다.
- **관리자 라우트의 응답** — `GET /admin/projects` · `GET /admin/users` · 비활성화 응답 · 넘기기 응답 · `GET /admin/audit` 다섯 몸에 페이지 · 메뉴
  이름의 표지가 0(카나리아 — 프로젝트 id 가 그 가운데 셋 이상에 나온다).
- **세션 전용** — `/api/admin` 아래 **15 줄 전부**가 관리자의 API 토큰(그 사람이 owner 인 프로젝트의 토큰 — 같은 토큰이 제 프로젝트 트리에는 200)
  만으로 401. `/api/auth/invites` · `/api/auth/resets` 4 줄은 토큰을 실어도 안 실은 것과 상태 · 몸이 같다. `/api/admin` · `/api/auth` 아래 35 줄
  가운데 `:projectId` 파라미터를 가진 줄은 **0**.
  - 잴 때 하나 걸린 것: `POST /api/admin/theme-packages` 에 JSON 본문을 실으면 내용 형식 검사가 인증 앞에서 **415** 로 끊는다(토큰 결함이 아니다 —
    본문 없이 보내면 401). 인구조사가 본문을 싣지 않는 까닭이다.

### 4. 비활성화의 «즉시» — 성질이 지켜진다

파일 `apps/api/test/rv-ac-deactivate-inflight.test.ts` 의 앞 두 케이스(초록).

| 판 | 비활성화가 선 자리 | 결과 |
|---|---|---|
| REST 코멘트가 재확인을 **지난 뒤**(`insert into "comments"` 앞에 붙잡음) | `delete from "sessions"`(사슬로 확인 — «결정» 1 그대로) | 코멘트 201 이 먼저 끝나고 비활성화 200 · 코멘트 1 · 교착 0 |
| WS `patch` 가 재확인 **앞**(세션 `for key share` 앞에 붙잡음) | 안 섬(곧바로 200) | patch 는 `patch-error` 401 · `head_seq` 그대로 · 새 판 0 · 연결은 4403 으로 닫힘 |

«비활성화 커밋 뒤에 커밋된 그 사람의 쓰기» 는 두 판 다 없다 — 재확인을 지난 쓰기는 비활성화보다 먼저 커밋되고, 못 지난 쓰기는 401 로 안 남는다.
WS 의 닫힘 이유 글이 «로그아웃했습니다» 다(아래 «발견» L2).

### 7. «마지막 접속» 갱신 — 성질이 지켜진다

같은 파일의 뒤 두 케이스(초록). 테스트 트랜잭션이 그 사람의 사용자 행을 쥔 채 `GET /api/auth/me`:

| 쥔 모드 | 요청 | 그동안 `last_seen_at` | 놓은 뒤 |
|---|---|---|---|
| `FOR SHARE`(관리자 재확인 · 로그인과 같은 모드) | 200 · 25ms · 줄 안 섬 | `null`(건너뜀) | 다음 요청이 고침 |
| `FOR NO KEY UPDATE`(비밀번호 바꾸기 · 비활성화와 같은 모드) | 200 · 80ms · 줄 안 섬 | `null` | 다음 요청이 고침 |

교착 0. 갱신은 자동 커밋 한 문장이고 `SKIP LOCKED` 라 어떤 잠금도 기다리지 않는다 — 기다리지 않는 문장은 교착의 고리에 들 수 없다. 비활성화와 겹친 그 사람의
요청은 사용자 행이 아니라 세션 행 갱신(`update "sessions"`)에서 비활성화의 `DELETE` 를 기다리고 401 이다 — 이 트랙 앞부터 있던 길(`session-logout-race.test.ts`).

## 발견

높음(인가 우회 · 남의 데이터 · 잃음 · 교착)은 **0** 이다. 브리프의 일곱 가운데 다섯(1 · 2 · 3 · 4 · 7)은 성질이 지켜졌고(위 «잰 값»), 둘(5 · 6)에서 아래가 나왔다.

### M1 (중간) — 초대 · 재설정 링크 원문이 요청 로그에 남는다

- **재현:** `apps/api/test/rv-ac-link-exposure.test.ts` 의 `describe.skip('M1 — …')` 두 케이스. `LOG_LEVEL=info`(운영 기본 — `src/config.ts` 의 `logLevel`)로 앱을
  세우고 초대 링크를 확인(`GET /api/auth/invites/<원문>`) · 가입(`POST …/signup`), 재설정 링크를 확인(`GET /api/auth/resets/<원문>`)한다.
- **skip 을 뗐을 때의 실패 값:** «초대 링크 원문이 로그에 없다» — `expected 2 to be +0`(확인 · 가입의 «incoming request» 줄마다 `url` 에 하나),
  «재설정 링크 원문이 로그에 없다» — `expected 1 to be +0`. 까닭은 pino 기본 `req` 시리얼라이저가 `url` 을 그대로 적는 것이다(`src/app.ts` 의
  `buildLoggerOptions` 머리말이 «method · url · …» 을 적는 그 시리얼라이저다).
- **무게:** DB 에는 해시만 두는 성질(계획 «공통 제약» «토큰 원문은 저장하지 않는다»)이 로그 파일에서 안 선다. 로그를 읽는 사람(로그 수집 서비스 ·
  디스크를 읽는 사람)이 «여러 명» 링크로 만료(최대 90 일) · 거둠 · 다 씀 전까지 가입하고, 재설정 링크는 그 사람이 열고 아직 안 쓴 동안(열고 그만둔
  판은 24 시간) 남의 비밀번호를 바꾼다. DB 에 손이 닿는 운영자는 이미 무엇이든 할 수 있으므로 높음으로 안 셌다. 입구(Caddy `docker/web/Caddyfile`)는
  접근 로그를 안 켠다 — 앞단 프록시의 접근 로그는 이 저장소 밖이라 안 쟀다.
- **고칠 방향 한 줄:** `buildLoggerOptions` 에 `serializers.req` 를 두어 `/api/auth/invites/` · `/api/auth/resets/` 뒤 경로 조각을 가린 `url` 을 적는다.
- **그 방향을 그대로 짜면 죽을 것:** 커스텀 `req` 시리얼라이저가 기본처럼 `headers` 를 빼지 않으면 `buildLoggerOptions` 머리말의 «redact 는 방어선» 전제가
  바뀌고 `apps/api/test/logging.test.ts` 세 케이스(쿠키 · 인증 헤더 · 실 파이프라인)가 그 머리를 읽는다 — 시리얼라이저는 기본의 칸(method · url · host ·
  remoteAddress · remotePort)만 내야 한다. 원문을 경로에서 본문으로 옮기는 길은 API 계약(«API 계약» 표의 경로 넷 · 웹 `api/http-client.ts` ·
  `apps/web/test/api/http-client.test.ts` 의 엔드포인트 표)과 m 트랙이 믿는 링크 주소 꼴을 바꿔 고르지 않는다.

### L1 (낮음 · 이월 후보) — «여러 명» 링크 하나로 한 주소가 한 창에 만드는 계정 수에 한도가 없다

- **재현:** 같은 파일의 `describe.skip('L1 — …')`. 한 주소(`10.62.0.1`)에서 다른 이메일로 40 번 가입.
- **skip 을 뗐을 때의 실패 값:** `expected 40 to be less than or equal to 30` — 보낸 40 · 만든 40 · 429 0(주소 한도 `perAddress` 30 · 창 15 분).
- **까닭:** 가입은 로그인 한도에 세지만 성공은 제 자리를 걷는다(`src/auth/login-limit.ts` 머리말 «성공은 두 키에서 이 시도의 자리만 걷는다»). 한도는
  scrypt 를 돌리는 **실패** 시도만 묶는다. 설계는 이것을 막지 않았다(브리프 6).
- **고칠 방향 한 줄:** 가입 성공을 주소 · 링크마다 따로 세는 한도를 둔다(로그인 한도의 `succeeded` 와 떼어서).
- **그 방향을 그대로 짜면 죽을 것:** 가입이 쓰는 한도는 로그인과 **같은 `LoginLimiter`** 다 — `succeeded` 가 자리를 남기게 바꾸면 로그인에도 번져
  `apps/api/test/login-limit.test.ts` «성공은 남의 다음 답을 안 바꾼다» 와 머리말이 닫았다고 적은 «주인이 로그인했다» 신호가 다시 선다. 가입만의 셈을
  따로 둬야 한다.

### 관찰(결함으로 안 셈)

- 비활성화 · 재설정이 닫는 WS 의 닫힘 이유 글이 «로그아웃했습니다» 다(`src/ws/notify.ts` 의 `closeSessionConnections` — 비밀번호 바꾸기와 같은 길).

## 못 잰 것 · 안 본 것

- **id 순 잠금이 교착을 막는다는 것은 이 케이스들이 안 잰다(V-D2 가 산다).** 고리 판은 한 요청을 붙잡고 나머지를 하나씩 보내 사슬에 세우므로, 정렬을 떼도
  셋이 첫 행을 동시에 쥔 판이 안 선다. 그 판은 요청 셋을 «첫 잠금 뒤» 에 함께 세워야 하는데 프록시의 붙잡기 칸이 하나다(`pg-fault-proxy.ts` 머리말
  «붙잡힌 질의는 칸을 비운다»). 성질 자체(정렬된 차례에 고리가 없다)는 «결정» 1 의 차례 표로 읽힌다.
- 웹 링크 화면 둘(jsdom · 실브라우저), 가입 · 재설정 화면의 문장, 관리자 기록의 쪽 넘김, owner 넘기기 × 프로젝트 삭제, 마이그레이션 `down` 은 다시 안 봤다
  (구현 보고 케이스가 있다).
- 앞단 프록시의 접근 로그 · 링크 화면의 `Referer` 는 이 저장소 밖이라 안 쟀다(M1 은 api 로그만).
- 전량 게이트는 브리프대로 안 돌렸다.

## 지침

1. **붙잡기 칸이 하나라 «셋이 첫 잠금을 함께 쥔 판» 을 못 세운다** — 무엇이 빠졌나: `.ruler/30-delegation.md` «교착을 잴 때는 누가 먼저 잡느냐를 뒤집은 판과
   옛 판을 함께 세운다» 는 차례를 뒤집으라고만 하고, 셋 이상의 고리에서 `holdQuery` 로 하나를 붙잡고 나머지를 하나씩 보내면 정렬을 뗀 변조(V-D2)도 산다는
   것을 안 적는다. 어디: 그 문단 끝. 넣을 문장: «**고리가 셋 이상이면 하나를 붙잡고 나머지를 하나씩 보낸 판은 «정렬된 차례가 고리를 막는다» 를 못 잰다** —
   뒤 요청이 앞 요청 뒤에 줄 서 첫 행을 함께 쥐지 못한다(`pg-fault-proxy.ts` 의 붙잡기 칸이 하나다). 정렬을 떼는 변조가 사는지 한 번 돌려 적고, 살면 그
   성질은 «못 잰 것» 으로 보고에 넘긴다(`docs/superpowers/plans/2026-10-31-rv-ac-report.md` V-D2).»
2. **줄 선 판을 재는 케이스는 붙잡은 쪽을 놓은 뒤 답을 기다린다** — 무엇이 빠졌나: `settledOrQueued` 로 «안 기다린다» 를 재는 케이스가 붙잡은 트랜잭션을
   놓기 **전에** 요청의 답을 기다리면, 줄을 서게 만든 변조에서 값(`'queued'`)이 아니라 시간 초과(`STACK_TRACE_ERROR`)로 죽는다(V-I3 첫 판). 어디:
   `.ruler/20-verification.md` 「목 · 계측은 불린 수를 값으로 확인하고 …」 문단의 «`waitFor` 콜백 안에 DOM 을 바꾸는 읽기 …» 문장 뒤. 넣을 문장:
   «**«줄을 안 선다» 를 재는 케이스는 줄 섰는지의 값을 먼저 읽고, 붙잡은 쪽을 놓은 뒤에 답을 기다린다** — 놓기 전에 답을 기다리면 줄을 서게 만든 변조가
   값이 아니라 시간 초과로 죽는다(`apps/api/test/rv-ac-deactivate-inflight.test.ts` «마지막 접속»).»
